## §1 ① 血链不能把 `boss_*` / `ally_*` 策反过来

### 1.1 旧代码为什么只挡住了 boss、挡不住法阵守护者

排除逻辑散在三个地方，判断口径**不一致**：

| 位置 | 旧判据 | 漏了什么 |
|------|--------|---------|
| `_nearest_non_boss()` | `_is_boss_fighter(o)` | `ally_*` 不是 `boss_*` 前缀、也没有 `is_boss` 字段 → **完全合法** |
| `_link_targets_without_doom()` | `_is_doom_guard_fighter` / `_is_unique_fighter` | 同上；且**连 boss 也没排**（注释说"交给 `_nearest_non_boss` 拦"） |
| `_skill_shared_hp_link()` 的重连守卫 | `_is_boss_fighter(current)` | 已连上的 `ally_*` 不会被断开 |

`ally_*`（法阵守护者，第 21 回合按法阵血量召唤）血量 1400~5200、攻击 77~160，
被一发血链白拿走等于直接判负 —— 与既有「Boss 免疫」的口径同类。

### 1.2 改法：一条新谓词，三个调用点都接同一个

```gdscript
# 与 _ignores_treasure 用同一个 `is_formation_ally` 字段（BattleSimShared._fighter_from_def
# 写入），并补一条 ally_ 前缀兜底，防止 def 缺失时漏网。
static func _is_formation_ally_fighter(fighter: Dictionary) -> bool:
	var d: Dictionary = fighter.get("def", {})
	var id := str(fighter.get("id", d.get("id", "")))
	return bool(fighter.get("is_formation_ally", false)) or id.begins_with("ally_")
```

三处各加一次（**同一函数、同一判据**，不各抄一遍）：

```gdscript
# _skill_shared_hp_link：已连上的目标是 boss / 法阵友军则断开重连
if _is_boss_fighter(current) or _is_formation_ally_fighter(current):

# _nearest_non_boss：候选里跳过
if not bool(o.get("alive", false)) or _is_boss_fighter(o) or _is_formation_ally_fighter(o) or not _can_target(f, o, opponents):

# _link_targets_without_doom：候选池里跳过
if o == caster or _is_doom_guard_fighter(o) or _is_unique_fighter(o) or _is_boss_fighter(o) or _is_formation_ally_fighter(o):
```

### 1.3 ★ 探针当场抓出一个「我以为改完了」的漏

`probe_blood_link_boss_immune_925` 第一次跑就是 **44 PASS / 2 FAIL**：

```
[diag] 候选池 ids=["boss_thunder_core", "human_militia"]
FAIL [pool] 候选池只剩 1 只（boss 与 ally 都被排除）    got=2 want=1
FAIL [pool] 候选池里就是那只民兵                       got=["boss_thunder_core","human_militia"] want=["human_militia"]
```

**`_link_targets_without_doom` 里还留着 boss。** 行为上它没酿成错（该函数只有一个调用点，
结果直接喂给 `_nearest_non_boss`，而那里排 boss），但函数名承诺的是"可连目标池"，
留一只 boss 在里面，第二个调用方一出现就会踩坑。于是把 `_is_boss_fighter(o)` 也加进去，
并把那段"boss 交给 `_nearest_non_boss` 拦"的注释改成现在的说明。加完 46/46 全绿。
**这就是本次唯一一处"写完又回头补"的地方，且是被判据抓出来的，不是靠走查。**

### 1.4 期望值怎么做到不自证

- 场景结构独立：敌方只放 `boss + ally + 1 个民兵`，**合法目标恰好只有 1 个**，
  所以"应当连到民兵"是由**我摆的场景**推出来的，不是借 `_is_boss_fighter` 算出来的。
- 谓词那组用 **id 前缀**（`boss_` / `ally_`）做独立线索交叉验证，并显式记下
  `_is_boss_fighter(ally) = false` —— 这一条正是旧代码栽掉的原因。
- **否定断言必须非空过**：只放 boss（或只放 ally）时"没有链"这条，
  先断言**守卫仍存活**（否则"没连上"可能只是技能压根没跑），再断言没链。
- 谓词/候选池用 `_link_targets_without_doom` / `_nearest_non_boss` 直接跑生产实现；
  端到端那条走 `build_test_state` + 400 次 `step_state`，实测第 5 帧左右锁上。

## §3 ③⑴「前置任务」提示缩短 —— 这条改动了门禁口径

### 3.1 改的是什么

`TutorialMode.follow_arrow_hint()` 的兜底原本是
`"这一步还没完成：%s" % <整段目标文案>`。提交文档 ③⑴ 说它"过于冗长"，截图
（docx `image3` / `image4`）里玩家在商店连点卡片，同一句长文案铺满整个屏幕：

```
image3：这一步还没完成：从待命区把3个棋子拖到棋盘。棋盘上的棋子才会参战。
image4：…步还没完成：点击下方「商店」按钮…（同一句重复十几行）
```

现在统一收敛成一句短的：

```gdscript
# 9.25 教程优化第 1 条：原来这里回「这一步还没完成：<整段目标文案>」。
return _t("请先完成前置任务", "Finish the previous task first")
```

商店遮挡那条分支**保持原样**（商店开着时仍复述目标并提示先关商店）—— ③⑴ 说的是
"完成前置任务"那句，不是这条。

### 3.2 ★ 这条与既存门禁 `V3 P1-10` 正面冲突，必须显式裁决

`tutorial_text_leak_check` 里有一条断言 `invalid_tap_hint_is_one_size_fits_all`：
**"每一步都回同一句话 = 没说明原因"**，要求 22 个步骤至少有 **5 种不同说法**。
改完立刻红：

```
FAIL [invalid_tap_hint_is_one_size_fits_all] [zh] 22 个步骤的无效点击反馈只有 1 种说法
FAIL [invalid_tap_hint_is_one_size_fits_all] [en] 22 个步骤的无效点击反馈只有 1 种说法
```

这不是"改坏了"，是**用户把设计口径改掉了**：P1-10 当年特意让它复述目标，
理由正是"只回一句等于没说明原因"；9.25 文档反过来判定复述目标太长。
两条要求不能同时满足 —— **"请先完成前置任务"就是唯一那句**。

处理方式：**换口径，不放松**。把"至少 5 种说法"换成一条逐字断言：

```gdscript
var want := "请先完成前置任务" if locale == "zh" else "Finish the previous task first"
_h.expect(hint == want, "invalid_tap_hint_not_short_sanctioned",
	"[%s] 步骤 %s 的无效点击反馈不是收敛后的短句「%s」：%s" % [locale, str(keys[i]), want, hint])
...
_h.expect(seen.size() <= 1, "invalid_tap_hint_not_single_short_text",
	"[%s] 非商店步骤的无效点击反馈出现了 %d 种说法（应为 1）" % [locale, seen.size()])
```

新断言钉住两件事：**（a）确实是那句收敛后的文案**（防止漂移回长句）；
**（b）不再复述整段目标**（只要有人把长句塞回来，这里立刻转红）。
非空、无枚举名泄漏、无内部标识、商店遮挡仍须提到「商店」、采购步骤不得提示关商店
—— 这五条**一条都没放宽**。

⚠️ **这是本轮唯一一次修改门禁判据本身。** 按仓规已追加到 `docs/CHECKS.md`。
理由、新旧口径的取舍、以及"为什么这不是把门禁改松"全部写在同一处，便于日后复核。

## §4 ③⑵ 萝卜营地：删步骤 + 升级按钮当场亮起

### 4.1 先定位"第三、第四步"到底是哪几步

提交文档里的"第三、第四步"指的是**萝卜营地教学截图里的第 3、4 张图**，不是
`STEP_SEQUENCE` 的条目。用 Windows OCR 读 docx 内嵌图片（`image5`~`image9`）得到：

| docx 图 | OCR 到的气泡文字 | 属于哪一步 |
|---------|-----------------|-----------|
| `image5` | 新资源「萝卜」来了！点击右侧的「萝卜营地」… | `CARROT_CAMP`（步 12/22，营地**关**） |
| `image6` | 点「升级采集」，花 100 金币把每回合产量从 3 提到 6 | `HARVEST_UPGRADE`，营地**开**，按钮**灰** |
| `image7` | 点击「萝卜营地」打开营地。 | 又回到"开营地"这一态（营地被关掉了） |
| `image8` | 点「升级采集」…（同 image6） | 重开营地后按钮才亮，点它 |
| `image9` | 采集升级了：…点右上角「×」关闭营地，去挑战 Boss | 升级完成 |

也就是说：**玩家的实际路径是"开营地 → 按钮灰 → 关掉营地 → 再开一次 → 按钮才亮"**。
"第三、第四步"= image7 那个"白关一次再开一次"的来回；"第五步"= image9 的完成态。
用户要的是：**在第二步（image6 那一态）按钮就是亮的，点完升级直接进第五步**。

### 4.2 根因：**视图刷新早于步骤推进**

营地页面板里「升级采集」按钮的 `disabled` 有一项是
`not allows_carrot_action("harvest_upgrade")`，它只在 `step == Step.HARVEST_UPGRADE` 时为假。
而 `PrepUI._toggle_carrot_camp()` 的顺序是 **先 `toggle()`（内部会 `refresh()` 一次）
再上报状态**：

```
turn 1: 玩家点营地
  → toggle() 刷一次视图：此刻 step 还是 CARROT_CAMP → 按钮禁用（灰）
  → 上报 _report_carrot_camp_state() → sync() 推进到 HARVEST_UPGRADE
  → 推完之后没有任何人再刷视图  ← 窟窿在这
  → 按钮一直灰着，直到玩家关掉营地再打开（第二次 toggle 时 step 已经是 HARVEST_UPGRADE）
```

修法沿用本项目既有做法（`UPGRADE_2` / `UPGRADE_3` / `FORMATION_HP` 等分支都是这么写的）
—— **推进改变面板内容的步骤后请求一次刷新**：

```gdscript
if step == Step.CARROT_CAMP and _camp_open:
	_advance_to(Step.HARVEST_UPGRADE)
	# 9.25 教程优化第 2 条：必须在这里刷一次视图。
	_refresh_prep()
```

于是按钮在营地打开的**同一帧内**就亮起来，image7 那个来回自然消失，
玩家点完「升级采集」直接落到 image9 的完成态。

### 4.3 没做的事

**没有删任何 `STEP_SEQUENCE` 条目**，也没有删 `_harvest_upgrade_text()` 的分支：
第 3、4 步本来就是**同一个步骤（13/22）的中间态**，不是独立步骤。
删掉那两个中间态只会让"营地没开 / 页签不对"这类真实情况失去指引。

## §5 ③⑶ 商店刷新：无限次 + 永久免费 + 不出死侍

### 5.1 "免费"和"无限次"是同一件事

`EconomyService.shop_refresh_cost(uses, all_free)` 在 `all_free` 为真时**恒返回 0**，
而 0 费用既不扣钱、也不会让 `shop_refresh_uses_this_round` 递增（那个计数只喂给递增价公式）。
所以只要"免费"，"无限次"自动成立 —— **不需要另加计数器**。

### 5.2 判定只留一处（避免两处漂移）

新增唯一判定源：

```gdscript
# 9.25 教程优化第 3 条：教学里商店刷新「无限制次数 + 一直免费」。
# **判定必须只在这一处**：PrepBoardController._on_refresh_shop（真正扣钱的那边）和
# ShopPanel.refresh（画按钮、写「免费」标签的那边）各算一遍的话，两处一旦漂移就会出现
# 「按钮写着免费、点下去照扣」这类只在一处生效的错。
func shop_refresh_all_free() -> bool:
	return GameState.tutorial_mode or TreasureService.has_set("money")
```

两个使用点改为读它（原先各写一份 `TreasureService.has_set("money")`）：

- `scenes/prep/PrepBoardController.gd::_on_refresh_shop()`
- `scenes/prep/panels/ShopPanel.gd::refresh()`

非教学局回落到原有「金币」套装口径，行为不变。

### 5.3 死侍

`FILL_SHOP` 从 `["human_swordsman", "human_mage", "human_cleric", "human_death_servant"]`
改成去掉死侍的三种。`_apply_shop()` 按 `offers[i % size]` 循环填满 4 个卡位，
刷新（`_roll_shop` → `tutorial_shop_ids`）也走同一张表 —— 所以
**「不再出现」和「不再刷新出」两条由同一处保证**，不会只生效一半。
`START_SHOP`（开局那批）本来就不含死侍，未动。

## §6 ③⑷⑸ 开战前的最低上阵数门槛

### 6.1 "步骤 3/5/14/22"就是气泡右上角的「步 N/22」

docx 里说的是"步骤 3、5、14、22"。用 OCR 读图片确认过这四张图的气泡分别为
`步 3/22`、`步 5/22`、`步 14/22`、`步 22/22`，且**就是 `STEP_SEQUENCE` 的 1-based 序号**：

```
3  = START_PVE_1   、5  = START_PVE_2   、14 = START_BOSS  -> 至少 3 个
22 = START_PVP                                            -> 至少 7 个
```

### 6.2 实现

```gdscript
# 上阵数一律取 GameState.normal_unit_count()：board_slots 上的**普通**棋子数，
# 与 PLACE_3 / FILL_7 的完成条件同一口径（佣兵在 mercenary_slots，不算）。
func battle_board_gate_message() -> String:
	var need := 0
	if step in [Step.START_PVE_1, Step.START_PVE_2, Step.START_BOSS]:
		need = EARLY_DEPLOY_UNITS          # 3
	elif step == Step.START_PVP:
		need = FILL_TARGET_UNITS           # = GameConstants.NORMAL_UNIT_CAP = 7
	if need <= 0 or GameState.normal_unit_count() >= need:
		return ""
	return _t("上阵棋子数目少于%d" % need, "Deploy at least %d units first" % need)
```

- `EARLY_DEPLOY_UNITS := 3` 是**共享常量**：`PLACE_3` 的完成条件与这里用同一个值，
  两处不会各自漂移。
- `FILL_TARGET_UNITS` 取生产常量 `GameConstants.NORMAL_UNIT_CAP` 而不是写死 7 ——
  规则改了这里跟着走。
- 拦截点在 `PrepFlowController._on_start_battle()`：

```gdscript
if GameState.tutorial_mode:
	var gate := TutorialMode.battle_board_gate_message()
	if not gate.is_empty():
		show_message(gate)
		return
```

- **"文本格式与完成前置任务的提示文本一致"**：两者走**同一个出口**
  （`PrepFlowController.show_message`），样式天然一致，没有为它新建一种提示控件。

## §14 追加订正（用户回执，2026-09-25 下午）：商店刷新「免费」只生效了一半 —— 第三处判定漏抄

### 14.1 现象

用户截图回执：教程里商店刷新**刷几次之后就点不动了** ——
按钮还在、标着免费，按下去**毫无反应**。注意不是"扣了钱"，是**完全无响应**。

### 14.2 根因：§5.2 只点名了两处，实际有三处

刷新费用在客户端被算了**三遍**：

| # | 位置 | 作用 | §5.2 是否点名 |
|---|------|------|---------------|
| 1 | `ShopPanel.refresh()` | 画按钮、把 cost 写成「免费」 | ✅ |
| 2 | `PrepBoardController._on_refresh_shop()` | 真正扣钱 / 摇牌 | ✅ |
| 3 | `PrepUI._on_refresh_shop_control_pressed()` | 决定放不放燃烧动画 | ❌ **漏了** |

第 3 处原样保留着旧的 `var all_free := TreasureService.has_set("money")`：

```gdscript
func _on_refresh_shop_control_pressed() -> void:
	if _shop_refresh_burn == null or _shop_refresh_burn.is_playing():
		return
	var all_free := TreasureService.has_set("money")   # ← 漏了 GameState.tutorial_mode
	var refresh_cost := EconomyService.shop_refresh_cost(GameState.shop_refresh_uses_this_round, all_free)
	if GameState.gold < refresh_cost:
		return                                          # ← 静默 return：不播动画、不刷新
	_shop_refresh_burn.play(Callable(self, "_on_refresh_shop"))
```

于是形成**两套判定的正面冲突**：

- 按钮由**正确**判定（第 1 处）置成「免费、可点」；
- 点下去先撞上**错误**判定（第 3 处）：`all_free=false` ⇒ `cost = escalating_unit_price(uses)`
  递增 ⇒ 超过金币 ⇒ `return`。

为什么是"刷几次之后"才失效 —— `shop_refresh_cost` 的短路：

```gdscript
if all_free or refresh_uses_before <= 0:
	return 0
return escalating_unit_price(refresh_uses_before)
```

`uses=0` 时**免费**（所以第一次刷新永远成功），从 `uses=1` 起按 10 → 20 → 40 … 递增；
金币被递增价吃干那一刻起，按钮就"死了"。用户的"刷到一定次数" = 金币见底。

### 14.3 改法

第 3 处接**同一个函数**（不是照抄同一串条件）：

```gdscript
	var all_free := TutorialMode.shop_refresh_all_free()
```

### 14.4 这条为什么以前没被发现

`PrepUI.gd` 那处**没有任何门禁覆盖**。§5.2 引入的 `shop_refresh_all_free()` 只在
**行为**层面被测过（费用是不是 0），而**没有任何判据检查「这个函数被谁调用」**。
换句话说，当时那句「判定必须只在这一处」是**约定**，不是**判据** —— 约定管不住第三个调用点。

### 14.7 排查中捡到的两个坑（都已写进新门禁的注释）

1. **`_func_start` 必须连 `static func` 一起认**。第一版只认 `func `，而 `EconomyLedger.gd`
