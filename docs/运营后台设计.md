## 二、封号

### 玩家会遇到什么

- 封号之后：登录画面显示「账号已被封禁」+ 原因 + 解封时间（永久的写永久）。**新包**才有这个画面；
  旧包只会显示「登录失败」，但**不会换号、不会漏网**（见下面 403 那条）。
- 正在线上：10 秒内被踢下线（网页后台封号是当场踢）；排队、匹配里的位置同时摘掉。
- **正在打的那一局照常打完** —— 其他五个人的对局不该因为一个人被封而作废。打完回菜单时回到登录画面。
- 解封之后：点「重试」就回到**原来那个号**。

### 为什么只改账号服务器，战斗服务器不用动

同事文档的 OPS-05 要给战斗服务器新建一条「制裁控制通道」。不需要：出战名片 60 秒过期、一张只能用一次、
没有名片坐不进任何房间（`backend/app/loadout.py` 的 `CARD_TTL_SEC`，`NetworkService._accept_seat_card`）。
账号服务器不再给他发名片，最多 60 秒后他就进不了任何新对局。所以**协议号不动**。

### 🔴 两处容易做错的地方

1. **被封回 403，绝不能回 401。** 旧包续期收到 401 会清掉本机凭证、自动注册一个新匿名号 ——
   回 401 等于替他换了个号。403 只显示登录失败，凭证留着。
2. **续期时 Supabase 会先把旧凭证换掉，我们之后才知道他被封了。** 新凭证要是没存下来，玩家下次拿旧凭证来，
   Supabase 当成「用过的凭证被重放」，把整条会话作废 → 401 → 旧包自动注册新号，封号白封，解封后原来的号也登不回去。
   所以被封时把 Supabase 换出来的新凭证存进 `ban_refresh_handoff`：还封着就直接 403、**不再碰 Supabase**；
   解封后用存着的那张去续。**这张表不定期清理**（永久封号的人一年后回来也得接上）。

   2026-09-24 本机端到端验过：同一张旧凭证重试 3 次都是 403，Supabase 只被调了 1 次；解封后拿旧凭证回到原来的号。

### 怎么封

网页后台「玩家」页，或者 Supabase SQL Editor：

```sql
select ban_player(p_friend_code => 'ABCD2345', p_duration => interval '7 days',
                  p_reason => '使用外挂', p_actor => 'arvin', p_note => '举报截图 9/24');
select ban_player(p_friend_code => 'ABCD2345', p_duration => null, p_reason => '盗号', p_actor => 'arvin');  -- 永久
select unban_player(p_friend_code => 'ABCD2345', p_actor => 'arvin', p_note => '误封');
```

`p_reason` 玩家看得到，`p_note` 看不到。解封是**撤销他现在生效的全部封号**，记录都留着。
SQL 里封的人不会被当场踢，最多等 10 秒巡检。

封号和信誉分系统的「排位禁赛」（`player_credit.banned_until`）是两回事：那个是自动的、只管排位。

## 三、注销 = 删资料、留账目

以前注销是 `delete from players`，靠外键把二十多张表一起删 —— 连钻石流水、订单、封号记录也没了：
接了充值后查不到他买过什么，被封的人注销一下封号记录就没了。

现在（`017` 的 `erase_player()`，一个事务）：

- **删**：资料、登录方式（删了就登不回这个号）、好友 / 拉黑 / 好友请求 / 在线状态、最近同房、私聊（双方的消息）、被封期间寄存的凭证；
  昵称改「已注销玩家」、头像回默认；**好友码换成一个新的随机码** —— 别人手上记着的旧码从此查不到任何人。
- **留**：钱包与流水、订单与归属、邮件与领取记录、对局座位、排位 / 信誉 / 赛季归档、封号记录。

`backend/tests/test_profile.py` 钉着：**每一张引用 players 的表都必须归到「删」或「留」一边**，以后加新表会被逼着想清楚。

游戏里注销页的说明已经改成写明「购买与对局记录会去掉身份后保留」（商店的注销政策要求写明）。

## 四、网页后台

地址：`https://glorytd-api.duckdns.org/admin/`（和账号服务器同一个域名，Caddy 不用改）。

### 加管理员（至少要两个人，不然发钱的申请没人能批）

1. Supabase Dashboard 左边栏从上往下第 5 个图标（锁头，**Authentication**）→ 上方 **Users** →
   右上角绿色 **Add user → Create new user**，填邮箱、密码，勾 **Auto Confirm User**，创建。
2. 左边栏 **SQL Editor**，跑一行（邮箱用第 1 步那个，第二个是名字）：
   `select add_admin('arvin@example.com', 'arvin');`
   名字会写进所有操作记录和钱包流水的操作人一栏。
3. 打开 `/admin/` 用那个邮箱密码登录。第一次会出一个二维码，用手机验证器 App（Google Authenticator / Microsoft Authenticator）扫，
   输入 App 里的 6 位数字。以后每次登录：邮箱 + 密码 + 6 位数字。

停用：`update admin_users set active = false where name = 'arvin';` —— 下一个请求起就进不去。**不要删行**（操作记录里写的是名字）。
重新启用：再跑一次 `select add_admin(...)`。

手机丢了 / 换手机：SQL Editor 跑
`delete from auth.mfa_factors where user_id = (select id from auth.users where email = 'arvin@example.com');`
下次登录会重新出二维码。

Supabase 里要开着的：Authentication → Sign In / Providers → **Email**（默认开）；Authentication → **Multi-Factor → TOTP**（默认开）。

### 能做什么

| 页面 | 功能 | 要不要第二个人批 |
|---|---|---|
| 玩家 | 按好友码 / 玩家编号精确查，按昵称给候选；看资料、在线、钱包（付费 / 赠送 / 黄金分开）、流水、订单、拥有、邮件、排位信誉、最近对局、后台对他做过什么 | — |
| 玩家 → 封号 / 解封 | 天数（空 = 永久）、给玩家看的原因、内部备注 | 不用 |
| 玩家 → 发钱 | 赠送钻石（≤10 万）/ 黄金（≤100 万），填原因 | **要** |
| 审批 | 等批准的申请：别人的可以「批准并执行」或拒绝，自己的只能撤回；最近 100 条的结果 | — |
| 邮件 | 单人（好友码）或全服；没附件当场发，带附件变成申请；撤回；看每封有多少人领了 | 带附件**要** |
| 公告 | 新建 / 编辑 / 发布 / 撤下、上传图片（原图进 Supabase 的公告桶）、大改时让玩家重新看到红点 | 不用 |
| 操作记录 | 最近 200 条：谁、什么时候、做了什么、成没成 | — |

所有时间按**马来西亚时间**显示和输入。顶栏一直标着「正式服」还是测试环境。

### 规则都没有另写一套

后台只是给已有的入口套一层网页：发钻石走 `grant_diamonds`、发黄金走新加的 `grant_coin`（同形状）、
邮件走 `send_mail` / `send_mail_all` / `withdraw_mail`、封号走 `ban_player` / `unban_player`、公告写 `announcements` 表。
**钱包、邮件、封号的规则都还在那些函数里。** 在 SQL Editor 里直接调它们照样可以，只是没有审批、不进后台的操作记录。

### 审批怎么防出错

- 批准那一刻**在同一个事务里**改状态 + 发钱 + 记操作记录。没有「批了还没执行」这种中间状态。
- 自己不能批自己（数据库约束也挡着）；两个人同时点批准只有一个生效；连点提交只建一条（页面每次提交带一个编号）。
- 申请之后内容不能改，要改就撤回重提 —— 批的就是看到的那一份。
- 执行失败（例如申请之后玩家注销了）记成「执行失败」并写明原因，不会一直挂在等批准里。
- 流水的操作人写「申请人/批准人」（例如 `bob/alice`），备注写「后台#申请编号 原因」。
- 带奖励的全服邮件**不能**勾「之后注册的新玩家也能收到」：那样总量没有上限（同事文档 5.2 那条）。

### 安全

- 登录：Supabase 验密码 → 查名单（不在名单里的和密码错的看到**同一句话**）→ Supabase 验手机验证码，拿到两步验证级别的令牌才算登录。
  之后发一个我们自己的随机会话放在 HttpOnly Cookie 里，**Supabase 的令牌用完就丢**。
- 每个请求都重查名单，停用立刻生效。会话在进程内存里：**账号服务器重启后所有管理员要重新登录**。
- 写操作要带 `X-Glory-Admin` 头（防跨站），Cookie 是 SameSite=Strict；页面有严格的内容安全策略，
  玩家昵称这类别人填的字一律当纯文字显示（有测试钉着页面代码里不许出现 innerHTML）。
- 玩家的令牌进不了后台接口。登录尝试每个 IP 15 分钟 10 次。
- 操作记录只能追加：数据库触发器拒绝改、删、清空。

## 五、部署顺序

1. **Supabase SQL Editor 按顺序跑** `database/016_bans.sql` → `017_account_deletion.sql` → `018_admin.sql`。
   `update.sh` 不跑 SQL（排位那次踩过）。
   - 016 没跑时账号服务器照常放行（查不到封号表 = 没人被封，只在日志里报错）；
   - 017 没跑时注销会失败（报错，不会删一半）；
   - 018 没跑时网页后台打不开，游戏不受影响。
2. 按第四节加至少两个管理员。
3. GitHub Desktop 推送 → 服务器 `update.sh`。**网页后台就能用了**（`/admin/`）。
4. 出新 APK（封号画面、注销页说明）。旧包不出也不会漏：被封只会显示登录失败，不会换号。
5. 战斗服务器**不动**，协议号不变。

验证：打开 `/admin/` 能看到登录页；封一个测试号，那台手机 10 秒内回到登录画面；日志里没有 `player_bans 表不存在`。

## 六、没做的（对照同事文档）

| 同事文档 | 状态 | 理由 |
|---|---|---|
| OPS-05 战斗服务器制裁通道 | **不做** | 名片 60 秒过期 + 一次性，停发名片就够（第二节） |
| 8 种角色 / 额度预算表 / 公司单点登录 | 不做 | 现在能进后台的就几个人；只保留「发钱要第二个人批」 |
| 任务队列、outbox、定时发邮件、批量名单 | 不做 | 没有要排程或批量的需求；公告本来就能设开始时间 |
| 测试环境（staging） | 没有 | 只有一个 Supabase + 一台 GCP。本机测试库 + 假 Supabase 替代了一部分（第七节） |
| 文字 / 语音禁言、举报与申诉、客服工单 | 以后 | 游戏里还没有举报入口 |
| 赛季管理页面、信誉分更正、权益发放撤销、服务状态页 | 以后 | 需要时再加一页，规则都在现成的函数里 |
| 充值、退款、补单 | 以后 | 等真实支付接上（商城第 6 步） |
