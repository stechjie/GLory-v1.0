# 9.23 第五批 — boss 技能音「挂错时刻」订正（双通道）

> 起因：用户逐条点名 5 只 boss 的技能音「没在正确的时刻响」，要求重新检测、
> 测试、修复，然后覆盖两个桌面交付夹。

## 一、用户口径（逐条，原文为准）

| # | boss | skill_id | 用户口径 |
|---|------|----------|----------|
| ① | 雷怒核心 | `overload_counter` | 「触发技能造成伤害时播放音效」，**不是**开局播放 |
| ② | 镜像魔君 | `mirror_clone` | 「召唤分身时播放」，**不是一直播放** |
| ③ | 噬魂领主 | `soul_devour` | 音效**未生效** —— 应在**击杀单位后**播放 |
| ④ | 血怒魔王 | `blood_rage` | 音效**未生效** —— 应在**进入暴走状态时**播放，**仅播放一次** |
| ⑤ | 灭世裁决者 | `apocalypse_charge` | 音效**未生效** |

★ ④ 的「仅播放一次」是用户在本轮追加强调的，不是从代码推出来的。

## 二、根因：9.22 把 7 只 boss 全挂在同一条边沿上

9.22 的做法是在 `BattleVfx._play_skill_cast_vfx` 里用**一张全量素材表**
`SfxService.boss_skill_cue_for(uid)` 派发，触发点是 `skill_ready` 的**上升沿**。
这条边沿对 7 只里的 **6 只是错的**：

| boss | 为什么错 | 表现 |
|------|----------|------|
| `overload_counter` | 不在 `_tick_skills` 的 `match` 里，**没有 `skill_ready` 上升沿** | 一次都不响 |
| `soul_devour` | 同上 | 一次都不响 |
| `blood_rage` | 同上（它是「挨打时按血量触发」的被动） | 一次都不响 |
| `twin_revive` | 同上 | 一次都不响 |
| `mirror_clone` | 在 `match` 里，但 `skill_ready = elapsed + 1.0` | **每秒重响一次** = 用户说的「一直播放」 |
| `apocalypse_charge` | 走的是 `apocalypse_charging = f.has("apocalypse_due")` 的 diff | 见下节 |

只有 `holy_priest` 与 `meteor_caster` 的「施法这一下」确实等于用户要的那一声。

## 三、更要紧的一层：那两条「看起来对」的判据过不了回放边界

★ 这是本轮最值得记的一条。

真实 3v3 打的**不是本地模拟**，而是 `BattleScreen._start_replay` →
`_apply_replay_frame` 播**回放**。而回放帧只打包 **13 个数值列**
（`BattleSimulator._replay_capture_frame`），`_state` 里的单位字典也只按
`_load_replay_roster` 那一组**固定键**重建。

于是 `apocalypse_due` / `blood_rage_active` / `killer_uid` 这类字段
**在回放侧根本不存在**：

* `apocalypse_charging = f.has("apocalypse_due")` 在回放侧**恒为 false**
  → BattleVfx 里那整段蓄力音派发是**死代码**；
* 这就是用户报的 ⑤「音效未生效」，也解释了为什么源码里
  「明明写了、素材也在、门禁全绿」却一声不响。

**结论（写进 `audio_0922_check.gd` 头部）**：

> 音效的判据必须跟着**会过回放边界的数据**走。

## 四、修法：拆成两条通道

### 通道 A —— 施法边沿（只留 2 只）

`SfxService.boss_cast_edge_cue_for(boss_id)`，只有：
`boss_holy_priest` / `boss_meteor_caster`。
触发点仍是 `BattleVfx._play_skill_cast_vfx` 的 `skill_ready` 上升沿。

### 通道 B —— 真事件（其余 6 只）

`SfxService.BOSS_EVENT_ACTIONS`，**键是 `skill_id`**，值是 `{cue, stop}` 动作表
（`stop` 非空则「先收口、再放音」）：

| skill_id | cue | stop |
|----------|-----|------|
| `overload_counter` | 雷怒核心 | — |
| `mirror_clone` | 镜像魔君 | — |
| `soul_devour` | 噬魂领主 | — |
| `blood_rage` | 血怒魔王 | — |
| `twin_revive` | 双生守门人复活 | — |
| `apocalypse_charge` | 蓄力开始 | — |
| `apocalypse_impact` | 蓄力完成 | 蓄力开始 |
| `apocalypse_stop` | （不补音） | 蓄力开始 |

消费端：`BattleVfx._maybe_play_boss_skill_proc(event)`，
挂在 `sfx_proc` 事件分支上（**先问 boss 那一支，接了就结束**，
免得同一条事件被四星 / 佣兵那两支再按 `skill_id` 判一遍）。

★ 这一支**不做归属门控**（与施法边沿同口径）：boss 固定是敌方单位、
不属于任何 `owner_slot`，用户口径是「boss 技能音效播放，我方队友都能听见」。
并进 `_maybe_play_sfx_proc` 就是永远不响 —— 那一条开头就是
`_is_own_or_ally_unit(source_uid)`。

### 事件的来源分两类

1. **模拟器补**（经 `BattleSimShared._emit_sfx_proc` → `state.visual_events`
   → 回放采集进 `frame_events`，**过得了回放边界**）：
   * `mirror_clone` —— `_tick_skills` 里 `if _skill_mirror_clone(...) > 0`
     （返回值 = 这次真的召唤出几个分身）；
   * `soul_devour` —— `_on_unit_killed` 的 `soul_devour` 支（击杀后回血加攻那一处）；
   * `blood_rage` —— `_apply_boss_attacker_passives` 的 `blood_rage` 支，
     **挂在 `not blood_rage_active` 守卫里面** → 「仅一次」由代码结构保证；
   * `apocalypse_charge` / `apocalypse_impact` / `apocalypse_stop` ——
     `_tick_skills`（返回 `bool`：「这次真的开始了」）与 `_process_boss_charges`
     （被打断 → `stop`；到点且 `hit_any` → `impact`，到点但没打到人 → 只 `stop`）。
2. **BattleVfx 就地构造**（判据本来就会过回放边界，不必绕模拟器）：
   * `overload_counter` —— 过载层数 `stack_delta < 0` 那一格（= 反击真的打出去了）；
   * `twin_revive` —— `alive` 由假转真那一格。

### 关键实现细节

* `_emit_sfx_proc` **搬到 `BattleSimShared`**：`BattleSimulator` /
  `BattleSimSkills` / `BattleSimTreasures` 三个兄弟模块都要用，
  放共享基类上避免循环依赖。
* `_skill_apocalypse_charge`：`void` → `bool`。
  没有返回值，「开始蓄力响一次」会退化成「每次 match 都响」。
* `_skill_mirror_clone`：`void` → `int`。
  没有返回值，镜像魔君会退化成「每秒响一次」（= 用户报的「一直播放」）。
* `_process_boss_charges`：**两档都收口**（打断 / 完成但没打到人），
  且 `apocalypse_impact` **先 stop 再 play**（表里 `stop` 字段），
  否则 2 秒的蓄力一次性音会和完成音叠在一起。
* `BattleVfx` 里那三条**旧调用点删干净**
  （`play/stop_cue(CUE_BOSS_APOCALYPSE_CHARGE)`、`play(CUE_BOSS_APOCALYPSE_IMPACT)`）：
  它们挂的 `apocalypse_charging` 在回放侧恒为假，留着就是
  「看起来很全，实际不响」+ 和事件通道叠成两声。

### 6.3 ★★ 本文件自己也制造过一次假绿（值得单独记）

`audio_0922_check.gd` 里 `_check_blood_rage_emitter` 的一条提示串写成：

```gdscript
"血怒魔王掉到 30% 血（暴走）却没有补事件（实际 %d 条）" % hits.size()
```

`30%` 后面那半截是**裸百分号**。GDScript 报
`String formatting error: unsupported format character`，
**该函数当场中断、它后面所有断言一条都不执行**。

要命的是它的表现：整体只是「失败数没变多」，看上去像全绿 ——
被跳过的正好包括用户明确要求的「仅播放一次」那一条。
必须写成 `30%% 血`。

**教训**：`%` 格式化的串里出现百分比一定要 `%%`；而且
**只有变异测试能发现「整段断言根本没跑」**，因为 `contains` 类判据全绿。

配套踩到的第二个坑：**同一个 `.gd` 在一次消息里连发两条 Edit 会互相覆盖**
（后一条按旧快照重写文件，先前那条静默丢失）—— 三条变异第一次只生效了两条，
排查了一轮才发现。改同一份文件要**一次一条**。

### 6.4 `ui_feedback_check` 的归因（环境态，非本批回归）

批跑首轮它红一条 `shake_did_not_start`。归因：`UiFeedback.shake()` 除了
`screen_shake` 还会看 `Tokens.reduced_motion()`（设置页「降低动态效果」），
为真时直接归零返回 false；而该检查只快照了 `screen_shake`。
实测磁盘 `user://profile.json` 里 `reduced_motion_enabled=true`。

（`work/_qa_922/attribute_ui_feedback_922.py` 已做过同样的对照归因：
把磁盘值改成 false → 门禁转绿；改回 → 红。结论一致。）

本轮**顺手把它修好**：`_check_reject` 把两个开关都纳入快照，
测抖动那一段强制关掉 `reduced_motion`，收尾一并还原并断言还原成功。

★ 更要紧的是它同时在**制造假绿**：`shake()` 提前返回 false 时不建 tween、
不动控件，于是 `shake_does_not_restore_rotation` /
`shake_does_not_restore_pivot` / `shake_leaks_tracking` 三条
「什么都没抖所以什么都没坏」全部通过 —— 真出了「抖完不回原值」
的 bug 也照样绿。修完 checked 40 → 41。
