# 9.27 「备战期刷新商店 → 掉线重连 → 刷新费用变少」调查报告

> 状态：**仅调查，未修复**（用户明确要求：先别修，等通知）。
> 触发：用户怀疑存在「备战时候刷新过商店 → 掉线重连 → 回来发现刷新需要的费用变少了」。

## 一、结论（先说结果）

**存在，但和"重连把计数清零"不是同一条路。**

用户猜的机制（重连后计数器被清零 ⇒ 费用回落）**在代码上不成立** —— 我把「掉线重连」
这条链上每一个可能写 `GameState.shop_refresh_uses_this_round` 的地方都单独驱动验过，
**没有任何一处会把它清零**（详见第三节 A~F）。这一点可以放心。

但探针挖出了**另一条真缺口，症状正好也是"刷新费用变少"**：

> **服务端的权威刷新次数从来没回流到客户端的计费计数器。**
> `room_state.economy.shop.refresh_uses` 到达客户端后，只被存进
> `NetworkService.server_shop`（一份数据副本），**从不写回
> `GameState.shop_refresh_uses_this_round`**。而 UI 上那个刷新价签、
> 以及"点下去扣多少钱"的判断，读的**全是** `GameState` 这个字段。

后果：**只要有一次刷新的回执没能被客户端处理（掉线、丢包、重连、切后台），
客户端的计数就永久落后于服务端，之后每一次刷新都比应价的便宜** ——
最极端的情况是服务端已经记到 3、客户端还是 0，于是**显示并收取 0 金，而服务端应收 40**。

探针实测（复刻该场景，直接驱动生产函数）：

```
srv_costs              = [0, 10, 20]   # 服务端权威：三次分别收 0/10/20
srv_uses               = 3             # 服务端 refresh_uses = 3
client_after_reconnect = 0             # 重连后客户端计数仍是 0
server_shop_refresh_uses = 3           # 数据其实就在手上（server_shop 里）
client_next_cost       = 0             # 客户端显示的下一次刷新价
server_next_cost       = 40            # 服务端真正会收的价
```

**这就是"刷新费用变少"。** 而且它是**可持续复现**的：由于缺口是"只进不出"，
计数一旦落后就再也追不回来（除非回合推进时被 `reset_shop_refreshes()` 归一 —— 那反而是重置）。

**更关键的是：触发不是"碰巧丢包"，而是确定性的。** 回执入口有一道幂等闸
（`_tx_consume` 查等待表），而 `NetworkService.reset()` 里有 `_tx_pending.clear()`
—— 所以**走 `reset()` 的重连（app 被杀重开 / `begin_resume_from_disk()`）下，
掉线前那笔刷新的回执必定被丢弃**。探针实测：`consume_before_reset=true` →
`consume_after_reset=false`。（瞬断重连走 `_begin_reconnect()`，不调 `reset()`，
等待表保留，那条路径要靠真丢包才触发。）

> ⚠️ 需要说清楚的边界：**这不是"重连本身把费用改小"**，而是"重连**保证**了一个
> 已经存在的计数不同步会暴露出来"。玩家掉线前刚刷过、回执被丢，回来就发现便宜了。
> 没有掉线、回执正常送达时，两边是一致的，看不出问题。

## 二、费用模型（先把"变少"量化）

`EconomyService.shop_refresh_cost(uses, all_free)` → `escalating_unit_price(uses)`：

| `refresh_uses` | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 刷新价 | **0**（首刷免费） | 10 | 20 | 40 | 80 | 160 |

**关键：`uses == 0` 是"免费"，不是"很便宜"。** 所以计数只要**回落到 0**，
费用就从 40 直接掉到 0 —— 这是"费用变少"能被观察到的原因。
（探针 `cost_curve` 断言把这条曲线钉死，后面的推理才可解释。）

`ShopPanel.refresh()` 的价签（`scenes/prep/panels/ShopPanel.gd:535`）：

```gdscript
var refresh_cost := EconomyService.shop_refresh_cost(GameState.shop_refresh_uses_this_round, all_free)
refresh_button.disabled = GameState.gold < refresh_cost
refresh_cost_label.text = tr("ui_free") if refresh_cost == 0 else str(refresh_cost)
```

**UI 读的是 `GameState.shop_refresh_uses_this_round`** —— 客户端本地字段，不是服务端的值。

## 三、逐条排查：谁**会**清零这个计数（结论：重连链上都不）

`GameState.shop_refresh_uses_this_round` 的**全部**写入点（全仓 grep，排除 `work/` 备份）：

| 位置 | 写法 | 触发时机 |
|---|---|---|
| `PrepBoardController.gd:990` | `+= 1` | 本地刷新成功 |
| `NetworkService.gd:5614` | `= result.refresh_uses` | 收到 `shop_refresh` **回执** |
| `GameState.gd:138`（`reset_run()`） | `= 0` | **开新局**（换一本账） |
| `GameState.gd:285`（`reset_shop_refreshes()`） | `= 0` | **回合推进** |
| `SaveManager.gd:332`（`load_run()`） | `= 存档值` | **读盘** |

`Main.gd` **不直接写**这个字段（探针 §1 反向断言 `main_no_direct_write` 钉住）。

现在逐条评估"重连会不会碰到它们"：

### A. `_begin_reconnect()`（瞬断，网络抖动）— **安全**
`:4143`。注释明写「掉线 -> 进入 RECONNECTING：保留 team 上下文，仅重置网络对象」，
只调 `reset_peer_only()`，**连 `reset()` 都不调**。
探针实测：`after_begin_reconnect = 3`（刷新 3 次后瞬断，计数保持 3）✅

### B. `NetworkService.reset()`（app 被杀重开 / `begin_resume_from_disk()`）— **安全**
`:4079` 一整块清了 `server_four_star_cost_version`、`four_star_request_id`、
`latest_match_state`、`team_active`、`_tx_pending` 等一票**会话态**，
但**完全不碰 `GameState`**（它是另一本账，归 GameState 管）。
探针实测：`after_ns_reset = 3` ✅

### C. `GameState.reset_run()` — **会清零，但重连不该走到**
它是"换了一本账"，`shop_refresh_uses_this_round = 0` 是**正确语义**。
问题只在于：`begin_resume_from_disk()` 调的是 `NetworkService.reset()`，
**不是** `GameState.reset_run()`（两者是不同对象的同名方法，容易看混）。
⚠️ 这是**命名陷阱**：两个 `reset()` 语义完全不同。已在报告标明，未见误用。

### D. `_apply_team_match_state_payload()` 里的 `reset_shop_refreshes()` — **有守卫**
`Main.gd:2846` 确实会清零，但它在 `if not result.is_empty():`（`:2838`）之内，
即**只有真的打完一场、带着战斗结果**才会走到。
而重连路径 `_on_network_match_state_received()`（`:2926`）调用时**不传 `result`**：

```gdscript
if GameState.team_mode:
    _apply_team_match_state_payload(state_payload)   # ← 没有第三个参数
```

所以那条路径跳过清零。探针 §6 两条断言（`D_settle_guard` / `D_reconnect_no_result`）钉住。
✅（这也解释了为什么这个设计是有意的 —— 见 `:2931-2936` 的注释：
内嵌服务器会在本回合刚就绪时立刻发战后 match_state，此时玩家可能还在备战，
不能提前应用。）

### E. `SaveManager.load_run()` — **会恢复，且依赖闸门**
读盘会把计数恢复成存档值（`SaveManager.gd:281` 写、`:332` 读）。
刷新流程末尾**确实**调了 `save_run()`（`PrepBoardController.gd:1001`），
所以"刷新完立刻掉线"读到的存档是**新的**，不会变小。✅

### F. 但 `load_run()` 在 mid-match 根本不跑 — **反而避开了风险**
`Main.gd:384`：

```gdscript
if _team_run_state_is_fresh():
    SaveManager.load_run()
```

而 `_team_run_state_is_fresh()`（`:538`）=「棋盘**和**备战席**全都为空**」：

```gdscript
func _team_run_state_is_fresh() -> bool:
    for cell in GameState.board_slots:
        if cell != null:
            return false
    for cell in GameState.bench_slots:
        if cell != null:
            return false
    return true
```

对局中玩家棋盘上必有棋子 → 返回 `false` → **不读盘** → 计数沿用内存值。
（注释里写明这是刻意的：活着的重连内存就是最新状态，不能用可能过期的存档覆盖。）

**⇒ A~F 全部排除。"重连把计数清零"这个机制不存在。**

## 四、真正的问题：服务端权威值**只进不出**

### 4.1 服务端是费用权威

`EconomyLedger._shop_refresh()`（服务端侧唯一算价处）：

```gdscript
var uses := int(shop.get("refresh_uses", 0))        # ← 读服务端自己的账
var free := TreasureService.has_set_in(ctx.get("owned_treasures", []), "money")
var cost := EconomyService.shop_refresh_cost(uses, free)
if int(prep.get("gold", 0)) < cost:
    return {"ok": false, "error": "not_enough_gold"}
...
shop["refresh_uses"] = uses + 1                      # ← 服务端自己递增
...
return {"ok": true, "result": {"cost": cost, ..., "refresh_uses": uses + 1}}
```

**服务端不信任客户端的次数**，自己按 `prep.shop.refresh_uses` 算价并递增 —— 设计正确。

### 4.2 客户端只在**回执**里接收它

`NetworkService.gd:5611-5614`：

```gdscript
"shop_refresh":
    GameState.gold = maxi(0, GameState.gold - int(result.get("cost", 0)))
    GameState.shop_refresh_uses_this_round = int(result.get("refresh_uses", GameState.shop_refresh_uses_this_round))
```

**这是全仓唯一一处"把服务端次数写回 GameState"的代码。**

### 4.3 而 `room_state` 里带来的那个值被丢掉了

`_apply_server_shop()`（`:5540`）—— 重连恢复的主通道：

```gdscript
func _apply_server_shop(state: Dictionary) -> void:
    if state.is_empty():
        return
    var shop: Variant = state.get("shop", {})
    if typeof(shop) != TYPE_DICTIONARY:
        return
    if str((shop as Dictionary).get("offer_id", "")).is_empty():
        return
    server_shop = (shop as Dictionary).duplicate(true)     # ← 只存副本
    # ← 没有一行写 GameState.shop_refresh_uses_this_round
```

`_apply_carrot_state()`（`:5551`，重连时被 `Main.gd:402` 调用）同样不碰这个字段。

**服务端明明在 `room_state.economy.shop.refresh_uses` 里把权威次数发过来了**
（`NetworkService.gd:1975`：

```gdscript
"shop": { "offer_id": ..., "offers": ..., "sold": ..., "refresh_uses": int(shop.get("refresh_uses", 0)) },
```

），`_apply_server_shop` 也把它整份存进了 `server_shop`，**但没有任何代码把它搬进
`GameState.shop_refresh_uses_this_round`** —— 也就是 UI 与扣费实际读的那个字段。

探针把这条缺口钉成两条互补断言：

- `H_receipt_write_exists` = **true** → 回执分支那处写入确实存在（不是没写）
- `H_no_roomstate_sync` = **true** → 而 `room_state`/`state` 路径 **不存在**回写

两者同时成立 ⇒ 缺口是**通道性的**（只有回执这一条路能给客户端同步次数），
不是"某处忘了初始化"。

### 4.4 触发是**确定性的**，不只是"可能丢包"

回执入口有一道幂等闸（`NetworkService.gd:5507-5511`）：

```gdscript
@rpc("authority", "call_remote", "reliable")
func _rpc_economy_receipt(request_id: String, receipt: Dictionary) -> void:
    if not _tx_consume(request_id):
        return                       # ← 不在等待表里的回执直接丢弃
    _apply_carrot_receipt(receipt)
```

`_tx_consume()`（`:3913`）：

```gdscript
if not _tx_pending.has(rid):
    return false  # 不是本机在等的单子（换会话后的迟到包）
```

而 `NetworkService.reset()`（`:4136`）里有一行：

```gdscript
_tx_pending.clear()
_tx_done.clear()
```

**⇒ 只要走了 `reset()` 那条重连（app 被杀重开 / `begin_resume_from_disk()`），
等待表被清空，此前所有 in-flight 的交易回执**必定**被丢弃。**
于是"刷新发出 → 进程被杀/重开 → 重连"这条路径下，
`GameState.shop_refresh_uses_this_round` **必然**停在旧值，而服务端**必然**已经递增过。
这不是概率问题，是**确定性**的。

（瞬断重连 `_begin_reconnect()` 不调 `reset()`，等待表保留，
所以那条路径要靠"真的丢包"才触发 —— 概率性。两条路径的严重度不同。）

### 4.5 症状链（完整）

```
玩家（客机，非房主）在备战期刷新商店
  └─ PrepBoardController._on_refresh_shop():972
        server_shop 非空 → NetworkService.request_shop_refresh() → return
        ★ 注意：本地 GameState.shop_refresh_uses_this_round 在这里**不递增**
          （递增只发生在 :990 的本地分支，或回执到达时的 :5614）
  └─ 服务端 EconomyLedger._shop_refresh() 算价、扣钱、refresh_uses += 1
  └─ 回执 _apply_carrot_receipt() → GameState 计数跟上
                        ↑
                    【掉线 / 丢包 / 切后台，回执没送到】
  └─ 重连：room_state 到达，economy.shop.refresh_uses = 3
        _apply_server_shop() → 存进 server_shop（3 就在手上）
        ✗ 但 GameState.shop_refresh_uses_this_round 仍是 0
  └─ ShopPanel.refresh() 读 GameState → 显示 0（免费）
  └─ 玩家点刷新 → _on_refresh_shop 走 intent 分支 → 服务端按 uses=3 收 40
        ⇒ 玩家预期 0、实际扣 40（或反之的"看起来变便宜"）
```

## 五、影响面

- **受影响**：非房主客机（走 intent 分支，`PrepBoardController.gd:972`）。
  这是"本地不递增、全靠回执同步"的那条路，所以对回执丢失**最敏感**。
- **房主 / 单机**：走本地分支 `:978-990`，本地即时递增 → 不受这条缺口影响。
- **触发条件**（按确定性从高到低）：
  1. **app 被杀 / 重开后重连**（走 `reset()`）→ 掉线前那笔刷新的回执**必被丢弃** → 确定性。
  2. **瞬断重连**（走 `_begin_reconnect()`，不清等待表）→ 需真的丢包 → 概率性。
  3. 切后台、弱网丢包 → 概率性。
- **不能自愈**：缺口是单向的。计数落后之后，后续每次刷新的回执都会把它
  覆盖成"服务端当时的次数"，看似会追平 —— 但**下一次刷新前的显示价**始终是低的，
  且服务端会按真实次数收钱 ⇒ 表现为"价格显示与实际扣费不符"。
  回合推进时 `reset_shop_refreshes()` 才归零，两边重新一致。

> 说明：这条缺口的**可见度取决于玩家行为**。要在"刷过商店"和"看下一次价签"之间
> 发生一次回执丢失。app 被杀重开这条路径是确定性的，所以**复现步骤很明确**：
> 客机在备战期刷新商店（不必等回执显示）→ 杀进程 → 重开并重连 → 看价签。
> 这一点建议做一次真机确认，比猜测更省事。

## 六、待确认（需要现场证据，本机无法判定）

1. **是"显示价变低"还是"实际扣费变少"？**
   这两者在代码里读的是**同一个字段**（`GameState.shop_refresh_uses_this_round`），
   所以只要缺口存在，两者会**一起**变低；而服务端按自己的次数记账 ⇒
   服务端库里的金币会比客户端预期更少扣。**请确认玩家看到的是哪种**：
   - 若"价签显示 0 但金币实际少了 40" ⇒ 正是本报告描述的缺口。
   - 若"金币也真的只少了 0" ⇒ 还有第二条路径（服务端也没收到记账），需要另查。
2. **发生时机**：是不是都发生在**掉线/切后台之后**？还是也有"没掉线也变便宜"的例子？
   后者会把范围从"回执丢失"扩大到 `_apply_server_shop` 之外的通道。
3. **是客机还是房主**？房主理论上不该出现。

**落地**（`scripts/autoload/NetworkService.gd` 的 `_apply_server_shop`）：
拿到 `room_state` 广播里的 shop 时，若带 `refresh_uses` 就把它同步回
`GameState.shop_refresh_uses_this_round`：

```gdscript
server_shop = (shop as Dictionary).duplicate(true)
if (shop as Dictionary).has("refresh_uses"):
    GameState.shop_refresh_uses_this_round = maxi(0, int((shop as Dictionary).get("refresh_uses", 0)))
```
