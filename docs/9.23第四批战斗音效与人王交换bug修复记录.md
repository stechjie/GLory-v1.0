## 二、接线：boss 技能音（用户口径 1）

> ⚠️ **本节（以及 §三）的连接方式已被
> `docs/9.23第五批boss技能音双通道订正记录.md` 整体推翻**，
> 保留在此只是为了记录当时的判断过程。
>
> 出错的地方**不是**「做不做归属门控」—— 那部分结论至今成立；
> 错的是**触发时刻**：
> * 7 只 boss 全挂在 `skill_ready` 上升沿上，其中 4 只压根没有这条边沿
>   （`overload_counter` / `soul_devour` / `blood_rage` / `twin_revive`
>   → **一次都不响**），镜像魔君是 `skill_ready = elapsed + 1.0`
>   → **每秒重响一次**（用户报的「一直播放」）；
> * §三 灭世裁决者那两处挂的 `apocalypse_due`
>   **不过回放边界**，真实 3v3（播回放）路径上是死代码 → 用户报的「音效未生效」。
>
> 现在：boss 技能音拆成**两条通道** ——
> `boss_cast_edge_cue_for()`（施法边沿，只剩圣愈祭司 / 天罚投星者两只）
> 与 `boss_event_action_for()`（真事件，其余 6 只）。
> 下面的 `BOSS_SKILL_CUES` 已退化为「7 只 boss 的素材全量表」，不再承担派发。

用户口径：**「boss 技能音效播放，我方队友都能听见。」**

`ui/services/SfxService.gd` 新增 15 个 cue 常量与 `CUES` 登记，并新增一张 `BOSS_SKILL_CUES`
（boss 单位 id → cue，7 条）：

```gdscript
const BOSS_SKILL_CUES := {
	"boss_mirror_lord": CUE_BOSS_MIRROR_LORD_SKILL,
	"boss_thunder_core": CUE_BOSS_THUNDER_CORE_SKILL,
	"boss_holy_priest": CUE_BOSS_HOLY_PRIEST_SKILL,
	"boss_soul_devourer": CUE_BOSS_SOUL_DEVOURER_SKILL,
	"boss_meteor_caster": CUE_BOSS_METEOR_CASTER_SKILL,
	"boss_blood_demon": CUE_BOSS_BLOOD_DEMON_SKILL,
	"boss_twin_gate": CUE_BOSS_TWIN_GATE_REVIVE,
}
```

`scenes/battle/BattleVfx.gd` 的 `_play_skill_cast_vfx()` 里加了一条**不做归属门控**的派发：

```gdscript
var boss_cue := SfxService.boss_skill_cue_for(uid)
if not boss_cue.is_empty():
	SfxService.play(boss_cue)
```

★ **为什么必须不做门控**：boss 在 3v3 里固定在场上、**不属于任何玩家的 `owner_slot`**，
把它塞进 `_is_own_or_ally_unit` 只会变成「永远不响」，而不是「更精确」。
探针用一个**缩进判据**钉死这一点（`boss_indent == 1`，即函数体层级）。

★ **「我方队友都能听见」是做到了的**，但要说清口径边界：局内战斗画面**所有玩家看的是同一场战斗演出**，
所以这条音不是「按玩家过滤」，而是「每个客户端都播」。真正按玩家区分的是**语音**，不是战斗音效。

**留空项**：狂战灾兽（`boss_rage_beast`）本轮**没有素材**，按用户口径**先留空、不播放**。
它**故意不进** `BOSS_SKILL_CUES` —— 探针里有一条 `boss_unexpected_cue_*` 断言会把「偷偷补了别的音」判红。
将来给素材时只要往这张表加一行。

## 三、接线：灭世裁决者三段（用户口径 2）

用户口径：**「蓄力时播蓄力音；蓄力被打断要同步停止播放；蓄力完成打出全场伤害再播完成音。」**

`BattleVfx.gd` 里挂三处（都在既有的 apocalypse 分支上，没有新事件类型）：

1. **蓄力开始**：`sid_now == "apocalypse_charge" and not prev_apocalypse and now_apocalypse` 的上升沿 →
   `SfxService.play(SfxService.CUE_BOSS_APOCALYPSE_CHARGE)`。用**上升沿**而不是「只要在蓄力就一直播」，
   否则会变成每秒重播一次。
2. **打断 / 完成共用出口**：`apocalypse_ended` 循环里，**先无条件**
   `SfxService.stop_cue(SfxService.CUE_BOSS_APOCALYPSE_CHARGE)`，**再**分「打断」「完成」两支。
   ★ 顺序是这个功能的全部难点：若把 stop 放到 `if 打断` 里面，那「完成」那一路就会
   **蓄力音与完成音叠着响**。探针专门断言 `stop_cue` 出现在两个分支**之前**。
3. **完成**：`apocalypse_complete` 支里 `SfxService.play(SfxService.CUE_BOSS_APOCALYPSE_IMPACT)`。

## 四、接线：普攻「技能触发」音（用户口径 3）

| 四星刺灵 | `defense_down_attack` | 破防那次普攻 |

| 四星巨甲灵 | `poison_reflect_armor_stack` | 反弹生效 |
| 四星魔童 | `curse_attack` | 减速那次普攻 |

### 4.1 新事件类型 `sfx_proc`（**只出声，不加特效**）

这些触发散落在 `scripts/battle/BattleSimulator.gd` 的三个不同函数里，而**播放**统一在
`BattleVfx.gd`。原来没有一条「纯音频事件」的通道 —— 若复用既有的 `unit_skill_proc`，
`_play_unit_procedural()` 会**给本来没有特效的棋子凭空加一层特效**。

所以新增一个视觉事件类型 `sfx_proc`：`BattleSimulator` 只往 `state["visual_events"]` 里补事件，
`BattleVfx` 收到后**只调 `SfxService.play()`**，不碰任何 procedural。

- `scripts/battle/BattlePresentationEvent.gd`：`KNOWN_TYPES` 加 `"sfx_proc"`，
  可见性登记 `VISIBILITY_IMPORTANT`（未知类型会产生 `push_warning` + `unknown_type:` 校验错，
  所以**必须登记**）。
- `BattleSimulator` 新增静态方法：

```gdscript
static func _emit_sfx_proc(state, skill_id: String, source: Dictionary, target: Dictionary) -> void:
	state["visual_events"].append({
		"type": "sfx_proc", "skill_id": skill_id,
		"source_uid": str(source.get("sim_uid", "")),
		"target_uid": str(target.get("sim_uid", "")),
		"time": float(state.get("elapsed", 0.0)),
	})
```

- 5 个调用点：`_perform_attack` 的 `balance_judge` 支、`_apply_attack_statuses` 的
  `curse_attack` / `poison_attack` / `defense_down_attack` 三支、
  `_apply_defender_reaction` 里巨甲灵那条（条件 `dealt > 0 and target.alive`）。
- `BattleVfx._play_visual_events()` 加 `elif ... == "sfx_proc": _maybe_play_sfx_proc(event)`，
  后者按 `_is_own_or_ally_unit` 门控后，四星走 `proc_skill_cue_for()`、佣兵走 `merc_proc_cue_for()`。

### 4.2 派发表

```gdscript
const MERC_PROC_SKILL_CUES := { "balance_judge": CUE_MERC_LIBRA_JUDGE_PROC }
```

`STAR4_PROC_SKILL_CUES` 扩了 4 条（`defense_down_attack` / `poison_attack` /
`curse_attack` / `poison_reflect_armor_stack`）。★ 审判剑士是**佣兵不是四星**，
所以它**不能**并进 `STAR4_PROC_SKILL_CUES`（佣兵升不到四星，并进去就是一条永远不响的音）——
探针里有一条 `poison_in_merc_table` 反向断言看着这一点。

### 4.3 `merc_gemini_assassin` 补进 `MERC_SKILL_CUES`

镜像刺客的技能音走的是 `MERC_SKILL_CUES` 而不是 `BOSS_SKILL_CUES`（它是佣兵）。
★ 这是本轮**探针抓出来的一个真漏洞**：一开始只登记了 boss 表，`merc_gemini_assassin`

## 五、接线：最终回合 PVP 开局音（用户口径 4）

用户口径：**「优化最终回合开始的号角音效，使其在播放完毕后，棋子再开始行动。」**

★ 这一条**本轮只换了素材、没有改代码** —— 时序机制 9.21 就已经建好了，而且正好是按本条口径建的。
说清楚它是怎么成立的，免得后人以为这里没做事：

- 播放入口：`scenes/battle/BattleUI.gd:186 _begin_final_round_intro()` → `SfxService.play(CUE_FINAL_ROUND_PVP_INTRO)`；
  调用点在 `BattleScreen._prepare_battle_models()` **末尾**（`BattleScreen.gd:371`），
  也就是「**模型全建完、战斗马上开打**」那一刻，而不是进场景那一刻。
- 「棋子再开始行动」由 `BattleUI.gd:248 _resolve_pending_battle_music()` 的 `await` 实现：
  它 `await get_tree().create_timer(SfxService.cue_length(cue)).timeout` 之后才起 PVP 战斗 BGM；
  而 `BattleScreen` 在 `175` / `294` 两处 `await _prepare_battle_models()` ——
  **这个 await 链就是「音播完 → 才继续往下走」**，所以后面的棋子行动自然被推后。
- ★ **等的是素材的真实长度，不是写死的秒数**（`SfxService.cue_length()`）—— 这正是本轮换素材
  **不需要动一行代码**的原因：换成更长/更短的号角，等待时长自动跟着变。
- 换素材的同时保留了「先停后响」（`_begin_final_round_intro()` 先 `MusicService.stop()` 再 `play()`），
  否则开局音头几毫秒会和备战 BGM 叠在一起。

## 六、接线：黄金重骑音量（用户口径 5）

用户口径：**「修复黄金重骑技能音效在 pvp 战斗 bgm 下播放不明显的问题。」→ 提高 6dB（约 2 倍响度）。**

`SfxService` 新增**按 cue 的音量覆盖表**，并在 `play()` 里叠加：

```gdscript
const CUE_VOLUME_DB := { CUE_MERC_TAURUS_CHARGE_SKILL: 6.0 }

func cue_volume_db(cue: String) -> float:
	return float(CUE_VOLUME_DB.get(cue, 0.0))
```

```gdscript
	voice.volume_db = volume_db + cue_volume_db(cue)   # 原来是 voice.volume_db = volume_db
```

★ 做成**表 + 函数**而不是「在调用点写 `play(cue, 6.0)`」的原因：调用点在 `BattleVfx`，
而"这只棋子这条音该多响"是**音频侧的知识**，放调用点会散掉；表放在 `SfxService` 里，
将来调另一只只加一行。`play(cue, volume_db)` 的第二个参数仍然保留（调用点级微调）。

★ 探针有一条**顺序断言** `volume_assign_order_wrong`：音量赋值必须排在 `voice.play()` **之前**，
否则这一声还是按旧音量走（赋值晚了只影响下一次播放）。变异测试专门验过这条。

## 七、bug 修复：「两个同星级人王在进行交换操作时，存在交换无效的问题」

> **本节经过一次订正。** 我第一版把现场写成「一只在场上、一只在待命区」，并据此把根因
> 归到人王的 `unique_on_board`。用户指出方向有误：**两只同星人王都在备战区**，互换位置
> 无效；而**不同星级**的能换。订正后的根因与星级边界见 7.2 / 7.3，订正说明见 7.6。

### 7.1 现场（用户口径）

> 「两个同星级的人王（叠加属性不同），他们在备战区，然后我进行操作他们两个互换位置，
> 却发现互换不了，而不同星级的却可以」

两个关键事实：**都在备战区**（不是一在场一在备战区）、**变量是星级**（不是所在区域）。

### 7.2 根因

`scenes/prep/PrepBoardController.gd` 的四个搬运 handler（`_move_or_merge_board` /
`_move_or_merge_board_to_bench` / `_move_or_merge_bench_to_board` / `_move_or_merge_bench`）
原来都是这个写法：

```gdscript
	elif PrepRules.can_merge_cells(to_cell, from_cell):
		if not _merge_copies_into_cell(to_cell, from_cell, ...):
			_board_hud._selected_board = -1
			_refresh_all()
			return          # ← 静默吞掉这次操作
```

`can_merge_cells()` 判的是「**同 id、同星、未满星**」——**两只同星人王满足它**。
但「满足 `can_merge_cells`」与「这一下合得成」是两件事：升星要几份看
`GameConstants.STAR_UPGRADE_COPIES = {1: 2, 2: 3}`，**2 星还得再凑第 3 份同名同星**。
两只人王互相交换时，能凑的份数只有这两份，**第 3 份凑不出来** →
`_merge_copies_into_cell()` 返回 `false` → 代码**直接 `return`**，
既不合成也不交换 → 玩家看到的就是「**交换无效**」。

用户报的正是 `_move_or_merge_bench`（备战区↔备战区）这条路。

### 7.3 星级边界：为什么偏偏是「2 星」暴露

`MAX_MERGE_STAR = 3`。三个档位在**旧写法**下的表现完全不同 —— 这正好解释用户那句
「不同星级的却可以」：

| 星级 | 升星需要份数 | 旧写法下的行为 | 玩家观感 |
|---|---|---|---|
| **1 星** | 2（`{1: 2}`，待合成这两份就够） | 真的**合成**，升为 2 星 | 不是「无效」，看不出这个 bug |
| **2 星** | 3（`{2: 3}`，缺第 3 份） | 静默 `return` | **交换无效** ← 用户报的 |
| **3 星** | —（`star < MAX_MERGE_STAR` 不成立 → `can_merge_cells` 为假） | 走 `else` 正常交换 | 本来就好 |

**为什么只有人王让人察觉**：人王的 `unique_on_board` 限的是**场上**（上限 1），
**备战区仍可放多只**，两只同星人王同时在备战区是常态；而每只的成长层数
（`king_growth_stacks`）各自独立，所以「换位置」是玩家真会做、且一眼能看出没生效的操作。
普通棋子同样中招，只是两只同星凑不出第三份时等价、换不换看不出来，故一直没被报上来。

### 7.4 改法

把「能合」与「合得成」并成一个条件，**合不成就落到下面的交换分支**：

```gdscript
	elif PrepRules.can_merge_cells(to_cell, from_cell) \
			and _merge_copies_into_cell(to_cell, from_cell, ...):
		_shadow_report_merge()
		GameState.board_slots[from_index] = null
	else:
		...  # 正常交换
```

★ **为什么 `and` 是安全的**：`_merge_copies_into_cell()` 在失败路径上**不改任何状态** ——
`_take_extra_merge_piece()` 只在真的取到时才清格子，找不到就返回空字典。所以不存在
「合了一半又去交换」。这条已写进代码注释，避免后人误以为有副作用。

★ 四处 handler 都要改（一个 handler 只覆盖一种拖动方向），漏一处就只修好一种操作。

### 7.5 变异证据（修复到底是不是修复了**这条路**）

### 7.6 订正说明：我第一版错在哪

第一版写的是「人王 `unique_on_board`，所以两只同星人王**必然**是一只在场上、一在待命区」。

## 八、过程事故：一个我自己造的解析期错误（重要）

批跑第一轮出 **12 PASS / 5 FAIL**，其中 `voice_check` 从既存红的 **8** 变成 **9**，
多出来的那条是 `voice_script_unloadable`：`res://scenes/battle/BattleScreen.gd` 加载失败。

顺继承链查下去：

```
BattleVfx.gd:461   Parse Error: Expected indented block after "elif" block.
  → BattleResult.gd    Could not resolve super class inheritance from BattleVfx.gd
    → BattleScreen.gd  Could not resolve super class inheritance from BattleResult.gd
```

**是我在第二节那次编辑造成的**：加 boss 派发时把 `elif _owned:` 的 merc 三行**整段抬出了缩进**，
于是 `elif _owned:` **只剩注释** —— GDScript 里「`elif` 没有语句体」是**解析期错误**。

### 三条教训

1. **★ 探针读源码文本的判据，看不见解析错误。**
   我本批为 BattleVfx 写的缩进 / `contains` 判据当时**全绿**，因为它们只是 `String.find`。
   → 已给 `audio_0922_check` 补一条 `vfx_merc_dispatch_dedented`（断言 merc 那条派发的缩进必须
   是 2 = 留在 `elif _owned:` 里），让这条文本探针至少能识别「被抬出去」这个形态。
2. **★★ 全量批跑里没有 `cold_parse_chain_check` 是本轮最大的过程漏洞。**
   这条门禁**本来就是有效的**（变异测试证明它能判红），只是我第一轮批跑的 19 条里**没有它**。
   → 已加进 `work/_qa_922/run_gates.py`（现 20 条），并在检查器源码里写了「凡改动
   `scenes/battle/**` 或任何被继承的脚本，这条必跑」。
   → 同时把它**加厚**：把战斗继承链 `BattleUI / BattleArena / BattleRenderer / BattleVfx /
   BattleResult` 每一层都单列成一个 target（原来只有 `BattleResult.gd`，坏了要靠上层**连带**才抓得到）；
   script 类判据从「`load()` 非 null」升级为 **`can_instantiate()`** ——
   实测一个解析失败的 GDScript，`load()` 照样返回非 null 对象（`is Script` 为真），
   只有 `can_instantiate()` 为 false、`get_script_method_list()` 为 0 条。
3. **★★ 变异脚本必须单次调用内自还原 + 二进制读写。**
   本批的 `mutate_swap_fix.py` / `mutate_audio_fix.py` 原是**两阶段**（`backup` / `restore`），
   我把不带参数的调用当成「只打印基线」跑了一次 → **变异留在工作树上**；再跑一次 `backup`
   把 `.mutbak` 覆盖成**变异后**的内容 → 备份也失效。
   又因为它们用**文本模式**读写，把全文件 CRLF 静默归一化成了 LF。
   → 两个脚本都重写成与 `mutate_cold_parse_922.py` 同一套纪律：
   单次调用跑完、`try/finally` 自还原、**二进制 I/O**、探针硬超时、启动自愈残留 `.mutbak`、
   还原后校验 sha256 并与基线复跑比对。
   → 事故的救回办法：从**另外 3 个未被变异的 handler 逐字节取** FIXED 片段 + sha256 验收
   （`work/_qa_922/restore_prep_swap_922.py`），**不手抄字符串**。
