## 一、用户给的两条硬约束

原话：

> 一、以上战斗音效都只有自身的棋子才会播放。
> 二、人王战斗结束未阵亡奖励属性，要满足两个条件才会播放：1、本次战斗自身人王未阵亡；
> 2、本次战斗自身人王可以触发技能，有属性加成，而不是已达到上限。

二次确认（问答）后补充的口径：

- 「四星」前缀**不是合成时刻**，而是**该棋子四星时释放技能 / 攻击**才播；
- 弓箭手 / 牧师 / 极光射手这类**攻击触发**的技能，在那一下真的触发时才播；
- 人王奖励音**不放战后结算面板**，要在**战斗结束那一刻**、在自身人王身上出一个
  **只有自己看得到**的闪光升级特效，并伴随该音效。

## 三、逐条接线

### 3.1 按「怎么触发」分三张表（`ui/services/SfxService.gd`）

`STAR4_SKILL_CUES` 原是「四星技能音」的唯一表，但它的调用点是 `skill_ready` 的**上升沿**——
只覆盖「施法型」技能。「第 N 次普攻触发」的三家**根本没有 skill_ready 边沿可挂**
（见 `BattleSimulator._step_team:636/640` 与 `_perform_attack:697`）。所以拆成三张表：

| 表 | cue | 派发入口 | 门控 |
|---|---|---|---|
| `STAR4_SKILL_CUES`（扩了 4 家） | 剑士 / 法师 / 神侍 / 天使 | `star4_cue_for(uid, true)` | 自身 **且** 四星 |
| `STAR4_ATTACK_SKILL_CUES`（新增） | 弓箭手 / 牧师 / 极光射手 | `attack_skill_cue_for(uid)` | 自身 **且** 四星 **且** 这次真触发 |
| `MERC_SKILL_CUES`（新增） | 星轨猎人 / 泡沫术士 / 圣愈修女 | `merc_skill_cue_for(uid)` | 只判自身 |

**为什么佣兵必须单独成表**：佣兵**升不到四星**（`EconomyLedger._use_upgrade_stone` 会拒），
把它们并进 `STAR4_SKILL_CUES` 就等于要求调用方再叠一个永远为假的 `star == 4`，
结果是一条永远不响的音。

新增 9 条 cue 常量 + 9 条 `CUES` 登记，`EXPECTED_CUE_COUNT` **37 → 46**。

### 3.2 「自身棋子（不含队友）」怎么判

沿用 9.18 那套：`BattleVfx._is_local_owned_unit(sim_uid)` —— 判据是
`owner_slot == NetworkService.team_local_slot`（非组队时退化成
`team == "player" and owner <= 0`）。队友是**别的 owner_slot**，所以天然被排除，
不需要额外写「排除队友」；敌方更不用说。

### 3.3 「四星 **且** 这次真的触发」

- **施法型**：`_play_skill_cast_vfx` 本来就在 `skill_ready` 上升沿调用，
  原有的 `_is_local_owned_unit() and _is_star4()` 门控直接复用（人王 / 神王 / 母灵 / 黑龙 /
  大天使 / 末日守卫六家早就在这条路上），四家新棋子只是往表里加了映射。
- **攻击型**：挂在 `_play_attack_unit_procedural` 里、`_attack_skill_vfx_ready()` **通过之后**。
  那一步判的就是 `attack_count % every == 0`，所以「走进来」本身就等于「这一次真的触发了」。
- **佣兵**：`_play_skill_cast_vfx` 里新加一条 `elif _owned:` 分支，只判自身。

### 3.4 人王「战斗结束未阵亡 · 奖励属性」

`BattleVfx._play_human_king_reward()`，由两条收尾路径调用：

- 本地模拟：`BattleResult._emit_finished()`
- replay / 组队：`BattleScreen._finish_replay()`

两条都在 `_return_emitted` 之后、**水晶演出之前**调用，`_play_human_king_reward` 里再用
`_human_king_reward_played` 二次去重（每局一次，`BattleScreen._start_replay()` 清空）。

**为什么必须在水晶演出之前**：赢的那一方棋子会被 `_vanish_crystal_attacker()` 逐个淡出并
`queue_free()` —— 挂在水晶演出之后就**没有人王可以闪光了**。

三个条件全部满足才响（缺一不可）：

| 条件 | 判据 | 对应 `Main` 侧的同源逻辑 |
|---|---|---|
| 自身人王 | `_is_local_owned_unit(uid)` | `result.player_survivor_slots` |
| 本场未阵亡 | `_state` 里该 uid `alive == true` | 同上 |
| 还有成长空间 | `king_growth_stacks < max_stacks` | `Main._grow_human_king` 的 `cap` 判定 |

**上限一律经 `UnitFactory.apply_star_stats(d, star)` 取**，与 `Main._grow_human_king` 同一条路：
`max_stacks` 在 `star4` 里被覆写（★1~3 = 5 层 / ★4 = 8 层），而 `cell.def` 是**未做星级缩放的
原始表项** —— 直接读它会把 4 星的上限读成 5 层，于是人王明明已经封顶了还在响奖励音。

**闪光特效**：3D 程序化 `GROWTH_AURA`（绿色光环 + 上升粒子，就是「成长」那条特效）
叠一层同 id 的 2D 光环，落在**人王本体**的 `world_foot` / `foot_pos` 上，
不是队伍中心 —— 用户要的是「在自身人王身上」。

## 四、顺手修的既有缺陷（本轮发现）

### 4.1 cue 路径漏了 `attack_count` / `skill_every`（D6 迁移遗留）

`_attack_skill_vfx_ready()` 用 `attack.get("attack_count")` 与 `attack.get("skill_every")`
判断「这次普攻是不是技能触发那一击」。D6 把老的 snapshot-diff 路径换成 cue 路径时，
`cue_play_basic_attack()` 拼的 `attack` 字典**漏了这两个字段**，
于是每次调用都读到缺省值（`attack_count = 0`、`every = 4`）→ `0 % 4 == 0` → **恒为真**。

后果是弓箭手 / 牧师的技能演出**每一次普攻都在放**，而不是「每第 N 次」。
（`_collect_vfx_units` 一直在写这两个字段，只是没人读 —— 属于「数据有、消费方漏读」。）

修法：在 `cue_play_basic_attack()` 里从快照取回这两个字段。
`every` 只在 > 0 时才写进字典，否则让 `_attack_skill_vfx_ready()` 走它原本的缺省，
1~3 星与非该类技能的行为与改动前逐字一致。

> **不修它就没法接音效**：四星弓箭手是「每 3 击」（★1~3 是每 4 击），
> 这个数字只有快照里的 `def.every` 知道。

### 4.2 门禁 `indirect_cue_entry_unused` 的 `contains()` 能被前缀骗过

`audio_sfx_check._check_every_cue_has_call_site()` 用
`corpus.contains("SfxService." + entry)` 检查派发入口有没有生产调用点。
变异测试实测：把调用改名成 `attack_skill_cue_for_MUTATED` 时，
**不带 `(` 的 `contains()` 依然命中**（那是它的前缀），门禁照旧全绿。

已收紧为 `corpus.contains("SfxService." + entry + "(")`（要求的是**真调用**，不是「出现过这个名字」），
并把这行变异写进注释。收紧后同样的变异正确变红。

## 五、bug 文档第 1 条：剑士技能未显示冷却时间

原文：

> 1、剑士技能未显示冷却时间，在「盾击」后面增加冷却时间描述，「盾击（冷却5.0秒）：」

**根因**：`BattleSimulator._tick_skills` 里剑士的技能是

```gdscript
"front_cone_stun":
    BattleSimSkills._skill_front_cone_stun(caster, opponents, d, state)
    caster.skill_ready = float(state.elapsed) + float(d.get("skill_cd", 5.0))   # ← 缺省 5.0
```

但 `data/units/race_units.json` 里 `human_swordsman` **根本不带 `skill_cd` 字段**，
而 `UnitDetailFormat.skill_cd_text()` 只在 `d.has("skill_cd")` 时才吐「（冷却X秒）」
→ 文案少了一整句。原来的 `black_hole` 是同一个问题的特例（硬编码了一句 8.0 秒）。

**修法**：把「数据不带、但实现确实有冷却」的技能登记成一张表，数值与模拟器缺省值同源：

```gdscript
const IMPLICIT_SKILL_CD := {
    "black_hole": 8.0,
    "front_cone_stun": 5.0,
}
```

`black_hole` 从硬编码分支改为走这张表，输出与改动前**逐字相同**；
`front_cone_stun` 现在渲染成：

```text
盾击（冷却5.0秒）：攻击最近敌人，造成自身攻击150%伤害并眩晕1.0秒。   （★1）
盾击（冷却5.0秒）：攻击最近敌人，造成自身攻击300%伤害并眩晕2.0秒。   （★4）
```

中英文两支都跟着走（英文是 `Shield Bash (CD 5.0s): ...`）。

### 6.1 行为级探针 `work/_qa_919/probe_battle_sfx_919.tscn`（**34 项，全过**）

headless 下不 instantiate 重型 3D 场景，只 `preload` 目标脚本、`BattleVfx.new()`（**不进树** ——

- 剑士文案 5 项：★1、★4 均以「盾击（冷却5.0秒）：」开头，且 `black_hole`、
  带 `skill_cd` 的、无冷却的三条既有分支未被改坏。

**探针自身踩到的三个坑（都记在脚本注释里）**：

1. `_play_skill_cast_vfx` 第 4 个参数是 `Array[Dictionary]`，传 `[]` 会报
   「does not have the same element type」而**整条调用被拒** —— 断言于是静默地什么都没验。
   必须传类型化空数组。
2. `SfxService` 的 **40ms `RETRIGGER_GUARD_MSEC`**：神侍与天使共用同一条 cue，
   同一帧连调两次第二次必然被挡掉。凡是「同一条 cue 响 N 次」的断言，两次之间必须
   `reset_counters_for_check()` 或间隔 > 40ms。
3. 「每场只响一次」这类断言必须先清掉上一用例留下的每场一次标记，
   否则用例①置的 `true` 会让用例⑥静默拿到 0。
4. 脚本**解析期**报错时场景里的 Node 拿不到脚本 → `quit()` 永不执行 → 进程不报错也不退出，
   表现为「挂死」（实测 5 分钟无输出）。所谓「重型场景不能 instantiate」的观感里，
   至少有一次其实只是解析错误。

## 八、追加：人王奖励属性的**金光特效** + 离线自测入口（同日补做）

用户追问：「之前说的给人王增加一个增加属性时的金光特效，加上了吗」→ 答案是**没有**：
§三 那版复用的 `GROWTH_AURA` 是 **绿色**（`ProceduralVFXEffect.gd:40` 写死
`Color(0.45,1.0,0.45)`），而且**它那一层 3D 调用根本是死的**（见下）。用户拍板改成金色。

### 8.1 先修一个真 bug：原来的 3D 那层是「静默无表现」

原来写的是：

```gdscript
_play_unit_procedural("GROWTH_AURA", king.get("world_foot"), king.get("world_head"), ...)
_spawn_vfx("GROWTH_AURA", king.get("foot_pos", Vector2.ZERO))
```

`_play_unit_procedural()` → `_play_boss_procedural()` → `BossProceduralVFX3D.play()`，
那是**3D 技能入口**，只认 `UNIT_SKILLS` 里的技能 id，其余全部落到
`BossSkillVFXComposer3D.play_skill()` 的默认分支 —— 而 composer 里**没有** GROWTH_AURA
（或任何 2D 特效 id）的分支，所以**什么都不做**。

> 判据：`grep -n "GROWTH" effects/vfx3d/boss/BossSkillVFXComposer3D.gd` → 0 处；
> 其余所有 `_play_unit_procedural()` 调用点传的都是**技能 id**，只有这一处传了 2D 特效 id。
> 也就是说：**当时真正能看见的只有 2D 那一层**，我原先写的「3D + 2D 叠着放」是错的。

处理：**删掉那行 3D 调用**（留着只是误导），金光做成一条**专用 2D 特效**。
要在 3D 侧也加金光，得先在 `BossSkillVFXComposer3D` 里加分支（本轮没做，已告知用户）。

### 8.2 新增专用特效 `HUMAN_KING_REWARD`（金色）

| 文件 | 改动 |
|---|---|
| `effects/ProceduralVFXEffect.gd` | 新增 `HUMAN_KING_REWARD` 分支 |
| `effects/scenes/human_king_reward.tscn` | **新增**（与 `growth_aura.tscn` 同构，`effect_id = "HUMAN_KING_REWARD"`） |
| `effects/EffectDatabase.gd` | 登记进 `EFFECT_SCENES` |
| `scenes/battle/BattleVfx.gd` | `_play_human_king_reward()` 改调新特效；删掉死掉的 3D 调用 |

四层叠起来读作「就地升级」（金色扩散环 + 地面金色光晕 + 金色迸发 + 上升金粒子）：

```gdscript
_play_ring(Color(1.0, 0.85, 0.32, 0.95), 26.0, 92.0, 0.8, 6.0)   # 金色扩散环
_play_disc(Color(1.0, 0.84, 0.34, 0.22), 64.0, 0.8)              # 地面金色光晕
_play_burst(Color(1.0, 0.88, 0.42), 26, 1.0)                     # 金色迸发
_play_rise_particles(Color(1.0, 0.90, 0.52), 20)                 # 上升金粒子
```

★ **两条硬约束（都是踩出来的）**：

1. **不能调 `_play_hit()`**：它内部 `_free_after(0.42)` 会把整条特效砍到 0.42 秒就收掉。
2. **`_free_after` 在一次 `play()` 里只有「最先到期」的那次生效** —— 后到的那次比较
   `_generation` 已经变了、直接 `return`；`_release_self()` 也只在第一次跑。
   所以整条特效的寿命 = 这里**最短**的那次调用，即 burst 的 **0.85s**
   （这也是为什么黄金版比 `GROWTH_AURA` 的 0.67s 略长）。
3. 同名的池化子节点**只有一份**：`Ring` / `Disc` / `Flash` 各一个，**同一个 play() 里
   不能调两次 `_play_ring()`**（第二次会把第一次的 tween 和目标一起盖掉）。
   可共存的组合上限就是 Disc + Ring + Flash + BurstParticles + RiseParticles。

## 九、追加 2：离线自测「人王属性 +1（战后胜利）」点了没反应 —— 修掉

**用户反馈**（附截图）：离线自测里点那个按钮，**既没有属性加成、也没有金光特效**。

### 9.1 根因一：两道门读的是**两份不同的数据**

`BattleVfx._play_human_king_reward()` 上挂了两道门，它们读的**不是同一份状态**：

| 门 | 读什么 | 谁写的 |
|---|---|---|
| `_local_living_human_king()`（自身 + 存活） | **战斗模拟态 `_state`** | `OfficeTestSim.build_test_state()` |
| `_human_king_can_grow()`（没到上限） | **`GameState.board_slots`** | 按钮自己临时塞 |

第一版的 `_fire_human_king_reward()` **只改了 `board_slots`**，`_state` 一动没动 →
`_local_living_human_king()` 在模拟态里根本找不到人王 → 直接 `return`，**一声不响**。

### 9.2 根因二：人王摆在哪一路

离线自测把「自身」钉死在 **红 A（slot 0）**（`_is_local_owned_unit()` 覆写要求
`owner_slot == 0`），红队 1/2 号位按口径是**队友位**。诊断探针
（`work/_qa_920/probe_king_row_diag`）逐座位实测：

```text
slot 0 → local_king=YES    slot 1 → ---    slot 2 → ---    (3/4/5 无我方单位)
```

→ 人王摆在红队 1/2 号位时，正式逻辑**按口径就不该触发**；但界面上
`_find_own_human_king()` 接受红队 0~2，于是「标签显示人王在位、点按钮毫无反应」——
**两条判据不一致，且失败完全静默**。

### 9.3 修法

1. `_fire_human_king_reward()` 现在**同时**临时改写两处：`GameState.board_slots`
   **和** `_state`（`_state_with_king_as_self()` 把那枚人王的 `owner_slot` 临时改成自身位），
   跑正式逻辑，跑完**两处都还原** → 人王摆红队哪一路都能验收；
   标签会写明「（队友位槽N · 自测临时按自身处理）」。
2. **不再静默**：跑完回头看 `_human_king_reward_played`，没触发就把**是哪道门没过**
   打到状态栏（找不到存活人王 / 已到上限 / 未知）。
3. **属性加成做成真的**：层数不再只记在屏幕上，而是写进摆放字典
   （`OfficeTestSim.set_king_growth`），`def_for_placement()` 按正式口径
   （`Main._grow_human_king` 的 `mul = 1 + post_battle_all_stat_growth`，**只乘 hp/atk/def**）
   重放 → 属性面板 / 长按详情看到的是**加成后**的数值。
   ★ 倍率与上限都要经 `UnitFactory.apply_star_stats()`（读原始 `def` 会把 ★4 倍率读成 ★1~3 的）。
   改星 / 重摆会经 `set_placement` 重建字典 → 层数归零（两档上限不同，有意为之）。
