## §1 举报弹窗：按钮边框画反了

**现象（截图 image1）**：未选中的按钮**带**边框；选中的（「外挂/作弊」）**没有**边框。
用户要求：未选中无边框、选中带外边框，**保持原有布局、文字、配色不变**。

**根因**：不是「少画了边框」，是**边框色与底色几乎一样**。
选中态的样式盒来自 `GloryTokens.button_box(SURFACE_RAISED, ...)`，
其中 `pressed` 态的边框色是 `SURFACE_RAISED = (0.105, 0.121, 0.161)`，
而弹窗底色是 `SURFACE = (0.071, 0.082, 0.110)` —— 两者差值只有 ~0.03，
在深色背景上肉眼判为「无边框」。所以「选中看起来没边框」是**配色问题**，
不是绘制缺失。

**做法**：在 `ReportDialog._ready()` 的按钮循环里显式覆写三态样式盒，并新增
一个 `static _selected_box()`：

```gdscript
button.add_theme_stylebox_override("normal", Tokens.button_box(Tokens.BORDER, Tokens.BORDER, false))
button.add_theme_stylebox_override("hover", Tokens.button_box(Tokens.CYAN, Tokens.CYAN, false))
button.add_theme_stylebox_override("pressed", _selected_box())

static func _selected_box() -> StyleBoxFlat:
	var box := Tokens.button_box(Tokens.SURFACE_RAISED, Tokens.CYAN_HOVER, false)
	box.set_border_width_all(Tokens.BORDER_WIDTH * 2)
	return box
```

★ 选中态**同时**把边框换成高饱和的 `CYAN_HOVER` **并**加粗到 2× —— 只改色不改宽，
在这种低对比底色上仍然读不出来（这正是原 bug 的形态）。`_pick()` 用
`set_pressed_no_signal` 写状态，未被改动，布局/文字/配色原样保留。

## §2 已过时的邀请：按钮变灰不可点

**现象（截图 image3）**：点「立即参与」才弹「邀请已过时」。
用户要求：按钮**直接**变成不亮的「已过时」，玩家点不动。

**做法**：把失效判定从「点击时判」**前移到渲染时**。`ChatScreen._render_messages`
末尾调 `_refresh_invite_states()`：

- 仅当当前会话里含「**别人发来的**、`room_id > 0` 的邀请」时才去拉一次好友列表，
  写进 `_invite_peer_room` 缓存后**重画**（一次异步 prefetch + 缓存，不是每条消息各拉一次）；
- `_invite_bubble` 读 `_invite_expired(msg)`，失效则 `disabled = true`
  + GHOST 变体 + 文案 `RoomInvite.expired_text()`；未失效才 PRIMARY + 「立即参与」；
- `_on_invite_join` 仍保留实时复查（`await _inviter_state_now(...)` 刷新缓存后再判），
  失效则 toast + 重画 —— **两道**：渲染时就不让他点，真点了也不会误进。

★ 判定用的 `RoomInvite.is_expired(...)` 签名（5 参）本轮**没改**，
改的只是「什么时候问它」。

## §3 开局后先前发出的邀请失效（第 3 条）

**现象（截图 image5）**：邀请朋友但对方没进房就开了局，被邀请人点「立即参与」
提示**「连接中」**（而不是「邀请已过时」）—— 因为加入流程走到服务端才被拒，
客户端此前只把「连接中」当占位。

**用户选型**：在**后端加 `started` 标志**（而不是让客户端猜）。

**为何要加标志**：`player_presence` 原来只报 `room_id`，「这个房间的**对局**开没开」
不可得。上一轮（9.27）留了 `is_expired` 的 `room_started` 形参，但拿不到数据，
只能靠加入流程兜底 —— 正是本条 bug。

**数据源边界（照既有 presence 口径）**：客户端**经 HTTPS 自报**。
`AccountManager` 新增第二个 provider `_room_started_provider`，
`Main._room_started_now()` 判定规则：

- `team_room_id <= 0` → `false`；
- `server_phase` 非空 → `!= ROOM_LOBBY`（即 prep / battle / result 都算已开始）；
- `server_phase` 为空 → 退回 `team_round_active`。

`presence.heartbeat(player_id, room_id, room_started=False)` 落库，边界是
**「说谎没有收益」**（跟 `room_visibility` 同一条）—— 谎报「没开」只是让自己
的邀请看起来还能点，点了照样被服务端拒。**没有**把它做成服务端权威计算。

**迁移**：`database/022_presence_room_started.sql`，加列带默认值 `false`，按
`database/README.md` 代价表属 🟢。

**跨端逐段结构断言**（`room_invite_check`）：客户端**传了** ≠ 后端**读了**。
本条的管道有四段，每段都钉了结构断言：
`AccountManager` 组 `room_started` → `routes/presence.py` 的 `HeartbeatBody` 有字段
→ `presence.heartbeat` 写进 upsert → `routes/friends.py` 的 `FriendItem` 带出去。

★ 上一轮 9.27 的教训「客户端传了 kind、后端根本没读」，本条**主动防了**：
四段全判。

**客户端渲染**：`ChatScreen._inviter_state_now(code)` 返回
`{"room_id", "started"}`，`RoomInvite.is_expired` 拿 `started = true` → 失效。

## §4 新消息音效的场景门控

**现象（截图 image7）**：房间（3v3 大厅）里收到新信息**没有**音效，
返回大厅后才响。用户口径：**「大厅、房间收到信息会即时响，对局收到不响」**。

**做法**：不把「当前在哪个界面」硬编码进 `ChatService`（那会让它反向依赖场景树），
改成**由 `Main` 推一个显式标志**：`ChatService.in_match`。

- `ChatService._on_dm_push` 里音效 `if not in_match: SfxService.play(CUE_CHAT_ALERT)`；
  **红点始终亮**（刷新路径 `refresh_unread` / `apply_chat_list` 一律不播音效 ——
  这就满足「对局结束回大厅只显示红点不播音效」）；
- `Main._set_chat_sound_suppressed(true)` 在 `_show_prep` / `_show_battle` /
  `_show_game_over` / `_show_selftest` / `_begin_resume_replay` 各处调用；
- **3v3 大厅 `_show_team3v3_lobby` 故意不调** —— 用户口径里「房间」要响；
- `Main._clear()` 里复位 `in_match = false`。

★ 注释里写明 `in_match` 的语义是「**不含房间 / 3v3 大厅**」，避免以后有人
看到 `in_match` 就当「在对局上下文里」而误加一处抑制点。

## §5 邀请 10 秒冷却：改为「仅换房计时」

**现象（截图 image8）**：邀请一个朋友后，再邀**第二个**朋友提示「10 秒后才能再次邀请」。

**用户选型（原话）**：**「A方案，只有换房时，邀请同一个人，才会计冷却。」**

**口径变更**：旧实现是**按发送者计时** —— 只要 10 秒内发过邀请（不论邀谁）就拦。
新口径是**仅当 `room_id` 变化时才计时**：

```gdscript
# RoomInvite.send_blocked_reason（3 参 → 5 参）
if same_room_already_sent:
    return "duplicate"
if last_sent_sec > 0 and last_sent_room_id > 0 and last_sent_room_id != current_room_id \
        and now_sec - last_sent_sec < RATE_LIMIT_SEC:
    return "rate_limited"
return ""
```

- 客户端 `Team3v3Lobby` 新增 `_invite_last_room_id`，成功后与 `_invite_last_sec` 一起记；
- 后端 `_check_invite_rules` 的 (b) 分支改为扫最近一条邀请时**同时取
  `payload ->> 'room_id' as room_id`**，仅 `last_room_id != room_id` 时才比 10 秒；
  新增模块级辅助 `_room_id_of_payload(raw)`（`None`/非数字 → 0）。

★ 两端**都**改：只改客户端等于「换个客户端就能绕过」，只改后端等于「老客户端仍被拦」。

**判据**：`room_invite_check` 的 `_behavior_rate_limit()` 全部改到新 5 参签名，
并新增两条**同房放行**断言（`allow_same_room_1s` / `allow_same_room_same_sec`）——
旧实现在这两条上必红，正是这条 bug 的回归闸。

## §7 顺手修的一条门禁假红（`ui_component_check`）

**症状**：`ui_component_check` FAIL 2 条 `feedback_row_state_is_colour_only`
（`ui_sound` / `haptics` 文案开与关完全相同）。**与本批 5 条 bug 无关** ——
`git stash` 到 HEAD 复跑是 **PASS**。

**根因（实测，不是推测）**：`SettingsScreen._on_locale_changed()` 现在是
**整页重建**（`_build()`），而 `LocaleManager.set_locale()` 会 emit `locale_changed`。
门禁在该函数里第 559 行无条件切了一次 locale（为了验「语言选中标记跟着变」），
这一刀把整页重建了 —— `_presentation_btns` 里被换成**一批全新的 CheckButton**，
旧节点已 `remove_child` 离树。

而门禁在循环开头就把按钮引用攥在手里（`row_btn`），之后一直用它读 `text`：
读到的**是已经离树的旧节点**，它的文案永远停在重建那一刻 —— 于是
`row_on == row_off` 恒成立，**对完好的实现报假红**。

**修法**：

1. 新增 `_row_btn_now(screen, row_key)`，**每次**要读按钮都从 `_presentation_btns` 现取，
   绝不跨 `set_locale()` 缓存引用；
2. 收尾的 locale 还原从 `if marked_before: set_locale("zh")` 改成**无条件还原**
   （原来的写法在「开局不是中文」时不还原，把 locale 留在切换后的那一半，
   污染同进程后续检查）。

★ 教训归到本仓既有的那条：**判据要指着能坏的那一处**。
坏的是「切换后文案没跟上」，不是「这个节点对象」——
所以每步都得现取，而不是把节点当坐标系。
