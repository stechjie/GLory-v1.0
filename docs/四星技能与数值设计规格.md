# GLORY 四星技能与数值设计规格

> 文档状态：数值方案，待实现  
> 编写日期：2026-09-08

本文只管**棋子本身**：3★ → 4★ 具体改什么、改多少，以及配套的代码改动。
**4★ 的获取途径（升级石怎么来）不在本文范围**，另行确定。

> 表格中「仓库现值」直接读自 `data/units/race_units.json` 与战斗代码，非人工转录。  
> 🔒 = 触发了某项封顶　⭐ = 特例　⚠ = 与初稿有实质分歧　❌ = 初稿有误

---

## 1. 总则

| 项 | 规则 |
|---|---|
| 升级条件 | 消耗一颗对应属性（天 / 地 / 人）的升级石，把 3★ 升为 4★。**不能靠合成获得**（见 5.1） |
| *（升级石从哪来）* | *不在本文范围，另行确定* |
| 参与单位 | **32 只全部参与** |
| 属性系数 | 4★ = 3★ × **1.15** → 绝对系数 **3.45** |
| 属性系数·特例 | **小灵 = 3★ × 1.50 → 绝对系数 4.50**。它是全表唯一没有技能的单位，用属性补 |
| 系数作用范围 | **仅 HP / 攻击 / 防御三项**，不含攻速、暴击、射程、移速 |
| 与技能百分比的关系 | **互不影响**。技能里的百分比读技能自己的字段，不走星级系数 |
| 出售返还 | `售价 × 3`（= 3★ 返还的 2 倍）。见 5.5 |

**为什么攻速不含在内**：攻速直接乘 DPS。若攻速也 ×1.15，实际战力增幅是 `1.15(攻) × 1.15(攻速) × 1.15(血) ≈ 1.52×`，而不是预期的 1.15×，所有伤害型 4★ 会悄悄超出设定力度。

## 2. 配平口径

总口径：**基准 ×4，按技能类型设封顶**。

| 类型 | 规则 | 理由 |
|---|---|---|
| 伤害倍率 `damage_atk_pct` | **×2 封顶** | 已随 atk 吃过星级放大，×4 = 单体一击清场 |
| 治疗 / 护盾（% 最大生命） | **40% 封顶** | 超过就等于永不死 |
| 减伤 | **65% 封顶** | 50% 减伤已是有效血量 ×2 |
| 增益 / 减益光环（攻 · 防 ±%） | **×4 吃满** | 基数只有 8~15%，×4 后仍只是 +32% |
| 攻速加成 | **45% 封顶** | 攻速直接乘 DPS，等于再乘一次 |
| 控制时长 | **×2 且 ≤ 3 秒** | 控制价值非线性，>3 秒 = 点名删除 |
| 概率（闪避 · 触发） | **≤ 50%** | 接近 100% 战斗就没有变数了 |
| 减防总量（每层 × 层数） | **≤ 100%** | 不能打出负防御 |
| 冷却 | **缩短 25~35%** | 最通用的强化，且不改变技能手感 |
| 绝对值（+3 防 / +30 血 / −5 防） | **一律改成百分比** | 绝对值不随星级缩放，4★ 与 1★ 效果相同 |

按此配完，31 只的有效战力增幅落在 **1.8× ~ 2.6×** 区间（对照：2★→3★ 是属性 ×2）。

## 5. 代码改动清单

### 5.1 ⚠️ 最关键的一条：星级上限和合成上限必须拆开

现在这两件事共用同一个常量 `GameConstants.MAX_STAR = 3`：

| 位置 | 用途 |
|---|---|
| `scenes/prep/PrepRules.gd:59` | `can_merge_cells` 判定 `star < MAX_UNIT_STAR` 才能合 |
| `scripts/multiplayer/EconomyLedger.gd:202` | 服务端合成封顶 `if star >= MAX_STAR` |
| `scripts/units/UnitFactory.gd:10` | `out.star = clampi(star, 1, 3)` |

**如果只把 `MAX_STAR` 改成 4，就会同时开放「3 个 3★ 合成 4★」，完全绕过升级石。**

而且 `GameConstants.copies_to_upgrade(star)` 读的是 `STAR_UPGRADE_COPIES.get(star, 3)`，表里只有 `{1:2, 2:3}`，`star=3` 会走**默认值 3** —— 也就是说这条路径已经现成可用，改完常量当天就会被玩家发现。

**必须拆成两个常量：**

```gdscript
const MAX_STAR := 4        # 星级上限（4★ 存在）
const MAX_MERGE_STAR := 3  # 合成上限（合成最高只到 3★）
```

然后 `PrepRules.can_merge_cells` 和 `EconomyLedger._merge()` 都改读 `MAX_MERGE_STAR`，`UnitFactory` 的 clamp 改读 `MAX_STAR`。

### 5.2 毒伤：参数化 + 可见性（决策 2 / 7）

**先确认一件事：毒伤本来就在生效**，一直在扣血、也能毒死人。看起来「没效果」是因为它对玩家完全不可见，共四层：

| # | 现象 | 位置 |
|---|---|---|
| 1 | 不飘伤害数字（有意为之，注释写着 DoT ticks stay silent） | `DamageService.gd:39-43` |
| 2 | **毒灵的输出统计恒为 0** | `_record_damage` 只在 `_stat_source_uid` 非空时记 `damage_dealt`，而 `_tick_statuses` 每个 fighter 前都 `clear_stat_context()` |
| 3 | 毒杀不给击杀金 | 同上，`killer_uid` 是空串（`docs/金币系统.md` 已记为已知缺口） |
| 4 | `StatusEffectService.tick()` 返回的 `damages` 数组被丢弃 | `BattleSimulator.gd:648` 是全项目唯一调用点 |

实际伤害量并不小：毒灵攻速 1.0，对 900 血目标每跳 27（死灵羁绊 ≥4 翻倍 → 54），一场 30 秒约 30 跳 = **810 伤害**；而它自己 atk=33，30 次普攻是 990。**接近一半的输出是隐形的。**

#### (a) 参数化

`scripts/battle/BattleSimulator.gd:728` 现在是写死的字面量，不读 `def`：

```gdscript
// 现在
elif sid == "poison_attack":
	StatusEffectService.add_poison(target, 4.0 * duration_bonus, 0.03, SynergyService.safe_factor(syn, "undead_poison_bonus"))

// 改成（同时传入施加者 uid，供 (b) 使用）
elif sid == "poison_attack":
	StatusEffectService.add_poison(target,
		float(d.get("poison_duration", 4.0)) * duration_bonus,
		float(d.get("poison_pct_max_hp", 0.03)),
		SynergyService.safe_factor(syn, "undead_poison_bonus"),
		str(attacker.get("uid", "")))
```

对照：同一个函数里 `curse_attack` 读 `d.get("duration", 4.0)`、`defense_down_attack` 读 `d.get("def_down_pct", 0.10)`，**只有 `poison_attack` 是写死的**。
不改这行，毒灵 1★ 到 4★ 完全一样，而且毒灵和飞灵共用 `poison_attack`，永远同值。

#### (b) 可见性 —— 方案 A

1. `add_poison` 增加 `source_uid` 参数，存进 status 的 params
2. `StatusEffectService.tick()` 里跳伤前后设置 / 清除 stat context：

```gdscript
if key == "poison":
	...
	DamageService.set_stat_source_uid(str(s.get("source_uid", "")))
	DamageService.apply_damage(fighter, dmg, true)
	DamageService.clear_stat_context()
```

3. `DamageService._maybe_emit_hit_number` 放行 DoT：`var show := _hit_kind in ["skill", "basic", "dot"]`，跳伤前 `set_hit_context("dot")`，飘绿字

> ⚠️ **A 会自动把「毒杀给击杀金」也做了。** `apply_damage` 里 `target["killer_uid"] = _stat_source_uid` 与伤害统计读的是**同一个变量**——要让毒伤计进毒灵的输出，就必须设置 stat context；一旦设置，`killer_uid` 就有值，`_process_pending_kill_rewards` 会给毒杀结算击杀金。
> 两者拆不开，除非专门加一个「只记伤害不记击杀」的旗标（不建议）。
> **影响量级**：PVE 小怪单价固定 15 金，毒流阵容约 20~30% 的击杀来自毒跳，全程约 **+300~500 金**（对约 4500 的总收入是 8%）。这条本来就是 `docs/金币系统.md` 里登记的缺口，顺手补上方向是对的。

**两个现成的放大器**（配数值时要一起算）：
- 死灵羁绊 ≥4 → `undead_poison_bonus = 1.0`，**毒伤直接翻倍**（`SynergyService.gd:28`）。4★ 毒灵在满死灵阵里是 12%/秒目标最大生命，任何单位约 8 秒毒死
- 对 Boss：`_boss_reduced_params` 把中毒的数值参数 ×0.5

### 5.3 毒的跳伤不吃攻速（决策 8）

**现状与 UI 文案不符。** 文案写「每秒造成目标最大生命 3% 伤害」（`UnitDetailFormat.gd:167`），实际是**每次普攻跳一次**——
因为 `add_status` 刷新 DoT 时把 `tick_left` 归零，下一个 sim 帧（0.1 秒后）立刻跳。

```gdscript
// 现在（scripts/battle/StatusEffectService.gd:25）：每次普攻把计时器归零 → 跳伤频率跟着攻速走
next["tick_left"] = minf(float(existing.get("tick_left", 0.0)), float(next.get("tick_left", 0.0))) if existing.has("tick_left") else 0.0

// 改成：刷新只延长持续时间，跳伤计时器照常走 → 严格 1 跳/秒
next["tick_left"] = float(existing.get("tick_left", 0.0)) if existing.has("tick_left") else 0.0
```

首次施加时 `tick_left` 仍是 0，所以中毒**立刻生效**，只是后续刷新不再重置节奏。

**连带范围**——这个分支同时管 poison / bleed / burn：

| 状态 | 谁在用 | 受影响 |
|---|---|---|
| `poison` | 毒灵、飞灵、自爆灵亡语、巨甲灵反伤、宝藏属性效果 | ✓ |
| `bleed` | **只有宝藏**（`BattleSimTreasures` 四处，血契之刃那条线） | ✓ 同样降为严格 1 跳/秒 |
| `burn` | `burn_claw`（不在 32 只玩家单位里）、一个技能 | ✓ |

数值上：毒灵攻速 1.0，本来就约 1 跳/秒，**几乎无变化**；**飞灵攻速 1.2，从 1.2 跳/秒降到 1.0，约 −17%**。以后的攻速光环也不再放大毒伤。

### 5.4 民兵：打断 → 眩晕（决策 4）

`scripts/battle/BattleSimulator.gd:734` 现在调 `StatusEffectService.interrupt(target)`，其时长在 `StatusEffectService.gd:68` **硬编码 1.0 秒**。
改成 `StatusEffectService.add_status(target, "stun", float(d.get("stun_sec", 0.5)), {})`，并新增 `stun_sec` 字段。

| | 效果 | 时长 |
|---|---|---|
| `interrupt`（现在） | **只锁普攻**，仍能移动、仍能放技能 | 硬编码 1.0 秒，不可配 |
| `stun`（改成的） | 完整定身，**连技能一起锁** | 可配 |

### 5.5 出售返还（决策 10）

**结论：`4★ 返还 = 售价 × 3`**（即 3★ 返还的 2 倍）。

#### 为什么不用「3★ 返还 + 100」

定额加成是**累退的**——小灵的 cost 只有次便宜单位的一半，100 金比它整笔投入还多：

| cost | 9 份成本 | 3★ 返还 | +100 方案 | 净收支 | `售价 × 3` 方案 | 净收支 |
|---|---|---|---|---|---|---|
| 10 | 90 | 15 | 115 | **+25 净赚** ❌ | 30 | -60 ✓ |
| 20 | 180 | 30 | 130 | -50 ✓ | 60 | -120 ✓ |
| 30 | 270 | 45 | 145 | -125 ✓ | 90 | -180 ✓ |
| 50 | 450 | 75 | 175 | -275 ✓ | 150 | -300 ✓ |

叠上折扣宝藏更糟：折扣令牌 ×0.8 → 小灵 9 份 72 金、卖 115 = **+43**；清仓特卖 ×0.6 → 9 份 54 金、卖 115 = **+61**。

> **把 +100 调小也没用**：即使降到 +50，清仓特卖下小灵仍是「花 54 退 65 = +11」。只要是定额，小灵就会被撬动，因为它的 cost 只有别人的 1/2 到 1/5。

#### 这会撞穿一条现有的硬断言

`tools/sell_refund_check.gd:76` 的 `_case_no_arbitrage` 写着：

> 硬不变量：卖出退款**必须严格小于**取得成本。等于成本也不行——那意味着可以零成本反复换阵容。

它遍历**全表单位 × 三种折扣状态**（无 / 折扣令牌 / 清仓特卖）逐个检查。用 +100 方案，**小灵会在三种状态下全部触发 `sell_for_profit`**，headless 检查直接红。

`售价 × 3` 方案在三种状态下全表安全（最紧的一格是清仓特卖下的小灵：花 54 退 30，−24）。

**测试本身也要改**：`for star in [1, 2, 3]` → `[1, 2, 3, 4]`，否则 4★ 根本不在覆盖范围内。
另外 `_case_matches_server_rule` 要求客户端退款等于服务端账本的结果，所以 `EconomyLedger` 那侧要同步。
