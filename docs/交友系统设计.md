## 一、先纠正两条已经作废的判断

写在最前面，因为它们都曾经是「不能做」的理由，现在都不成立了。

### ① 「等 `C14`」—— 作废

`C14`（战斗链路明文）2026-09-09 已完成并部署。但更重要的是：
**在线状态 / 邀请好友 / 最近同玩这三个功能本来就不需要动 ENet**，
当初把它们记成「被 `C14` 卡住」是想岔了。具体怎么做见第二节。

### ② 「绑定登录是交友系统的前置」—— 作废，但要换个说法

绑定登录（Google + Apple OAuth）**不是交友系统的前置，是「有真实玩家」的前置。**
今天没有已发布的客户端，所以「换手机丢好友」影响 0 个人。

但它必须有一个写下来的硬触发条件，否则会无限往后滑
（`docs/玩家资料系统设计.md` 第八节第 5 条已经踩过这个模式）：

> **任何形式的对外发行（把内测包发给非团队成员也算）之前，绑定登录必须可用。**

**为什么会丢，说清楚**（这条被问过，值得写死）：
匿名账号的全部凭证就是 `user://glory_account.json` 里那个 `refresh_token`，
**只有一份，只在这台设备上**。`AccountManager.login()` 的逻辑是
「有 refresh_token 就刷新，没有就注册新号」。所以：

| 情况 | 结果 |
|---|---|
| 同一设备、文件完好 | **不该丢，丢了就是 bug**（`_atomic_write` + `.bak` 回退 + `player_id` 不变量就是在防这个） |
| 换手机 / 重装 / 清数据 | **必然丢，且原理上不可能不丢** —— 新设备没有任何东西能证明「我是原来那个人」 |
| `glory_account.json` 坏了但 `profile.json` 还在 | 同样丢：服务器对已存在的 `player_id` 回 409 拒绝认领，客户端重签新 id |

服务器堵死「认领」这条路是对的（`backend/app/routes/auth.py`）——
不然任何人抄一个 `player_id` 就能抢号。

对交友系统的具体伤害不是「自己心疼」，是**别人列表里多一个永远打不通的死号，
而且对方不知道发生了什么**。安卓自动备份**可能**把 `user://` 搬过去，
但取决于用户有没有开、跨品牌能不能用 —— **不能拿它当方案**。

## 二、核心机制：② 侧关联客户端自报的房间号

这一节是整个设计的地基。

三个「值钱」的功能用同一个机制实现，**不动 ENet、不需要 ②↔③ 通道、
不往 `NetProtocol` 加任何账号字段**（RFC 第六节 🔴 第 3 条完好）：

| 功能 | 做法 |
|---|---|
| 在线状态 | 客户端经 HTTPS 报「我在线，房间号 N」 |
| 邀请 / 加入好友的局 | 好友列表显示房间号，点一下调**已经存在的** `NetworkService.team_request_join_room(N)` |
| 最近一起玩过 | ② 把「同一时间报了同一个房间号」的人关联起来（`database/006_room_visits.sql`） |

第三条要特别说明：**客户端不知道队友是谁**（`NetworkService` 里没有任何
`player_name` / `friend_code`，这是对的），所以不能由它上报「我和谁玩了」。
但它知道自己的 `team_room_id`，**② 一关联就知道了**。
这正好绕开了那条红线。

### 🔴 客户端自报的边界（本文最硬的一条）

**自报只能用于「说谎没有收益」的数据。**

- 谎报在线 → 没收益。
- 谎报房间号 → 让好友进错房间。而房间号**本来就是任何人知道号就能进**
  （`team_request_join_room` 就是这么设计的），没有新增攻击面。

**「最近同玩」是唯一有真实滥用面的一条**：谎报房间号把自己塞进陌生人的
「最近同玩」列表 = 定向骚扰入口。对策是**要求双向**：只有两边都报了同一个
房间号、时间窗重叠才算。要伪造就得真的进那个房间 —— 那时你本来就是队友。

> **这条边界必须守住。** 下一个人很容易顺手拿这套机制去做战绩、排行或奖励，
> 而那些是**有价值的数据**，自报立刻不成立。要做那些，只能等 ②↔③ 通道
> （RFC `9.2`，未拍板）。

## 三、数据库：`005_friends.sql`

按 `database/README.md` 的规矩，**编号只增不改，001–004 一个字都不动。**

### 好友关系：一段关系一行，不是两行

```sql
create table player_friendships (
  low_id       uuid not null references players(player_id) on delete cascade,
  high_id      uuid not null references players(player_id) on delete cascade,
  requested_by uuid not null,
  status       text not null default 'pending',
  created_at   timestamptz not null default now(),
  accepted_at  timestamptz,
  primary key (low_id, high_id),
  constraint ordered check (low_id < high_id),
  constraint requester_is_party check (requested_by in (low_id, high_id)),
  constraint status_allowed check (status in ('pending', 'accepted'))
);
create index player_friendships_by_high on player_friendships (high_id);
```

**为什么不用「每段友谊存两行有向边」**（那样查列表只要一次索引扫描，没有 `or`）：

有向边有一个**能表示出来的坏状态** —— 两行不一致 = 单向好友。
写漏一行不报错、不崩溃，表现是「他的列表里有我，我的列表里没他」，
而且只在特定玩家身上出现。这正是 RFC 第七节那条不变量在防的那类静默 bug。

canonical 排序这版让这个坏状态**不可表示**：物理上只有一行。
代价是查列表要扫两个索引（`low_id` 走主键、`high_id` 走上面那个索引），
在「好友上限 100、玩家几万」的量级上不是问题。

**交叉请求顺带被解决**：A 加 B 的同时 B 加 A，第二个事务撞主键，
捕获后发现 `requested_by` 是对方 → 直接置 `accepted`。
重试必须包在 **savepoint** 里 —— 理由同 `players.py` 的好友码重试：
PostgreSQL 里一条语句失败后整个事务进入 aborted 状态，不开 savepoint 的话
重试循环 100% 是摆设。

### 拉黑：单独一张表

```sql
create table player_blocks (
  blocker_id uuid not null references players(player_id) on delete cascade,
  blocked_id uuid not null references players(player_id) on delete cascade,
  created_at timestamptz not null default now(),
  primary key (blocker_id, blocked_id),
  constraint no_self_block check (blocker_id <> blocked_id)
);
create index player_blocks_by_blocked on player_blocks (blocked_id);
```

**拉黑是有方向的**（A 拉黑 B ≠ B 拉黑 A），塞不进上面那个 canonical 对。

`docs/玩家资料系统设计.md` 当初把拉黑推迟，理由是「今天没有任何互动方式，
屏蔽一个只能看、不能互动的人没有意义」——
**交友系统上线那一刻这个理由就失效了**：好友请求本身就是一条能反复戳人的通道。
所以拉黑进批次 1，不是「以后再说」。

### 请求日志：**这是「拒绝就删记录」这个决定的直接代价**

```sql
create table friend_request_log (
  requester_id uuid not null references players(player_id) on delete cascade,
  target_id    uuid not null references players(player_id) on delete cascade,
  created_at   timestamptz not null default now()
);
create index friend_request_log_by_requester
  on friend_request_log (requester_id, created_at desc);
```

已确认的产品决定是「**拒绝 = 删掉记录**，靠每日配额和拉黑兜底」
（另一条路是留一行 `rejected`，但那样误拒的人永远加不回来）。

代价是：`player_friendships` 里不再留有历史，**配额就没有可数的东西了**，
所以必须单开这张日志表。漏掉它的话，「每日配额」根本无从计算，
而这个漏洞不会报错 —— 只会表现为有人能无限重发请求。

**配额判在数据库上，不能用 `backend/app/rate_limit.py`。**
那是进程内滑动窗口，重启即清零、多 worker 各算各的（它自己的注释写着）。
它仍要挂着，但它防的是刷接口，不是业务配额。这与改名冷却判在数据库是同一条教训。

日志要有清理：**保留 30 天**，再久没有用途，而它是一张只增的表。

### 在线状态：单独一张表，不加在 `players` 上

```sql
create table player_presence (
  player_id           uuid primary key references players(player_id) on delete cascade,
  last_seen_at        timestamptz not null default now(),
  room_id             bigint,
  presence_visibility text not null default 'friends',
  room_visibility     text not null default 'friends',
  constraint presence_visibility_allowed check (presence_visibility in ('friends', 'nobody')),
  constraint room_visibility_allowed check (room_visibility in ('friends', 'nobody'))
);
```

**为什么单独一张**：presence 是**高频写**（每个在线玩家每 60 秒一次），
`players` 是**每个请求都读**。写在同一行，每次心跳都会让那一行失效。
这与 `002` 当初分出 `player_bio` 是同一条理由
（「`players` 每个请求都读，bio 一个月读一次」）。

**为什么可见性用文本枚举而不是 bool**：同 `004` 的原话 ——
现在只有两态，bool 更省事，但放宽一条 check 约束是 🟢，
而 bool → enum 是代价表里 🔴 的「改一列的含义」。多写几个字换掉一次数据迁移。
（已定：在线状态**只对好友可见**，没有 `'public'` 档；留着枚举是为了以后能加。）

`room_visibility` 单独一个开关，因为「在不在线」和「在哪个房间」
泄漏的东西不是一回事 —— 后者是行为轨迹。

**没有「离线」字段。** 在线与否由 `last_seen_at` 加 TTL 推出来，
不存一个会说谎的布尔值：客户端崩溃时不会发「我下线了」。

## 四、接口

```
GET    /v1/me/friends                       好友列表（join players 拿昵称/头像/好友码 + presence）
GET    /v1/me/friends/requests              收到的 + 发出的
POST   /v1/me/friends/requests              {friend_code} 发起
POST   /v1/me/friends/requests/{code}/accept
DELETE /v1/me/friends/requests/{code}       拒绝 / 取消（删记录）
DELETE /v1/me/friends/{code}                删好友（双向）
POST   /v1/me/blocks                        {friend_code}
DELETE /v1/me/blocks/{code}
GET    /v1/me/recent-players                最近一起玩过、还不是好友的人
PUT    /v1/me/presence                      {room_id | null} 心跳
PUT    /v1/me/presence/visibility           两个开关
```

**一律用好友码定位，不用 `player_id`** —— 沿用 `docs/玩家资料系统设计.md`
第六节那条：`player_id` 是内部身份，不该出现在客户端可见的地址里。

### 一处必须同时改的现有接口 —— ✅ 2026-09-10 已做

`GET /v1/players/by-code/{code}` **仍然不需要登录**，但现在
`Authorization` 是**可选**的：带了有效令牌就多返回一个 `relation` 字段
（`none` / `pending_out` / `pending_in` / `friends` / `blocked` / `self`），
资料页靠它决定按钮显示「加好友」还是「已是好友」。
匿名调用的行为与之前**逐字节相同** —— 那条路径上一个键都没多。

用的是新加的 `optional_claims` 依赖，不是 `current_claims`。区别是
**令牌无效时当匿名，不回 401**：

| | 后果 |
|---|---|
| 401 | 令牌过期的玩家点开别人资料页 → **整页打不开** |
| 降级成匿名 | 按钮显示成「加好友」，点下去收到「你们已经是好友了」—— 那句话本身就解释了发生什么 |

后者明显轻。⚠️ **这个依赖绝不能用在会改数据的接口上** ——
那里必须 `current_claims`，无效令牌就该 401。有 AST 断言钉着
`optional_claims` 里不许出现 `raise`。

### 心跳的四条纪律

1. **事件驱动 + 慢心跳，不要纯轮询。** 进房间 / 出房间 / 回主菜单时立刻报一次；
   平时每 **60 秒**保活（`friends.HEARTBEAT_INTERVAL_SEC`）。状态变化那一刻才有价值，中间的重复上报没有。
   **TTL 150 秒**（`friends.PRESENCE_TTL`）—— 必须大于心跳间隔、且能容忍丢一次，
   否则在线状态会闪烁。有断言钉着这条不变量。
2. 🔴 **限流按 `player_id`，不能按 IP。** `rate_limit.py` 自己的注释就写了
   「同一出口 IP 的人共用额度 —— 办公室、校园网，**手机运营商 NAT 尤其严重**」。
   心跳是每个在线玩家都在发的东西，按 IP 限流会把同一个基站下的正常玩家批量误杀。
3. **要防的是读，不是写。** 1000 人在线 = 每秒约 17 次 upsert，Postgres 无感。
   但客户端**不许持续轮询好友列表**：打开拉一次、面板开着时每 30 秒刷一次、
   支持下拉手动刷、**关掉就停**。
4. **第一版不做缓存、不上 Redis。** presence 挪去 Redis 或 ② 的进程内存是
   以后真上量的逃生口。提前做只会在这里直接产生隐私 bug
   （同 `docs/玩家资料系统设计.md` 第八节第 7 条）。

## 五、实施顺序

**批次 1 与批次 2 一起发布，当成一个功能。**（已确认）

理由：批次 1 单独上线基本没用 —— 只能手抄 8 位好友码把人加进一个列表，
然后什么也做不了。**批次 2 才是这个系统的价值所在**
（看到朋友在线 → 一键进他的局）。

| 步 | 内容 | 主要文件 |
|---|---|---|
| 1 | 数据库迁移 | `database/005_friends.sql` |
| 2 | 后端：关系 / 拉黑 / 配额 | `backend/app/friends.py`、`routes/friends.py` |
| 3 | 后端：presence | `backend/app/presence.py`、`routes/presence.py` |
| 4 | 后端测试 | `backend/tests/test_friends.py` |
| 5 | 客户端门面 | `AccountManager` 加一组方法，走已有的 `_request` |
| 6 | 界面 | `scenes/menu/FriendsScreen`；`Main.gd` 路由；`MainMenu.gd:168` 换信号 |
| 7 | 心跳接线 | 进出房间时报一次 + 慢心跳 |
| 8 | 门禁 | `tools/friends_check.tscn` |

**批次 3（最近一起玩过）✅ 2026-09-10 已做**，比原计划提前 —— 它复用了
批次 2 的心跳，增量只有一张表（`006_room_visits.sql`）、一条关联查询和
一个接口 `GET /v1/me/recent-players`。

实现要点：
- **只在房间号真的变了时记一行**，不是每次心跳都记（一局对战一行）。
  转换检测搭在心跳那条 upsert 的 CTE 里，常见路径仍然只有一次往返。
- **未闭合的访问记录是常态**（客户端崩溃、进程被杀），查询一律
  `coalesce(left_at, now())`。少一处就会漏掉「明明一起打过但列表里没有他」。
- 排掉四类人：已是好友或有待处理请求的、互相拉黑的、**设了隐身的**、我自己。
  隐身也排掉是刻意的 —— 这个功能是从 presence 推出来的，
  玩家关掉 presence 曝光时不该还能从这里被翻出来。
- 保留 7 天，最多返回 20 人。两个上界都是必须的：前者是「最近」的定义，
  后者是响应体上界。

### 顺带补掉一个 TODO

`scenes/main/Main.gd:794` 写着「今天还没有任何入口能拿到别人的好友码
（好友/聊天都还没做）」。好友列表点进去就是那个入口 ——
直接调已有的 `ProfileScreen.configure_public(code)`。

## 六、容易写错的地方

### 🔴 1. 自报数据的边界

见第二节。**这条被突破的时候不会报错**，只会让一个本来没有价值的数据通道
悄悄变成有价值的，然后被刷。

### 🔴 2. 「拒绝就删记录」必须配日志表

见第三节。漏掉的症状是「有人能无限重发好友请求」，而配额代码看起来是写了的。

### 🔴 3. 单向好友这个坏状态要靠表结构堵死，不能靠代码自觉

见第三节。选 canonical 对就是为了这个。

### 🟡 4. 幽灵在线

客户端崩溃不会说再见，只能靠 TTL。代价是「刚下线」最多显示成在线 2.5 分钟。
**没有更好的办法，接受它** —— 任何「下线时发个包」的方案都挡不住进程被杀。

### 🟡 5. 一键加入会失败，且失败原因要说清楚

房间满了 / 已经开打了 / 房间号已回收 / 对方刚好离开。
**不能只说「加入失败」** —— 那是玩家最容易截图来问的东西。
错误分级复用 `scripts/multiplayer/NetError.gd`。

### 🟢 6. 删好友是双向的

Steam、王者、微信都是双向消失；单向只存在于「关注」模型。
而且对我们不是选择题：选了互相同意，删除就**必须**对称，
否则会造出第三节要堵死的那个不一致状态。

- **不通知对方**（微信、Steam 都不通知；通知等于制造对抗，对方也做不了什么）
- **但要提示操作的人**「对方也会从他的列表里消失」

### 🟢 7. 举报和拉黑在 UI 上别混

举报是给我们看的、异步的；拉黑是即时生效的。
资料页已经有举报按钮（`ProfileScreen._report_button`），位置要明显不同。

### 🟢 8. 好友数上限 100

否则 `GET /v1/me/friends` 的响应体无上界。在事务里 count + 判断。

## 七、非目标（明确不做）

- **不做聊天。** 聊天按钮就在朋友按钮下面（`MainMenu.gd:171`），
  但私聊要消息存储 + 内容审核 + 举报证据链，比交友系统大一个量级。
  别因为「都是社交」就顺手做进同一批。
- **不做单向关注。** 已选互相同意模型。
- **不做模糊搜昵称。** `players.player_name` 不唯一，且默认名是 `Player`；
  好友码就是为此而生的（`docs/玩家资料系统设计.md` 第八节第 1 条）。
- **不拿自报数据做任何有价值的东西。** 战绩、排行、奖励一律不行，见第二节。
- **不碰 `NetProtocol`、不碰 ENet。** 本系统全部在 ①↔② 的 HTTPS 链路上。
- **不缓存好友列表与 presence。** 见第四节第 4 条。
