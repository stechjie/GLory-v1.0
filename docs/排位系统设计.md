## 二、时间窗口

### 三刀的含义

| 时间（MYT） | 发生什么 |
|---|---|
| 19:00 | 排位队列开放 |
| 23:00 | **停止匹配新局**。已经凑齐 6 人正在进房的放过去；还在队里没凑齐的踢出队并提示 |
| 00:00 | 当日排位期结束。**正在打的局不受影响，打完照常算分** |

23:00 到 00:00 这一小时是留给已开打的局跑完的。按一局 20～30 分钟算，
23:00 最后开的那局约 23:30 结束，**余量 30 分钟**。

### 🔴 最后开局时间要做成配置，不要写死 23:00

```
最后开局时间 = 00:00 − 一局 P95 时长 − 10 分钟余量
```

一局 25 分钟 → 23:05（23:00 正好够）；一局 45 分钟 → 得提前到 22:45。
数值调过、回合变慢之后写死的 23:00 就会变成每晚固定事故。

### 时长是怎么反推出来的

`data/rounds/round_schedule.json` 写死 21 回合（PvP 只在第 6 / 12 / 18 / 21 回合）。

```
25 分钟 ÷ 21 回合 = 每回合 71 秒（含备战 + 战斗演示 + 回放 + 结算）
```

战斗演示加回放按 30 秒算，**备战只剩约 40 秒**。这是「20～30 分钟」这个目标
对备战节奏的硬约束 —— 记在这里，等做倒计时时不用重新算。

### ⚠️ 备战倒计时先不做的后果

现在备战阶段**没有倒计时**，六个人全按「准备」才推进
（`scenes/prep/PrepFlowController.gd`）。唯一的闸是 `PREP_TIMEOUT_SEC = 30 分钟`
关整个房间（`scripts/multiplayer/RoomService.gd`，安全阀，不是节奏控制）。

所以第一版排位里：

- 一个人不按准备，其他五个最多被拖 30 分钟
- 更糟的是他能**故意拖到窗口结束**

服务器已经有「缓存棋盘代交」的能力（`NetworkService` 看门狗那条路），
倒计时接上去不难。**这条是排位真正上线（第九节第 5 步）前的前置，不是第 1、2 步的前置。**

### 时区

马来西亚 **UTC+8，没有夏令时**，固定偏移。

后端现在全是 UTC（`dt.datetime.now(dt.UTC)`），而且现有的「每日配额」是
**滚动 24 小时**、不是墙钟日切（`backend/app/friends.py`）。
排位窗口是这个项目**第一个需要墙钟本地时间的东西**。

- 存 UTC 不变，判窗口时用一个 `+8` 常量
- 🔴 **不引 tz 数据库**：马来西亚不会有夏令时，多一个依赖不值
- 🔴 **窗口判定只能服务器说了算**。客户端改系统时区就能绕过，而排位是发分的，
  不能像 `backend/app/admission.py` 那样接受「拦人的是客户端」
- 窗口外点「排位」显示**距离开放的倒计时**，不是「敬请期待」

## 三、段位与分数

### 结构：只有一个分数，段位是它的显示切片

```
段位 = clamp(分数 ÷ 100, 0, 7)     # 8 段
第 8 段（≥700 分）不封顶，分数继续往上涨
```

匹配、排行榜、赛季结算**全部读同一个数字**。段位切片以后想调宽窄
（发现玩家全卡在某一段），只改配置表，**一条玩家数据都不动**。

### 一局加减多少

```
D = 对手队伍平均分 − 自己队伍平均分

赢： +25 + clamp(D ÷ 20, −15, +15)    →  10 ~ 40
输： −25 + clamp(−D ÷ 20, −15, +15)   →  −10 ~ −40

连胜 3 局起：赢的那一份 × (1 + 0.2 × min(连胜数 − 2, 3))   # 上限 +60%
```

打高 300 分的队伍：赢 +40 / 输 −10。打低 300 分的：赢 +10 / 输 −40。

### ★ 为什么必须有段位差修正

固定 ±25 是**跑步机**：只要胜率 >50%、局数够多，所有人最后都会到第 8 段
（满梯 800 分 = 净胜 32 局）。段位最后反映的是「打了多少局」，不是「多强」。

加上段位差修正之后，数学上就是 Elo，会自动收敛到真实水平，
同时保留「赢一局大概 25 分」的心理模型。

### 待确认（未拍板）

- **每段 0 分是地板**：掉到本段 0 分再输不掉段。一局 25 分钟，输一局的沉没成本比 MOBA 大得多
- **定级赛 5 局**，之后落在第 2～4 段之间，不要都从 0 开始。窗口制下从 0 爬到该去的位置要
  8～10 个晚上，高手会在第三个晚上弃游

## 四、信誉分与惩罚

### 阈值与恢复

| 信誉分 | 效果 |
|---|---|
| 起始 | 100 |
| < 85 | 警告 |
| < 70 | 不能排位 |
| < 60 | 不能普通匹配（只能玩娱乐模式） |

恢复：**每天 +5**（无条件）+ **正常完成一局 +2**。

⚠️ 娱乐模式还没建。在它做出来之前，信誉分 <60 的人**只剩自定义房间**。

### 🔴 跑路的判定线：不是「有没有转过 AI」

`RESERVE_GRACE_SEC = 20 秒`，到点座位转 AI 接管
（`scripts/multiplayer/ReconnectService.gd`）。
**但转 AI 之后玩家还能回来** —— `NetworkService._resume_seat()` 只要求房间没关、
对局没打完。主菜单那个「↩ 游戏重连」按钮走的就是这条。

20 秒对手机切后台、过隧道、4G 切 WiFi 完全不够。拿它当跑路线会误伤一大片正常玩家。

> **跑路 = 对局结束那一刻，这个座位仍然没人在线。**

中途断了又回来的**不罚**。AI 代打了几回合记进战报（第七节），
等有真实数据再决定要不要按代打回合数分级。

★ 服务器分不出「拔网线」和「真的断网」，所有游戏都一样。这是已知并接受的。

### 计数窗口：最近 7 天，7 次一档

档位跟着天数走 —— 7 天窗口，7 次一档：

| 档 | 7 天内第几次 | 信誉分 | 禁排位 |
|---|---|---|---|
| 1 | 第 1 ~ 7 次 | −5 | 不禁 |
| 2 | 第 8 ~ 14 次 | −8 | 15 分钟 |
| 3 | 第 15 ~ 21 次 | −11 | 30 分钟 |
| 4 | 第 22 ~ 28 次 | −17 | 45 分钟 |
| 5+ | 以此类推 | ×1.5 递增 | 60 分钟封顶 |

扣分公式：`round(5 × 1.5^(档位−1))` = 5 / 8 / 11 / 17 / 25 / 38…

> ⚠️ 拍板时举的例子第 3 档写的是 10，而 ×1.5 算出来是 11。这里按 ×1.5 写。要 10 的话改这一格。

禁赛 60 分钟封顶的理由：窗口只有 4 小时，60 分钟已经是当晚的 1/4。再长不如交给信誉分
—— 信誉分是跨天的，禁赛不是。

### ★ 为什么是滚动窗口而不是「连续 N 次」

这两个直觉写法都会炸：

**「连续」= 中间打一局正常局就归零**

```
一晚 4 局，跑路-正常-跑路-正常：
  −5 −5 +2 +2 +5(每日) = 净 −1 分/晚
从 100 掉到 70 要 30 个晚上 → 等于没有惩罚
```

**永不归零（累计）**

```
−5 −8 −11 −17 −25 −38 …
一个玩了一年的老玩家累计断线 8 次（一年断 8 次网很正常）→ 永久掉到警告线以下
```

滚动窗口两边都不沾：

- 正常玩家一个月断 2 次 → 7 天窗口里都算第 1 档，每次 −5，一天 +5 就回来了，**无感**
- 交替刷的人 7 天内稳定累到第 2、3 档，每晚净 −11 左右，**三个晚上掉到禁排位线**
- 自动衰减，不需要单独的「计数清零」设计

### 跑路的完整后果

1. 本局按输计算
2. 分数额外扣：**输的那一份 × 1.5**
3. 信誉分按上表扣
4. 按上表禁排位

### 没按准备

匹配成功后要弹确认框（这个环节现在不存在，见第五节）。不确认的后果**按次递增，不分档**：

| 7 天内第几次 | 信誉分 | 禁排位 |
|---|---|---|
| 1 | −1 | 不禁 |
| 2 | −2 | 不禁（给提示） |
| 3 | −5 | 3 分钟 |
| 4 | −8 | 15 分钟 |
| 5 | −11 | 30 分钟 |
| 6+ | ×1.5 递增 | 60 分钟封顶 |

第 4 次起 = `round(5 × 1.5^(N−3))`。

**不用 7 次一档**：没按准备给别人造成的损失只有 30 秒（局还没开），比跑路轻得多，
但它是最容易被拿来**躲匹配**的动作 —— 看到对手段位不想打就不确认。所以递增要快。

🔴 **另外 5 个人不受任何惩罚，并且放回队列最前面。**

### 信誉分只给自己看

别人看不到。理由和资料页那套一样（`docs/玩家资料系统设计.md`）——
公开等于发一个新的骂人理由。以后接举报系统时也一样。

## 五、匹配

### 组队规则

- **只能单排，或者满 3 人车队**。不做 2 人车队 —— 2+1 是所有匹配系统里最恶心的情况
- 3 排**优先配 3 排**；等 60 秒找不到，下放给 3 个单排
- 单排优先凑单排

### 3 排的匹配分要加车队补正

```
车队匹配分 = max(三人平均分, 最高分 − 50)
```

取平均会让「一个高手带两个低分号」一直打低分局。

### ★ 语音已经按队伍分房了 —— 这是单排/3排能成立的前提

`scripts/voice/LiveKitAuth.gd:65`：

```gdscript
static func room_name(room_id: int, salt: String, team: int) -> String:
	return "g%d-%s-t%d" % [room_id, salt, team]
```

一个对局房间、一个队伍一个语音房。**3 个陌生人也有队内语音**，
这把「3 人车队 vs 3 个散人」的优势砍掉了一大半。这条已经做好了，不用新做。

### 搜索放宽

| 排队时间 | 分数窗口 |
|---|---|
| 0 秒 | ±100 |
| 每 10 秒 | 再放宽 ±50 |
| 上限 | ±500 |
| 3 分钟后 | 不限，随便凑 |

### 🔴 排位绝不填 AI

凑不齐就是排不到。明确提示「当前排队人数不足」，不要一直转圈。
填了 AI 分就没意义了。

### 六个人怎么分两队

按分**蛇形分队**（排序后 1、4、5 对 2、3、6），让两队平均分尽量接近。

3v3 里一个人的影响是 1/3，5v5 里是 1/5 —— 队伍平均分差 100 分，
在这里造成的胜率偏差比 MOBA 大得多。

座位与队伍的对应关系照现有的来：`slot < 3` 是 A 队，`slot >= 3` 是 B 队
（`NetworkService._room_build_match_states`）。

## 六、匹配归谁管

🔴 **账号服务器**。战斗服务器不认识账号（`docs/账号系统RFC.md` 第六节红线第 3 条：
`NetProtocol` 不加账号身份字段），它不知道谁是谁、更不知道谁多少分。

但这样账号服务器就得能「指定六个人去战斗服务器的同一个房间」，
而两台服务器之间现在**一条网络通道都没有**。解法见下一节。

## 七、结果怎么回到账号服务器

### 现状

两台服务器之间只有一条单向的、非网络的通道：

```
账号服务器用私钥签「出战名片」 → 客户端原样转交 → 战斗服务器用公钥验章
```

（`backend/app/loadout.py` 签，`scripts/multiplayer/BattleCard.gd` 验，协议 30 落地）

反方向一条都没有。`backend/app/routes/` 下所有接口都是玩家 JWT 的 `/v1/me/...`，
没有任何服务端到服务端的接口，也没有服务端密钥。
`docs/账号系统RFC.md` 第九节 `9.2`（③ → ② 的结算用什么服务端凭证）**至今空着**。

### 🔴 方案：双向都用「签名 + 客户端转交」

```
去程（匹配）
  账号服务器凑齐 6 人
    → 给每人签一张「排位入场券」(match_id / 队伍 / 六人名单哈希 / 有效期)
    → 客户端拿券去战斗服务器
    → 战斗服务器验章，按 match_id 把六人放进同一房间，按券分队

回程（结算）
  打完 → 战斗服务器用自己的私钥签一份「战报」
    → 交给客户端 → 客户端 POST 给账号服务器
    → 账号服务器验章、按 match_id 去重、结算分数与信誉分、存进历史表
```

**整个排位不需要任何服务器到服务器的网络通道。** `9.2` 可以继续不回答。

### 为什么这样最好

1. ★ **一份战报结算全场六个人** —— 6 个人里只要有 1 个交上来就够。
   赢的 3 个有动力交，输的不交也没用。激励结构自洽，不怕「输了就不交」
2. 复用已经跑通、坑也踩完的那套 RSA 签/验（RSA-2048 / PKCS#1 v1.5 / SHA-256）
3. 不用新开网络通道、不用在线协商密钥轮换
4. 红线第 2 条仍然成立：**写持久化的还是账号服务器**
5. 战斗服务器仍然无状态，重启不丢已结算的局

### ⚠️ 已经踩过的坑，别再踩一次

`Crypto.verify()` 收的是**摘要**，不是原文 —— 传原文进去会一直返回 `false` 且不报错。
2026-09-16 名片那次实测踩过，见 `docs/商城系统设计.md` 第五节。

先验签、再解析，**绝不重新序列化** —— 签的是那串字节，验的也是那串字节。

### 钥匙

战斗服务器要一把**自己的**私钥（和名片那把方向相反），账号服务器持它的公钥。

- 生成工具照 `deploy/make_battle_card_key.py` 的样子做
- 🔴 **私钥绝不进 `tools/`** —— `make_server_zip.ps1` 会把整个 `tools/` 打进战斗服务器包
- 部署步骤照 `deploy/BATTLE_SERVER_KEY.md` 的格式补一节

## 八、游戏历史

### 🔴 只存最终状态，不存过程

战报里带：

| 内容 | 说明 |
|---|---|
| 对局 | `match_id`、赛季、开始 / 结束时间、总回合数、结果（A 胜 / B 胜 / 平） |
| 每个座位 | `player_id`（从入场券来）、队伍、**最终棋盘**、最终金币、用掉的萝卜、法阵 HP |
| 判罚依据 | 结束时在不在线、AI 代打了几回合 |

大小估算：名片是 705～1673 字节；战报带六个座位的最终棋盘 + 经济数据，估 **5～20 KB**。
六个人各传一份，最多 120 KB/局，可以接受。

### 为什么「不存过程」要现在就定死

存每回合的棋盘，大小翻 21 倍 —— 这条「客户端转交」的路就走不通了。

以后真要做回放级历史，那是另一套（对象存储 + 战斗服务器直传），**不能挂在这条路上**。

#### 三处踩过 / 差点踩的

1. **`seat_profiles` 会广播给全房间**（`room_state`），所以 `pid` 必须另存一份
   `seat_pid`。塞进 `seat_profiles` 等于把每个人的账号 id 发给同房间所有人。
2. **`reported_by` 那一列是死路。** 按 `on delete cascade`（`test_profile` 那条门禁要求的）
   会让交战报的人一注销就**删掉整局记录**；按 `set null` 过不了门禁。
   它本来就只是排查用，于是归日志不归表。理由写在 013 里。
3. **影子期没有「服务端自己算的金币」。** `_room_prep(room, slot)["gold"] = gold_after`
   每回合把账本覆盖成客户端自报的那个数。所以历史里的金币可信度 = 客户端，
   由 `gold_authoritative` 列如实标明。萝卜那一列才是真的服务端权威。

#### 部署顺序（这一步）

1. 在 Supabase SQL Editor 跑 `database/013_match_history.sql`
