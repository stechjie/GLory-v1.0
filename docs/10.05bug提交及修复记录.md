### 1. 第 3 条 —— 不是「落待命区」错了，是**优先级没排**

我最初把它读成 bug，写了两轮读码分析去怀疑「拖到棋盘 → `_drop_on_ended` 优先于 `_drop_data` → `_snap_drop_to_nearest` 把 shop 载荷吸到待命格」。**用户的澄清推翻了那个假设**：自动落待命区本身就是要保留的行为，缺的是「**能升星就先升星**」。⇒ 正确做法是给「上阵已满」这个分支**补排优先级**，而不是删掉分流。

**修法**（`scenes/prep/PrepBoardController.gd`）：`_buy_or_merge_shop_to_board()` 的「上阵上限」分支原来只弹一句 `toast_board_full`（棋盘人口已满）就 `return` —— 玩家拖了半天得到一句拒绝，而待命区其实还有空位。现在改成调新抽出的 `_auto_dispatch_shop_when_board_full(shop_index, offer)`，按序：

| 序 | 条件 | 行为 |
|---|---|---|
| ① | 棋盘上有同名同星可升星 | 就地升星（不占新格，还直接变强） |
| ② | 待命区里有同名同星可升星 | 在待命区升星（同样省一个格子） |
| ③ | 待命区还有空位 | **落到待命区**（本条正文） |
| ④ | 都不行 | 「棋子已满，无法购买」（第 3 条之（3）的既有口径） |

★ 抽成独立函数而不是就地写：它必须**复用** `_buy_or_merge_shop_to_board` / `_buy_or_merge_shop_to_bench` 那一整套买入流程（扣钱、`shop_sold`、影子账 `_shadow_report_buy`、音效、存档）。照抄一遍等于把「哪一步会漏」的机会复制一份。

### 3. 第 5 条 —— 根因是**两条**，都不是"参数没调好"

用户截图里读条上那只猫「只剩斗篷和一块白」。逐层量下来是两个独立的错：

| 别 | 根因 |
|---|---|
| **时机** | `PetPreview.normalize()` 是在 `build_runner()` 里**当场**调的，而那一刻 frame 还没被调用方 `add_child` ⇒ 模型不在树里、`PetCatAnimated._load_action_models()` 还没跑（它建在模型自己的 `_ready()` 里）⇒ `aabb_of()` 找不到任何网格，落到兜底 `AABB(Vector3.ZERO, Vector3.ONE)`（高 **1.0**）⇒ `factor = 0.95 / 1.0 = 0.95`，而真实需要 **0.60** ⇒ 宠物**偏大 1.58 倍**。 |
| **基准** | `MeshInstance3D.get_aabb()` 给的是**绑定姿势**的盒子，而且**关于网格节点原点对称**（实测猫 `[-0.794, +0.790]`、蘑菇 `[-0.747, +0.749]`、兔 `[-0.949, +0.948]`）—— **高度是对的，基准错了半身**。而真正被动画驱动、真正被渲染出来的几何（骨骼当前姿势）是 **`[0.000, +1.178]`，脚底恰好落在 local y = 0**。`normalize()` 拿盒底当脚底 ⇒ 宠物被整体抬高半身 ⇒ 头顶出画。 |

取证（`work/_qa_1005d/probe_petaabb_1005d` / `probe_petbones_1005d`，均非 headless）：

```
AABBDUMP   mesh Mesh1_0   visible=true  y=[-0.794,+0.790] size=(1.898,1.585,1.113)   ← get_aabb()，三个动作子模型完全相同
BONES      骨骼 40 根     local 包围盒 y=[+0.000,+1.178] x=[-0.570,+0.355]           ← 真正被驱动的几何
BONES     PetCatAnimated / ModelRoot / Idle_model / Armature(scale=100) / Skeleton3D  ← FBX 的 100× 单位换算
```

★ 顺带排除了一个错误假设：三个动作子模型（idle/attack/run）的 AABB **逐字节相同**，所以「不可见子模型把包围盒撑大」**不成立**——不是它的锅。

### 4. 第 5 条的修法

- **`fit_when_ready(model, pet_id)`（新）**：模型已在树里就直接 `normalize()`，否则挂一次性 `model.ready` 信号（该信号在 `_ready()` 之后才发）。`build()` 与 `build_runner()` 两条入口都改走它。
  - 顺带保住既有的一条顺序约定：`build_runner()` 里 `fit_when_ready` **先**挂、`play_run()` **后**挂，两者都挂在 `ready` 上，按连接顺序回调 ⇒ 先归一化、再切跑动。
- **`skeleton_bottom(root, box)`（新）**：遍历找 `Skeleton3D`，取所有骨骼原点在模型 local 空间的最小 y 作为脚底基准；找不到骨骼才退回 `box.position.y`（同改前口径，不会更差）。`normalize()` 里 `model.position.y = -anchor * factor + model_y`，**高度仍用 AABB**（实测与骨骼一致）。
- **`build_runner()` 补 `camera_size` / `camera_y_offset` 两个参数**（与 `build()` 同名同义，默认取常量）：目的是让**同一份生产代码**能做取景标定，探针里不照抄相机参数。

## 二、第 1 条：升级石列表「按住上下滑」（根因是两个，不是一个）

### 1. 先看改动前的原版（`git show 3ea330df:ui/components/TouchScrollContainer.gd`，共 34 行）

该文件**不是本轮新建**，是 9.30「结算面板、语音功能优化」那批带进来的。原版只有触摸一条路：

```gdscript
if event is InputEventScreenTouch:
    if event.pressed and _finger < 0 and get_global_rect().has_point(event.position):
```

两个缺陷叠在一起：

1. **只认 `InputEventScreenTouch`，完全没有鼠标分支** ⇒ 桌面端与模拟器（MuMu / 雷电 / BlueStacks）用鼠标按住拖，容器**根本不进手势**，只剩滚轮与滚动条 ⇒ 正是用户说的「需要滚轮或者按住滚动条才能上下滚动」。
2. **命中判定与位移都只用一种坐标空间**（`get_global_rect().has_point(event.position)`、`movement = event.position - _start`）⇒ 根视口在 `stretch = canvas_items` 下会把窗口坐标换算成画布坐标再投递，而带缩放的 CanvasLayer 里的控件又是画布层局部坐标；**手机分辨率与 1600×720 基准不同时两者差一个缩放系数**，于是真机上「怎么按都滚不动」且**没有任何日志**。

### 2. 修法

- `_input` 在**子控件之前**观察原始事件（本仓这几个列表内容**全是按钮**，手指按在按钮上时按下事件会被子控件吃掉，`ScrollContainer._gui_input` 再也收不到后续拖拽）。
- 三类输入都接：真机触摸 `ScreenTouch/ScreenDrag`、桌面鼠标 `MouseButton/MouseMotion`、**滚轮保持 `ScrollContainer` 原行为**（不拦、不标记已处理）。
- 纵向位移超过 `DRAG_THRESHOLD = 5.0`（原 6.0）才判拖拽，并 `propagate_notification(NOTIFICATION_SCROLL_BEGIN)` —— `BaseButton` 收到它会取消当前这次按压 ⇒ 拖完松手**不会**误触发列表里被按住的按钮；轻点（< 5px）原样放行。
- **双坐标空间**：`_accepts()` 先按控件自身坐标判一次（路径 1），不中再按窗口坐标判一次（路径 2），任一命中即算命中；坐标空间在手势开始时定死（`_window_space`），拖动过程沿用同一套 —— 中途换算基准变了会让滚动量突然跳一下。
- Android 上 `emulate_mouse_from_touch` 默认开着，同一次触摸会来「触摸 + 模拟鼠标」两路，用「先到先占」去重（`_pointer`），不依赖设备号。
- 新增 `set_drag_zone(getter: Callable)`：把可**起手**区域扩到整张升星卡片（「按住升星区域上下滑动」的手感），只扩大起点判定，轻点仍照常落到子按钮上。`CarrotCampPanelV3.gd` 已接：`scroll.set_drag_zone(func() -> Control: return inventory_card)`。

### 3. ★ 顺带修掉一处「假绿」

`var local := _accepts(pos)` —— `_accepts()` 返回 `Variant`，`:=` 从 `Variant` 推断触发本工程**当错误用**的 `inference_on_variant`，**解析期直接失败**。但 `TouchScrollContainer.gd` 当时**不在 `cold_parse_chain_check` 的 TARGETS 里、也没有别的 .tscn 连带它** ⇒ 门禁照报 `status=PASS`，只在日志里留一行 `SCRIPT ERROR: Parse Error: The variable type is being inferred from a Variant value`。已改 `var local: Variant = _accepts(pos)`（同处 `_in_drag_zone` 的 `var zone` 一并标注），并把本轮全部改动文件逐个单列进 TARGETS。教训与 9.22 同款：**没有单列 = 靠别人连带，而别人连带失败时 `CHECK_RESULT` 仍可能是 PASS**。

### 4. 门禁 `tools/touch_scroll_check.tscn`（11/0）

判据**一律走真实事件** `get_viewport().push_input(...)`，**不直接调** `_begin()` / `_advance()` —— 直接调私有方法只能证明「函数写得对」，证明不了「事件真的会走到它」，而这一条的现场恰恰是「事件根本没走到」。

用例：轻点不滚动且照常触达子按钮 / 按住拖动真的滚 / 再拖继续滚 / 拖动不误触按钮 / 位移小于阈值仍算点击 / 手势区扩大起手点 / **反向对照**（没设手势区时容器外起手不该滚）/ **根视口 canvas 带缩放时的双坐标回退**。
