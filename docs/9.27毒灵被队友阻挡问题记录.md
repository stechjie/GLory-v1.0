### §2.5 ★★ 最终根因（本条是本轮真正的结论）

**毒灵与前方队友移动速度相同（各 16.5px/tick），且队友始终位于它与敌人之间的连线上。**

因此这不是"绕行失败"，而是**几何上无法绕开**：

1. `_step_team` 每 tick 位移被 `min(speed*TICK, dist - attack_distance)` 截断，
   两者速度相同时**位移量也相同** → **相对距离恒定不变**；
2. `_move_without_pushing` 的侧移分支（`:691`）触发条件是
   `remaining.length_squared() < 0.000001`，即**残余量必须恰好为 0**。
   同速并行时残余量恒不为 0（两者一起前进），**所以侧移分支几乎不触发**；
3. `_separate_units`（`:706`）只解"重叠"，不提供绕行推力；
4. 结果：**毒灵永远贴着队友后背，直到队友先到达射程边缘停下（`ally_y=325`），
   毒灵才停在 `d≈32.7`** —— 刚好差一点点进不去。

**用户看到的现象是真的**：前面那段时间它确实"没走上去"（相对于队友它一直贴着），
敌人身上也确实没有中毒标记（因为**它还没进射程，打不出毒**）。
**但原因不是"抢了同一个目标"，也不是"被碰撞体积卡住"，而是"同速并行的人墙"。**

## §3 已有机制：绕行**已经写在代码里**

`scripts/battle/BattleSimulator.gd:651-694` 的 `_move_without_pushing` 已经是
"圆-射线扫掠 + 沿法线滑行 + 迎面侧移"：

```gdscript
		position += direction * travel
		if normal == Vector2.ZERO:
			break
		remaining = direction * (length - travel)
		remaining -= normal * minf(0.0, remaining.dot(normal))
		# Head-on blockers have no natural tangent. Walk around with a stable
		# UID tie-break instead of repeatedly pushing the blocker each tick.
		if remaining.length_squared() < 0.000001 and length - travel > 0.001:
			var side := 1.0 if str(f.get("uid", "")) < hit_uid else -1.0
			remaining = Vector2(-normal.y, normal.x) * (length - travel) * side
	f.pos = Vector2(clampf(position.x, 45.0, ARENA_W - 45.0), clampf(position.y, 40.0, ARENA_H - 40.0))
```

注释明确写着"**Walk around**" = 绕过。探针 B 证明它**确实在工作**。

### §3.1 但它是"单次绕行"，没有持续路径规划

`for iteration in 3:` —— 每 tick **只有 3 次**迭代机会。
探针 E 的三人墙场景（3 只队友排成一排）里，毒灵需要绕更远；
`crowd_*` 场景下自始至终有位移（`crowd_advanced_y=153.7`），但**速度明显变慢**。

**这是唯一值得优化的真实点**：不是"不会绕"，而是"绕得慢 / 遇到墙式排列要挤很久"。

## §5 修复方式（**已按 §2.5 真因重写**）

### ★ 真因回顾（一句话）

> 毒灵与前方队友**移动速度相同**，且队友始终位于它与敌人的连线上 →
> 每 tick 两者位移相等 → 相对距离恒定 → **永远贴着队友后背，卡在射程外约 30px**。

### 关键：修复必须打破"同速 + 共线"这两个条件之一

#### 方案 A：让侧移在"同速逼近"时就触发（**最小改动，推荐先试**）

**问题**：`_move_without_pushing:691` 的侧移触发条件是
`remaining.length_squared() < 0.000001` —— **残余量必须恰好为 0**。
同速并行时残余量恒不为 0，所以侧移根本不触发。

**改法**：把触发条件从"残余为 0"放宽为"**本 tick 被截断且 blockers 在场**"：

```gdscript
# 现状（:691）
if remaining.length_squared() < 0.000001 and length - travel > 0.001:

# 改成：只要被挡住了（travel 被截断），就主动侧移一点
if length - travel > 0.001 and travel < length * 0.5:
```

**风险**：中。这会改变所有单位的寻路手感，可能让密集阵型"全体抖动"。
**必须先跑批跑门禁 + 观感验收。**

#### 方案 B：给"被挡住的单位"累积侧移记忆（**更稳，但改动大**）

新增每单位字段 `sidestep_bias`（±1），一旦检测到"连续 N tick 被同一 uid 挡住"，
就**持续**朝那一侧偏移，直到越过。这需要：

1. 在 `_move_without_pushing` 里记录 `last_blocker_uid` 与连续计数；
2. 触发阈值后，把 `side` 写进单位状态；
3. 门禁要覆盖"同一单位不会被反复卡住"。

**风险**：中高。需要新字段、新门禁、回放兼容性检查（★ 注意 `frames` 是 13 列，
**不能加列**，所以只能放在非回放字段里）。

#### 方案 C：设计层决策 —— 允许友军之间"软穿透"

若玩法上接受"友军可部分重叠"，则直接绕过整个问题。
但这与现有碰撞体设计冲突，**需要你先拍板**，我不建议单方面改。

#### 方案 D（不建议）：给毒灵单独加"绕队友"特判

让 `undead_poison` 独享更高的侧移优先级。
**不推荐** —— 这是把通用寻路问题变成单位特判，会让同类问题在别的单位上复现，
也与项目"判定只留一处"的既有约定冲突。

### ★ 建议的先后顺序

1. **先真机确认**：按 §2.5 的机理，毒灵应当**始终显示在队友正后方、不越过**。
   请你在真机上盯一眼"毒灵是否从未超过它前方的队友"——
   若是，则 §2.5 完全成立，可以进入修复。
2. 若成立 → 先做 **方案 A**（一行条件放宽），跑批跑 + 观感验收；
3. 方案 A 不够 → 上 **方案 B**（侧移记忆）；
4. 方案 C 需你拍板。

### 方案 A 详解：放宽侧移触发条件（最小改动）

**现状**（`BattleSimulator.gd:691`）：

```gdscript
		if remaining.length_squared() < 0.000001 and length - travel > 0.001:
			var side := 1.0 if str(f.get("uid", "")) < hit_uid else -1.0
			remaining = Vector2(-normal.y, normal.x) * (length - travel) * side
```

**为什么同速时不触发**：`remaining` 是"沿法线滑行后的残余向量"。
同速并行时毒灵每 tick 仍能沿队友表面滑掉一点点，残余恒不为 0 →
**这个分支永远不进**。

**改法（两选一）**：

| 选项 | 改动 | 风险 |
|---|---|---|
| **A1 放宽阈值** | `< 0.000001` → `< 0.01` | 改动最小；必须变异测试证明真有差别 |
| **A2 按截断比例触发** | 加 `travel < length * 0.5`（被挡住一半以上就主动侧移） | 更稳，但影响面更大 |

**A1 建议先试**。★ 无论选哪个，都必须：
① 跑全批门禁；② 做变异测试（改坏 → 判据红 → 还原验 sha256）；
③ 观感验收（这类改动会改所有单位的寻路手感）。

### 方案 B 详解：侧移方向记忆（中等改动）

现在 `side` 每 tick 由 `uid` 字典序**重新决定**，所以"这一 tick 往左、下一 tick 往右"会来回抖。
加一个 `f["side_step_bias"]` 记住上次方向，**同一侧连续绕**：

```gdscript
# 伪代码
if blocked_by_same_uid_for_n_ticks:
    f.side_step_bias = f.get("side_step_bias", side)
    side = float(f.side_step_bias)
```

★ 新增字段**只放 fighter 字典，不要塞进回放 frames**（`ReplayDigest.SIMULATION_TOP_FIELDS`
含 `frames`，加列会改冻结哈希）。

### 方案 C 详解：迭代次数 / 群体绕行（大改动，暂不建议）

| 改动 | 做法 | 注意 |
|---|---|---|
| **C1 迭代次数** | `for iteration in 3:` → 5~6 | 影响所有单位；`SEPARATION_MAX_TRAVEL` 等预算常量要一起复核 |
| **C2 群体绕行** | 把"前方 N 只友军"合并成一个"墙"来绕，而不是逐个圆 | 改动最大，收益最高，但风险也最高 |

**这两条都建议放在 A/B 验证有效之后再考虑。**

### 方案 D：设计层决策（需你拍板）

1. **友军之间关闭碰撞**（只对敌方保留）—— 会带来"模型重叠"的观感问题，
   且与 `_separate_units` 对所有 `player + enemy` 统一解算的设计意图冲突。
2. **接受这是解算极限**，不改行为，只在 UI 上让"挤不进去的单位"有可辨识状态。

**这两条都涉及玩法口径，必须你先定。**

## §5.5 ★★ 用户需求（第二轮追加）：让它"更智能地选敌 + 绕路"，而不是原地等队友死

用户原话：

> 「我的想法是，让它会更智能选择敌人和前进方向绕路进行攻击，
>   而不是像视频里一样呆在原地等待队友死亡再上前。」

这个需求比我原来的"方案 A 放宽侧移阈值"**更能解决问题**，而且探针证实
**杠杆极大**。本节是完整的实现思路。

### §5.5.1 关键前提验证（探针 K / L，两个字）

**先说结论：不需要让它"穿过队友" —— 只要选一个"斜距可达"的敌人就能参战。**

探针 L（`probe_poison_reach_927`，PASS 3/0）扫描"敌人相对队友轴线的横偏"：

| 敌人横偏 | 最近距离 | 攻击次数 | 伤害 |
|---|---|---|---|
| **0px（正后方）** | 37.5 | **20** | **240** |
| 20px | 32.8 | **69** | **900000（满血秒杀）** |
| 30px | 33.7 | 69 | 900000 |
| 40px | 34.5 | 69 | 900000 |
| 60px | 34.3 | 69 | 900000 |
| 140px | 32.8 | 63 | 900000 |

**横偏只要 ≥20px，攻击次数 20 → 69（3.5×）、伤害 240 → 满血秒杀。**

★★★ **而现有选敌逻辑永远选"直线距离最近"的那个** ——
探针 L 的 `l3_*` 读数：`l3_picked_uid=e_front`，`l3_front_dist=290.0` vs
`l3_side_dist=297.3`。`_team_select_target`（`BattleSimShared.gd:800-810`）
用 `distance_squared_to` 打分，**正后方那个直线距离最短 → 它被选中 →
于是毒灵一辈子够不到**。

**这就是"不够智能"的确切位置：选敌只用了直线距离，没有考虑"这条路走不走得通"。**

### §5.5.2 实现思路（三层，可独立上也可叠加）

#### 第 1 层 ★ 选敌时加"可达性"判据（**推荐先做，收益最大**）

**目标**：不要选"直线最近"的敌人，要选**"沿着它的方向能不能走过去"**的敌人。

**做法**：在 `_team_select_target` 的候选打分里，从
```
score = 直线距离²
```
改成
```
score = 直线距离² + 绕行惩罚
```
其中"绕行惩罚"用**射线是否被友军挡住**估算：

```
沿 (f.pos → candidate.pos) 方向做一次圆-射线扫掠（复用 _move_without_pushing 的
几何），若被某个存活友军挡住，惩罚 += BIG（或按被挡比例加权）。
```

★ 关键设计点：
- **不要新写一套几何**：`_move_without_pushing`（`:651`）里的
  `towards / discriminant / contact` 算的就是"沿这个方向第一个挡路人是谁"，
  应当**抽成 `static` 纯函数**（如 `_first_blocker_along(from, dir, bodies)`）
  给它两处共用 —— 符合项目"判定只留一处"的约定；
- **纯函数化后可直接写行为探针**，不必在探针里复刻几何（防止随生产漂移）；
- 惩罚要**分级**（挡住一半/完全挡住给不同权重），否则会出现"轻微遮挡就换目标"的抖动；
- ★ 必须**保持既有锁定语义**（`_select_target:721-729` 的 9.24 注释：锁定当前目标，
  只有死了/打不到/转阵营才重选）—— **只在"重选"那一刻应用新打分**，
  不要在每 tick 都重算，否则会回到"打着打着突然换目标"的老 bug。

**预期效果**：毒灵会主动去打侧后方的敌人（横偏 ≥20px 就够用），
而不是死磕正后方那个永远够不到的目标。

#### 第 2 层 前进方向：把"贴着队友蹭"改成"先横移到空档再前进"

**目标**：当它的目标确实被队友挡住时，**主动先横移**，而不是靠 `:691` 那个
"残余恰好为 0 才侧移"的分支。

**做法（两种，建议 A 优先）**：

| 选项 | 做法 | 风险 |
|---|---|---|
| **A 放宽侧移触发** | `:691` 的 `< 1e-6` 放宽为 `< 0.01`（或加"被截断比例"条件） | 小；但影响所有单位手感 |
| **B 显式绕行意图** | 检测到"连续 N tick 被同一 uid 挡住、且目标距离不再缩短"→ 设一个 `detour_side`（±1）持续横移，直到越过后清空 | 中；需新字段（**别进回放 frames**） |

**B 的伪代码思路**：
```
if 本 tick 位移 < 阈值 and 目标距离 - 上 tick 目标距离 < 阈值:
    detour_ticks += 1
    if detour_ticks > N (如 5):
        detour_side = 上次未用过的方向（用 uid 字典序定，保持确定性）
else:
    detour_ticks = 0
    detour_side = 0
# 有 detour_side 时，位移方向 = 原方向 + detour_side * 横向分量
```

★ **确定性**：`detour_side` 必须由**稳定输入**（uid 字典序）决定，不能用随机或
"当前帧的浮点误差"，否则回放会漂移。

#### 第 3 层 目标可达性缓存（性能 + 稳定性）

若第 1 层的射线检查放在每 tick 每候选上，会放大开销。
建议**只在"重选目标"时算一次**（重选本来就低频），并缓存到该单位字段。
★ 缓存字段同样**不进回放 frames**。

### §5.5.3 与"等队友死亡再上前"的关系

用户提到"呆在原地等待队友死亡再上前"。这与探针读数一致：
- 队友（前排队友）先到达射程边缘停下，毒灵继续往前挤；
- 只有当**前方队友死亡**（不再占用碰撞圆）时，毒灵才能真正前压。

所以本方案的三层里，**第 1 层（选可达的敌人）收益最大且风险最低** ——
它让毒灵**不必等队友死**就能参战，直接命中用户诉求。

### §5.5.4 建议的实施与验收顺序

1. **先做第 1 层**（选敌加可达性），因为它：不收改动所有单位手感、
   直击"够不到"、且能被探针量化验收（攻击次数 20 → 69 的对照）；
2. 第 1 层验收通过后，再评估是否还需要第 2 层（若实际观感"还是会卡"再加）；
3. 第 3 层是性能优化，可最后做。

★ **每一层都必须"先红后绿"**：改之前先用探针记下现状读数（本节的 20 次/240 伤害、
`l3_picked_uid=e_front`），改完之后断言这些值必须变化到预期区间。
★ **不要一次上三层** —— 无法归因是哪层起的作用。

### §5.5.5 一个必须澄清的设计问题

"选可达的敌人"会改变**战斗结果**（毒灵会去打别的敌人）。
这可能影响：
- 集火效率（大家都去打"可达"的，可能分散火力）；
- 冥界执行者等**已有选敌特化**的单位（`death_hunt` 走 `prefer_low_hp`，
  `_team_select_target:804-805`）—— 新打分**不能覆盖**这些既有特化，
  只能是"在同等特化条件下的次级排序"。

★ **这一点需要你拍板**：是"只给近战被挡的单位用"，还是"全体通用"。
我的建议是**只对"目标被友军挡住"的单位启用**（其余单位维持现有 `最近` 逻辑），
这样集火行为不变、改动面最小。

## §6 门禁设计（改代码时必须同时补）

### 6.1 要钉住的行为（★ 本节的断言必须来自 §2.5 的真因，不是旧诊断）

- **同速队友可被绕开**：给定"正前方 1 只**同速**队友 + 后方敌人"，改完后毒灵必须
  `passed_ally == true` **且** `final_d_foe <= 射程 + EPS`。
  ★ 这是**先红后绿**的核心断言：**改之前它必然红**（探针 H `front0_reached_range`
  在 `d=32.7` 边界、`passed_ally=false`），所以有区分力。
- **速度关系敏感性**（探针 J 的场景固化）：队友 40px/s 时 `passed=true`、
  同速 165 时改完后也应 `passed=true`（现状是 `false`）。
- **未回归**：单人无阻挡时"从起点到射程"的 tick 数不得变长（防止放宽阈值后
  出现抖动反而更慢）。基线：探针 F 的 `b3_first_damage=8`。
- **有/无队友的输出差**不得反转（探针 E 的 594 vs 1155 作为量级参照，
  但注意这条**当时测的是"已在射程内"的场景**，不能直接当"够不到"场景的判据）。

### 6.1.1 ★★ 断言类型必须齐全（照 working memory 的教训）

| 类型 | 断言什么 | 为什么不能省 |
|---|---|---|
| **行为** | `passed_ally`、`final_d_foe`、`first_reach_tick` | 证明"真的绕过去了" |
| **结构** | 侧移分支的**调用点仍在场**（用注释感知的 `has_live_code()`，且要连 `static func` 一起认） | 行为断言看不见"谁调用它"；只注释掉调用行时行为断言可能仍绿 |
| **反向** | 不得新增 lane 约束 / 不得改回放 `frames` 列数 | 防止"顺手加约束"把玩法锁死 |

★ 纯函数优先：把侧移判定抽成 **`static` 纯函数**（如 `_sidestep_side()`）让探针直调，
避免在探针里复刻一份逻辑（会随生产漂移）。

### 6.2 结构断言

- `_move_without_pushing` 的侧移分支必须仍然存在（`Head-on blockers` 注释在场）；
- 若做 A/B，改动必须落在**同一函数**，且 `f.pos` 的 clamp **仍只有竞技场外框**
  （与 9.27 隔断调查的 `no_lane_bounds_in_simulator` 断言呼应，别顺手加 lane 约束）。

## §10 结论

**（9.27 第二轮订正版 —— 以本节为准）**

**你描述的机制是成立的**，而且你对视频的观察（"前面没走上去、敌人没中毒标记"）
**完全正确** —— 第一轮我判"不成立"是错的，原因见 §2.6（初始距离设得太近）。

**真正的根因（§2.5）**：

> 毒灵与前方队友**移动速度相同**（各 16.5px/tick），队友始终位于它与敌人的连线上。
> `_step_team` 每 tick 位移被 `min(speed*TICK, dist - attack_distance)` 截断，
> 同速 ⇒ 位移相同 ⇒ **相对距离恒定** ⇒ 它永远贴着队友后背，
> 直到队友先停在射程边缘（`ally_y=325`），毒灵才停在 `d≈32.7`，
> **刚好差一点点进不去近战射程（32）**，于是打不出毒、敌人身上也不亮中毒标记。

**决定性证据**（探针 J 速度差实验，§2.4.5）：

| 队友速度 | 毒灵能否越过 | 最终距敌 |
|---|---|---|
| 40px/s（慢） | **能**（`passed=true`） | `30.1`（**进射程**）|
| 165px/s（同速） | 不能 | `32.7`（临界，够不到）|
| 330px/s（快） | 不能 | `33.4`（更够不到）|

**这不是"抢了同一个目标"**（§0 的 `same_*` 读数已证伪：同目标时它照样推进 84px、
照样打出伤害），**也不是"被碰撞体积钉住"**，而是**同速并行造成的几何锁死**。

**修复建议 —— 两个版本，以第二个为准：**

### 版本一（§5，纯"运动"层）

- **方案 A**：把 `_move_without_pushing:691` 的侧移触发条件
  从"残余恰好为 0"放宽为"被截断即可侧移"；
- **方案 B**：加"侧移方向记忆"字段，持续朝同一侧绕；
- **方案 D（不建议）**：给毒灵单独加特判 —— 违反"判定只留一处"约定。

### 版本二（§5.5，★ **用户追加需求，推荐以此为准**）

用户要求"**更智能地选敌 + 绕路**，而不是原地等队友死"。探针 L **已验证可行且杠杆极大**：

| 敌人横偏 | 攻击次数 | 伤害 |
|---|---|---|
| **0px（正后方）** | 20 | 240 |
| **≥20px** | **69** | **满血秒杀** |

**而现有选敌逻辑只按直线距离打分**（`_team_select_target` 用 `distance_squared_to`），
必然选中正后方那个永远够不到的目标（`l3_picked_uid=e_front`，290 vs 297.3）。

**→ 推荐做法（§5.5 第 1 层）**：在选敌打分里加"可达性惩罚" ——
沿"单位→候选"方向做一次圆-射线扫掠（**复用 `_move_without_pushing` 的几何，
抽成共用的 `static` 纯函数，不要写第二套**），被友军挡住就加惩罚。
只在**重选目标那一刻**应用（保持 9.24 的锁定语义，避免"打着打着突然换目标"回潮）。

**这个方案的好处**：
1. **不需要让毒灵穿过队友** —— 它只要去打侧后方就能参战；
2. 直击用户"不要原地等队友死"的诉求；
3. 可被探针量化验收（20 → 69 的对照，先红后绿）；
4. 若限定为"只对目标被挡的单位启用"，则**不减所有单位手感**。

**未修，等你通知。** 需你先拍板 §5.5.5 的设计问题（只给被挡单位用 / 全体通用）。
