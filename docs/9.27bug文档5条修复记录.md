## §1 末日守卫：技能目标加星级上限 + 文案

**需求**：技能目标不得为高于自身星级的棋子；技能说明改为
「连接最近非Boss，非唯一棋子且星级不高于自身的敌人」。

**做法**：`_link_targets_without_doom()` 在既有的三类排除（末日守卫自己 / 唯一棋子 / Boss 与法阵 Boss）
之外，再加一条「星级不高于施法者」：

```gdscript
var caster_star := maxi(1, int(caster.get("star", 1)))
...
if maxi(1, int(o.get("star", 1))) > caster_star:
    continue
```

`maxi(1, ...)` 是**两处都取**：`star` 缺失时按 1 星算，不能让「没写 star」变成「0 星 → 谁都不能连」。

**文案**：`UnitDetailFormat` 的 zh/en 同步改成需求原句（en 侧补 "whose star is no higher than your own"）。
既有 4 星回血句一字未动。

**判据**：`probe_blood_link_boss_immune_925` 新增 Part 6（6a–6i，9 项），覆盖
「同级可连 / 高一级不可连 / star 缺失退化 / 施法者自身 star 缺失」。

## §2 房间邀请好友（新功能）

**需求原文 5 点**：
(1) 点朋友 ID 后亮一下，表示点击成功；
(2) 被邀请人在聊天「朋友消息」里收到邀请，有新消息音效 + 红点；
(3) 邀请是一个框，文案「我开启了新的房间，一起来玩吧」，右下角按钮「立即参与」；
(4) 同一邀请人同一房间只发一次；同一邀请人不同房间的邀请间隔 10 秒；
(5) 被邀请人离开 / 房间解散 / 对局已开始 / 过去 20 分钟 → 邀请失效，
失效后点「立即参与」在中上方提示「邀请已过时」（格式同「上阵棋子数目少于 7」）。

### 🔴 关键设计决定：邀请 = 一条**带类型的私聊**

要求 (2) 说邀请出现在「聊天功能朋友消息里」，还要音效与红点。
把邀请做成 `kind="room_invite"` 的私聊（payload `{"room_id": N}`），这三件事**全部白拿**：
发送走已经验过的 HTTPS，推送走 ② WebSocket 的 `dm` 分支，红点与音效在 `ChatService._on_dm_push`
（`CUE_CHAT_ALERT`）。**没有新开推送类型**——新类型只会多一套要单独维护的红点/音效通路，
而每一处漏掉都表现为「有时收不到」这种最难复现的 bug。

代价是给 `chat_messages` 加两列（`kind` / `payload`）：`database/020_room_invite.sql`，
按 `database/README.md` 代价表属 🟢（加列、带默认值、不改既有列含义）。

### 唯一的判据源：`scripts/multiplayer/RoomInvite.gd`

纯 static 函数，不碰界面/网络/autoload —— 门禁才能**直接驱动这一份实现**（不在探针里复刻）。

- `make_payload` / `is_invite` / `room_id_of` / `display_text`：payload 的**唯一拼法**。
- `is_expired(payload_room_id, created_sec, now_sec, inviter_room_id, room_started)`：
  要求 (5) 的**四个条件都在这里判**，不在界面里散着写。
- `send_blocked_reason(now_sec, last_sent_sec, same_room_already_sent)`：
  要求 (4) 的两条限流。

### 两处容易写反、且写反了不报错的地方

1. **「查不到」≠「不在房间」**。`inviter_room_id` 用三个值：
   `UNKNOWN_ROOM(-1)` = 查不到（好友列表请求失败）→ **放过**；
   `0` = 确定不在任何房间 → **判失效**（要求 (5) 第一种情况）；
   `>0` = 必须等于邀请里的房间号。
   混成一个 0 的后果是：要么网络抖一下就把正常邀请误杀成「已过时」，
   要么漏掉「邀请人已离房」——两种都不报错。门禁 `unknown_room_sentinel` +
   `expired_left_all` / `unknown_inviter_ok` 三条一起钉住它。
2. **文案只有一处拼法**。`我开启了新的房间，一起来玩吧` 与 `邀请已过时` 只许出现在
   `RoomInvite.gd`。门禁按**注释感知**扫描 `res://scripts` + `res://scenes` 全目录
   （注释里提到不算，真在代码里拼第二份才算）。

- 去重键 = (邀请人, 房间号, 收件人)。同一房间邀请**第二个好友要放行**，

## §3 重连后商店刷新费用变少

**根因**（详见 `docs/9.27商店刷新重连费用调查.md`）：服务端 `room_state` 广播里带的
`shop.refresh_uses` 是权威值，但 `NetworkService._apply_server_shop` 只覆盖了 `server_shop`，
**没有把刷新次数同步回客户端计数**。于是重连后客户端计数停在旧值（或 0），
而费用公式 `uses=0→0 / 1→10 / 2→20 / 3→40` 是递增的 —— 计数被压低 = 下一刷变便宜。

**做法**：`_apply_server_shop` 在有 `refresh_uses` 时同步
`GameState.shop_refresh_uses_this_round = maxi(0, int(...))`。
用 `has()` 守卫：回执（receipt）那条路径传的 shop **不带**这个键，
不加守卫会把计数打回 0 —— 那正是要修的 bug，反过来又造一个。

**判据**：`probe_shop_refresh_reconnect_927`（32 项）：费用曲线 → 唯一写入点盘点（结构）→
重连链逐点驱动 → 断言修复后客户端与服务端一致。

## §4 毒灵被队友挡住

**根因**（`docs/9.27毒灵被队友阻挡问题记录.md` 第二轮订正）：
毒灵 `range:1` → `range_px=32`，是近战。同速并排前进时与目标只差 `d≈32.7`，
**永远差一点进不了攻击距离**，于是「站着不动也不打」，看起来像卡住。

**做法**：选敌从「最近」改成**可达性感知**——用一条**圆的射线扫掠**
（`_first_contact`，class 级 static）判断「朝这个目标走，第一下会撞到谁」；
若第一下撞到的是**友军**，就把候选池换成该方向真正走得通的那一批再选。

**只对「目标被友军挡住」的单位启用**（用户口径）：没被挡住的单位行为一字不变。

★ 9.25 的教训在这里又踩了一次：`_tick_skills` 里的 `_skill_target_in_range`
会先于 `_step_team` 写 `locked_target_uid`，而它那条路径**一开始没带 bodies** →
「旧的最近目标」抢先锁住，端到端那两条一直红。把 `bodies` 一路穿到
`_skill_target_in_range` / `_step_team` 之后才通。

**判据**：`probe_poison_reach_927`（12 项，L5 纯射线 + L6 端到端 `l6_side_damage=900000`——
被挡的目标最后真的挨打了）。探针里 `_mk` 显式写 `f["lane"]`：`_fighter_from_def` **不设 lane**，
lane 是 `_place_in_lane` 写的，漏了这一列会让「可跨层」判据全部失真。

## §5 战场隔断越界

按 `docs/9.27战场隔断越界修复思路.md` 的推荐默认值做 **A+B+C 三层**：

- **A 层（单一真源）**：新增 `_lane_has_living_opponent(opponent_side, lane)`，
  `_can_target` 改为直接 return 它。玩法门禁、晶柱释放（`BattleArena._lane_cleared_by`）、
  宝物效果 1/4 全部**接同一个谓词**，不许各写一份。
- **B 层**：`_owner_lane_enemies_cleared` 从 `own_survivor` 口径换成
  「这条 lane 上是否**曾经**有过人」（`_lane_ever_occupied`），修掉「双方都空」时的误判。
- **C 层**：跨层技能（黑洞、低防后排瞬移、金币冲锋）不再看**全场**对手，
  改看 `_opponents_in_reachable_lanes(caster, opponents, state)` —— 只保留「施法者够得到的 lane」里的敌人。
  走位/推挤的软边界（C1）也接同一条可达性判定。

**为什么「修了 A 层还不够」**：A/B 只解决「门禁放不放行」，而玩家看到的那次越界是
**技能直接把单位搬到了打不到的 lane 后面**——那是 C 层的事。三层缺一层就还有一条肉眼可见的越界。

**判据**：`probe_lane_partition_927`（52 项）：单一真源委派（结构）+ 边界行为 α/β/γ/δ
（§13）+ 可跨层技能过滤（§14）。**M2 变异（把 Arena 退回 `own_survivor`）只有结构断言抓得住** ——
行为断言全绿。这正好印证了「行为断言 + 结构断言缺一不可」。

## §9 第二轮订正（2026-09-27 晚 · 用户回执）

用户带回 3 张图 + 4 个问题：

1. 点击朋友列表 ID 时**没有亮一下**；
2. **不需要**「你已经邀请过了」这个提示；
3. 被邀请方**收到两条**同邀请方同房间的邀请；
4. 邀请要**做成方框**（右下图里那条是纯文本），并且**缺了「立即参与」按钮**。

### 9.1 根因：客户端传了 `kind`，后端**根本没读**

这一轮真正的病因不在客户端判据，而在**后端一条从未打通的管道**。逐处列出：

| 处 | 文件 | 症状 | 为什么难发现 |
|---|---|---|---|
| a | `backend/app/routes/chat.py` → `SendBody` | **没有 `kind` / `payload` 两个字段** —— 客户端 `send_chat_message(kind, payload)` 传了也白传；`send_message` 也从不转发它们 | 请求体多出来的字段 pydantic 默认**忽略**，不报错 |
| b | `backend/app/chat.py` → `history()` | `select` 只取 `message_id, sender_id, body, created_at`，**把 `kind/payload` 丢在库里** | 收件人「重进聊天」走 history，拿到的是缺字段的版本 → 渲染成普通文本 |
| c | `backend/app/chat.py` → `send()` 的返回 | 末尾 `Message(message_id, sender_id, body, row["created_at"])` **没有 kind/payload** | HTTP 回包与 dm 推送都靠它 → 实时收到的那条也是普通文本 |
| d | `backend/app/chat.py` 顶部 | **没有 `import json`**，而 `_decode_payload` 用 `json.loads`、`send` 用 `json.dumps` | 只在**真有 payload** 时才触发 → 邀请一进库就 `NameError`（500），普通聊天永远碰不到 |

→ 这就同时解释了问题 3 与问题 4：**没有 kind** ⇒ 渲染成普通文本、没有按钮；
**后端去重没跑**（kind 不是 room_invite）⇒ 两条都落库、都推送。

客户端还有两处：

- e `Team3v3Lobby._on_invite_friend`：`_flash_row(row)` 排在 `send_blocked_reason` **之后**，
  于是「同一房间已经邀请过」时点了什么都不发生 —— 看起来跟没点到一样（问题 1 的实测原因）；
  而且 `send_blocked_text(blocked)` 会把 `duplicate` 也弹出来（问题 2）。
- f `ChatScreen._render_messages`：渲染前**没有任何去重** —— 库里已经有两条就显示两条（问题 3）。

### 9.2 逐条做法

- **(a)** `SendBody` 加 `kind: str = "text"` / `payload: dict | None = None`；
  `send_message` 先收敛 kind（不在 `_ALLOWED_KINDS` → 400 `chat_kind_invalid`），
  邀请再走 `_validated_invite_payload(body)`（房间号必须 int > 0），
  最后**转发**给 `chat.send(..., kind, payload)`。非邀请 kind 一律不带 payload（不让文本夹带任意字典进库）。
- **(b)(c)** `history()` 的 SQL 补 `kind, payload`，组装 `Message` 时用 `_decode_payload`；
  `send()` 末尾返回带上 `kind, payload`。
- **(d)** 补 `import json`。
- **(e)** 把 `_flash_row(row)` **提到限流判定之前**（点击必亮）；
  `duplicate` 改成**静默 return**（不再弹「已经邀请过了」）；服务端 `409`（`invite_duplicate`）同样静默；
  只有换房间的 `rate_limited` 保留提示（玩家需要知道为什么要等）。
  同时把亮度/时长从 `1.6×`/`0.28s` 提到 `2.6×`/`0.45s`（深色羊皮纸字乘 1.6 仍然偏暗，肉眼看不出来）。
- **(f)** `RoomInvite.dedupe_for_display(messages)`（纯 static）在渲染前把**同一 `room_id`** 的重复邀请
  收敛成一条、保留**最新**那条；`ChatScreen._render_messages` 调它。
  ★ 保留这一层的理由：后端去重只防未来的重复，**已经落库的旧两条不会被删** —— 显示层是唯一能收拾它们的；
  同时也是任一侧漏判时的兜底。
- **美化**：`_invite_bubble` 改成**金边方框**（`Tokens.panel_box(SURFACE_RAISED, GOLD, 14)`）+
  顶部小标题 `RoomInvite.title_text()`（「房间邀请」/「Room invite」）+ 底部一行「时间（右对齐，占满）+ 立即参与（右下角）」。

### 9.5 本轮**仍未**验的
