# GLory：给 Codex 执行的 3D 技能特效优化工作流

将本文件交给 Codex，再指定角色、技能或特效类别即可执行。目标是交付**符合真实技能、种族和战场风格，实际接入游戏且可复用的美术提升**。允许优化现有资源，也允许制作新文件替换旧表现。本文是普通 Markdown 执行说明，不需要先安装成 skill。

本文件中的项目入口于 **2026-10-02** 核对；代码、插件和工具版本以后必须现场复核。本文规定工作方法，不代表任何试点已经通过验收。

## 1. 同事怎样使用

在 GLory 仓库的 Codex 聊天中粘贴下面内容，至少填写“对象”；其他项可以省略，由执行者读取项目后提出明确默认值并继续工作。

```text
阅读并执行 docs/CODEX_VFX_WORKFLOW.md。

对象：<角色名称或 unit_id / skill_id / 某类特效，例如神族护盾>
范围：<仅技能 / 普攻及命中 / 完整角色 / 指定多个效果>
颜色：<保持种族风格；或指定白色、紫色、色号等>
方向：<更有空间感 / 更有力度 / 更清晰 / 参考图；可留空>
替换方式：<允许原地修改或新资源替换，保留可回退版本>
设备：<使用当前已连接手机；或指定设备>
限制：先用免费、开源工具，不改变玩法数值和目标规则。

请先读真实技能与正式播放链路，再实现、在 Godot 循环预览、
接入正式战斗并验证手机表现。交付前后对比、源文件、性能结果和可复现命令。
本次允许安装必要的免费工具/插件/skill/MCP，允许在指定测试设备运行；
如果已有授权覆盖所需操作，直接继续。不要自动提交、推送、发布或同步远端资源。
```

例一：“优化 `god_guard` 的 `guardian_shield_taunt`，白色为主，表现自身体积与周围嘲讽范围；先不改普攻。”

例二：“按本文件逐个优化神族远程普攻和命中；主色白，保留各角色区别。先完成一个样板，再复用到清单中的其他角色。”

例三：“优化黑洞技能，保持当前范围与吸引方向；这次执行者指定紫色，使用紫色取代默认种族主色，不改变技能机制。”

批量任务先建立 `unit_id / skill_id / 当前路由 / 新资源 / 状态 / 证据` 清单。每种独立效果各走一次完整流程，不能用第一个效果通过代替整批验收。

## 2. 执行前：读技能，确定视觉应当表达什么

### 2.1 核对工作区和执行边界

1. 找到同时包含 `.git`、`project.godot`、`effects/` 的根目录。本机通常是 `/Volumes/repository/github/GLory/GLory-v1.0`；外层 `GLory` 是交付容器，同事机器路径可以不同。
2. 阅读生效的 `AGENTS.md`，执行 `git status --short`、`git diff --stat`，记录开始时已有改动。保留其他人的资源、代码和未提交工作；不要使用全局 reset/clean 或批量覆盖。
3. 检查实际 Godot 二进制 `--version`、`project.godot`、导出预设和插件。当前配置声明 Godot 4.7、默认 Mobile，手机平台覆盖为 `gl_compatibility`；这些只是当前线索，运行日志与目标设备实际渲染器才是验收依据。
4. 简短说明本次对象、将改哪些路径、测试方式，然后执行已授权的本地制作、预览和修复。只有真正缺少必要输入或授权时才询问；不要为每次可回退编辑反复确认。

### 2.2 从名字追到逻辑，再追到画面

从以下入口按需查找，不要一次读取整个仓库：

| 要查的问题 | 当前入口（相对 Git/Godot 根目录） |
|---|---|
| 角色 ID、种族、技能 ID、星级参数、模型 | `data/units/race_units.json`；佣兵、怪物另查 `data/mercenary/`、`data/pve/` |
| 实际生效条件、选人、范围、持续状态 | `scripts/battle/BattleSimulator.gd`、`BattleSimSkills.gd`、`BattleSimShared.gd` 及它们调用的服务 |
| 战斗事件如何触发视觉、数据怎么传入 | `scenes/battle/BattleVfx.gd` |
| 世界坐标、模型缩放、挂点与镜头 | `scenes/battle/BattleRenderer.gd`、`BattleArena.gd` |
| 正式技能分发与组合 | `effects/BossProceduralVFX3D.gd`、`effects/vfx3d/units/UnitSkillVFXComposer3D.gd` |
| 图集/组合覆盖路由 | `effects/vfx3d/units/OgaSkillVFXCatalog.gd`、`OgaChessVFXCatalog.gd`、`effects/vfx3d/modules/` |
| 参数、预算、回收 | `effects/vfx3d/core/VFXProfile3D.gd`、`VFXQualityBudget.gd`、`effects/vfx3d/VFXBlockRoot.gd` |
| 已有贴图和材质 | `assets/vfx/`、`effects/vfx3d/profiles/`、`effects/SkillVFXConfig.gd` |
| 已有组合参考、视觉约束 | `docs/VFX_COMBINATION_LIBRARY.md`、`data/qa/non_ui_visual_freeze_policy.json`（使用前读适用范围） |

建议先用 `rg -n '角色名|unit_id|skill_id' data scripts/battle scenes/battle effects`。名称不唯一时显示找到的真实 ID 与技能；有足够上下文可明确说明合理假设并继续无歧义工作。若候选对应治疗、伤害等不同玩法，不能默默选错对象。

**当前命名提醒：** `god_priest` 名为“神侍”，技能是 `lowest_ally_heal`；`god_guard` 名为“光之卫士”，技能是 `guardian_shield_taunt`。“神侍卫”不是当前数据中的精确名称，应先对照这两个对象。

### 2.3 写一张技能约束卡，再开始改美术

把约束卡放进本次交付记录，填写来源文件与符号/行号：

```text
角色 / unit_id / race / skill_id / 星级：
触发：开场、普攻第几次、冷却释放、受击、死亡、状态变化……
作用对象：自己、单个友军、单个敌人、范围内多个目标……
空间：中心、形状、半径/长度、方向、挂点、坐标转换、是否跟随：
时序：触发帧、伤害/治疗/控制生效时刻、状态结束条件：
颜色：执行者明确指定 > 本技能现有明确设计 > 种族规则：
战场：相机、地面颜色、透明视口、角色尺寸、遮挡关系：
可改变：贴图、材质、几何、层次、粒子、表现阶段、艺术细节：
保持：伤害、治疗、冷却、范围判定、目标规则、同步/回放逻辑：
正式播放链路与即将修改的实际命中分支：
```

以下约束始终成立：

- 范围技能用正确中心与范围形状表达；单体技能不能做成看似全场生效的大爆炸。范围装饰不能伪装成另一个伤害判定圈。
- 神族默认白色主视觉，可以有少量现有设计允许的暖金边缘；不能直接套用工具示例中的蓝紫、毒绿。其他种族先读本项目资料，不凭印象发明颜色。
- 执行者指定颜色时覆盖默认配色，并记录覆盖；只改视觉，不顺便修改种族、元素或伤害属性。白色效果仍需要亮暗与透明度层次，不能将所有层同时拉到纯白过曝。
- 读取实际技能机制，不从技能名字臆测。以 `god_guard` 为例，当前代码是开场获得护盾并激活周围嘲讽，常规/四星的护盾比例、嘲讽半径不同；不应擅自改造成周期伤害爆炸。
- 状态表现随真实状态结束、目标死亡或换场清理；不要拿固定 1 秒的动画当成所有持续状态的寿命。瞬间释放动画可以有独立短尾，但不能暗示状态已结束或仍有效。
- 数据里的距离不一定是 Godot 米。使用 `BattleRenderer`/`BattleVfx` 的实际映射和锚点验证半径、朝向、脚底与身体高度。

## 3. 免费工具如何选与安装

先选足以解决本次缺陷的工具，再制作；无需把全部工具装一遍。以下来源是候选清单，版本、许可证原文、素材附带许可要在引入时重新记录。

| 工具与官方来源 | 用在什么地方 | 引入要求 |
|---|---|---|
| [Godot 原生](https://github.com/godotengine/godot)（MIT） | 网格护盾、环形范围、刀光、Shader、动画、少量粒子 | 优先复用本项目模块；原生方案也必须经过真实画面比较 |
| [Brackeys VFX 示例](https://github.com/Brackeys/vfx-in-godot)（CC0） | 学习、拆解并复用已完成的粒子层次和素材，改善爆发与命中 | 示例工程声明 Godot 4.6 / Forward+；只迁移选中的效果与依赖，再适配实际角色、配色与手机渲染器，不整体覆盖项目 |
| [Brackeys Particle Controls](https://github.com/Brackeys/brackeys-particle-controls)（MIT） | 在编辑器播放、暂停、拖动粒子时间，联看多个粒子节点 | 需要反复调粒子时再装；官方列出的测试版本为 4.4.1。它是预览辅助，不生成美术，也不证明真实技能事件已接通 |
| [Effekseer](https://github.com/effekseer/Effekseer) / [Godot 4 插件](https://github.com/effekseer/EffekseerForGodot4)（主体 MIT，另查工具/依赖许可） | 多阶段爆发、火焰、光束、复杂技能组合 | 项目已有 `addons/effekseer`，先核对版本与平台库，避免重复安装；保留 `.efkproj` 与运行资源、依赖；检查透明背景和导出包 |
| [VFEZ-godot](https://github.com/alexnikop/VFEZ-godot)（MIT） | 护盾边缘、UV 流动、溶解、网格材质 | 先在隔离示例中验证 3D 材质，再复制需要的文件；作者列出的测试版本为 4.3/4.4，不能据此宣称本项目版本与手机兼容 |
| [Energy Shield](https://github.com/nojoule/energy-shield)（MIT） | 球面/平面护盾、受击波纹、建立与崩解 | 仅在护盾任务中选用。示例声明 Godot 4.5 / Forward+；有 `examples-web.tscn`，仍须实测本项目 Compatibility、深度交界与透明 SubViewport。受击演示要绑定真实受击事件 |
| [Material Maker](https://github.com/RodZill4/material-maker)（默认 MIT，例外文件另查） | 制作噪声/侵蚀纹理、动态 Unlit 材质，或烘焙动画序列帧/图集 | 保留节点工程；流动/溶解需要参数实时控制时选 Shader，计算复杂且视角允许时选烘焙图集；检查导出 Shader 的渲染器支持、图集帧序和内存 |
| [RPicster VFX 贴图库](https://github.com/RPicster/Godot-particle-and-vfx-textures)（CC0-1.0） | 火花、光晕、光束和冲击纹理 | 选必要纹理并保留来源；旧演示工程不等于当前 Godot 兼容证明 |

具体选择：粒子爆发先看 Brackeys 示例，反复调时序可配 Particle Controls；网格护盾在原生 Shader、VFEZ、Energy Shield 中选一个合适方案；需要新纹理/动态材质时用 Material Maker；多阶段复杂组合再考虑 Effekseer。**免费 Godot 原生制作完全允许**，但须交付足够的材质、形状和时序质量，不能只放一个无细节的占位光圈。

Material Maker 不限于静态贴图：官方说明动态 Unlit 可导出 Shader，2D 预览可导出动画图片序列或 spritesheet；[Unlit 节点文档](https://rodzill4.github.io/material-maker/doc/node_material_unlit.html)说明可导出 Godot 材质，[官方发布页](https://rodzilla.itch.io/material-maker)提供免费取得方式。选择这两种输出时都不需要把制作软件整体带入游戏。

需要其他免费工具、插件、skill 或 MCP 时，可以在本次授权范围内安装。安装前做四件事：说明其解决的具体缺口；检查官方来源和许可证；确认当前环境/渲染器/导出平台支持；记录版本或 commit、安装路径与移除方式。先检查本机已有能力，优先项目局部安装。

不要把“仓库能看源码”“免费下载 Demo”“插件 MIT”自动解释成所有编辑器与素材都免费商用。当前任务不采用付费 EffectBlocks、Pixelpart 专业版或付费素材；免费预览包也须单独满足其使用许可。通用 AI skill 只辅助代码，不能替代视觉验收。

不为安装工具上传本项目源码、签名文件、账号信息或私有素材到第三方服务。遇到收费、账号登录或平台库缺失，先使用已有免费本地路径继续能做的部分，明确记录受限项。

每次引入外部资源记录：来源 URL、作者、许可证文件、版本/commit、原文件、修改内容、游戏内位置、是否进入最终包。MIT 保留版权与许可声明；具体素材如有独立许可按其实际条件处理。

## 4. 制作：先把主效果做好，再控制成本

### 4.1 先留可比基线

录制或截取修改前的起手、峰值、消散，并保存镜头、分辨率、画质档、单位/星级、参数、随机种子、代码版本。使用真实角色模型和实际战斗视角；只有工具官方演示不构成本项目基线。

先写清原效果 2～4 个具体问题，例如：“没有自身体积”“看不出范围”“贴片黑边”“峰值同时过亮”“低档完全看不见”。不要仅把增加粒子、换贴图或提高发光当作优化目标。

### 4.2 组织层次和空间

将所需阶段拆为“预备/建立 → 释放/生效 → 持续（若存在）→ 消散”，按真实触发对齐。被动开场技能不必生造蓄力；伤害/治疗帧不能为了演出延后。

一个普通技能先用清楚的主体轮廓、辅助范围/方向提示、少量点缀构成。优先改善形状、节奏、空间关系和材质细节，再增加粒子密度。护盾、环绕和连接线保留 3D 关系；烟雾、瞬间闪光适合序列帧。不能为了方便将所有东西压成面向镜头的一张平面。

检查地面贴层 Z-fighting、透明排序、黑底矩形、裁切、UV 接缝、朝向、角色遮挡、边缘抗锯齿，以及无 Bloom 时能否成立。低档保留主轮廓、技能语义、范围/状态提示。

### 4.3 选择改动方式并接入真正的路由

- **原地优化：** 当前结构正确、只是材质或层次欠佳时，修改局部资源和参数。共享材质使用独立实例/运行副本，避免改一个角色影响全部种族。
- **新文件替换：** 当前资源不适合空间关系或维护时，新增命名明确的模块/场景/配置，在正式分发分支切换引用。保留旧版在 Git 基线或隔离参考中，不把新旧主效果重复叠播。
- 在报告列出“正式事件 → 分发分支 → 实际模块/场景 → 素材”。检查前置目录命中、提前 `return`、旧的纹理层与状态层；修改一个没有被调用的同名旧函数不算接入。
- 使用真实 `source_unit_id`、`origin_node`、`target_node`、高度、状态时长、范围等上下文。预览中补齐的字段也必须在正式链路存在；缺少时只补表现数据传递，不改玩法规则。
- 对逐目标效果，追溯“哪个施法者、哪次技能、哪几个目标”的权威记录，并检查数据是否经过联机回放序列化。不能把同帧所有敌方掉血、所有存活敌人或最近敌人直接当成该技能目标。现有上下文若只是近似推断，记录缺口并补准确的表现数据；不要为了套效果扩大判定范围或改变选人。
- 资源导入、释放、异步回调、场景切换均不能报错。遵守现有 `VFXBlockRoot` 的生命周期、并发计数和预热约定，不通过绕过预算让节点无限累积。

## 5. 性能：有表现、可并发、能降档

画面质量优先：先建立一个能明显改善原效果的样板，再测量成本并调整。禁止为了跑分把主体删掉，也禁止用数百层透明面或海量粒子堆出效果。

### 5.1 起始预算（不是设备性能结论）

复用 `VFXQualityBudget`。当前代码的单效果粒子上限低/中/高为 **48/96/160**、并发效果数量为 **18/30/48**；这些是现有管理接口，执行前复核，并检查目标模块是否真的接入。不能将“每个发射器没超过上限”当作整个技能合规：一个技能所有发射器、子效果与爆发重叠的存活粒子必须合计。

| 项目 | 普通技能的建议起点 | 调整原则 |
|---|---|---|
| 同时存活点缀粒子 | 低 12～24 / 中 24～48 / 高 48～80 | 依据轮廓、粒子大小和寿命调节；纯网格效果允许 0 粒子 |
| 主体层 | 通常 1～3 个有明确职责的层 | 数量少但轮廓和材质要完整，避免相同层重复增亮 |
| 辅助透明层 | 按现有质量接口控制，移动端先尽量少 | 优先缩小透明覆盖面积；大面积叠层常比粒子数量更贵 |
| 纹理 | 小粒子优先 64～256；主体按屏幕尺寸选 256～512 起步 | 大图集须计算解压内存与 mipmap，禁止只看 PNG 文件大小 |
| 动态灯/扭曲 | 可不用则不用，低档通常关闭装饰项 | 不依赖设备不支持的特性；移动端无此特性时主视觉仍完整 |

复杂大招可以超过普通起点，但需要写明层次理由、全技能峰值成本、并发和真机数据。不要全局抬高预算去容纳某一个技能。

低/中/高共用颜色、范围、核心时序与识别轮廓；削减顺序通常是次要火花 → 远离主体的拖尾 → 重复烟雾/透明覆盖 → 装饰灯和扭曲。关键控制、护盾状态和范围提示不能被预算静默吞掉。群体装饰可以减少重复爆点，真实命中/状态与范围表达仍应完整。

### 5.2 用同场景前后数据判断

1. 固定设备、分辨率、质量档、战斗阵容、相机与可复现操作，先测旧版，再测新版。记录设备型号、系统、GPU（可获取时）、渲染器和包哈希。
2. 分别测试单次、典型多单位同时施放、预期最大并发。短采样每组建议 30～60 秒；连续重放至少 3 分钟检查积累与温升趋势。持续状态另覆盖提前死亡、移动、目标消失、退出场景。
3. 记录帧时间中位数、p95、明显长帧次数、峰值存活特效/粒子、draw calls（可获取时）、内存和资源清理。平均 FPS 不能单独证明不卡；离线固定帧截图速度也不是运行性能。
4. 先确认项目/设备实际采用 30 还是 60 FPS，再使用相应每帧预算 33.3/16.7 ms。将相同场景 p95 增长超过 10%、重复出现 >100 ms 长帧、稳定帧率跨档下降或存活节点持续增长作为需要调查的触发线；它们是本流程的起始门槛，不是已经实测的结果。
5. 若原场景已超预算，明确旧问题与新增开销，先减透明过绘、合批/复用材质、共享纹理、预热和回收，再调粒子。保持能看见的主体。达不到视觉和性能两项时，继续迭代或保留旧正式版本，将候选标记为未通过。

Compatibility 与其他渲染器支持不同。依据当前 Godot 官方文档与实测选择粒子/Shader 功能，不把桌面上的拖尾、深度采样、扭曲或发光默认移植成功：[渲染器差异](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)、[粒子拖尾](https://docs.godotengine.org/en/stable/tutorials/3d/particles/trails.html)。

## 6. 必须实际预览与验证

### 6.1 先查错，再看真实画面

对本次改动做 Godot 导入/脚本解析与必要的生命周期、路由回归，运行 `git diff --check`。优先复用 `tools/vfx_timer_lifetime_check.gd`、`tools/battle_vfx_preload_check.gd`、`tools/vfx_warmup_check.gd` 等现有工具；**先读脚本确认覆盖目标与调用方式**，不把无关全绿当作本技能验证。

用 Godot 编辑器打开目标 `.tscn` 并运行循环预览。循环间隔覆盖完整寿命并留观察间隔；提供重新播放、暂停、质量档选择，必要时加旧/新切换。持续技能展示建立、保持、移动、破盾/死亡/退出等场景，不能只重播开场闪光。

当前 `effects/preview/VFXPreview.tscn` 主要走旧 `Node2D` 效果注册表，不足以验收本任务的 3D 技能。优先使用已有 3D 截帧工具或制作小型专用 3D 预览场景；正式主场景入口保持原样。独立预览场景只能作为视觉迭代证据，仍要进入实际战斗验证事件链。

### 6.2 使用现有 3D 截帧工具

阅读 `tools/README_vfx_capture.md` 和 `tools/vfx_capture.gd`。该工具调用 `BossProceduralVFX3D`，支持真实角色和画质档；固定随机种子便于前后对比。先确认目标技能正式链路确实经过这个组合器；若正式事件已改走独立持续模块，这个工具可能截到旧分支，不能把结果标为正式效果。它不运行完整战斗逻辑，默认每技能 2 秒，不能覆盖所有持续状态/范围上下文。

单技能截图命令示例（先填写本机变量；不要给图像捕获加 `--headless`）：

```bash
VFX_PROJECT="/本机路径/GLory-v1.0"
VFX_GODOT="/本机路径/Godot可执行文件"
VFX_OUT="/本机路径/delivery/vfx-dark-dragon/before"
mkdir -p "$VFX_OUT"
"$VFX_GODOT" --path "$VFX_PROJECT" --rendering-method gl_compatibility \
  --script res://tools/vfx_capture.gd \
  --write-movie "$VFX_OUT/frame.png" --fixed-fps 12 --quit-after 34 \
  -- --out "$VFX_OUT" --skills black_hole --unit dark_dragon \
  --owners black_hole=dark_dragon --tier medium
```

此例选择当前走该组合器的黑龙；换其他技能时同时替换技能和真实角色 ID，并重新查路由。`34` 来源于当前脚本的 6 帧预热 + 24 帧技能 + 4 帧尾段；脚本变化时重新计算。修改后用相同条件输出到 `after`，保存完整日志与 manifest；`--out` 决定 manifest 目录，`--write-movie` 决定截图目录，两者必须对应。`vfx_diff.py` 只能证明像素变化或疑似空表现，不能证明更美观、机制正确或手机性能达标。

### 6.3 正式战斗和手机

至少在正式战斗确认：真实事件触发新效果、源/目标正确、范围与坐标正确、伤害/治疗/控制时刻匹配、低档仍清楚、多个角色同屏可辨、结束后无残留。使用 `scripts/qa/FixedBattleFixture.gd` 等已有固定阵容能力前先确认适用流程；不得为演示改变线上玩法参数。

形成三项相互对应的证据：实际战斗中的施放/状态事件与单位 ID、由该事件创建的新节点/资源、同一时刻的游戏画面。可使用短期定向日志或运行时节点检查，记录后移除无用调试输出。联机游戏还要走实际回放路径，确认必要字段能传到客户端。仅手动调用 `.play()` 的专用 Demo、给测试场景直接注入模拟上下文，或 grep 到一个引用，均不能代替此项。

手机已获授权时直接检测连接，Android 使用 `adb devices -l` 并指定序列号，iOS 使用当前可用的 Xcode/设备工具。工具能处理的普通“允许/确认”可在授权范围内操作；设备端锁屏、系统安全确认等无法代办时准确说明所需一步，同时继续本地独立工作。

先检查构建脚本参数再构建：`tools/workspace/build_apk.sh`、`tools/android_smoke.sh`、`tools/android_baseline.sh` 是现有入口。不要为了测本地特效默认加 `--sync`，否则远端同步可能改变本次源码。确认临时构建目录、包内资源、签名、版本和安装结果与本次代码对应；保留用户应用数据，不通过卸载重装消除问题。

实际录屏或截图证明新效果已在手机运行，性能使用正常实时运行采样。安装成功、进程存在、桌面预览、Mac 上通过都不能代替手机特效画面与性能。手机或打包受阻时写“桌面已验证 / 真机待验证”及精确原因，不写“全部完成”。

## 7. 交付、失败处理和批量复用

每个效果交付可编辑源文件、运行资源、正式路由改动、循环预览入口、许可记录，以及一份简洁报告。证据建议放在项目外层 `delivery/vfx-<unit或skill>-<日期>/`，避免大量截图/录屏被导入游戏资源。报告包含：

```text
对象与技能约束卡：
旧版问题 → 新版具体改善：
工具/版本/素材来源与许可证：
变更文件；旧正式路由 → 新正式路由；回退方法：
预览入口和可复制命令：
旧/新同视角起手、峰值、消散对比；完整循环录屏：
低/中/高画质与颜色；范围/单体/状态语义验证：
实际战斗证据与触发日志：
手机型号/系统/渲染器/包哈希；前后性能数据与采样方式：
错误检查、回收检查；未验证项与后续动作：
结论：通过 / 视觉候选待验收 / 真机待验证 / 退回修改：
```

完成标准逐项核对：

- [ ] 目标 ID 与技能逻辑有源码依据，颜色遵循指定要求，原玩法规则未改变。
- [ ] 单体/范围/方向/挂点/状态持续语义正确，新增画面解决了明确的旧版问题。
- [ ] 免费工具与素材来源、许可证可追溯；可编辑源文件齐全。
- [ ] Godot 编辑器中有可循环观察的 3D 预览，前后对比条件一致，画面无黑片/过曝/遮挡/残留缺陷。
- [ ] 正式战斗实际触发新资源，无旧新重复叠播、无共享资源误改其他角色。
- [ ] 低/中/高档均保留主视觉与玩法可读性，预算在代码里实际生效。
- [ ] 目标手机已展示本次效果并完成前后性能/并发检查；没有用其他平台数据代替。
- [ ] 解析、运行、资源导入和生命周期检查通过；证据足以复现，保留他人改动与回退路径。

不能只凭截图非空、像素变多、测试全绿或粒子数降低认定美术改善。执行者要亲自检查动态节奏与战斗视角，报告视觉选择的理由；用户/美术的审美反馈可能仍需下一轮迭代。

批处理先完成一个代表性样板，再提取可复用配置/模块/素材规则，按清单逐项推进。不要把同一种光圈统一替换所有技能。每个技能独立保留约束卡、正式路由与证据，公用模块改动应抽查其他受影响技能。

发生问题时优先修复根因并复测：资源缺失检查源文件、导入、引用和最终包；路由不命中检查分支；黑片/透明异常检查材质混合和视口；卡顿先查透明覆盖、Shader 编译、节点回收与共享资源。若候选仍不合格，保留可复现试验文件与失败记录，恢复**仅本次替换点**，继续改进，不提交一个“预览很好但游戏没用上”的完成结论。
