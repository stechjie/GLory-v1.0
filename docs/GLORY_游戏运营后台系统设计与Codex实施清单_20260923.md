## 1. 目标、版本基线与实施边界

后台要让运营人员无需写 SQL，就能安全地查玩家、封禁/解封、发钻石/金币、发邮件、发公告，并能回答“谁、因为什么、给谁、做了什么、是否真正生效、如何纠正”。

本方案依据本次拉取的 GitHub `origin/main = 9c440fe`，以及保留本地移动端字体修复后的合并提交 `72de47f`。代码已包含账号、商城、系统邮件、公告、语音、匹配、战报、排位与赛季实现；**代码存在不代表这些迁移已在生产执行，本轮未连接生产库验证。** 开工时重新确认最新提交与实际迁移状态，不能把本文版本号永久当作“最新”。

### 1.1 必须保持的边界

1. 后台管理的是账号级数据；不通过后台修改正在进行的战斗数值、随机种子、局内商店或战斗胜负。
2. 复用现有 FastAPI、PostgreSQL 与游戏服务；不另建第二套钱包、玩家 ID 或邮件领取系统。
3. 管理端浏览器不直连 Supabase 数据表，不持有 Supabase secret、数据库密码、战斗签名私钥、LiveKit 密钥。
4. 运营发放进入赠送钻石；充值、退款与运营补偿分账，不能混用。
5. 所有写入都要服务端鉴权、校验、幂等、审计；隐藏按钮不是权限控制。
6. 先完成安全基础和最小运营闭环，再扩展活动、支付、分析与多实例。
7. 本文中的新表、新 API、新文件名均为**拟新增**，除明确标注“已有”的部分外，不得声称已经实现。

## 4. 建议架构与目录

```text
运营浏览器（独立管理站点，不使用玩家令牌）
  → HTTPS / 管理员会话 / CSRF / 权限及环境校验
  → 现有 FastAPI 中隔离的 /admin/v1 路由
  → 管理命令、审批、审计、持久任务
  → 复用的钱包/邮件/公告/排位业务服务 → PostgreSQL
  → 事务内写 outbox → 单实例分发器
                     → 现有 WS / 匹配队列
                     → 新增的受认证战斗控制通道 → 战斗房间 / LiveKit
```

- 第一阶段建议在现有后端中增加隔离的管理路由，复用同一进程的实时 Hub；通过管理域名/代理访问策略限制入口，应用仍逐次鉴权。生产公网玩家入口默认不能访问管理路由。
- **不要再用 `uvicorn app.main:app` 起一份“后台实例”**：现有 `main.py` 会启动公告、邮件、赛季、匹配等循环，且有 `single_instance` 保护。不得为了后台方便关闭保护或直接把 workers 调大。
- 前端建议独立 `admin-web/`，采用团队熟悉的 TypeScript Web 管理栈；可用 React + Vite，已有 Vue 栈也可，只要 API/权限契约一致。技术选型不要求重写 Godot 或账号服务。
- 首版异步任务落 PostgreSQL，固定并发的 dispatcher/worker 在既有生命周期下启动；重型图片处理放线程/独立执行器，不能卡住承载全部 WS 的事件循环。将来分离 worker，必须使用专用入口，不能导入并运行玩家服务的全部 lifespan。
- 新能力建议目录：`backend/app/admin/{auth,permissions,operations,audit,players,sanctions,wallet,mail,announcements,jobs}.py`、`backend/app/routes/admin/`、`backend/tests/admin/`；共用业务逻辑需要提取时放共享 service，不让管理 API 复制钱包算法。
- 不需要本期搭建微服务、数据仓库或 Kubernetes。独立身份、事务和审计不可因规模小而省略。

## 5. 管理员身份、角色、审批与审计

### 5.1 身份与权限

使用组织的 OIDC/SSO + MFA，或经审核的成熟身份提供方；具体提供方由团队确认。开发可用隔离测试身份，生产无身份配置则拒绝启动管理入口。管理员名册通过受控引导流程创建，禁止公开注册、玩家改 metadata 获得管理员权限。

会话建议为服务端会话 + `HttpOnly/Secure/SameSite` Cookie；写请求校验 CSRF 与 Origin，CORS 精确白名单。高危动作要求近期 MFA/二次认证。签名/issuer/audience/到期校验、角色撤销和会话注销都在服务端，管理员权限变更后旧会话不能继续操作。不要把长寿命管理员令牌放 localStorage。

|角色|默认可做|默认不可做|
|---|---|---|
|只读分析员|聚合报表、脱敏运行指标|私聊正文、货币/处罚写入、原始个人资料导出|
|客服|按工单查玩家、查看必要流水、提出补偿/处罚申请|自己审批自己的操作、直接发钱、批量导出全量玩家|
|运营编辑|起草邮件/公告、测试预览、建立活动草案|直接群发奖励、修改钱包、管理管理员|
|运营审批人|复核指定环境与额度内的发布/发放/处罚|批准本人创建或本人修改的草稿、越额度执行|
|风控|处理举报、申请/执行批准的制裁、查看授权证据|充值入账、无理由浏览私聊|
|财务|钱包/订单对账、复核经济纠错；未来支付对账|改战斗胜负、替换历史流水|
|运维|服务状态、维护/限流配置、任务排障|无业务审批擅自发奖励；下载密钥到浏览器|
|管理员所有者|人员/角色配置和受控紧急通道|无痕操作、删除审计、绕过钱包事务|

角色只是权限集合；后端权限键还要绑定环境、动作、对象范围、数量/金额额度。例如 `wallet.grant.propose`、`wallet.grant.approve`、`sanction.create`、`announcement.publish`、`audit.read`、`pii.export`，不可只有一个 `is_admin=true`。

默认拒绝、最小权限和每次请求授权应作为代码门禁，而不是界面约定。[OWASP 授权指引](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

### 5.2 统一操作状态机

```text
draft → pending_approval → approved → scheduled/queued → running
                                                    → succeeded / partially_succeeded / failed
draft/pending/approved/scheduled → cancelled
pending_approval → rejected；批准内容变化/审批过期 → 重新审批
```

- P0 生产加钱、封禁/解封、全服邮件和紧急公告默认双人复核；阈值尚未定，不擅自设置“低于某金额免审批”。开发/测试可配置更简流程但必须保留审计，环境不能由请求任意选择连接串。
- 预览冻结目标 ID、内容版本、数量、时间窗、附件、名单 hash 和预算；审批绑定 `payload_hash/version`。改一个字节的奖励数量或换收件人，都使原批准失效。
- 提交执行时再次检查操作人/审批人权限与额度、目标状态、批准是否过期、资源是否合法。撤权后尚未执行的操作不得自动继续。
- 申请人与审批人不得为同一主体；worker 是技术执行者，不是绕过复核的第三位管理员。
- 预算按货币分别预留：单次、单收件人、单日管理员、活动累计、环境总量。拒绝未配置额度的生产发放，不以无限大兜底。
- 超时返回 `operation_id`，页面查原操作状态，不创建新请求“再试一次”。同一幂等键不同 payload 返回 409。
- 群发涉及未来新用户时无法提前固定总人数：P0 默认不允许带奖励的 `include_new_players=true`；需先有领取侧总预算/领取人数上限的原子预留机制再开放。仅在发送时算当前注册人数不够。
- 紧急通道只允许预定的保护性动作，如暂停发奖/撤下公告/停止新匹配；设短有效期、理由、告警、事后复核。不能用它跳过发钱审批。

审批需让操作者确认实际目标和数量，且确认内容不能在执行时被替换。[OWASP 交易授权指引](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)

### 5.3 审计记录

必填：`operation_id/request_id`、管理员稳定 ID、审批人、环境、动作、目标、理由码、工单号/证据引用、脱敏前后值、数量/币种、业务回执、UTC 时间、执行来源、错误码、幂等键。`actor` 由认证上下文生成，不接受浏览器自行填写的人名。

审计只追加；纠错另写关联原操作的补偿记录。管理角色无 update/delete 审计权限；高危数据成功写入与成功审计同事务，失败尝试另以安全事件记录。操作员不能通过关闭普通日志关闭审计。定期导出校验摘要/只读副本到独立存储，审计可用性异常时停止高危写操作。

不记录密码、访问/刷新令牌、购买凭证原文、签名私钥、数据库 URL。玩家个人信息、IP、举报证据最小化存储，访问与导出也留审计；保留周期由团队按实际市场与用途确认，不默认无限保存所有个人资料。

## 6. 玩家工作台与账号封禁

### 6.1 玩家详情页

搜索支持完整 `player_id`、精确好友码；昵称只返回候选，不能用昵称直接处罚或发钱。确认卡同时显示昵称、好友码、完整 UUID、环境、注册时间。输入错误/不存在明确报错，不自动创建玩家。

详情页分栏：概览、身份绑定（仅显示现有 provider 与脱敏标识）、钱包三分账、流水/订单、已拥有/已撤销权益、已发送/可领取邮件、战绩/赛季/信誉、处罚/申诉、审计时间线、客服工单。

“在线”来自实时连接状态并带采样时间；`last_seen_at` 不等于实时在线。当前没有的数据字段标注未采集，不捏造渠道、充值等级、设备指纹或归因信息。邮件可能是懒计算收件箱，不能仅查 `mail_states` 就说“从未收到”。

### 6.2 制裁类型与语义

|制裁|服务端影响|不能混淆的已有功能|
|---|---|---|
|账号封禁|禁止受保护账号玩法、匹配、发名片及受保护写操作；在线连接终止；保留申诉/封禁说明受限通道|不是删除账号，不是单纯让 JWT 刷新失败|
|匹配限制|可登录看公告/邮件/申诉，但禁止指定 casual/ranked；自定义房间是否限制需单独范围|不覆盖 `player_credit.banned_until`，保留系统信誉处罚独立生效|
|文字禁言|拦私聊及将来的公共频道服务端发送；保留必要只读/客服能力|玩家个人拉黑不等于运营禁言|
|语音禁言|禁止签发新语音令牌、移除或停止既有参与者发言；验证 LiveKit 端效果|只灰掉麦克风按钮无效|

字段：处罚 ID、player_id、类型、范围、开始/结束时间（永久使用 null，不用魔法年份）、理由码、对玩家公开文案、内部证据、申请/审批人、关联工单、撤销事件、策略版本。多个有效处罚合并取有效限制；撤销一条不应解除其他处罚，解封不重置信誉分。

### 6.3 封禁接线必须覆盖全部入口

1. 提取共用 `require_active_player/require_player_capability` 依赖，覆盖各 `routes/*` 中重复的 `_me` / `get_by_auth_uid` 解析，不只改 `/v1/me`。只验 JWT 不等于检查当前账号状态。
2. `routes/auth.py` 的登录/刷新响应与 `AccountManager.gd` 对接独立错误码 `account_banned`。保留受限凭证或封禁状态通道；**不能把封禁伪装为 401 后让客户端清 token 自动匿名注册**。
3. `routes/ws.py` 在 accept 前校验，建立连接后处理制裁变化；踢出旧连接同时清理 admission 名额及 matchmaking 排队/待确认分配。
4. `routes/matchmaking.py` 在入队、确认和最终分桌前再校验；封禁与匹配并发必须不会把已封号的人发进房间。
5. `loadout.issue_card()` 拒绝受限账号；名片离线验签不能获知新封禁，因此战斗服需新增受认证制裁快照/增量同步与准入检查，覆盖普通建房、加入自定义房间、匹配入房、断线重连和已有座位。
6. 通过新控制通道下发带 `command_id/policy_revision/expiry` 的撤权/踢出指令，战斗服回执并防重放。不得把现有房主踢人 RPC 当管理员通道，也不得让浏览器直接打 ENet。
7. 语音在 `NetworkService.voice_token_for_peer()` 等入口拒绝签发，结合 `LiveKitAdmin.remove_participant()` 做现有连接清理；房间/参与者标识由可信座位映射获取，不接受随意 room/identity。
8. 新处罚写库、版本递增和 outbox 同事务；通知可重试，数据库状态为权威。后台区分“已保存”“账号端已应用”“战斗服待回执/部分失败”，不得仅写表成功就显示“全链路生效”。

建议验收目标：健康网络下新 HTTP 请求立即拦截，在线连接/战斗服在 5 秒内收到并确认（目标值需压测确认）；超过目标自动告警。战斗服与制裁服务失联时拒绝新的受保护准入并返回可重试不可用错误，不把故障误报为玩家被封。已进行对局的断连、托管与结算沿既有规则，不靠后台篡改其他玩家结果。

匿名用户重建账号/换设备的规避不可能单靠 player_id 封禁彻底解决。设备/IP 风控作为后续策略，不自动扩大到整网段，也不采集硬件标识冒充已授权能力。离线单机行为不在在线封禁的可保证范围。

## 7. 钱包：加钻石、加金币、流水与纠错

### 7.1 两本账必须分开

|后台显示|真实字段|允许的运营动作|
|---|---|---|
|赠送钻石|`player_wallets.diamond_free`|补偿、活动、手工发放进入此列|
|付费钻石|`player_wallets.diamond_paid`|仅真实验证过的渠道支付/退款流程修改；普通管理员无加付费钻石按钮|
|账号金币（黄金）|`player_wallets.coin`|本次需求新增的直接赠送路径，或既有邮件附件路径；产出策略和额度需审批|
|局内金币|`GameState.gold`、`room.slot_gold`|后台不给编辑入口；每局重置，不与账号钱包兑换或同步|

现有钱包 schema/目录说明 coin 第一版没有常规产出口，但邮件已经支持 coin 附件；不能把“常规来源未开放”误写成数据库不能发金币。消费钻石维持先赠送后付费，客户端仍显示两者合计。

### 7.2 直接发放流程

1. 输入好友码/UUID → 后端解析唯一玩家 → 选择赠送钻石或账号金币 → 输入正整数、理由、工单。
2. 预览明确显示环境、目标、币种、增量、当前余额、预期变化、日额度和重复工单提示；审批的是**增量命令**，不批准一个会被并发消费覆盖的“设置余额”。
3. 后端执行时原子认领 `operation_id`/业务去重键，锁审批和预算，再按固定顺序锁玩家的钱包行。
4. 复用 `shop._lock_wallet()` 和 `_apply()` 或提取兼容的公共钱包服务；同事务写金额、`wallet_ledger(source='grant')`、管理员/理由、操作关联、额度实际消耗、审计和 outbox。
5. 提交后返回 operation/ledger ID 与实际余额；通知在线客户端重新调用现有钱包查询，客户端不自己加金额。

现有 `grant_diamonds()` 保证余额与流水原子，但**没有后台业务幂等键、审批或预算**，不可简单套一个 HTTP 按钮重复调用。可在同一个数据库事务外层认领唯一操作后调用该函数，或统一提取钱包服务；最终必须避免形成三套不同的写账规则。`grant_coin` 是拟新增能力，不是现有函数。

客户端请求中的 `actor`、`balance_after`、SQL 列名不可信。币种白名单只收 `diamond_free/coin`；金额在 API 校验正整数、权限上限和数据库 bigint 上限，禁止浮点。新管理 API 的 bigint 金额/ID建议用十进制字符串传输，避免浏览器 Number 精度损失；不顺便破坏现有 Godot API 契约。

事务内行锁保证并发写入互斥，但多玩家批次还需统一锁顺序、短事务和死锁重试，不能把整份大名单放一个长事务。[PostgreSQL 显式锁说明](https://www.postgresql.org/docs/current/explicit-locking.html)

### 7.3 纠错与对账

- 不提供“编辑余额”“删除流水”按钮。误发回收是一笔新的受审批反向操作，关联原 ledger/operation；累计回收不能超过原发放，重复回收请求只能执行一次。
- 已消费导致余额不足时，默认拒绝自动扣到负数并生成待处理案件；不自动挪用付费钻石、扣其他币或删玩家宠物抵债。冻结消费/债务政策需另行批准。
- 纠错不是渠道退款；建议新增独立 `grant_reversal` 来源及关联字段，修改现有 `SOURCES` 和测试时一起交付新迁移，不能偷用 `iap` 掩盖。
- 对账核对每玩家三列余额与对应流水重放、发放与操作回执、邮件领取与 `mail_id`。差异只生成告警/修复申请，不后台自动覆写余额。
- 发放权限、允许币种、单次/单日限额、是否允许向被封玩家发补偿由配置与审批确定；默认封禁期间可以准备补偿草稿，领取仍遵守制裁策略。

## 8. 系统邮件与批量补偿

### 8.1 P0 邮件界面

字段沿用 `mails`：中英文标题/正文、单人或全服、钻石、coin、内容 ID 列表、有效期、内部备注。现有限制：中文标题 1–60 字、正文最多 2000 字；英文标题最多 60 字、正文最多 2000 字；单封钻石 0–100000、coin 0–1000000、附件最多 10 项；天数 1–365，默认 30。**这是数据上限，不是运营自动获批额度**。

附件选择器从服务端当前允许赠送的内容目录生成，显示 `content_id`，不把 `shop_pet_cat` 当 `pet_cat`。未知/未上架内容先拒绝；重复拥有沿现有规则跳过物品、不折算钻石，其余附件照常领取。客户端可用性和战力影响必须在预览中显示。

建议流程：草稿 → 指定测试账号实际预览/测试发送 → 目标与总附件预算预览 → 审批 → 立即发送或定时任务 → 展示 mail_id/执行回执 → 跟踪已读/领取/异常。

注意：当前 `mails` 没有草稿与发送时间状态。草稿/排程存在新管理表，**到真正发送时**才调用 `send_mail/send_mail_all` 写入正式表；提前插入“未来发送”的邮件会让现有客户端提前看到。过期时间从实际发送计算。

### 8.2 全服、定向和撤回语义

- 现有全服邮件只有一行，`player_id=null`；不要为现有全服模型强行复制所有玩家行。`include_new_players=false` 的资格是注册时间不晚于邮件创建时间。
- P0 需要“冻结事故发生前人群”时不能误用实际发送时的注册时间；应使用 P1 收件人快照，或新增明确的 `audience_cutoff` 并同步修改服务端可见性判断后再开放该选项。
- 定向名单/分群（P1）使用单人邮件及 `admin_job_targets` 唯一键，或经设计扩展收件关系；**不能把分群内容直接调用 `send_mail_all`**。
- 撤回打标记，不删邮件；已领取奖励不自动追回。撤回界面显示已领人数、已发货币和剩余可领取风险，并在确认框写清边界。
- 当前 `mail.claim()` 的可见性读取在领取事务前，撤回并发存在需要专项验证的时间窗口。后台撤回上线前统一领取/撤回的锁与事务内再次校验，覆盖过期、删除、撤回、单领/一键领取竞态；不能只认为有 `claimed_at` 锁就解决了全部问题。
- 当前一键领取是每封一个事务，允许部分成功；后台查询要展示每封真实结果，不把部分成功误报全失败然后再发一遍补偿。
- `mail_states` 无行代表未读/未领，不代表未送达；统计区分资格人数、邮件可见、推送尝试、已读、已领、过期未领。奖励负债估算不能只数已经产生 state 的玩家。

### 8.3 批量任务（P1）

导入只支持受限 CSV 字段如 `friend_code/amount/reason`，严格大小、行数、编码、公式注入与重复行检查；CSV 只是名单，不允许 SQL、任意文件路径或表达式。无效 ID 单独列出，默认要求用户修正或明确剔除后重新审批，不能静默少发。

审批前持久化目标 UUID 快照、筛选条件、名单 hash、目录版本、每人附件与总预算。worker 分批认领，唯一 `(operation_id, player_id, reward_component)` 防重；业务 `campaign_id+recipient+reward_slot` 防止复制任务绕开幂等。支持暂停、取消未执行目标、对失败目标重试；已经成功的目标不撤销、不重发。

发送成功与在线通知是两件事。通知失败只重发通知，不重建邮件；任务重启从持久回执恢复。冻结名单若排程期间有人删除账号，按“跳过并报告”处理，不创建幽灵玩家。涉及保留预算时失败/取消释放未执行部分，已发奖励不可因任务取消回收。

## 9. 公告与内容发布

### 9.1 复用当前字段与行为

- 分类沿用 `event/news/update/urgent`；状态沿用 `draft/published/withdrawn`，撤下不删除。
- 编辑 `title_zh/body_zh/title_en/body_en/image/popup/sort_order/starts_at/ends_at/preview_codes`；`problem` 只读，由后端图片/内容处理写回，不能靠清空它伪造发布正常。
- 中文标题最多 60 字、正文 4000 字；英文标题最多 80 字、正文 8000 字。英文为空时回退中文，应在预览明显显示“当前使用中文回退”。按服务端字符规则校验，不只依赖浏览器字符计数。
- 运营输入显示明确时区，落库 UTC，统一以服务端时间判断上下线。日期必须带时区，禁止把浏览器本地无时区时间直接传数据库。
- 正文建议纯文本或现有白名单格式，不接受任意 HTML/脚本；中英文和图片均提供游戏近似尺寸预览，最终仍需真实客户端预览账号确认。

### 9.2 发布、改版与图片

1. 保存草稿后可让 `preview_codes` 中测试账号查看。正式发布先验证图、目标时间、文案与弹窗影响，再审批；定时公告可以使用已有 published + starts_at 行为，但批准前仍保持 draft。
2. 新增编辑版本 `lock_version` 或 ETag 防止两位运营互相覆盖；它与玩家看到的 `revision` 分开。文字微调是否重新红点/弹窗由发布者明确选择，后端控制 revision 递增，不能自由写任意数值。
3. 紧急公告发布前展示“将向所有在线玩家推送”，增加冷却/频率约束。现有推送基于轮询和进程内状态，不能保证每人恰好收到一次；需要可靠运营回执时加持久事件 ID，客户端去重，离线用户通过列表读取。
4. 图片复用 `announcements.prepare_image()`：当前原图最多 10 MiB、1600 万像素，接受 PNG/JPG/WebP，拒绝 GIF，转后最多 1 MiB。不要在管理站上传口引入 SVG/任意 URL 抓取，避免脚本和 SSRF。
5. Storage 上传只在服务端执行，文件实际解码并去除无关元数据；保存不可变路径/内容 hash，新图片用新文件名，不能覆盖旧路径期待缓存自动更新。
6. 公告上线前检查处理结果可读，失败不宣称发布成功；后台显示“数据库已发布”“账号服务已加载”“推送已尝试”的不同状态。保留 revision 快照与前后差异供回滚；回滚是新版本，不删除历史。

## 10. 未来运营需要的相邻模块

### 10.1 客服、举报、禁言与申诉（P1）

工单字段：玩家、分类、状态、责任人、优先级、附件证据、关联 match_uid/mail_id/order_id/operation_id、处理时限和回复历史。处罚页面可直接跳工单，但公开处罚理由与内部证据分离。

举报入口是拟新增客户端能力；后台先可人工录入案件，不假设已有玩家举报 API。证据访问需要具体案件授权；当前私聊按最近消息/过期策略保留，后台必须说明“已超出保留窗口”，不能伪造完整聊天历史。语音默认不录音，新增录音取证需另定告知、权限和保存方案。

处理工具限定为隐藏违规展示字段、强制改名流程、文字/语音禁言、申请封禁、恢复误处罚、发送补偿。禁止一键伪装玩家发消息或展示其 token。客服身份核验与账号找回属于独立安全流程，不能凭昵称/好友码直接改 Auth 绑定。

### 10.2 商城、权益、活动与兑换码

- P1 先提供目录只读、归属查询、批准后的发放/撤销；复用 `shop._grant()` 等逻辑，并新建权益事件历史。现有归属主键行可被重新激活，单看最后一行不足以审计所有往返。
- 当前“不在商品目录里的内容默认免费”。**直接从 `data/shop.json` 删除一个商品可能把对应内容变成免费**，不能把删行当下架。商业内容身份/entitlement 要求与售卖状态必须先解耦，再做 `enabled/starts_at/ends_at/price_version` 等运营能力。
- 当前目录从 JSON 读取。首版不做生产上网页任意改文件；若需配置发布，新增版本化目录与明确唯一读取源、服务端校验、预览、审批、原子切换、回滚、客户端 catalog revision，防止数据库和 JSON 两套真相。
- 头像、默认框等已有免费内容不得无声改成收费；宠物/种族可能影响出战资格，发布前显示游戏影响。历史订单价格取下单快照，不跟随新价格重算。
- 撤销权益需要重新校验已装备宠物/头像/种族，后续出战名片不得继续携带已撤权内容；已签名片与正在战斗如何生效遵循第 6 节的撤权合同，不直接改当前对局状态。
- P2 活动/兑换码复用奖励组件：有效期、渠道/环境、每账号次数、总人数/总预算、资格、码哈希、限流、幂等领取。兑换码不是管理员令牌，不存无限可刷奖励的明文通配码。

### 10.3 战绩、排位、信誉、赛季（P1）

查询页面关联 `match_records/match_seats/player_ranked/credit_events/player_ranked_history`，展示战报验签/去重结果、模式、席位、正常结束/离场、积分变化与处罚原因。匹配池状态只从实际单实例查询，不能用数据库历史推算实时队列。

- 信誉日恢复与临时禁赛分开显示；当前信誉规则、排位开放时间取服务端 `ranked.py`，页面不能写死另一个时区或阈值。
- 信誉误扣更正走新的操作事件；现有 `credit_events.kind` 有 CHECK 白名单，新增 admin_adjust 必须新迁移，并确认不被“滚动 7 天逃跑次数”统计算作违规。
- P1 不提供“修改段位”字段：当前段位是 score 的派生值。必要的积分纠错须先设计积分变更账本、match_uid 关联和审批；历史赛季归档的 tier 保留当时快照，不重算旧档。
- 赛季页面配置开始/结束、名称、各段奖励，检测时间重叠/编号冲突、目录合法性、预算；结算前预演参与人数、每档人数和总奖励，批准后冻结奖励版本。
- `settle_season()` 已以 `settled_at` 认领实现幂等，重复返回 -1；后台必须复用该语义，禁止把 settled_at 清空后再跑。
- **当前自动任务直接结算到期赛季，不检查未来的后台审批。** 开放赛季管理前必须让 `seasons.due_seasons()` 与 SQL 结算入口共同执行批准/冻结/预算闸，否则管理员未批准时自动任务仍可能发奖。手动结算还要检查已到期；“提前结算”另走特殊审批，不能靠现有 SQL 函数裸调。
- 结算与晚到战报/赛季切换需明确合同：停止旧赛季新匹配、给进行中对局设结算宽限、按权威战报归属记录赛季；截止后战报进入人工/延迟处理队列，不无意算进下一赛季。需要新字段或规则时新增迁移和兼容测试。
- 赛季奖品已发错只新增更正邮件/操作；不删玩家领取记录再发。已有领取和钱包数据不可通过“回滚赛季”整体抹掉。

### 10.4 服务状态、维护与监控（P1）

后台展示：账号服务健康/配置是否齐全（不显示秘密）、WS 连接、admission 在线名额/队列、casual/ranked 匹配队列、战斗服心跳与制裁版本、邮件/公告巡检时间、任务积压、失败率、钱包对账异常、赛季结算进度。

维护开关分离：停止新登录、停止新匹配、暂停商城购买、暂停邮件领取、暂停运营发放。每个开关有理由、开始/结束、负责人、版本、回滚计划；优先让正在战斗的玩家自然结束。公告时间到不等于维护闸已生效。

当前 `admission_file` 是在线数量热配置，不是完整维护开关。原子写文件只能作为该既有能力的受限适配，不能接受任意路径。真正阻止操作的开关需在后端入口执行，不能只靠客户端禁用按钮；数据库中保存配置与各消费者已应用版本。

建议运营告警：大额/高频发放、重复业务请求、批次错误率、制裁回执超时、异常匿名注册、购买/领取失败、公告图片处理失败、赛季重复结算尝试、备份恢复演练失败。告警发给预先配置的内部通道，不包含敏感原文。

### 10.5 分析、支付与数据治理（P2）

- 指标字典先定义时区、去重、窗口、机器人/测试号排除：DAU、新注册/匿名重建、留存、同时在线、排队等待、对局完成率、邮件领取率、币种产销与存量、付费订单/退款。
- `last_seen_at` 只能提供有限活跃信息，不足以复原历史 DAU/留存；需新埋点/汇总。商城钻石消费不是人民币/美元收入，不能用 `shop_orders.price_snapshot` 画现金流水。
- 当前没有已完成的真实支付验单链路。充值/补单/退款页面先只读或关闭；接入后服务端验渠道凭证，唯一渠道交易 ID、回调乱序/重复、退款回收和对账各有测试，人工“补单”不得跳过验单变成加付费钻石按钮。
- 帐号注销需要先重审：当前 `profile.delete_player()` 物理删 players，多张经济/处罚关联表为 cascade；不能同时宣称“永久保留财务与处罚证据”而忽视级联删除。新后台不得提供物理删除玩家按钮；应设计停用、匿名化、保留最小业务凭证及审批流程，并同步约束现有玩家注销路径。具体保留范围/期限由负责人按实际市场确认。
- 不把手机号、设备指纹、地理定位、支付渠道等当前不存在的数据作为默认筛选项；新增采集需单独目的与隐私审查。

## 11. 数据结构草案与数据库约束

以下为拟新增表/字段。迁移必须接在实际仓库最大编号之后；本次最大为 015，**不要修改 001–015 历史 SQL**。所有管理表启用 RLS，默认不向客户端暴露；服务端还要用独立、最小权限的数据库角色及表/函数授权。

|`admin_principals` / `admin_role_bindings`|OIDC issuer+subject 唯一、active、role、environment、scope、version|内部人员身份；不复用玩家 profiles 作为管理员名册|
|`admin_sessions`|会话摘要、主体、MFA 时间、expires/revoked、权限版本|撤销会话与二次认证，不存明文 token|
|`admin_operations`|UUID、type、environment、creator、payload、payload_hash、status、business_key、idempotency_key、version、expires_at|状态机主记录；`(environment, creator, idempotency_key)` 唯一；业务重复约束另外定义|
|`admin_approvals`|operation、payload_hash/version、approver、decision、time|批准与内容绑定；审计保留历史，执行检查最后有效批准；禁止自批|
|`admin_audit_events`|event_id、operation、actor、action、target、before/after、result、time、request_id|只追加，脱敏；不能随删除玩家级联消失|

|`admin_jobs` / `admin_job_targets`|operation、schedule、lease、attempt、cursor、target、component、status、result_ref|批次持久化；目标唯一，worker 崩溃可恢复|
|`admin_outbox` / delivery receipts|event_id、operation、destination、payload_version、status、attempt、lease、ack|提交后发通知、制裁同步；按消费者/事件去重|

|`admin_config_versions` / consumer acks|key、schema、value、version、approved、effective_at、consumer version|维护、目录、额度等可验证配置发布，不存秘密|

### 11.1 幂等、并发与异步任务的实现合同

- `operation_id` 是系统操作身份，`Idempotency-Key` 是传输重试身份，`business_key` 是同一次运营活动的业务身份；三个不能互相替代。相同业务换一个 HTTP key 仍不得重复发奖。
- 执行先锁操作/预算，再按 player_id 稳定顺序锁业务对象；领取与撤回统一明确的锁序。重试 PostgreSQL 死锁/序列化错误必须重跑整个事务，并重用同一操作 ID。
- 认领操作、业务变更、流水、成功审计、outbox 同事务提交。worker “执行中”崩溃不代表业务没提交；恢复时查询唯一回执，禁止盲目再加一次。
- job lease 需要到期回收、owner/token 校验，不能只写 running 就永远卡住；执行者失去 lease 后不得覆盖新执行者状态。`FOR UPDATE SKIP LOCKED` 可用于认领，不代替业务幂等。
- 数据库与 LiveKit/战斗服无法一个事务提交：采用 outbox、重试、ACK、超时告警。后台显示 pending/partial，不承诺跨系统恰好一次；消费者处理效果要幂等。
- 发奖结果与客户端推送解耦：可以推送多次“请刷新”，不允许因此发钱多次。刷新丢失时下次正常查询仍能读到正确余额/邮件。
- 限额、活动人数和预算不得只放 Redis/进程内计数；账目真相与成功回执在 PostgreSQL。未来 Redis 可作缓存/限流，但不能决定有没有发过钱。
- 既有 Supabase Table Editor/SQL 函数写入口须收口到受控数据库角色；关闭普通运营直写权限，审计保留受限制的 DBA 紧急通道。RLS 并不能阻止具有绕过权限的数据库账号。

## 12. 管理 API 草案

下面均为拟新增 `/admin/v1`，不是现有可调用接口。写接口遵循统一 operation/审批，不直接执行隐藏副作用。分页使用稳定游标，限制 page_size；敏感查询/导出均鉴权。API 错误结构建议 `code/message/request_id/operation_id/details`，不回堆栈/SQL/密钥。

|接口|职责/权限|
|---|---|
|`GET /session`，OIDC callback，`POST /logout`|当前管理员与权限；身份提供方跳转白名单，防开放重定向|
|`GET /players?friend_code=...`、`GET /players/{id}`|精确查询/脱敏详情，`player.read`|
|`GET /players/{id}/wallet`、`/ledger`、`/orders`、`/entitlements`|账目/权益只读；不同敏感等级分别授权|
|`GET /players/{id}/mails`、`/matches`、`/sanctions`、`/audit`|关联查询；不能通过换 UUID 越权|
|`POST /operations`|提交指定 type 的草案；只接受严格 schema，禁止任意 action/SQL|
|`POST /operations/{id}/preview`|冻结目标、金额、影响面和 hash；不得实际发钱|
|`POST /operations/{id}/submit`、`/approve`、`/reject`|状态转换与双人复核；附 expected_version|
|`POST /operations/{id}/execute`、`/cancel`|执行或取消；异步返回 202 和回执，不能自带新 payload|
|`GET /operations/{id}`、`GET /jobs/{id}/targets`|状态、逐目标结果、失败原因；默认脱敏|
|`POST /jobs/{id}/retry-failed`、`/pause`|仅重试允许恢复的未成功目标，权限/预算再次校验|
|`GET/POST /mail-drafts`、`GET/PATCH /mail-drafts/{id}`|邮件草稿 CRUD；发布关联 operation，不直接在 POST 发出|
|`GET/POST /announcements`、`PATCH /announcements/{id}`|编辑草稿和版本；发布/撤回经 operation|
|`POST /media/announcement-images`|受限图片上传；无任意 URL 下载能力|
|`GET /seasons`、`POST /seasons/{id}/preview-settlement`|赛季及结算预演；正式结算走批准操作|
|`GET /service-status`、`GET /configs`|运行态只读；配置变更通过批准版本发布|
|`GET /audit-events`、`POST /exports`|受控检索和短期下载；导出创建本身也要审计|

统一写命令示例（示例 UUID 为占位，不能直接作为线上操作执行）：

```json
{
  "type": "wallet.grant",
  "environment": "staging",
  "target": {"player_id": "<resolved-player-uuid>"},
  "payload": {"currency": "diamond_free", "amount": "500"},
  "reason_code": "service_incident_compensation",
  "ticket_id": "INC-EXAMPLE",
  "business_key": "INC-EXAMPLE:<player-uuid>:compensation-v1",
  "expected_version": 1
}
```

请求头另带稳定的 `Idempotency-Key`；actor、批准信息、预算消耗和 ledger ID 由服务端生成。请求里的 environment 必须与当前部署及会话范围一致，不能用它切换任意数据库。

统一错误码至少包括：`admin_unauthenticated`、`permission_denied`、`mfa_required`、`approval_required`、`self_approval_forbidden`、`version_conflict`、`idempotency_conflict`、`duplicate_business_operation`、`budget_exceeded`、`player_not_found`、`invalid_reward`、`operation_not_executable`、`consumer_ack_pending`。只有真正的未认证用 401；被封玩家错误不要触发匿名重建流程。

## 15. 必须覆盖的验收用例

### 15.1 安全与权限

- 普通玩家 JWT 打管理 API、过期管理员会话、猜 UUID、修改 body.actor、跨环境/跨范围、撤销角色后的旧会话全部被拒绝。
- CSRF、恶意 Origin、SSO 回调篡改、上传伪扩展名/超大图/压缩炸弹、正文脚本、CSV 公式注入有测试。
- 自批、批准后改人数/金额、过期批准、越日额度、复制业务 key、以不同 HTTP key 重发同工单均不产生第二次业务效果。
- 后台页面、响应、日志、审计、错误堆栈和导出中不出现服务端密钥、玩家 token、支付凭证原文。

### 15.2 钱包、邮件和并发

- 同一发放重复 100 次只一份流水/增量；相同 key 不同 amount 返回冲突；不同操作并发加钱并发购买不丢更新。
- 首次钱包创建并发、最大合法整数、超过 bigint、负数、零、字符串小数/科学计数法、JS 安全整数边界逐项测试。
- 在“改余额后写流水前”“提交后回 HTTP 前”“发通知前”注入故障；回滚或重试后余额、流水、操作状态一致。
- 两台设备领同一封、单领与一键领、领取与撤回/过期/删除并发；附件仅到账一次，已领不被撤回抹掉。
- 邮件不认识内容 ID、重复已有宠物、全服新用户开关、名单冻结后新注册/注销、过期未领取、英文回退正确。
- 长任务一半成功后进程停止、lease 过期、取消、重试；已成功目标不重发，预算不泄漏也不重复释放。
- 纠错已消费余额不足时明确失败/转案件，不扣付费余额、不负数；对账能定位原发放与反向记录。

### 15.3 封禁与实时链路

- 活跃 HTTP/WS、旧 access token、refresh、已签出战名片、自定义房间、匹配确认、重连与现有 LiveKit 会话逐一验证。
- 同时封禁与匹配就绪不会漏放；取消匹配/踢出后状态一致；封禁到期、解一条仍剩另一条、系统信誉低等交叉规则不误解禁。
- 战斗服断联/回执丢失/命令重放时状态可解释；后台显示部分应用而非假成功；客户端收到 account_banned 不新建匿名用户。
- 封禁不删除玩家/订单/邮件/战绩，不擅自改当前对局胜负或其他玩家奖励。

### 15.4 公告、赛季和运行保障

- 公告草稿预览范围、时区、起止边界、改图新路径、不同 revision 弹窗、发布与撤回并发、加载失败可见。
- 同一个赛季自动任务与手工结算同时触发仍只发一份；未批准/未到期拒绝；奖励冻结后编辑拒绝或重新审批；跨赛季晚到战报有明确归属。
- 后台上线不意外多起 `main.py` 的实时循环，不关闭单实例保护；大量查询/导出不会饿死游戏 WS。
- 新表从空数据库顺序迁移可建；既有测试通过；旧玩家客户端能正常读钱包/领邮件/看公告/匹配；关管理开关不会破坏玩家游戏。
