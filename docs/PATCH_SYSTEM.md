# GLory Patch 与 Hotfix 实施记录

状态：开发中，尚未部署。工作分支 `codex/patch-system`。

## 目标与发布规则

- 后台上传、校验、发布、撤销强更补丁；文件由 Firebase Hosting 分发。
- iOS、Android、Windows 启动均检查版本；无变化不下载，未达到要求版本不能进入游戏。
- 同一发布序号包含分平台产物；基础包标识绑定引擎、原生插件、导出配置与基础内容，不能只比较显示版本号。
- `tools` 提供补丁构建入口，包含图片、音频、场景与 GDScript，排除引擎和原生库/SDK；基础包与补丁须来自兼容构建。
- 服务器在线应用代码 hotfix，客户端通过现有 WebSocket 接收 GDScript hotfix；重连取完整快照而非只依赖推送。
- 每次服务器部署或强更补丁发布，使全部旧 hotfix 失效并从有效列表移除，保留不可执行的审计信息。客户端需要撤回旧效果。
- 强更界面有进度、大小、阶段与重试；hotfix 不弹玩家通知。
- 所有渠道使用一致的版本选择规则，不针对审核身份、IP、设备隐藏更新。

## 协议决定

协议版本 `1`；平台 `ios/android/windows`，渠道初始为 `stable`（内测使用 `internal`）。
`base_id` 是基础构建标识，`patch_seq` 为正整数，显示名称独立。同一渠道的发布序号不可复用。
每份平台产物指定基础包、SHA-256、大小、Firebase HTTPS 地址与加载顺序。
客户端比较服务端要求的精确发布序号；高于要求也不能绕过回滚。
初次启用前必须发带更新器的基础安装包，不能要求旧包自己获得更新能力。

Hotfix 快照包含单调递增 revision、服务器 deployment_id、当前 patch_seq 和有效项全集。
发布补丁、服务器部署、撤销 hotfix 都增加 revision；广播失败时客户端重连/补偿检查恢复完整状态。
服务器与客户端执行器须具备 apply/revert 生命周期、兼容性判断与应用失败回退，不能把任意字符串 eval 当作完整方案。

## 本地构建模块（开发中，尚未接入正式构建入口）

- `tools/workspace/prepare_patch_base.py`：只操作无 `.git` 的独立 staging 目录，保存原 Autoload 顺序与入口，把 Autoload 替换为空节点，安装更新界面及独立中文字体。必须在 Godot 导入与导出之前执行，不能对正式源码目录运行。
- `tools/workspace/glory_patch.py`：比较同平台、同基础包的 Godot 导出 ZIP，生成相对原始安装包的累计补丁及 JSON 校验信息。禁止删除基础文件，禁止修改启动器、项目配置、原生库、全局脚本类注册表。涉及这些变更需发布新基础安装包；新普通脚本可以新增，新 `class_name` 注册暂不支持。
- 资源 ZIP 必须来自平台导出，不能把源文件目录直接压缩冒充运行时产物。跨平台基础包和补丁分别生成。
- 新增构建测试 8 项通过；更新器脚本通过 Godot 4.7 解析检查。真实完整工程构建、联网下载与设备验收尚未完成。
- 下载/状态写入错误可以重试；一旦挂载补丁或初始化业务单例，失败只允许重启，避免同一进程反复挂载造成资源混用。

## 后台与账号服务器实现进度

- 已接入 FastAPI 生命周期和现有 MFA 管理员鉴权；未配置 Firebase site 时服务返回 503，现有部署不会自动启用强更。
- 管理页面加入草稿、平台 ZIP 上传进度、发布、回滚和上传任务记录。发布接口使用 revision 检查，上传与发布串行；Firebase 全量文件列表保留旧版本地址。实际浏览器 UI 验收仍待执行。
- 已增加账号服务器 Python Hotfix：源文件只能包含 `def apply(ctx)`，副作用放函数内，通过 `ctx.replace_attr` 和 `ctx.replace_item` 记录撤销动作。支持替换真实运行中的模块函数；不是玩家代码沙箱。管理员代码必须遵守上下文接口约定，直接写文件、直接赋值等外部副作用无法自动撤销。
- Hotfix 应用失败恢复先前有效集合；发布补丁先撤销运行效果，提交失败则恢复。有效列表删除旧项，审计记录保留。
- 启动时根据实际部署的后端 Python 和数据文件计算部署标识；同代码重启恢复有效 Hotfix，代码变化使其失效。战斗服务器部署联动仍未接入。

## 客户端 Hotfix 进度

- 新增不可变启动器内的 `HotfixAgent.gd`、`HotfixRuntime.gd`、`HotfixContext.gd`；通过完整快照替换有效集合，支持 SHA-256 校验、重复快照不重放、失败回退、反序撤销。
- GDScript 格式为 `extends RefCounted` 和 `func apply(ctx) -> bool`，通过 `ctx.set_node_property("/root/节点路径或通配符", "visible", false)` 等登记 UI 改动。支持已有节点及后来新建的场景节点；效果无弹窗。发布强更时则清空 Hotfix 并阻挡界面，提示重启完成资源更新。
- 管理后台支持 `.gd` 文件及代码预览；后端调用同版本 Godot 验证语法和接口契约，需配置 `GLORY_PATCH_GODOT_BINARY`。每个渠道最多 12 个有效客户端 Hotfix，各不超过 128 KB。
- 在线通过现有 WebSocket 的 `t=patch_hotfix_snapshot` 直接推送代码全集；连接恢复以及每 30 秒通过版本检查协议补偿。不同渠道客户端只应用自己的快照。发布补丁、撤销热修均推送空/新快照；部署标识变化时先撤销旧效果。
- 真引擎测试验证现有按钮、后建按钮、失败回退及撤销恢复。HTTP 路由测试调用真 Godot 验证器，并核对在线推送源代码、重新检查补发与撤销后的空快照；相关 20 项后端测试通过。
- 尚未做三端完整安装包与真实服务器的端到端验证；战斗服务器 Hotfix、服务端精确版本入场校验和正式构建入口仍待接入。

## 平台导出工具与战斗数据执行器

- `tools/workspace/export_patch.py` 接受隔离的 `--stage`、`--godot`、`--preset`、`--platform`、`--config` 和新建的 `--output` 目录。无 `--base` 时保存原始 `base.zip` 及导出身份清单；带 `--base /原始目录/base.zip` 时生成相对原始包的累计补丁。Windows 可以使用 `--executable Glory.exe` 同时导出基础可执行程序（需匹配的 Windows 模板）。
- 导出身份清单记录引擎版本、平台、基础包标识、导出配置哈希及原生文件哈希。与基础包不一致时拒绝生成补丁。原始 ZIP 和 `.export.json` 必须成对保留。
- 真 Godot Windows 资源导出测试通过：基础导出→改动脚本→再次平台导出→生成累计 ZIP→同时挂载基础与补丁，实际执行补丁 `service.gdc` 返回新值。这个用例不等于完整 Windows EXE 已验收。
- 新增 `BattleHotfixContext.gd`，为可信 GDScript 提供可撤销的 Dictionary 和对象属性替换。真引擎用项目 `bosses.json` 验证运行中更改 Boss 血量并撤销恢复。当前改动作用于配置对象；已经复制配置的战斗实例不会自动回填，修改已有战斗状态需由 Hotfix 明确定位对应状态对象。
- 战斗进程与后台之间的分发、确认及部署联动尚未接入；该执行器当前只是经过验证的组件，不能视为线上可用。

## 战斗进程分发与回执（后续实现）

- 已接入同机原子文件协议：账号后端拥有 desired 文件，战斗服务拥有 status 文件；路径由服务器配置指定，不接受管理员请求传入路径，也不开放公网执行代码接口。
- `BattleHotfixAgent.gd` 由专服启动入口在配置存在时加载，每 2 秒检查完整快照并回写修订号/错误。15 秒没有新鲜快照、部署不匹配时清空效果。后台界面每 3 秒刷新执行回执，避免把“下发”显示成“执行成功”。
- 后台观察战斗部署标识变化后，使 client/account_server/battle_server 全部旧 Hotfix 失效，并提升 `hotfix_epoch`；重复观察相同部署不会再次失效。客户端也按 epoch 先清除旧效果，避免失败回退恢复跨部署的旧代码。
- 真 Godot 子进程联调通过：后台发布→Boss 配置变化→应用修订号回执→账号部署变化撤销→过期快照撤销。另有战斗部署变化使全部目标失效的测试。
- 服务端 ZIP 打包脚本已加入共用运行器；`deploy/glory-server-patches.conf` 提供专服 systemd drop-in，尚未安装到线上。后端须配置 `GLORY_PATCH_BATTLE_DESIRED/STATUS/INSTANCE`，战斗进程通过对应 `GLORY_BATTLE_HOTFIX_*` 读取路径。双方只读对方文件，保持各自目录的写权限。
- 这部分已经有本地进程间证据，仍不能视为生产部署或现有真实对局验收通过。
