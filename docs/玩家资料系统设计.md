# 玩家资料系统设计

> 2026-09-09。配套文档：`docs/账号系统RFC.md`（身份模型、四层边界、`C14` 依赖）、
> `database/README.md`（迁移文件的规则与代价表）、`docs/CHECKS.md`（门禁怎么跑）。
>
> 本文记录的是**取舍与理由**，不是接口手册。字段清单会随实现调整，
> 但下面每一条「为什么」在推翻之前都应该先被读到。

入口是主菜单左上角那个人物名牌，代码在 `scenes/menu/MainMenu.gd` 的
`_add_hit(Vector2(18, 12), Vector2(550, 178), _show_coming_soon, "left")`。
在此之前它一直是「敬请期待」，名牌上的 `GloryMaster` 和 `等级 45` 是写死的假数据。

## 一、先说清楚这一版做出来的是什么

把市面上的资料页拆开，只有五个区块：

| 区块 | 字段 | 谁在做 |
|---|---|---|
| ① 身份 | 头像、头像框、昵称、ID / 好友码、名片背景 | 全部 |
| ② 实力证明 | 等级、段位、奖杯、平均名次、战绩 | 全部竞技游戏 |
| ③ 收集进度 | 卡牌收集度、图鉴、成就数、探索度 | 有收集要素的 |
| ④ 展柜 | 常用英雄、角色展柜、最爱卡牌 | 中大型 |
| ⑤ 自我表达 | 签名、性别、生日、地区、状态、称号 | 社交做得重的 |

参照物：王者荣耀五块全满且 ⑤ 做到极致（含情感状态、亲密关系、荣耀战区）；
Clash Royale 是 `#P0LYQ8` 好友码 + 奖杯 + 卡牌收集度 + 最爱卡牌；
金铲铲这类自走棋的 ② 不是胜率而是**平均名次和前四率**——品类不同，炫耀单位就不同；
原神做名片 + 签名 + 成就数 + 八个角色展柜；Steam 把 ④ 做成了页面主体。

**这五块的作用完全不同**：①⑤ 是社交信息，零门槛，填了就有；
②③④ 是留存驱动，它们的价值**全部来自「得不到」**——别人看你的段位有感觉，
是因为他自己上不去。

### Glory 今天只能填 ① 和 ⑤

盘点结果：**没有等级系统、没有段位、没有持久战绩表、没有跨局货币、没有皮肤系统。**
`grep` 过一遍，②③④ 里除了本地的宠物与图鉴，一格真实数据都没有。

所以这一版做出来的是**一张通讯录，不是陈列柜**。它不带来留存——留存来自 ②③④，
那是另外三个项目。**写下这句话是为了以后不要拿留存指标去衡量它。**

那为什么还要做：

1. **它是 ②③④ 的容器。** 等级、段位、战绩以后都得有地方显示。先把容器和后端接口
   做对，以后填进去是加字段（🟢）；反过来，做等级系统时才发现没有资料页，
   那要临时糊一个。
2. **它把主菜单那块假数据变成真的。** `GloryMaster` / `等级 45` 是发出去会被
   玩家立刻发现的东西。
3. **它是第一个让玩家产生「我不想丢」的东西**——见第八节第 5 条，这条比看起来重要。

## 二、放什么，不放什么

### 做

| 字段 | 区块 | 为什么 |
|---|---|---|
| 昵称 | ① | 默认名是 `Player`，不改的话所有人同名 |
| **好友码** `#7K2M9Q4B` | ① | 见第八节第 1 条——没有它，公开视图没有可靠入口 |
| 头像（预设池，精选 16-20 张） | ① | 见第四节 |
| 头像框（**只建列，UI 只有默认框**） | ① | 全部游戏都有，且是**最便宜的奖励载体**：一张图、零逻辑。现在加列 10 分钟，以后加要写迁移 |
| 签名（60 字） | ⑤ | |
| 性别 / 生日月日 / 地区 | ⑤ | `database/002_player_bio.sql` 已经建好表 |
| 注册天数「第 128 天」 | ① | 免费、有情感价值，且比精确日期少泄漏信息 |
| 展示宠物（单个） | ④ | Glory 唯一有辨识度的展示物。**客户端自报、服务端不校验拥有权** |
| 占位区块（等级/段位/战绩、图鉴/宠物/皮肤） | ②③ | 产品决定：先占位显示「敬请期待」，上线前补齐 |
| **举报入口** | — | 见第八节第 4 条。**发布必需，不是 nice to have** |
| 「绑定账号防丢失」入口位 | — | 功能不在本批，位置先留 |

**占位区块只在自己的页面显示，公开视图里不渲染。**
自己看到「以后有段位」是预期管理；陌生人看到一整页「敬请期待」得到的信息是
「这游戏没做完」，而公开视图存在的全部意义就是留印象。代码上只是一个
`is_self` 判断，不增加成本。

### 不做，以及为什么

| 不做 | 理由 |
|---|---|
| 等级 / 段位 / 战绩的**真实数据** | 系统不存在。**放假数据比留空更糟** |
| 图鉴进度 / 拥有宠物进**公开视图** | 是真实进度数据，上云等于服务端要为「你拥有什么」负责，牵出一整套校验。属于进度同步项目，见 RFC `9.5` |
| 名片背景 / 横幅 | 要美术，且没有获取来源 |
| 点赞 | 便宜，但要防刷，且没有社交入口时无意义 |
| 成就 / 称号 | 没有成就系统 |
| ~~在线状态 / 好友~~ | ~~社交系统，比资料页本身大~~ → **2026-09-09 已开工，见 `docs/交友系统设计.md`**。当时判断「比资料页大」是对的，但它不需要等任何东西 |
| ~~屏蔽 / 拉黑~~ | ~~今天没有任何互动方式——屏蔽一个只能看、不能互动的人没有意义。等聊天做了再说~~ → **2026-09-09 作废**：交友系统上线那一刻这条理由就失效了 —— **好友请求本身就是一条能反复戳人的通道**。拉黑随交友系统第一批做，不等聊天 |
| 自定义照片上传 | 独立项目：对象存储 + 图片处理 + **内容审核** + 举报下架。工作量是预设方案的 5-10 倍，且没有审核方案就有下架风险。**但 `avatar` 列的结构现在就留好口** |

## 三、隐私与「删除资料」

**不做单独的「清空我的资料」功能。** 可见性开关本身就是删除功能，
多做一个只会多一处要维护、多一次二次确认、玩家还要多理解一个概念。

| 字段 | 底层 | UI |
|---|---|---|
| 性别 | 值 + 独立可见性开关 | 选项：男 / 女 / 其他 / **不显示** |
| 生日 | 值（**只设一次**）+ **独立可见性开关** | 填月日 + 「不公开」勾选 |
| 地区 | 值 + 独立可见性开关 | 选项列表 + **不显示** |
| 签名 | **不要开关** | 清空文字 = 不显示 |

两条容易写错的：

**① 生日的「不显示」必须是开关，不能是字段值。**
生日只能设置一次（用 `birth_month is not null` 判断，不需要额外加列）。
如果「不显示」是生日字段的一个*值*，玩家选了它就等于用掉了唯一一次设置机会，
**这辈子再也填不了真生日**。

**② 签名不给可见性开关是有理由的，不是偷懒。**
签名是*表达*，不存在「我写了但不给你看」这种状态；
性别生日地区是*事实*，「填了但不公开」是真实需求（例如为了以后的生日礼物）。

**③ `002` 里已有的 `gender = 'undisclosed'` 这个值，新 UI 一律不写。**
统一走可见性开关，否则同一件事有两种表示法，以后必然出不一致。
老数据里的 `undisclosed` 保持合法，不动它——改列的含义是 🔴。

### 「注销账号」在本批，而且必须在

> **2026-09-09 修订。** 上一版这里写着「注销账号属于绑定登录那一批，不在本批」。
> 那是错的，而且错的原因很具体：

上面三条合起来产生了一个洞 —— **玩家填了生日之后，再也无法删除那条个人数据**：

| 玩家想 | 能不能 |
|---|---|
| 改生日 | ❌ 只能设一次（产品决定） |
| 清掉生日 | ❌ 不做「清空资料」（产品决定，对的） |
| 隐藏生日 | ✅ 但**藏 ≠ 删**，数据还在库里 |
| 注销账号 | ← 只剩这一条路 |

每一条单独看都成立，合起来就是一条永久不可删除的个人数据。
可见性开关解决不了它 —— 它管的是「谁能看见」，不是「还在不在」。

合规上要把话说准：Google Play 与 App Store 的「必须提供应用内注销」都挂在
**「允许创建账号」**上，而 Glory 今天是自动创建的匿名账号、玩家没主动注册过，
**那条规定是否适用其实是灰的**。但 PDPA / GDPR 的删除权挂在**个人数据**上，
与有没有「创建账号」无关 —— 而资料系统刚好把昵称、性别、生日、地区、签名
全塞了进去。接了 Google / Apple 登录之后，商店那条也毫无疑问适用。

**做法**（见第六节接口与 `scenes/menu/ProfileScreen.gd` 的危险区）：

- **确认关卡是「手打一遍自己的好友码」。** 匿名账号没有密码，没有任何东西
  可以在删号前再问一次「真的是你吗」。同 GitHub 删仓库要你打仓库名。
  **服务端也校验一次** —— UI 上的确认挡不住一个写错的客户端，而这个操作没有撤销。
- **不做冷静期。** 匿名账号没有邮箱、没有第二种登录方式，冷静期里玩家既收不到
  通知也没有第二条路回来撤销，它只是把删除推迟，不产生任何保护。
- **数据库只删 `players` 一行。** `player_bio` 与 `player_identities` 都是
  `on delete cascade`，全库只有这两张表引用它。
  `backend/tests/test_profile.py` 有一条断言钉着「引用 players 的表必须带 cascade」——
  以后加表忘了它，注销会变成「玩家看到已删除、数据还在」。
- **Supabase Auth 的用户刻意不删。** 今天全是匿名用户，那条记录里没有邮箱、
  没有任何可识别的个人数据；删它要把 secret key 引进 `supabase_auth.py`，
  而那个类明写着「不要在这里用 secret key」。**接了绑定登录之后这条必须重做**，
  那时 auth 用户里有邮箱。
- **本地要清账号态、留设备态**（`PlayerProfile.reset_account_state`）。
  判据用第五节那张表现成的：「换一台手机这个值该不该跟过去」——
  设备态不属于账号，不该被注销带走。⚠️ **`player_id` 必须重签**，
  否则下次匿名注册会把同一个 id 报上去，服务端看它空着就收下，身份原地复活。
  onboarding 与 locale 刻意保留：重看教学、重选语言不保护任何数据，只是摩擦。

**还欠一件**：Google 对「允许创建账号」的应用还要求一个**应用外可达**的删除申请
链接。等绑定登录那批一起做。

## 四、头像

**精选 16-20 张，不是全开。** 池子里 `assets/ui/unit_portraits/` 有 32 张、
`mercenary_portraits/` 有 12 张，共 44 张，其中相当一部分是小怪
（`undead_fly`、`undead_small` 之类），当头像不好看，玩家也不会选。

精选同时解决一个性能问题：选择器要把所有可选头像**同时铺出来**给玩家挑。
原图 `330×330`、磁盘上 180-320 KB、解码后每张约 435 KB 显存。
44 张 ≈ 19 MB 显存加一次明显的加载卡顿，而这是每个玩家进资料页必做的第一个操作。
另外仍然生成一套 `128×128` 缩略图给选择器用，资料页大图才用原图。

### 🔴 头像 id 必须独立于单位 id

```
数据库存的：       preset:avatar_012        ← 这个 id 永不改变
data/avatars.json： avatar_012 → "assets/ui/unit_portraits/dark_dragon.png"
```

不这么做会发生什么：玩家选了「暗黑巨龙」，数据库存 `preset:dark_dragon`；
三个月后美术重做并改名 `dark_wyrm`；**所有选了这个头像的玩家一起变空白**。

这不是假设——`SaveSchema.PET_ID_RENAMES` 里那条 `pet_duck → pet_rabbit`
就是同类事故留下的，现在只能靠每次读档时改写来补。`database/README.md`
也专门写了一节说「内容 id 会改名，数据库要跟着改」。

加一层映射的代价是多一个文件、多一次查表；收益是以后美术怎么折腾都不碰玩家数据。

## 五、数据库：`004_profile_display.sql`

按 `database/README.md` 的规矩，**编号只增不改，001/002/003 一个字都不动。**

文件内部分三段，顺序不能换：

```
① 加列（全部可空 / 带默认）        🟢 瞬时完成，不锁表
② 回填 friend_code                  ← 「回填」就是给已存在的行补值
③ 加 not null + unique 约束         🟡 必须在 ② 之后
```

第 ② 段是 `database/README.md` 代价表里那行「给已有列加 `not null` 要先给老数据回填」。
**现在做成本约等于零**（`players` 表基本是空的）；等有几万玩家再做，
就要写迁移脚本、处理生成冲突重试、分批执行避免锁表。所以现在是对的时机。

| 表 | 新列 | 说明 |
|---|---|---|
| `players` | `avatar` | `text not null default 'preset:avatar_001'`，格式 `^(preset\|upload):[A-Za-z0-9_-]{1,64}$` |
| | `avatar_frame` | 同上。UI 只有默认框，列先建好 |
| | `friend_code` | 8 位，唯一。字母表 `23456789ABCDEFGHJKMNPQRSTUVWXYZ` |
| | `name_changed_at` | `timestamptz`，null = 从没改过名 |
| | `showcase_pet` | 展示用，**服务端不校验拥有权** |
| `player_bio` | `signature` | `char_length between 1 and 60` |
| | `gender_visibility` | `text not null default 'public'`，`in ('public','private')` |
| | `birth_visibility` | 同上 |
| | `region_visibility` | 同上 |

### 为什么头像放 `players` 而不是 `player_bio`

`002` 的分表理由是「`players` 每个请求都读，bio 一个月读一次」。
头像和昵称是同一个访问模式——名牌、房间列表、战绩页都要——所以它属于 `players`。
签名和可见性是自愿填写的展示资料，属于 `player_bio`。

### 为什么 `avatar` 是一列而不是两列

不用 `preset_avatar` + `avatar_url` 两列，因为那样会出现「两列都有值时听谁的」。
这类分歧不会报错，只会让两台设备显示不同头像。带 scheme 前缀的单列以后接上传时
只是**放宽正则**——🟢。

### 为什么可见性用文本枚举而不是 bool

现在只有 public / private 两态，bool 更省事。但等有了好友系统要加 `'friends'`，
bool → enum 是代价表里 🔴 的「改一列的含义」，而放宽一条 check 约束是 🟢。
**多写四个字换掉一次数据迁移。**

### 好友码的字母表为什么排掉 `0/O/1/I/L`

它是给玩家互相抄的。`23456789ABCDEFGHJKMNPQRSTUVWXYZ` 共 31 个字符，
8 位 ≈ 8.5×10¹¹ 种。

**生成逻辑只有一份，在 SQL 里**（`glory_new_friend_code()`，同时是列的默认值），
重试在 Python 里 —— 生成规则写两份迟早会漂，而重试必须发生在持有事务的那一层。
随机源刻意用 `gen_random_uuid()` 而不是 `random()`：后者是每会话播种的普通 PRNG，
观察到若干个码之后可以预测后续。

⚠️ **两种唯一性冲突绝不能混为一谈**（`backend/app/players.py`）：
`players_pkey` 冲突是「客户端报上来的 `player_id` 被占了」→ 让它重签；
`friend_code_unique` 冲突是「我们自己生成的码撞了」→ 我们自己重试。
混在一起的后果是：一次好友码碰撞会被报成 `player_id` 冲突，
客户端照 `AccountManager` 的逻辑重签 `player_id` —— 本机存档的身份就被一次
纯运气事件改掉了，正是 RFC 第七节那条不变量要防的静默身份漂移。

重试必须包在**嵌套事务（savepoint）**里：PostgreSQL 里一条语句失败后整个事务
进入 aborted 状态，不开 savepoint 的话重试循环 100% 是摆设，
而且第二次的报错与真实原因完全无关。

## 六、接口

```
GET   /v1/me/profile              自己的完整资料（含隐藏字段与可见性开关）
PATCH /v1/me/profile              昵称 / 头像 / 头像框 / 展示宠物
PUT   /v1/me/bio                  性别 / 生日 / 地区 / 签名 + 可见性
GET   /v1/players/by-code/{code}  公开视图
POST  /v1/me/delete               注销账号（不可撤销，无冷静期）
```

> **2026-09-09 实现时的一处调整。** 原计划把「自己看自己」拆成
> `GET /v1/me` + `GET /v1/me/bio` 两个请求，落地时合成一个
> `GET /v1/me/profile` —— 底层本来就是一次 join，拆开只会让资料页发两个并发请求，
> 多一处会出「头像到了、名字没到」的中间态。原有的 `GET /v1/me` 不动。

**公开视图用好友码定位，不用 `player_id`。** `player_id` 是内部身份，
没必要出现在客户端可见的地址里。它**不需要登录** —— 只返回玩家自己选择公开的内容。

好友码大小写不敏感（玩家会照着截图手抄，不该因为按了大写锁失败），库里一律存大写。

### 必须钉死的五条

1. **裁剪在服务端做。** `private` 的字段**不出现在响应体里**，
   而不是「返回全量、客户端不显示」。门禁直接断言 JSON 的 key 不存在。
2. **头像必须过 catalog。** 数据库正则只管**格式**，不管**这个 id 存不存在、
   你有没有资格用**。`preset:不存在的id` 一律 400；`upload:` 在功能实现前一律 400
   ——正则允许它不等于放行。
3. **生日已设置（`birth_month is not null`）则拒绝修改。** 设置时 UI 要二次确认
   （「生日设置后不可更改，确认是 3 月 14 日吗？」），否则手滑填错的玩家会永久
   顶着错生日，并产生客服工单。
4. **改名冷却判在数据库上。** `name_changed_at` 为 null → 首次免费；否则 7 天。
   **不能用 `backend/app/rate_limit.py`**——那是进程内滑动窗口，重启即清零、
   多 worker 各算各的。它仍要挂着，但它防的是刷接口，不是冷却。
5. **昵称与签名都过 `text_guard`。**

### `text_guard` 的三层，以及一句诚实的话

| 层 | 内容 |
|---|---|
| 结构管控 | 零宽字符、控制字符、RTL 覆写符（能伪造文字显示顺序）、超量组合符（Zalgo）、首尾空白、连续空白、字符集收敛 |
| 引流模式 | URL、`加V` / `wx` / `vx`、QQ 群、Telegram、长数字串 |
| 词表 | 可外挂文件，以后能补而不改代码 |

**不要把这套叫「敏感词系统」。** 能真正扛住的中文过滤要处理谐音、拆字、同形字、
插入符号，那是独立项目或者接第三方（阿里云 / 腾讯云内容安全，按量付费）。
上线时诚实的说法是：**有基础管控 + 举报后处理**。

第二层是针对签名的，不是针对昵称的：签名 60 字且更自由，手游签名栏里
90% 的违规内容是**代练与外挂引流**，不是脏话。一份词表覆盖不了两种滥用。

## 七、实施顺序（八步）

每一步做完都能单独验证，不攒到最后一起测。

| 步 | 内容 | 主要文件 |
|---|---|---|
| **0** | **重构 `AccountManager` 的 HTTP 层**（见下，一切都压在它上面） | `scripts/autoload/AccountManager.gd` |
| 1 | 头像清单与缩略图 | `data/avatars.json`、`assets/ui/avatars/thumb/`、生成脚本 |
| 2 | 数据库迁移 | `database/004_profile_display.sql` |
| 3 | 后端 | `backend/app/routes/profile.py`、`profile.py`、`text_guard.py`、`avatar_catalog.py`；`players.py` 加建号时生成好友码 |
| 4 | 后端测试 | `backend/tests/test_profile.py` |
| 5 | 客户端门面 | `AccountManager` 加 `fetch_my_profile` / `update_profile` / `fetch_my_bio` / `update_bio` / `fetch_public_profile` |
| 6 | 界面 | `scenes/menu/ProfileScreen`、`AvatarPickerPanel`；`Main.gd` 路由；`MainMenu.gd` 换真数据 |
| 7 | 门禁 | `tools/profile_check.tscn` |

### 第 0 步为什么必须先做

`AccountManager._post` 今天有三个限制，资料系统一条都绕不开：

| 限制 | 资料系统的需要 |
|---|---|
| 只能发 POST | 要 GET / PATCH / PUT |
| 不带 `Authorization` 头 | 除公开视图外全部要带令牌 |
| **全类只有一个 `HTTPRequest` 节点** | 资料页会同时拉 `/me` 和 `/me/bio` |

第三条是真隐患：两个请求同时在飞时，`await _http.request_completed`
会收到**串台的信号**——A 请求拿到 B 的响应。这类 bug 不报错，
表现是「偶尔头像和名字对不上」，极难查。

改法：抽 `_request(method, path, payload, authed)`，**每次调用自建一个
`HTTPRequest`、用完 `queue_free`**。登录那两个调用改走同一入口，行为不变，
`tools/account_check.tscn` 必须继续全绿（它钉着「access token 永不落盘」）。

### 一条 UI 纪律

**昵称永远和好友码一起显示，任何地方都不许只显示昵称。**
`players.player_name` 不唯一（`001` 的设计），你叫 `Leno`，
别人改名成 `Leno` 就能冒充。这条要写进代码注释——否则三个月后
有人加个战绩列表就破了。

## 八、容易写错的地方

前四条是必须在动手前定好的。

### 🔴 1. 短 ID 撑不起搜索——好友码因此而来

`001` 定的是「同名玩家靠 `player_id` 前 4 位区分，例如 `Leno #52c7`」。
那是**同一个列表里几个同名的人**的显示区分符。

但默认名是 `Player`，匿名登录意味着**绝大多数玩家都叫 Player**。
四位 hex = 65536 种，按生日悖论，**同名玩家到 300 人左右就有 50% 概率撞短 ID**。

根因是把**显示区分符**当成了**查找键**：

| | 要求 | 长度 |
|---|---|---|
| 显示区分符 | 局部可分辨、好念 | 4 位够 |
| 查找键 | **全局唯一** | 要长得多 |

所以另加独立好友码，搜索按码精确查，**不做模糊搜名字**——在同名海啸下模糊搜
本来也没用。

### 🔴 2. 头像 id 与单位 id 脱钩

见第四节。

### 🔴 3. 正则是格式检查，不是授权检查

见第六节第 2 条。今天最坏结果只是头像显示空白（所有头像免费）；
等头像变成活动奖励或付费内容，**同一个洞就是白嫖限定头像**，
而且到那时还要处理已经写进去的脏数据。

| 层 | 管什么 |
|---|---|
| 数据库约束 | 格式对不对 |
| **应用层** | **id 存不存在、有没有资格用** |

### 🔴 4. 有 UGC 就必须有举报

昵称 + 签名 +（以后的）头像上传都是玩家可见的 UGC。
Google Play 的 UGC 政策与 App Store 审核指南 1.2 都要求提供举报机制；
审核员看到「能看别人的资料页、上面有自定义签名」就会问这件事。

**举报入口是发布必需项。**

### 5. 匿名账号 + 资料 = 在鼓励玩家往一个会消失的容器里投入

现在是匿名登录，没有绑定任何 provider。玩家花时间挑头像、写签名、填生日，
然后换手机——**全没了，而且找不回来**。

资料页恰恰是**第一个让玩家产生「我不想丢」的东西**，因此也是第一个让
「绑定账号」有说服力的地方——在此之前跟玩家说「绑定一下吧」，
他会问绑什么，反正也没东西。

**产品决定（2026-09-09）**：Google + Apple 登录要做，但**不进这一批**——
资料系统八步已经不小，而 OAuth 在 Godot 端是独立的真风险（见下）。
本批只在资料页留好「绑定账号防丢失」的入口位。

### 6. 生日礼物会撞上时区

以后做「生日当天送礼」时，跨时区玩家的「今天」不一样。不严重，但会有客服工单。
提前知道就行，现在不处理。

### 8. GDScript 里 `str(null)` 是 `"<null>"`，不是空串

后端有一批可空字段（`rename_available_at` / `signature` / `gender` / `region` /
`showcase_pet`）。JSON 的 `null` 解析进 GDScript 是 null 变体，而
`str(null)` 得到的是**字面量 `"<null>"`**。

直接写 `str(_data.get(key, ""))` 的后果是：**全新玩家会在界面上看到
「签名：<null>」「出战宠物：<null>」「下次可改名：<null>」** ——
而全新玩家正是最多的那一类。第一版预览截图就是这样，
所以 `ProfileScreen` 里所有读 `_data` 的地方一律走 `_field()` / `_field_int()`。

配套的 `scenes/debug/ProfileScreenReview.tscn` 有一个 `--shot=empty` 模式，
渲染的就是「什么都没填、可空字段全是 null」这个状态 —— 加字段时先看那一张。

### 7. 缓存会和隐私打架

如果为了性能缓存公开视图，玩家把生日改成隐藏之后，缓存里还留着。
**第一版不缓存，直接查库。** 量级不到需要缓存的时候提前优化，
这里会直接产生隐私 bug。

## 九、绑定登录（不在本批，但工作量先记下来）

产品已确认 Google 和 Apple 都要做。

| 部分 | 难度 | 说明 |
|---|---|---|
| Supabase 配 Google provider | 🟢 半天 | Dashboard 填 client id / secret |
| Google Cloud Console 建 OAuth 客户端 | 🟢 半天 | 流程标准 |
| **Godot 里走 OAuth 流程** | 🔴 **2-3 天，不确定性全在这** | 见下 |
| 匿名账号原地升级 | 🟢 已经设计对了 | 见下 |
| 冲突处理 | 🟡 1 天 | 见下 |
| Sign in with Apple | 🔴 | 审核指南 4.8：用了第三方登录就**必须**同时提供 |

**难点在 Godot 端：** 移动端 OAuth 要么拉起系统浏览器再用 deep link 回调
（Android 要配 intent-filter，还要处理 app 被系统回收后回来的情况），
要么接 Google Sign-In 的 Android SDK（需要 Godot 插件）。Godot 4 没有官方方案。

**一个好消息：** `database/003_player_identities.sql` 的注释里已经写了——
Supabase 匿名用户**原地升级**成正式账号时 `auth uid` 不变，
所以 `player_identities` 连新增一行都不用。这块当初设计对了。

**一个要提前想的：** 玩家在手机和平板各玩了一阵，各有一个匿名账号，
现在想都绑同一个 Google。**账号合并很麻烦**，第一版直接**拒绝并提示
「这个 Google 账号已绑定另一个存档」**，不做合并。

对应 RFC `9.3`（首个 Auth provider 选什么）——那一条现在从「以后再说」
变成了有明确答案：Google + Apple，排在资料系统之后。

> **2026-09-09 修订顺序。** 上面「排在资料系统之后」不够精确，实际约束是：
> **绑定登录不是任何功能的前置，它是「有真实玩家」的前置。**
> 今天没有已发布客户端，所以「换手机丢号」影响 0 个人，交友系统可以先做。
> 但必须写下硬触发条件，否则会无限往后滑（正是本节第 5 条描述的那个模式）：
>
> **任何形式的对外发行（把内测包发给非团队成员也算）之前，绑定登录必须可用。**
>
> 另：已确认**不绑邮箱**，就是 Google + Apple。既然本节把它标成 🔴「2-3 天，
> 不确定性全在这」，建议提前花一天做 timebox 技术验证（只验 Godot 里能不能
> 跑通一次 Google 登录回调），别等到发行前才发现卡住。
> 详见 `docs/交友系统设计.md` 第一节。

## 十、非目标

- **不放假数据。** 等级 / 段位 / 战绩的**真实值**一律不填，占位区块明写「敬请期待」。
- **不把进度数据放进公开视图。** 图鉴、拥有宠物属于进度同步项目（RFC `9.5`）。
- **不动 `001` / `002` / `003`。** 编号只增不改。
- **不做账号合并。** 见第九节。
- **不碰 ENet。** 本系统全部在 ①↔② 的 HTTPS 链路上，与 `C14` 零交集。
  「在房间里点对手头像看资料」需要往 `NetProtocol` 加账号身份字段，
  那是 RFC 第六节 🔴 第 3 条，等 `C14`。
