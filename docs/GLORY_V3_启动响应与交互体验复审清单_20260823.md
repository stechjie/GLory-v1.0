## 0. 结论与优先级

用户反馈的三个现象都成立，并且不是互相独立的小问题：

1. **加载偶发卡顿：已复现。** Activity 很快显示，但 Godot 初始化后立即把 96 项 VFX 预热放到场景树根节点，与语言页、教程和备战交互并发。真机日志出现 40–105 ms 的主线程处理帧，首屏进入备战时画面一度显示 `FPS 1`。
2. **确认界面不好看：已复现。** 教程“跳过”确认框由脚本临时拼出，按钮几乎是 Godot 默认样式；项目没有全局 Theme，42 处 `StyleBoxFlat.new()`、73 处 `Button.new()` 分散在代码里，弹窗之间没有一致的视觉和交互合同。
3. **点击 APK 偶尔没反应：玩家感知已复现，未发现 ANR/崩溃。** Android Activity 约 0.2–0.3 秒显示，但玩家还要经过黑屏、默认 Godot splash 和初始化，约 3–4 秒后才看到可交互语言页。首个控件出现前的点击没有任何反馈；进入 UI 后又可能被预热长帧、不可见加载条或全屏 `MOUSE_FILTER_STOP` 层延迟/吞掉。

因此不能只“美化一个弹窗”或“给按钮加动画”。正确顺序是：

1. 先建立启动与输入响应指标，消除重复同步工作和首屏预热竞争；
2. 再让每次异步动作都有立即、可见、可恢复的状态；
3. 然后建立统一 UI Theme、按钮和弹窗组件；
4. 最后补自动化压力测试、真机性能门禁和体验细化。

V2 中的资源缺失、白模、假绿检查仍是独立 P0。本清单不得用 UI 改造掩盖资源红灯，也不得在资源不完整时宣称整包验收通过。

## 2. 统一验收口径

后续每个 AI 任务都必须区分以下时间点，不允许只拿 `Activity displayed` 冒充“秒开”：

| 指标 | 定义 | 当前目标 |
| --- | --- | --- |
| T0 `process_start` | Android 进程启动 | 记录，不单独设体验目标 |
| T1 `first_branded_frame` | 首个非黑屏、可辨认 Glory 的画面真正 present | 当前真机冷启动 ≤ 800 ms，且无连续黑屏 > 500 ms |
| T2 `godot_main_ready` | 主场景 `_ready()` 完成 | 记录并拆解耗时 |
| T3 `first_input_ready` | 首个按钮可接受输入并能在 100 ms 内反馈 | 当前真机热缓存 ≤ 2 s、冷缓存 ≤ 3 s |
| T4 `first_action_complete` | 首次语言/继续/进入菜单动作完成 | 记录成功/失败/取消原因 |
| 交互帧 | 从 T3 起、玩家可操作页面上的帧 | 单帧不超过 50 ms；目标 1% low ≥ 45 FPS（60 Hz 口径） |
| 输入反馈 | touch down 到按压态/忙碌态可见 | P95 ≤ 100 ms，P99 ≤ 150 ms |
| 静默等待 | 按钮被禁用但无可见状态/解释 | 必须为 0 |

真机报告必须包含 APK SHA-256、包名、versionCode、Git commit、设备型号、Android 版本、刷新率、冷/热缓存条件。缺任一项时只能标记“开发样本”，不能标记 release 通过。

## 3. P0：先修“卡顿”和“点了没反应”

### [ ] P0-01 建立 `StartupTrace` 与可追溯构建身份

**目标**：先让每次启动都能回答“慢在哪一段、玩家何时能点击、测的是哪份代码”。

**AI 实施**：

1. 新增 autoload `scripts/autoload/StartupTrace.gd`，提供 `mark(name, metadata)`、`mark_first_frame()`、`mark_input_ready(screen)`、`mark_first_action(action, result)`。
2. 所有标记同时写结构化单行日志 `GLORY_STARTUP {...}`；Debug 可写 `user://startup_trace.jsonl`，Release 默认只保留聚合，不记录账号/房间/token。
3. 新增构建步骤生成 `res://build_info.json`：`git_commit`、dirty 状态、build time、package id、versionCode、preset、asset manifest fingerprint。运行时首条日志必须打印这些字段。
4. `Main.gd`、Bootstrap、语言/菜单/教程页与第一次有效按钮动作接入标记；每个标记只允许写一次。
5. 扩展 `tools/android_smoke.sh`，从 logcat 解析 T1–T4，超过阈值非 0 退出。

**自动测试**：伪时钟测试标记顺序、重复标记、缺标记、JSON 可解析；检查 Release 日志不含 token、IP、用户目录。

**验收**：一条命令生成包含 T0–T4、APK 身份和阈值判定的 JSON；报告不能再只输出 `Displayed +xxxms`。

### [ ] P0-02 增加轻量 Bootstrap 场景和 Glory 品牌启动画面

**目标**：点击图标后立刻看到“应用已响应”，同时把昂贵初始化从首帧移走。

**AI 实施**：

1. 新增 `scenes/bootstrap/Bootstrap.tscn/.gd`，作为 `run/main_scene`。场景只能包含纯 2D 品牌图、背景、轻量进度/呼吸动画和状态文本，不引用 3D、VFX、战斗模型或大图集。
2. 在 `export_presets.template.cfg` 配置同风格 Android/Godot splash；由现有 logo/可商用项目资源制作，不新增来源不明素材。系统启动页、Godot splash、Bootstrap 的背景色和横屏方向保持一致，避免竖屏启动器 → 横屏黑场 → 默认 Godot 标志的割裂。
3. Bootstrap 第一帧后再异步进入 Main；只在必要数据 ready 后显示可点击按钮。初始化期间显示真实阶段：`准备数据`、`载入界面`、`恢复存档`。
4. Bootstrap 自身加载失败时显示可操作的“重试/清理缓存说明/退出”，不能永久黑屏。

**验收**：真机 T1 ≤ 800 ms；从点击图标到 T3 之间始终有 Glory 品牌画面或明确状态；连续录屏逐帧检查无黑场 > 500 ms。

### [ ] P0-03 消除 `DataRegistry.load_all()` 重复同步加载

**目标**：每个进程只读取/解析一次静态 JSON，失败可诊断。

**AI 实施**：

1. 明确唯一所有者：建议保留 `DataRegistry._ready()`，删除 `Main._ready()` 的重复调用。
2. 给 `DataRegistry` 增加 `UNINITIALIZED/LOADING/READY/FAILED` 状态、`ready` 信号和幂等 `ensure_loaded()`；重复调用不再读盘。
3. 将开发期全量 schema 检查与玩家启动所需最小解析分开；Release 首屏只做必需检查，完整校验留在 CI/导出门禁。
4. 每个 JSON 记录文件大小、读取、解析、校验耗时和失败路径，但不打印完整内容。

**自动测试**：连续调用三次 `ensure_loaded()`，文件读取计数仍为 1；损坏 JSON 返回 FAILED 并显示错误页，不允许空字典继续运行。

**验收**：启动 trace 中只有一次 registry load；数据耗时下降且现有数据检查保持全绿。

### [ ] P0-04 重构 VFX 预热为“可暂停、可预算、可观测”的调度器

**目标**：保留首战所需 shader/pipeline 预热，但绝不与玩家正在点击的页面抢主线程。

**AI 实施**：

1. 将 `VFXWarmup` 从“创建后自主跑完”改成 `WarmupScheduler`：状态为 `PAUSED/IDLE_WINDOW/NON_INTERACTIVE/RUNNING/CANCELLED/FINISHED`。
2. Bootstrap/不可交互加载页只跑真正阻塞首战的最小集合；语言页、教程拖拽、商店、备战和弹窗打开期间默认暂停。
3. 记录最近输入时间；最近 500 ms 有 touch/mouse/key、当前帧 > 16.7 ms、页面正在 transition 或内存超预算时，本帧不启动新项。

## 7. AI 每项任务的固定交付格式

后续把任一 checkbox 交给 AI 时，要求按以下格式返回：
