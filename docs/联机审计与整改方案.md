## 一、总体结论

问题不是一堆孤立 bug,而是**一个贯穿始终的模式**:

> 客户端把算好的结果告诉服务器,服务器只做格式清洗,然后当权威广播出去。

金币、羁绊(`syn`)、宝物、宠物、星级、种族关系——全是这个模式的实例。架构方向
(专用服务器权威)是对的,但"权威"目前只体现在**格式**上,不体现在**数值**上。

第二个结构性问题:**服务器把所有事情放在一个进程的一个主循环里同步做**——所有房间
共用一个 `GameState` 全局、战斗模拟阻塞心跳、状态全在内存、重启即全场掉线。现有那一堆
掉线补丁(冻结宽恕、放宽心跳、僵尸清道夫、看门狗)都是这个结构的止痛药。

**热修部分能显著收敛最严重的作弊和掉线;结构性部分(经济权威化、房间隔离、持久化)
需要真正改造,短期修不完,要接受这个现实。**

带走一条规则,比带走这张清单有用:

> **这个字段是派生的吗?如果是,服务器为什么不自己算?**
> 凡是客户端能算出来的,服务器都能算,就没有理由让客户端传。
> 只有真正的"意图"(我买 3 号位、我把 A 放到 4 号格、我选这件宝物)才该上行。

### A 级:现在就能被利用

## 三、整改方案(分批)

### 第 0 批:建立验证能力(零风险,先做)

1. 收窄 headless 自动起服务器条件为只认 `--server`(C12)
2. 写 `tools/adversarial_client_node.gd`,**先对未修复的代码跑一遍拿基线**
3. 埋点:replay / team_boards / match_state 的真实字节数、压缩率、发送耗时、重传次数、pong 延迟
4. 加服务端特性开关(启动读 JSON 或 SIGHUP 重载),让第一批每一项都能单独关掉
5. 修打包脚本 `$src`、排除 `.bak`(C15 部分)

> **第 0 批是后面一切决策的数据来源。** 尤其第 3 项埋点——replay 到底多大目前全是估算,
> 它直接决定要不要走确定性那条重路(见第七节)。

### 第 1 批:服务端热修,**一次部署推完**

| 项 | 内容 | 风险 |
|---|---|---|
| 1 | `match_state` 改到 replay 之前发(B1) | 极低 |
| 2 | `server_relay = false`,在 `create_server()` 之前(A2) | 低,已核对无客户端依赖 |
| 3 | 服务端覆盖重算 `syn` + 全部入算浮点加 `is_finite()`(A1) | **中,影子模式** |
| 4 | 容器早退 + 字段数量/字符串长度上限;首次超限即断开+计数(A3) | 低 |
| 5 | 停止专服路径广播 `team_boards`,**保留 RPC 方法**(B3、A4) | 低,需先跑 4 场景 |
| 6 | 敌方 replay 改按需拉取(`replay_request`),不再默认双发(B2) | 低,立刻砍一半带宽 |
| 7 | 一人一房、房间总量上限、限流(peer 严/token 次/IP 只记录/全服熔断)(A6、A7) | 低 |
| 8 | 锁盘后生成每回合独立 seed;resume 不再下发 seed;RNG 流隔离覆盖经济结算(A4、C3) | 中高 |
| 9 | 在线暂时禁用黄金祭坛与赌博(C1、C2) | 低(技术),**产品需配套** |
| 10 | 宝物数量上界 = **严格小于当前回合**的宝物轮次数(A5 部分) | **中,影子模式** |
| 11 | session token 换 `Crypto.generate_random_bytes(32).hex_encode()`(纯替换,不含轮换)(C4) | 低 |

**影子模式**:第 3、10 项和金币差值统计,服务端两套都算、只记日志差异、不生效。
跑够一周零差异再翻开关。宝物上界在数据哈希(C11)上线前也只能跑影子模式,否则一次
数据表不同步就把诚实玩家判成作弊。

**限流四维**:per-peer 最严 → per-token 次之 → per-IP 只记录不拦截(CGNAT 下一个公网 IP
后面可能几千玩家,阈值等埋点出真实分布再定)→ 全服总量做最后熔断。

**部署纪律**:11 项打包成**一次**低峰窗口部署,不要分 11 次(每次 restart 都是一次全场
掉线)。配合第 0 批的特性开关,任一项翻车能单独关掉而不必再 restart。

### 第 2 批:session token 轮换(单独一批)

两阶段轮换 + ACK:
- 服务器签发 `new_token + token_revision`,旧 token 保留短期 grace
- 客户端保存成功后发 ACK,服务器收到 ACK 才彻底撤销旧 token
- 超时未 ACK 允许旧 token 再恢复一次
- 原子更新 `_token_seat` / `room.seat_tokens` / `_public_token_seat` / 客户端内存与磁盘

**排最后,因为它是唯一一个"失败模式比它防的攻击更糟"的项目**——写错就是玩家永久回不去
对局。而且轮换防的是线路窃取,收益要等第 3 批加密后才完整(明文下窃取存档一样能拿新 token)。

### 第 3 批:协议升级(客户端+服务端同发,协议号 +1)

- 握手校验 `protocol_version + client_build_id + simulation_manifest_sha256 + data_manifest_sha256`
  (manifest **构建期生成编进包**,不能运行时算)
- 接收型 RPC 改 `authority`
- 完整状态信封 `room_id + match_epoch + round_id + phase + phase_revision + message_id`
  + ACK + 幂等(客户端也拒收 revision 倒退的包)
- 删除 1v1 遗留 RPC(C13)
- resume 快照补全(C5) + `snapshot_revision` + 明确合并规则
- **分块 replay 协议**(见下)

#### 分块 replay 协议(第 3 批核心)

依据是**工程约束**,不是已确认的 Godot bug:限制单次分配/反序列化大小、避免可靠通道队头
阻塞、支持断点补传、完整性校验、避免底层自动分片导致一次丢包重传整包。

> 注:GitHub issue #82160 常被引为"可靠大包会被静默丢弃"的证据,但它的环境是
> 4.1.1 + pyenet + SSH/TCP 隧道 + `unsequenced+unreliable_fragment`,无 Godot-to-Godot
> 最小复现,archived 关闭。它说明的是**依赖隐式分片、缺乏可观测性**的风险,**不能**
> 证明 Godot-to-Godot 可靠 RPC 在某尺寸存在通用静默丢包缺陷。分块的理由是上面那串
> 工程约束,不是这个 issue。

**battle_manifest**(承载校验信息,不塞进 match_state,避免重发/覆盖/迟到导致错配):
```
battle_manifest:
  battle_id
  protocol_version
  simulation_version
  data_registry_hash
  input_hash            # 验证 seed、双方棋盘含星级、treasures、syn、pet 一致
  replay_hash           # 验证分块重组后 replay 字节完整
  final_state_hash      # 验证模拟最终结果一致
  replay_size
  chunk_count
```

**三种哈希回答三个不同问题**,缺一不可:
- `input_hash`:输入是否一致(seed/棋盘/星级/派生数据)
- `replay_hash`:传输内容是否完整(分块重组后字节)
- `final_state_hash`:模拟结果是否一致

只有 `final_state_hash` 无法区分"输入不同 / 模拟分叉 / replay 传坏了"三种情况。

**传输协议**(应用层 ACK 只确认"业务对象完整",不逐 UDP 包确认——那是 ENet 可靠层的活):
```
replay_begin(manifest)
replay_chunk(battle_id, index, bytes)
replay_status(battle_id, received_bitset)   # 每 16/32 chunk 汇报一次,避免 ACK 风暴
replay_missing(battle_id, missing_indices)
replay_complete(battle_id, replay_hash)
replay_abort(battle_id)                       # 重连落后者:跳过播放,直接用 match_state 结果
```
- 单块大小从 16–64 KiB **实测**,不要直接认定固定安全值
- **match_state(小、独立通道、必达)永远是权威结算;replay(大)是可跳过的播放素材**
- 分块前先量化/压缩:`var_to_bytes(replay)` → `raw.compress(FileAccess.COMPRESSION_ZSTD)`

**规范化序列化**(哈希前必须规定,否则 Dictionary 顺序/浮点表示/Variant 差异造假 desync):
- 字段固定顺序、数组顺序固定、单位按稳定 ID 排序
- 整数宽度和字节序固定
- 禁止 Node/Resource/RID/实例 ID
- 浮点量化为整数,或明确 IEEE 位模式
- 缺失字段和默认值统一编码
- **哈希对象是"离散分支结果"(hp:int、alive、目标 uid、技能 ready、行动顺序),不是量化
  坐标**——坐标漂移无所谓,分支翻转才致命。量化位置哈希会把分叉藏到后面才爆
- `String.hash()` 不用于协议完整性(32 位、易碰撞);replay/最终状态用 SHA-256,逐帧调试
  可用稳定 64 位哈希、最终再 SHA-256

**input_hash 的额外收益**:它覆盖 `(seed, 双方棋盘含星级, treasures, syn, pet)`,而 P0 我们
在服务端重算 syn。客户端与服务端交换 input_hash,就是**在线实时验证"客户端派生的 syn 和
服务端重建的 syn 一不一致"**——影子模式想离线回答的问题,input_hash 在线就答了,不一致直接
暴露 battle_id。一个字段同时服务确定性和反作弊。

### P1 / P2:结构性

- **确定性准入门槛**(见第七节):replay 分块压缩 → 埋点看压缩后大小 → 够小就停在权威 replay,
  太大才启动确定性测试矩阵 → 达标才切"客户端模拟为主、权威 replay 兜底"
- 消除浮点分叉源:伤害管线的 `float × 系数 + round()/int()`(如 `_apply_attack` 的 god_lifesteal
  `int(round(float(dealt) * ...))`)改定点/整数(千分比整数),把分叉面从弥散变成可消除
- `BattleContext` 去全局化 → 之后才能线程化(**先纯输入纯输出,再线程化**,否则数据竞争从
  "可能发生"变"稳定发生")
- 服务端备战账本(买/卖/刷新/祭坛/赌博全部 intent 化),经济彻底权威化
- 房间隔离为独立对象;HMAC token + 房间状态持久化
- 服务器地址下发(静态 HTTPS 端点返回 host/port/最低版本)+ 蓝绿部署
- 传输加密:DTLS(`ENetConnection.dtls_server_setup/dtls_client_setup` **API 存在但接入路径需先
  做最小原型**——`host` 只有 getter、`create_client()` 已开始连接、客户端配置须在 `connect_to_host()`
  前),P2

## 四、修改后对游戏的影响

### 玩家能感觉到的正面变化

- **结算不再卡**:`match_state` 不再排在几 MB 回放后面,战斗结束到结算面板的等待明显缩短
- **每回合少收一多半大包**:停 `team_boards` 广播 + 敌方 replay 改按需,弱网加载更快、掉线率下降
- **作弊者消失**:无敌秒杀这类离谱局面不会再出现

### 玩家能感觉到的负面变化——需要提前准备

| 变化 | 影响 | 建议处理 |
|---|---|---|
| **黄金祭坛/生财之道在线禁用** | 已持有者留着一件废物占宝物栏 | **产品决定,不是技术开关**。上线前定:从在线池移除+已持有者免费替换,或延后到服务端 intent 做完 |
| **战斗结果会和现在不同** | seed 改成锁盘后生成,同阵容打出的结果与今天不一样 | 玩家感知不到"变了"(本来就随机),但**不要在赛季中途改**,挑赛季边界 |
| **`syn` 重算若口径有差,战斗会静默改变** | 服务端只数棋盘、不含佣兵栏,必须和 `count_races_from_board` 完全一致 | 影子模式跑满一周零差异才生效 |
| **宝物上界可能误伤** | 依赖服务端与客户端 `round_schedule.json` 一致,不一致就误判 | 数据哈希握手上线前只跑影子模式 |
| **限流可能误伤** | CGNAT 下一个公网 IP 后面可能几千玩家 | per-IP 第一批只记录不拦截,等真实分布出来再定阈值 |
| **部署当次全服掉线** | 在场对局全部丢失(B5 未修) | 挑低峰窗口、提前公告、11 项一次推完 |

### 修完第一批之后**仍然存在**的问题(避免误判安全水位)

- **金币仍可伪造**(备战账本要到 P1),宝物**选择**仍可伪造(只限住了数量)
- **一个房间算战斗仍会冻住全服**(B4 未动)
- **重启仍杀全场**(B5 未动)
- **线路仍是明文**(C14 未动)
- **回合号仍是双份真相**(B6 要等状态信封)

第一批解决的是:**最严重的作弊(无敌秒杀)、最容易被无意触发的崩服路径(单包冻结)、
以及掉线的两个直接推手(发送顺序、冗余大包)。这是止血,不是治愈。**

## 五、业界与开源对照

审查方向经开源与业界共识印证,**没有一条需要推翻**。

**"派生数据服务端重建" = 业界标准。** Godot 多人游戏通行原则是只同步真正需要共享的最小集
(通常位置),其余本地推导。这正是本文"派生字段服务端重建"的通用版。
(注:此为通行原则,非 `MultiplayerSynchronizer` 文档的强制条文。)

**"传输入不传状态" = 确定性 lockstep 的定义。** 只发控制系统的输入、不发状态,带宽正比于
输入大小而非对象数量——自走棋/RTS 的教科书做法。我们现在传逐帧 replay 恰是它反对的。

**"replay 走独立 channel、心跳走 channel 0" = ENet 官方推荐。** Godot 4.0 官方确认:可靠/有序
模式下投递顺序按 channel 独立保证,一个 channel 阻塞不拖住另一个。传大数据用独立 channel
是官方点名的降延迟、降断线手段。(注:加 `transfer_channel` 前须先改 `create_server`/`create_client`
的 `max_channels`,两端都要。)

**跨平台浮点确定性极难。** Gaffer On Games 明确警告:同机确定 ≠ 跨编译器/OS/架构确定。这正是
我们要在 Android ARM64 和 Linux x86_64 之间做逐位一致的场景——所以确定性这条路必须带压缩
权威 replay 兜底,且有跨平台准入门槛(见第七节)。

**Godot 提供 authority/sender ID/RPC 权限等基础设施,但不提供规则校验、经济账本、身份认证和
反作弊系统**——引擎不替我们兜底,服务端校验是唯一防线。

**开源帮不上的地方**:扫过的 Godot 多人模板(lazercube、devmoreir4、AlixBarreaux、Svengali 等)
全是通用 3D 角色同步(位置/旋转插值),**没有一个是自走棋/回合制/带经济系统的**。所以**安全和
replay 照业界共识走;经济账本和重连/座位保留/AI 代打是我们自己的深水区,只能自己设计**——
而我们这套虽然补丁多,功能上已经比大多数开源模板走得远。

参考:
- Godot 官方:Multiplayer changes in Godot 4.0 — channels & ordering
  https://godotengine.org/article/multiplayer-changes-godot-4-0-report-2/
- Gaffer On Games:Deterministic Lockstep — https://gafferongames.com/post/deterministic_lockstep/
- Godot issue #82160(被否决的"大包静默丢包"证据)— https://github.com/godotengine/godot/issues/82160
- mas-bandwidth:Choosing the right network model
  https://mas-bandwidth.com/choosing-the-right-network-model-for-your-multiplayer-game/

## 六、被否决的捷径及原因

这些否定性结论最容易被下一个人重新踩一遍,单独留档:

| 想过的捷径 | 为什么不成立 |
|---|---|
| **改服务端 `@rpc` 注解就能单边止血 A2** | RPC 权限由**接收端**执行。只改服务器,旧客户端本地仍是 `any_peer`,照样接受另一个旧客户端伪造的包。止血靠 `server_relay=false`。<br>*(注:本项目已无已发布客户端,注解与删除已随客户端一并完成)* |
| **删掉 1v1 死路径就顺手放进 P0** | 删/改 `@rpc` 方法会平移整套 RPC 的 wire ID,新旧混连静默调错函数——**前提是线上有老客户端**。本项目尚未上线,该前提不成立,已直接删除。<br>**上线后这条重新生效**,届时任何 RPC 增删都必须协议号 +1 且两端同发 |
| **禁用生财之道赌博来"堵金币洞"** | 赌博只动金币,而金币本就 100% 客户端自报。对诚实玩家它是正常工作的;想作弊的人直接改存档,根本不需要这个按钮。禁用零安全收益、纯删功能 |
| **`local_ready` / `toggle_ready` 是单机在用,要保留** | 凭印象的判断。实际逐个追引用后发现:`_on_toggle_ready` 定义了但**无任何调用点**;`local_ready` 唯一读点是 `PrepUI` 里一个 `elif is_online()` 分支,而删掉 1v1 后 `is_online()` 必然蕴含 `team_active`,该分支永不可达。**删代码前必须逐个 grep 确认,不能凭印象** |
| **服务端只读 `room.slot_gold`、不读 `snap.gold` 就修好经济** | 服务器不知道备战期的买/卖/刷新/祭坛/赌博。直接用 slot_gold 当下轮 `gold_before`,诚实玩家花掉的钱会被加回来 = 所有购买免费。必须先做备战账本(P1) |
| **金币上界检查 `snap.gold <= room.slot_gold`** | 生财之道赌博一次就能合法翻倍,这条规则会把所有用赌博的玩家判成作弊 |
| **宝物上界用 `owned.size() <= 当前回合`** | 宝物在第 4/8/12/16/20 回合**战后**获得,`<=当前回合`会让第 4 回合开打前就能带一件。必须是**严格小于当前回合**的宝物轮次数 |
| **从最终棋盘重建 `race_relations`** | 关系进度是跨回合累积状态,服务端没有历史,光靠最终棋盘重建不出来。启用前必须先做服务端玩家状态 |
| **`battle_state_checksum` 放进 `match_state`** | match_state 会重发、被下一回合覆盖、迟到,checksum 会和战斗错配。必须放独立的 `battle_manifest` |
| **只放一个 checksum 验证确定性** | 无法区分"输入不同 / 模拟分叉 / replay 传坏了"。要 input/replay/final_state 三种哈希 |
| **直接对 Godot `Dictionary` 做哈希** | 顺序/浮点表示/Variant 差异造假 desync。必须先规范化序列化 |
| **量化坐标做 checkpoint 哈希** | 内部仍跑浮点时,两平台可能量化到同一 int、哈希相等,内部已分叉、后面才爆。要哈希离散分支结果 |
| **`ENet + DTLS` 是低成本加密** | API 存在但 `host` 只有 getter、`create_client()` 已开始连接、配置须在 `connect_to_host()` 前,便利构造插不进去,需最小原型。降 P2 |
| **WSS 加密替代 ENet** | WSS 是 TCP,队头阻塞是整条连接级(比 ENet 单 channel 级严重),会**加重**我们最痛的掉线问题,且丢掉多 channel 隔离 |
| **`determinism_check_node.gd` 已证明确定性** | 它只覆盖 4 种单位/单 seed/同进程,且**在一个自动启动的服务器旁边跑**(C12),结果作废,重做 |

## 七、补充与遗留决策

### 需要写进代码的三处小注释

1. `RaceRelationService.ENABLED` 上加注释:开启前置条件是**服务端要有跨回合玩家状态**,
   否则同时打开一个作弊面和一个不可重建的状态。防止有人顺手改成 `true`。
2. `NETWORK_PROTOCOL_VERSION` 注释补上:**删除和重命名 `@rpc` 方法同样致命(平移 wire ID),
   改注解不改 ID 但仍需两端同发**。这是唯一会被下一个改协议的人读到的地方。
3. 伤害管线的浮点→整数截断点(如 god_lifesteal `int(round(float(dealt) * ...))`)标注为
   确定性风险点,P1 定点化时优先处理。

### 确定性这条路的决策链(不要提前承诺)

seed+input 客户端模拟的代价是把整条战斗管线改定点/穷尽跨平台测试——**很重**。它买的是带宽。
但我们连 replay 到底多大都还是估算。正确的决策链:

```
P0 埋点量真实 replay 大小
  → 分块+压缩权威 replay(无论如何都要做)
  → 看压缩后大小
      ├─ 够小(如 <100KB):停在这里,永远用权威 replay,不碰确定性雷区
      └─ 仍太大:才启动确定性测试矩阵
              → Windows x86_64 / Linux x86_64 / Android ARM64 / Debug+Release
              → 数万组固定战斗语料,逐 checkpoint + 最终状态完全一致
              → 达标才切"客户端模拟为主、权威 replay 兜底"
```

**在这些测试通过前:服务端权威 replay 是正式路径,客户端确定性模拟是实验路径。**
否则客户端只有整场播完才发现结果错,玩家仍先看了一场"假战斗"。

### 还需要产品拍板的(技术问题都已收敛)

1. **黄金祭坛/赌博在线禁用后,已持有者怎么办**——退宝物栏 / 免费替换 / 延后到服务端
   intent 做完再上?影响玩家,需产品定。
2. **确定性这条路追不追**——但**现在不用定**,等 P0 埋点出 replay 大小再定(见上)。

### 对抗性测试台(`tools/adversarial_client_node.gd`)覆盖清单

巨大载荷测试只打**隔离服务器**并给服务器进程加 watchdog,避免冻住开发服。覆盖:
- 超长 treasures / race_relations / syn
- `NaN` / `INF` / 超大整数
- 重复与乱序 board submission
- 旧 round / 旧 room / 旧 token
- token 轮换响应丢失
- 同一 peer 连续创建/加入不同房间
- match_state / replay 重复发送
- RESULT 阶段多玩家同时 ACK
- replay 发送中断后恢复
- 同公网 IP 多个正常 peer,验证 IP 限流不过度误伤

每条 P0 修复对应这里一个用例。它也是回归网:以后加 RPC 先跑一遍。

### 遗留的小 bug(顺手记,别丢)

- `_room_try_finalize_boards` 内部不检查 `room.state`,安全靠 5 个调用点各自先判 `ROOM_BATTLE`。
  目前 5 处都判了,但漏一个就会同一回合算两次战斗、扣两次 HP。守卫应收进函数内部 + 幂等键。
- `_public_token_seat` / `_peer_public_token` 从不清理(peer 断开也不 erase),内存无限涨。
- `settle_post_battle_gold` 的 RNG 消费(C3)要和 token/房间号/宝物 roll 分成独立 RNG 流。

## 八、服务器部署

### 打包

双击 `make_server_zip.bat`(或 PowerShell 跑 `.\make_server_zip.ps1`)。

脚本已修好并实跑验证过:
- `$src` 默认取**脚本自身所在目录**(`$PSScriptRoot`),换机器/换用户名都不用改代码;
  打别处的项目用 `.\make_server_zip.ps1 -Src "D:\path\to\GLory-v1.0"`
- 自动剔除 `*.bak / *.tmp / *.orig`(`BattleSimulator.gd.bak` 一个就 112KB,且是过期实现,
  混在包里会被误读成现行代码)
- 输出文件名固定不带版本号,杜绝「传了 v4 解压了 v5」
- 结尾打印协议号与打包时间,写进包内 `build_info.txt`

最近一次验证:455 个文件 / 869,545 字节 / protocol 6,`.bak` 零,新增的
`ServerFlags.gd`、`adversarial_client*` 均已包含。

### 上传与重启

```
1. 上传 glory_server_upload.zip
2. unzip -o ~/glory_server_upload.zip -d ~/Glory/"Beta 0.04"
3. sudo systemctl restart glory-server
4. journalctl -u glory-server -n 3 --no-pager
   ^ 看到 server starting protocol=6 才算部署成功
```

**协议号必须与打包时打印的一致**,不一致说明解压到了错的目录或没重启成功。

- 配合 `ServerFlags` 特性开关:任一项出问题可单独关掉,**不必再 restart**

```json
{
  "metrics_payload_sizes": true,
  "metrics_sample_every_n_battles": 1,
  "send_rival_replay": true
}
```

| 开关 | 默认 | 说明 |
|---|---|---|
| `metrics_payload_sizes` | `false` | 载荷埋点。`var_to_bytes` 一份大 replay 本身有 CPU 开销,而服务器是同步主循环——**只在测量周开** |
| `metrics_sample_every_n_battles` | `1` | 每 N 场采样一次。测量周先用 1,量到 P99 后调大或关掉 |
| `send_rival_replay` | `true` | 敌方 replay(观战用)。关掉能省约一半 replay 出口流量,但**观战敌方会变空**——那是删功能。用途是测量周临时关掉量带宽 |

### 部署后要盯的日志

三个影子模式前缀,它们决定后续批次怎么做:

| 前缀 | 含义 | 该怎么读 |
|---|---|---|
| `shadow syn_mismatch` | 客户端派生的 syn 与服务端重建的不一致 | **应恒为零**。非零说明两边对羁绊的理解有分歧,玩家界面会和实际战斗对不上 |
| `shadow treasure_overflow` | 宝物数量超过该回合应有上限 | 大量出现多半是**数据表不同步**而非作弊(依赖 `round_schedule.json` 两端一致,见 C11) |
| `shadow gold_delta` | 上报金币与上一战结算值的差 | **这是 P1 备战账本要覆盖哪些路径的唯一依据**。差值来源:买卖、刷新、赌博、祭坛 |

另有 `rate limit` / `zombie peer reaped` / `board watchdog` / `metrics` 前缀可用于观察限流误伤、
僵尸连接、看门狗介入频率和 replay 真实体积。
