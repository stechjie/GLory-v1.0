### 已确认的 3v3 产品规则与必要工程解释（2026-07-28）

> 每项开头的产品语义来自本次确认；其后的协议、缓存、ACK 与安全约束是实现这些规则所需的
> 工程解释，不表示代码已经完成。

1. **固定的是 6 个逻辑参赛席位，不是必须有 6 名真人才能开局。** 一个房间始终由
   队伍 A、队伍 B 各 3 个席位组成；允许空席、1v1、3v1、2v2 以及真人和 AI 混合开局，
   只要两队各至少有一个真人或明确 AI 席位，且联机房整体至少仍有一名真人。这里的
   “1v1/3v1/2v2”只描述六席房内的实际占席结构，不是已经删除的旧 1v1 P2P 模式。
   纯 AI 对局仅允许本地/测试使用，不能创建或维持联机房。人数变化不能折叠
   `slot_id/team_id` 结构。
2. **所有真人玩家平等。** 无论属于哪支队伍、位于哪个 slot、是否为 leader，每名真人在
   replay 完整度与自动发送、传输优先级、重试/超时、断线恢复、权威结算、缓存和 ACK 规则上
   使用同一套策略。队伍只表示比赛归属和结果视角，不表示服务等级。
3. **AI 只是既有参赛席位的替代控制者。** AI 可以占用空席或接管离线/离开的真人席位；
   接管后原 `slot_id`、`team_id`、战斗结算和 replay 结构不变。AI 没有网络会话、session token
   或 replay 接收端，也不能被计作“在线真人”来维持房间。
4. **leader 只是大厅管理角色。** 当前 leader 仍在线时不改选；需要接任时，从当前在线真人中
   选择该房间 `join_seq` 最小者（最早成功加入者），不得按 slot 或队伍选择。换位和持 token
   重连不改变 `join_seq`；原房主重连不自动收回管理权。leader 不获得战斗、网络或回放优先权。
5. **两支队伍的 replay 都是完整参赛回放。** 每名在线真人自动接收队伍 A 与队伍 B 的完整
   replay；客户端可以优先显示本玩家所在队伍，但不得少发、改成点击后再发、降低另一队的
   重试/超时等级，或通过生产开关省略任一队伍。
6. **重连位置只服从服务器当前权威阶段。** 当前仍处于本轮战斗/结算的有效回放边界时，
   重连玩家补收同一 `battle_id` 的 A/B 两份 replay 和权威 `match_state`；服务器已进入下一轮
   `PREP` 时直接恢复当前摆放界面，不补播旧回放；已经终局时直接恢复最终结算。
7. **“全房离线”专指在线真人数为 0，不是某一支三人队离线。** 在线真人为 0 且有效 token
   为 0 时立即关房；仍有至少一个有效 token 时，从最后一名真人离线起保留 **300 秒**。
   任一有效 token 重连即取消倒计时；到期仍无人恢复则关房并清理 token、短码和缓存映射。
8. **联机宝物刷新必须保留。** 初始三选一正常；未触发 4 Money 时由服务器按权威
   `refresh_index` 收取 `50/100/200/400/...` 金币，单个玩家拥有至少 4 种不同 Money 宝物后，
   该玩家的商店刷新和宝物刷新都免费。套装判定、余额、扣款和候选生成全部以服务器记录为准，
   不能由客户端自报；单机/教学保持现有本地逻辑。
9. **黄金祭坛是每位拥有者自己的效果。** 每位实际拥有者每回合最多发动 3 次；每次在队伍共享
   水晶生命大于 10 时扣 1 点共享生命，只给发动者 `+50` 金币。拥有“胡牌手”联动时改为
   `+100`。扣生命、加金币、次数和联动判定必须是同一笔服务器幂等交易。
10. **慷慨命运必须保留并由服务器开奖。** 每位实际拥有者每回合一次；普通效果为 50% 金币
    翻倍、50% 只保留 20%，诡诈命运联动为 60% 翻倍、40% 保留 50%。结果只生成一次并保存，
    重试和重连不能重新开奖。
11. **金币规则统一。** 所有服务端金币变动最终限制在 `0..99,999`；出售退款按该单位服务器记录
    的实际投入成本 `cost_basis` 的 50% 取整，合成时累加投入成本，不能按未折扣原价退款。
    当前没有的“佣兵出售”功能不在本次方案中新增。

**术语边界**：面向玩家和产品方案统一使用“队伍 A / 队伍 B”“本玩家所在队伍 / 另一队”。
现有代码中的 `rival_replay`、`enemy_team_hp` 等是旧的相对视角字段，不代表真人玩家等级或
访问权。UI 中现存“观战敌方 / Watch Rivals”应另行改为“查看另一队 / View Other Team”；
战斗模拟内部的 `enemy` 若表示怪物或对立战斗单位，可保留其战斗语义。

## 一、总体结论

问题不是一堆孤立 bug,而是**一个贯穿始终的模式**:

> 客户端把算好的结果告诉服务器,服务器只做格式清洗,然后当权威广播出去。

金币、羁绊(`syn`)、宝物、宠物、星级、种族关系——全是这个模式的实例。架构方向
(专用服务器权威)是对的,但"权威"目前只体现在**格式**上,不体现在**数值**上。
二次复核进一步确认:服务器虽然会重建 `syn`,但仍不验证单位购买记录、星级升级来源、
阵容成本/数量与宝物/宠物持有权。修改客户端仍可提交任意合法 ID 组成的高星阵容。

第二个结构性问题:**服务器把所有事情放在一个进程的一个主循环里同步做**——所有房间
共用一个 `GameState` 全局、战斗模拟阻塞心跳、状态全在内存、重启即全场掉线。现有那一堆
掉线补丁(冻结宽恕、放宽心跳、僵尸清道夫、看门狗)都是这个结构的止痛药。

第三个结构性问题是**房间阶段、离场与恢复还没有形成同一个权威状态机**。start/toggle/kick/move
的 LOBBY 阶段门已在本地源码落地，但 leave 没有 ACK，技术失败仍可能误走主动离场，
RESULT ready、跨阶段 replay 和 revision/幂等也未闭环。这类状态机问题应先于 replay 带宽优化。

**热修部分能显著收敛最严重的作弊和掉线;结构性部分(经济权威化、房间隔离、持久化)
需要真正改造,短期修不完,要接受这个现实。**

带走一条规则,比带走这张清单有用:

> **这个字段是派生的吗?如果是,服务器为什么不自己算?**
> 凡是客户端能算出来的,服务器都能算,就没有理由让客户端传。
> 只有真正的"意图"(我买 3 号位、我把 A 放到 4 号格、我选这件宝物)才该上行。

#### replay 传输协议（最终同步协议核心）

依据是**工程约束**,不是已确认的 Godot bug:限制单次分配/反序列化大小、控制可靠发送队列
和内存峰值、支持背压/取消/断线恢复与完整性校验。ENet reliable 已负责同一活连接中的分片确认
和重传,不要再用“丢一个底层分片会重传整个应用层大包”作为分块理由。

> 注:GitHub issue #82160 常被引为"可靠大包会被静默丢弃"的证据,但它的环境是
> 4.1.1 + pyenet + SSH/TCP 隧道 + `unsequenced+unreliable_fragment`,无 Godot-to-Godot
> 最小复现,archived 关闭。它说明的是**依赖隐式分片、缺乏可观测性**的风险,**不能**
> 证明 Godot-to-Godot 可靠 RPC 在某尺寸存在通用静默丢包缺陷。分块的理由是上面那串
> 工程约束,不是这个 issue。

**battle_manifest**(承载校验信息,不塞进 match_state,避免重发/覆盖/迟到导致错配):
```
battle_manifest:
  battle_id
  room_id
  match_epoch
  round_id
  phase_revision
  source_team_id        # 0 / 1，稳定表示队伍 A / 队伍 B
  stream_id             # team_0 / team_1；禁止 own / rival / enemy
  protocol_version
  simulation_version
  data_registry_hash
  encoding_version
  codec
  input_hash?           # 可选诊断字段;下发锁盘后的完整规范输入后客户端才可复算
  replay_hash           # SHA-256(compressed_bytes),先验证后解压
  final_state_hash?     # 可选确定性诊断字段
  compressed_size
  uncompressed_size
  chunk_size
  chunk_count
```

`source_team_id` 是回放内容的稳定身份，不随接收者变化。服务器对同一 `battle_id` 生成
`team_0` 与 `team_1` 两个 stream，并把相同的两个 manifest/压缩对象自动交付给房间内每名
在线真人。客户端只在 UI 中决定先显示哪支队伍；接收者的 slot、队伍和 leader 身份不得进入
内容授权、缓存键或发送优先级。没有已确认的 spectator 角色，不提前把它写进协议。

**三种哈希回答不同问题,但不是所有路径都强制缺一不可**:
- `input_hash`:输入是否一致(seed/棋盘/星级/派生数据)
- `replay_hash`:传输内容是否完整(分块重组后字节)
- `final_state_hash`:模拟结果是否一致

确定性模拟/诊断路径需要三者区分“输入不同 / 模拟分叉 / replay 传坏了”;
纯服务器权威 replay 传输的最低要求是 `replay_hash` + 权威 `match_state`。
SHA-256 只能证明收到的内容与 manifest 一致;没有 DTLS/HMAC 时,不能证明发送者真实性,
中间人可以同时替换数据和哈希。

**传输协议**(应用层 ACK 只确认"业务对象完整",不逐 UDP 包确认——那是 ENet 可靠层的活;
`replay_id` 是服务端生成的全局/房间 epoch 内唯一 ID,绑定 battle + stream):
```
server -> client: replay_begin(replay_id, manifest)
server -> client: replay_chunk(replay_id, index, bytes)
client -> server: replay_status(replay_id, received_bitset)  # 限频，避免 ACK 风暴
client -> server: replay_missing(replay_id, missing_indices)
client -> server: replay_complete(replay_id, replay_hash)     # 只确认该 stream 完整
client -> server: replay_transfer_failed(replay_id, reason)   # 可恢复失败；不是完成/放弃
client -> server: result_applied_ack(battle_id, phase_revision)
```
- 单块大小从 16–64 KiB **实测**,不要直接认定固定安全值
- `match_state` 同样携带 `battle_id + match_epoch + round_id + revision`,防止跨 channel
  迟到的旧 replay/结算污染新一轮
- 服务端必须限制 `compressed_size/uncompressed_size/chunk_count/index`、重复 chunk、
  单 peer/单房间 in-flight bytes、并发 stream 与状态 RPC 频率
- 使用滑动发送窗口/credit 做背压,不能把整场 replay 切块后仍在一帧内全部排进 ENet 队列
- 两个 stream 对同房全部真人/有效 token 席位同权；每个 peer 的 ACK/缺块进度独立，
  但 A/B 两个 stream 使用相同的重试、超时和缓存 TTL。AI/空席不产生网络 ACK
- A/B 每个 stream 使用完全相同的重试配置；某个 stream 自身预算耗尽后可用
  `replay_transfer_failed(replay_id, reason)` 报告该流的可恢复失败，但 battle bundle 仍未完成，
  必须继续补齐缺失 stream。该信号不能降低某一队优先级、节省带宽或冒充 `replay_complete`
- `replay_status/missing/complete/transfer_failed` 都要验证 sender 仍绑定同一
  room/seat/battle；bitset、missing index 数、重复请求和调用频率都有硬上限
- 缓存键使用 `room_id + match_epoch + battle_id + source_team_id`，设置单 stream、单房和全服
  字节硬上限。权威阶段仍要求补发 replay（BATTLE/RESULT）时，以及该阶段内全房离线但仍在
  300 秒有效 token 恢复窗口时，A/B 两个对象必须一起固定，不能被 TTL/LRU 淘汰
- `result_applied_ack` 必须按 seat + battle + revision 记录；缓存至少保留到所有仍有恢复资格的真人
  完成 A/B 双流并 ACK。某席位只有在明确离房、leave receipt 已生效且 token/恢复资格已撤销后，
  才不再计入保留条件；本地 `playback_skip` 不能代替这个边界。权威阶段超过 replay 恢复边界
  或房间关闭后也可释放。TTL/LRU 只能淘汰没有任何有效恢复席位仍需的跨阶段/非固定对象；
  若容量不足，应背压/拒绝启动新战斗，或使用经过容量/完整性验证的磁盘 spill，不能删除已经
  承诺给有效 token 席位的任一队 stream。恢复保留期从最后一名真人离线/恢复资格起算，
  不能只从 replay 生成时刻起算
- 重连按权威阶段处理：仍在本轮 BATTLE/RESULT 边界就自动补 A/B 两个 stream 和 match-state；
  已进入下一轮 PREP 就直接恢复摆放；终局就恢复 terminal snapshot。不得播放跨阶段旧 replay
- BATTLE/RESULT 的客户端可先接收并暂存 `match_state`，但在 A/B 两个 stream 都验 hash 前
  不得把传输失败当作完成、不得提前导航到 PREP；`replay_complete`、`result_applied_ack`
  与玩家在完整收取后的本地 `playback_skip` 是三个不同状态，不能复用一个 `abort`
- 当前服务器只保留 `last_match_state`,没有 replay cache;缓存实现前,
  “断线后 missing 补传”只是协议草案,不能写成已有能力
- 解压前先验证编码版本、codec、压缩/解压大小和哈希,防解压炸弹与错误 codec
- **目标语义**:`match_state` 永远是权威结算，但传输失败不等于回放完成。服务器仍处于
  replay-required 的 BATTLE/RESULT 边界时，客户端保留 token、进入可恢复状态并继续补 A/B
  两个 stream；服务器已经进入 PREP 才丢弃旧 replay、应用当前状态并直接恢复摆放，终局则
  恢复 terminal snapshot。当前代码尚未达到
- 分块前先量化/压缩:`var_to_bytes(replay)` → `raw.compress(FileAccess.COMPRESSION_ZSTD)`

**哈希与规范化边界**：`replay_hash = SHA-256(compressed_bytes)` 只校验本次传输字节，
接收端直接对重组后的压缩字节计算，不要求跨平台重新序列化。只有 `input_hash`、
`final_state_hash` 或需要跨版本重建同一内容时，才必须规定规范化序列化：
- 字段固定顺序、数组顺序固定、单位按稳定 ID 排序
- 整数宽度和字节序固定
- 禁止 Node/Resource/RID/实例 ID
- 浮点量化为整数,或明确 IEEE 位模式
- 缺失字段和默认值统一编码
- **哈希对象是"离散分支结果"(hp:int、alive、目标 uid、技能 ready、行动顺序),不是量化
  坐标**——坐标漂移无所谓,分支翻转才致命。量化位置哈希会把分叉藏到后面才爆
- `String.hash()` 不用于协议完整性(32 位、易碰撞);replay/最终状态用 SHA-256,逐帧调试
  可用稳定 64 位哈希、最终再 SHA-256

**input_hash 的边界**:当前专服路径明确不向客户端下发双方锁盘棋盘和 seed,所以客户端
无法复算覆盖 `(seed, 双方棋盘, stars, treasures, syn, pet)` 的完整 hash。二选一:
1) 把它定义为服务器内部诊断值,客户端只回报自己的 `submission_hash`;或
2) 锁盘后下发经过权限过滤的规范输入,再允许客户端复算。
无论哪种,hash 都不能证明阵容合法或防作弊;真正安全边界仍是服务器验证与备战账本。

### P1 / P2:结构性

- **确定性准入门槛**(见第七节):replay envelope + 压缩 → 埋点看压缩后大小 →
  必要时再做分块/断点续传 → 仍太大才启动确定性测试矩阵 → 达标才切
  “客户端模拟为主、权威 replay 兜底”
- 消除浮点分叉源:伤害管线的 `float × 系数 + round()/int()`(如 `_apply_attack` 的 god_lifesteal
  `int(round(float(dealt) * ...))`)改定点/整数(千分比整数),把分叉面从弥散变成可消除
- 替换 `JSON.stringify(parts).hash()` 的 32 位 seed 派生为固定编码/字节序的稳定 64/128 位算法;
  所有相同主键排序增加稳定 UID 次级键,避免 Dictionary/原数组顺序决定玩法结果
- `BattleContext` 去全局化 → 之后才能线程化(**先纯输入纯输出,再线程化**,否则数据竞争从
  "可能发生"变"稳定发生")
- 服务端备战账本(买/卖/刷新/祭坛/赌博全部 intent 化),经济彻底权威化
- 房间隔离为独立对象;HMAC token + 房间状态持久化
- 服务器地址下发(静态 HTTPS 端点返回 host/port/最低版本)+ 蓝绿部署
- 传输加密:DTLS(`ENetConnection.dtls_server_setup/dtls_client_setup` **API 存在但接入路径需先
  做最小原型**——`host` 只有 getter、`create_client()` 已开始连接、客户端配置须在 `connect_to_host()`
  前),P2

#### P1：服务端权威备战经济账本（已确认：功能不得关闭）

不能只给宝物刷新、黄金祭坛或慷慨命运单独补一个扣款 RPC。当前商店购买/合成、出售、雇佣、
商店刷新和战斗结算仍有客户端金币或客户端阵容来源；只修三个按钮后，修改客户端仍可伪造金币、
重复出售或提交没有购买来源的高星单位。最小可信边界必须同时包含金币、商店 offer、单位 UID/
星级来源、实际投入成本、宝物归属和幂等回执。

六个逻辑 slot 使用完全相同的账本和校验；A/B 队、leader、加入顺序都不改变价格、次数、概率、
请求优先级或回执保留时间。建议的房间状态：

```text
room.prep[slot] = {
  match_epoch, round_id, phase_revision, economy_revision,
  gold,                         # 0..99,999
  shop: {offer_revision, offers, refresh_index},
  roster: {unit_uid -> {unit_id, star, kind, cost_basis, location}},
  owned_treasures,
  treasure_offer: {offer_id, offer_revision, candidates, refresh_index},
  altar_uses,
  gamble_used,
  receipts, request_high_water # 完整回执覆盖有效阶段和 300 秒恢复；压缩后仍留幂等 tombstone
}
room.team_resource[team] = {crystal_hp, revision}
```

客户端只发送操作意图，不发送“我应扣多少钱”“我有 4 Money”“随机结果”或“扣款后的金币”：

```text
intent = {
  request_id, match_epoch, round_id, phase_revision,
  expected_economy_revision, action, payload
}
receipt = {
  request_id, action_fingerprint, status/error,
  gold_before, delta, gold_after, resulting_revision,
  authoritative_patch/result
}
```

- `request_id` 作用域为 room + match + slot，并带该 slot 单调递增序号。完整 receipt 至少保留到
  所属 round/offer/action 不可能再次执行，并覆盖该席位仍可用有效 token 恢复所需的时间；
  全房离线 300 秒只是最低场景，不是统一 TTL 上限。期间同 ID、同内容重试返回完全相同的
  receipt，同 ID、不同内容直接拒绝并记录。
- 完整 receipt 之后可以压缩，但 `request_id + action_fingerprint + high-water/tombstone` 必须保留
  到 match 和恢复资格结束。命中已压缩 ID 时返回 `request_already_finalized` 和当前权威快照，
  绝不能因 LRU/TTL 淘汰而把旧 ID 当新请求再次执行。
- 旧阶段/旧回合/旧 revision、余额不足、已售 offer、不存在的 UID、未持有宝物等请求必须
  **零变更拒绝**，并返回当前权威 revision/必要 patch。
- handler 顺序固定为：认证 sender/slot → 限制输入并生成 canonical fingerprint →
  **先查 receipt/high-water/tombstone** → 同正文重放、异正文拒绝 → 仅新请求再检查
  phase/round/revision/余额并执行。不能先做 stale revision 检查，否则成功后丢 ACK 的重试会被
  新 revision 错拒，无法取回原 receipt。
- 联机客户端不得预扣或直接增加 `GameState.gold`，也不得本地运行赌博 RNG；只用服务器
  receipt/snapshot 覆盖本地显示。初期每个 slot 同时只允许一笔经济 mutation 在途，降低乱序面。
- 服务端战斗结算不得再以客户端 snapshot 的 gold 为 `gold_before`；必须只读取账本。
- 所有加减金币路径统一做饱和/下界检查，最终金币始终在 `0..99,999`。

**阶段前置整改**

当前流程在战后已经让客户端进入备战/宝物 UI 时，服务端仍可能停在 RESULT，直到后续 ready
才切 PREP；若直接给这些 intent 加裸 `PREP` 门，会误拒合法的第一笔宝物或祭坛请求。最终方案
应先把“战果已应用 → 下一轮权威 PREP → 开放宝物/商店/摆放”的切换时点闭环，再只允许
canonical PREP 的经济 intent。过渡实现若暂时跨 RESULT/PREP，必须使用绑定
`match_epoch + round_id + economy_window_id + phase_revision` 的明确窗口；不得笼统放行 RESULT。

**宝物选择交易**

1. 新请求在幂等查重后，验证当前 `offer_id/offer_revision/round_id/economy_window_id`，
   `tid` 必须位于服务器候选中、尚未拥有且未超过 `MAX_OWNED`。
2. 同一事务中把 `tid` 追加到 canonical `owned_treasures`，执行服务器权威联动副作用，
   把 offer 标为 claimed 并明确清成 `no_offer`，递增 revision，保存 receipt 后回复。
3. 重复 choice 只重放同一 receipt/owned/no_offer；旧 offer、同一 offer 选第二次或改 `tid`
   必须零变更拒绝。

**宝物刷新交易**

1. 完成通用认证和幂等查重后，服务端验证权威经济窗口、round、offer_id/revision。
2. 从服务端 `owned_treasures` 按宝物 ID 去重后判断该玩家是否拥有至少 4 种 Money 宝物。
3. 未触发 4 Money 时按服务器 `refresh_index` 计算 `50/100/200/400/...`；触发后费用为 0。
   4 Money 同时保持该玩家商店刷新免费；不影响队友，也不代表购买免费。
4. 费用计算必须使用 checked/saturating integer。金币上限为 `99,999`，因此非 4 Money 的
   `refresh_index >= 11` 可直接返回 `unaffordable`，不得继续乘法后再比较；index/revision 也
   必须有协议技术硬界限，不能溢出为负数。4 Money 费用仍为 0，不把 rate limit 或技术防溢出
   冒充正常玩法次数上限。
5. 在同一事务中检查余额、扣款、递增 index/revision、用服务器独立经济 RNG 生成候选并保存
   receipt，然后才回复。网络 rate limit 仍保留用于抗滥用，但不能伪装成玩法刷新次数上限。
6. 回复包含 `cost_charged/gold_after/candidates/refresh_index/money_set_active/revision`。
   初始三选一、单机和教学流程不变。

**商店刷新交易**

1. 普通规则保持现状：每回合第一次刷新免费，之后按 `10/20/40/80/...` 递增；
   `shop.refresh_uses_this_round` 在新回合由服务器重置。
2. 触发 4 Money 后，该玩家本回合所有商店刷新都免费；套装只影响费用，不省略服务器
   offer/revision、RNG、幂等和频率保护。
3. 普通费用同样使用 checked/saturating integer；按当前规则 `refresh_uses_before >= 15` 时
   下一次费用已超过 `99,999`，可直接返回 `unaffordable`，不得让翻倍运算溢出。
4. 服务端在同一事务中计算费用、检查/扣除金币、生成新 offer、递增 uses/revision 并保存
   receipt；客户端不得本地预扣或自行滚商店。

**黄金祭坛交易**

1. 服务端验证请求者实际拥有 `money_golden_altar`、处于 PREP、该玩家本回合使用少于 3 次，
   且队伍共享水晶生命当前大于 10。
2. 同一原子事务完成共享水晶生命 `-1`、该玩家次数 `+1`、本人金币 `+50`；
   若服务端确认“胡牌手”联动则改为 `+100`，再保存两类 revision 和 receipt。
   实际到账为 `min(奖励, 99,999 - 当前金币)`；到账为 0 时零变更拒绝且不扣共享生命，
   部分到账时 receipt/UI 必须显示实际数值，不能仍显示完整 `+50/+100`。
3. 其他队友只收到共享水晶生命更新，不获得发动者金币。同队三名实际拥有者并发且 HP=11 时
   只能有一笔成功，
   不能把生命扣到 10 以下。
4. 修复 UI 把实际 `+50` 显示成 `+5` 的错误，并根据联动动态显示 `+50/+100`。

**慷慨命运交易**

1. 服务端验证请求者拥有 `money_generous_fate` 且本回合未使用；使用记录按玩家、回合保存。
2. 普通效果由服务器一次性生成 50% 翻倍 / 50% 保留 20%；诡诈命运联动由服务器判断并改为
   60% 翻倍 / 40% 保留 50%。整数结果按现有规则取整，再应用 `99,999` 上限。
3. RNG 结果、倍率、gold_before/after 和 `gamble_used=true` 先写入不可变 receipt 再回复。
   ACK 丢失、重复请求和重连只重放该 receipt，绝不重新开奖。
4. UI 根据服务器确认的联动显示真实概率，不再始终显示基础概率。

**购买、合成、出售和其他金币路径**

- 商店 offer 由服务器生成并带唯一 offer_id；同一格只能购买一次。
- 每个购买单位由服务器签发 `unit_uid` 并记录实际 `cost_basis`；合成消耗明确 UID，
  新单位的 cost_basis 为被合成单位投入之和。
- 出售按 `floor(cost_basis * 0.5)` 退款且一个 UID 只能出售一次，封住折扣购买后按原价出售套利。
- 雇佣、商店刷新、宝物刷新、祭坛、赌博、Money 宝物效果和战斗结算全部写同一账本。
- 不新增当前代码没有的佣兵出售入口；以后若要增加，必须另行确认退款和状态来源规则。

**重连与发布**

- resume 必须下发完整权威备战快照：金币、商店与 sold 状态、roster/UID、宝物归属、当前 offer
  或明确 `no_offer`、祭坛次数、赌博使用状态、各 revision 和必要 receipts。收到 `no_offer` 必须
  清除客户端旧候选。
- 服务器已进入下一回合 PREP 时直接恢复摆放，不补播上一轮动画；仍在有效 BATTLE/RESULT
  回放边界时按既定规则补 A/B 双 replay。
- 实现可在本地分步骤完成，但**不得发布半套账本/半套客户端**。正式包一次切换联机客户端为
  receipt-only，并同时切换为服务器权威刷新、4 Money、黄金祭坛和慷慨命运；单机/教学仍走
  现有本地路径。

最低验收必须覆盖：同一请求重放 100 次只产生一次变更、同 ID 不同正文拒绝、ACK 丢失、
断线发生在提交前/后、旧回合/旧 offer/乱序、0–3 Money 正常收费与 4–5 Money 免费、祭坛
HP=10/11 边界及三队友并发、祭坛 `+50/+100`、赌博两组概率分支和奇数取整、购买一次/
出售一次/合成 UID 来源、`99,999` 饱和、六个 slot 镜像、leader 无特权，以及无本地存档时
仅靠 resume 快照恢复且不产生任何额外金币。

### 后置独立批:session token 轮换

token 轮换与 DTLS 解决的是不同问题：轮换 + ACK 解决旧 token、B13/B14 和竞态正确性，
DTLS 解决链路窃听与服务端身份。轮换可随最终同步状态信封先做两阶段提交，不应被 P2 DTLS
无限期阻塞；但在明文链路上，轮换不能防止正在窃听的攻击者获取新 token。

两阶段轮换 + ACK:
- 服务器签发 `new_token + token_revision`,旧 token 保留短期 grace
- 客户端原子保存成功后发 ACK,服务器收到 ACK 才彻底撤销旧 token
- 超时未 ACK 允许旧 token 再恢复一次
- 原子更新 `_token_seat` / `room.seat_tokens` / `_public_token_seat` / 客户端内存与磁盘

它是失败模式比所防攻击更糟的改动：写错会让玩家永久回不去对局，必须先完成原子保存、
ACK 丢失和双 token grace 测试。在明文链路上安全收益有限，但 B13/B14 的正确性部分不必等 DTLS。

## 四、修改后对游戏的影响

### 玩家能感觉到的正面变化(按当前已完成代码)

- **结算发送顺序已改善**:`match_state` 已移到 replay 前面,但 B4、B9、B10 未修前仍可能卡住

发送顺序和冗余 `team_boards`**。其余只做了部分缓解或仍未实施,这是止血,不是安全收口。

## 五、业界与开源对照

核心架构方向经开源与业界共识印证,但 **ENet channel、分片重传、RPC 映射与测试能力**
有若干技术细节经二次复核需要修正,不能把方向正确等同于每条实现结论都正确。

**"派生数据服务端重建" = 业界标准。** Godot 多人游戏通行原则是只同步真正需要共享的最小集
(通常位置),其余本地推导。这正是本文"派生字段服务端重建"的通用版。
(注:此为通行原则,非 `MultiplayerSynchronizer` 文档的强制条文。)

**"传输入不传状态" = 确定性 lockstep 的定义。** 只发控制系统的输入、不发状态,带宽正比于
输入大小而非对象数量——自走棋/RTS 的教科书做法。我们现在传逐帧 replay 恰是它反对的。

**channel 的准确结论**:Godot 的默认 channel 0 已按 transfer mode 分成 reliable、
unreliable、unreliable-ordered 三条内部流;当前问题是 replay 和 ping/pong 都声明为 reliable,
因此仍共享可靠顺序。目标映射应是:控制/结算走可靠控制流,ping/pong 走 unreliable 默认流,
bulk replay 走独立 reliable 用户 channel。`create_server/create_client` 的 `max_channels=0`
表示使用默认最大值,不是零通道;两端显式值不同也不是必然“直接连不上”,但 RPC 配置和协议必须
双端一致并在开发服验证。

**跨平台浮点确定性极难。** Gaffer On Games 明确警告:同机确定 ≠ 跨编译器/OS/架构确定。这正是
我们要在 Android ARM64 和 Linux x86_64 之间做逐位一致的场景——所以确定性这条路必须带压缩
权威 replay 兜底,且有跨平台准入门槛(见第七节)。

**Godot 提供 authority/sender ID/RPC 权限等基础设施,但不提供规则校验、经济账本、身份认证和
反作弊系统**——引擎不替我们兜底,服务端校验是唯一防线。

**开源帮不上的地方**:扫过的 Godot 多人模板(lazercube、devmoreir4、AlixBarreaux、Svengali 等)
全是通用 3D 角色同步(位置/旋转插值),**没有一个是自走棋/回合制/带经济系统的**。所以**安全和
replay 照业界共识走;经济账本和重连/座位保留/AI 代打是我们自己的深水区,只能自己设计**——
而我们这套虽然补丁多,功能上已经比大多数开源模板走得远。

## 六、被否决的捷径及原因

这些否定性结论最容易被下一个人重新踩一遍,单独留档:

| 想过的捷径 | 为什么不成立 |
|---|---|
| **改服务端 `@rpc` 注解就能单边止血 A2** | RPC 权限由**接收端**执行。只改服务器,旧客户端本地仍是 `any_peer`,照样接受另一个旧客户端伪造的包。止血靠 `server_relay=false`。<br>*(注:本项目已无已发布客户端,注解与删除已随客户端一并完成)* |
| **删掉 1v1 死路径就顺手放进 P0** | Godot 会基于 RPC 名称/配置建立并校验映射;删除、重命名或改签名会改变受影响的排序映射与校验,并非“整个表机械平移”。本项目尚未上线,已可直接删除;**上线后任何 RPC schema 变化仍必须协议号 +1、双端同发并拒绝混合版本** |
| **禁用慷慨命运赌博来“堵金币洞”** | 赌博只动金币,而金币本就由客户端自报。对诚实玩家它是正常功能；作弊者可直接改余额，根本不需要这个按钮。已确认功能必须保留，正确做法是服务器校验、开奖并写入幂等账本 |
| **账本完成前暂时关闭联机宝物刷新** | 已确认不可关闭；而且只关这个入口也封不住购买、出售、祭坛、赌博等客户端金币路径。正确做法是保留初始三选一和刷新，在同一最终双端包中切到服务器扣款/4 Money/候选/receipt |
| **`local_ready` / `toggle_ready` 是单机在用,要保留** | 凭印象的判断。实际逐个追引用后发现:`_on_toggle_ready` 定义了但**无任何调用点**;`local_ready` 唯一读点是 `PrepUI` 里一个 `elif is_online()` 分支,而删掉 1v1 后 `is_online()` 必然蕴含 `team_active`,该分支永不可达。**删代码前必须逐个 grep 确认,不能凭印象** |
| **服务端只读 `room.slot_gold`、不读 `snap.gold` 就修好经济** | 服务器不知道备战期的买/卖/刷新/祭坛/赌博。直接用 slot_gold 当下轮 `gold_before`,诚实玩家花掉的钱会被加回来 = 所有购买免费。必须先做备战账本(P1) |
| **只检查 `snap.gold <= room.slot_gold` 就算经济安全** | 慷慨命运一次就能合法翻倍；而已确认的 `99,999` 全局上限只能防溢出，不能证明金币来源。服务器必须记录每一笔合法增减 |
| **宝物上界用 `owned.size() <= 当前回合`** | 宝物在第 4/8/12/16/20 回合**战后**获得,`<=当前回合`会让第 4 回合开打前就能带一件。必须是**严格小于当前回合**的宝物轮次数 |
| **从最终棋盘重建 `race_relations`** | 关系进度是跨回合累积状态,服务端没有历史,光靠最终棋盘重建不出来。启用前必须先做服务端玩家状态 |
| **`battle_state_checksum` 放进 `match_state`** | match_state 会重发、被下一回合覆盖、迟到,checksum 会和战斗错配。必须放独立的 `battle_manifest` |
| **所有模式都强制三种 checksum** | 确定性模拟/诊断需要 input/replay/final-state 三者区分原因;纯权威 replay 传输最低只需 replay 内容完整性 + 权威 match-state。当前客户端拿不到完整双方输入与 seed,不能假装能复算完整 input hash |
| **直接对 Godot `Dictionary` 做哈希** | 顺序/浮点表示/Variant 差异造假 desync。必须先规范化序列化 |
| **量化坐标做 checkpoint 哈希** | 内部仍跑浮点时,两平台可能量化到同一 int、哈希相等,内部已分叉、后面才爆。要哈希离散分支结果 |
| **`ENet + DTLS` 是低成本加密** | API 存在但 `host` 只有 getter、`create_client()` 已开始连接、配置须在 `connect_to_host()` 前,便利构造插不进去,需最小原型。降 P2 |
| **WSS 加密替代 ENet** | WSS 是 TCP,队头阻塞是整条连接级(比 ENet 单 channel 级严重),会**加重**我们最痛的掉线问题,且丢掉多 channel 隔离 |
| **`determinism_check_node.gd` 已证明确定性** | 它只覆盖 4 种单位/单 seed/同进程,且**在一个自动启动的服务器旁边跑**(C12),结果作废,重做 |
| **只把 20 秒超时改成 60 秒** | 只能降低触发概率,不能解决主路径定位错误、无进度信号、迟到结算和单位结果漏应用。必须有 board ACK/进度、battle_id 与统一失败语义 |
| **只给固定 3 秒重连加随机抖动** | 下一次 tick 仍会 `reset_peer_only()` 拆掉正在握手/等待 resume 的连接。先做明确状态机与 attempt deadline,再加 capped full-jitter |
| **把 replay 切 chunk 后一帧全部发送** | 仍会把同样大小的数据排进 ENet 队列,内存峰值和队头阻塞几乎不变。必须有滑动窗口/credit、在途预算与取消 |
| **只信构建期 data manifest** | 无法发现部署目录损坏、覆盖解压残留或加载坏 JSON 后得到空字典。服务器监听前必须核验实际文件并 fail closed |

## 七、补充与遗留决策

### 需要写进代码的三处小注释

1. `RaceRelationService.ENABLED` 上加注释:开启前置条件是**服务端要有跨回合玩家状态**,
   否则同时打开一个作弊面和一个不可重建的状态。防止有人顺手改成 `true`。
2. `NETWORK_PROTOCOL_VERSION` 注释补上:**删除、重命名、改签名或 RPC 配置会改变映射/校验,
   混合版本不兼容,必须协议号 +1 且两端同发**。不要再写成“整表机械平移”。
3. 伤害管线的浮点→整数截断点(如 god_lifesteal `int(round(float(dealt) * ...))`)标注为
   确定性风险点,P1 定点化时优先处理。

### 确定性这条路的决策链(不要提前承诺)

seed+input 客户端模拟的代价是把整条战斗管线改定点/穷尽跨平台测试——**很重**。它买的是带宽。
但我们连 replay 到底多大都还是估算。正确的决策链:

```
P0 埋点量真实 replay 大小
  → 内部阶段 A: battle envelope + ZSTD + 大小/hash + 独立 channel + A/B 双队同权缓存
  → 看压缩后大小
      ├─ 够小且重连可接受整对象补发:停在这里,不增加 chunk/missing 复杂度
      └─ 仍太大或必须断点续传:内部阶段 B 再做 chunk/window/missing
              → 仍不足时才启动确定性测试矩阵
              → Windows x86_64 / Linux x86_64 / Android ARM64 / Debug+Release
              → 数万组固定战斗语料,逐 checkpoint + 最终状态完全一致
              → 达标才切"客户端模拟为主、权威 replay 兜底"
```

阶段 A/B 只是最终发布前的内部实施门，不是两个可分别上线的协议。只在全部发布门通过后生成
一套最新双端包；以后若已发布 schema 再新增 chunk/missing RPC 或改签名，仍必须提升协议号并
拒绝混合版本。

**在这些测试通过前:服务端权威 replay 是正式路径,客户端确定性模拟是实验路径。**
否则客户端只有整场播完才发现结果错,玩家仍先看了一场"假战斗"。

### 已确认的产品方向与仍待实现项

1. ✅ **固定六个逻辑席位但允许未坐满开局**：两队各至少一个真人或 AI、且联机房整体至少
   一名真人即可开始；空席合法。这里的 1v1、3v1、2v2 是六席房的占席结构，不是旧 P2P
   模式；纯 AI 对局只允许本地/测试。
2. ✅ **全房离线时长规则**：零在线真人且零有效 token 立即关房；仍有 token 时保留 300 秒，
   任一有效 token 重连取消倒计时。🟨 suspended 期间不跑新阶段/新模拟是工程整改方向，
   不是本次新增的产品确认。
3. ✅ **双队 replay 平等待遇**：每名真人自动获得 A/B 两队完整 replay，不按队伍降级，
   不改成点击后获取，也不允许生产开关选择性停发。
4. ✅ **leader 规则**：只负责大厅管理；失效时由在线真人中 `join_seq` 最小者接任，
   原房主重连不自动收回，与队伍和 slot 无关。
5. ✅ **阶段恢复规则**：仍处于本轮 BATTLE/RESULT 有效回放边界时补 A/B 双 replay；
   已进入下一回合 PREP 就直接摆放；终局就进入最终结算，迟到旧包不得把玩家拉回上一阶段。
6. ✅ **联机宝物刷新不得关闭**：初始三选一和刷新都正常；服务器检查余额、扣款、摇候选并
   幂等返回。4 Money 按每位玩家自己的权威宝物判定，使其商店刷新和宝物刷新都免费；
   单机/教学不变。
7. ✅ **黄金祭坛规则**：每位实际拥有者每回合最多 3 次；共享水晶生命大于 10 时每次 `-1`，
   只给发动者 `+50`，胡牌手联动补上 `+100`。整笔由服务器原子结算；UI 的 `+5` 错误要修正。
8. ✅ **慷慨命运规则**：每位实际拥有者每回合一次；普通 50% 翻倍/50% 保留 20%，诡诈命运
   联动 60% 翻倍/40% 保留 50%。服务器只开奖一次并保存 receipt，功能不得禁用。
9. ✅ **出售退款规则**：按服务器记录的实际 `cost_basis` 的 50% 取整；合成累加投入成本，
   不按未折扣原价退款。不新增当前不存在的佣兵出售入口。
10. ✅ **金币上限**：联机账本中的权威金币统一限制为 `0..99,999`，所有收入路径饱和，
    所有支出先检查余额，客户端显示只接受权威结果。
11. ✅ **最终发布方式**：不指定先上协议 6/7/8；完成全部发布门要求后只运行同一套最新双端构建，
    握手拒绝协议/build/manifest 不一致，不部署中间协议。
12. ⬜ **确定性路线**：现在不拍板，先完成 wire/P99 与内部阶段 A 的压缩测量。

### 对抗性测试台目标覆盖(`tools/adversarial_client_node.gd`)

下面是**目标清单，不是当前已覆盖能力**（现状：L1 对抗台 25/25，L2 只有
`handshake_check` 与 `persist_check` 两台）。巨大载荷测试只打隔离服务器,由测试进程外部
watchdog 负责超时杀进程;任一断言/超时必须返回非 0。至少覆盖:
- 独立客户端进程通过真实 ENet/RPC 发送恶意数据,不直接调用生产函数
- 房间 phase × sender role × RPC 的权限矩阵,含 BATTLE/RESULT 的 start/toggle/kick/leave
- 超长 treasures / race_relations / syn
- 超长 `public_id` / unit ID / pet ID / `prep_mercs` 与单包总字节预算
- `NaN` / `INF` / 超大整数
- 重复与乱序 board submission
- 旧 round / 旧 room / 旧 token
- 允许空席开局的合法矩阵：六席房内的 1v1、3v1、2v2、真人+AI；始终保留 A/B 各
  3 个逻辑 slot，联机房整体至少一名真人，纯 AI 仅本地/测试
- token 轮换响应丢失
- 同一 peer 连续创建/加入不同房间
- 换连接绕过 per-peer 限流、512 未认证 peer 槽位耗尽
- match_state / replay 重复发送
- RESULT 阶段多玩家同时 ACK
- 六个 slot 分别作为接收者时，replay stream 集都严格为 `{team_0, team_1}`，
  manifest/hash 不因队伍、slot 或 leader 身份改变
- replay 发送中断后恢复：BATTLE/RESULT 补双 stream，PREP 直接摆放，终局恢复最终结果
- 旧 peer 半开时的 `seat_taken` 竞态,以及可重试错误不清 token
- 公开短码恢复成功后的第二次断线
- 重连等待握手/resume 超过 3 秒时不得被下一次 retry 自拆
- 明确 leave 的 request/ACK 丢包与重复；技术失败不得发 leave 或清 token
  （L1 已覆盖：对抗台 `result_ack_and_leave`；**L2 仍缺**：真实丢包下的回执重发）
- 结算 ACK 闸门：未全 ACK 不推进、掉线/AI 席位不等、迟到 `battle_id` 丢弃、重复 ACK 幂等、
  60 秒兜底、`run_over` 房间不推进（L1 已覆盖）
- 全房零在线真人：零 token 立即关房；有 token suspended 299/300 秒边界且期间不跑模拟
- 房主换位及按 `join_seq` 接任；覆盖较早加入者在 B 队高 slot、原房主重连不抢回
- P1 账本：折扣买入+合成+出售的净收益必须 ≤ 0（套利）；拒绝的交易一字不改账本；
  账本自己绝不摇随机；伪造 `offer_id` 买不到东西；赌博每回合一次且服务端开奖；
  回合重置清赌博/刷新次数但不清金币；座位释放连账本一起清（L1 已覆盖，58 项）
- 交易幂等（E4）：同一 `request_id` 重试拿回**同一份成功结果**且副作用只发生一次；新 rid 才算新单子；回执日志定长、随座位清理、随房间持久化；客户端重复回复丢弃（L1 已覆盖）
- 宝物 choice/refresh 重复点击、ACK 丢失、空 offer resume、图鉴/联动同步；0–3 Money 收费、
  4–5 Money 免费，客户端伪造套装无效
- 黄金祭坛持有权、每位拥有者 3 次、`+50/+100`、HP=10/11 和同队三名实际拥有者并发
- 慷慨命运基础/联动两组概率分支、每回合一次、重连不重摇、`99,999` 饱和
- 购买 offer 一次、出售 UID 一次、合成 cost_basis、折扣购买后不得按原价出售套利
- Release headless 的 startup/auth/rate/resume/watchdog/metrics 日志可见且无 token/payload 泄漏
- 同公网 IP 多个正常 peer,验证 IP 限流不过度误伤

每条 P0 修复必须对应一个真实网络用例。函数级探针可保留作快速单元测试,但不能替代这张回归网。

**一个只会输出 PASS 的测试台不是测试台。** 2026-07-28 实测踩到三类"假绿"，每一类都表现为全绿：

| 假绿类型 | 实例 | 为什么看不出来 |
|---|---|---|
| 参数没生效 | `handshake_check` / `persist_check` 用 `OS.get_cmdline_args()` 读 `--` 之后的参数，而 Godot 只把它们放进 `get_cmdline_user_args()` | 三个握手用例全部退化成默认的 `ok`；持久化每次都跑 `save`，`load` 从来没执行过 |
| 脚本解析失败 | `tools/` 下的脚本**不在启动时解析**，`--headless --quit` 的零错误证明不了它们能跑 | 解析失败 → `_report()` 不执行 → `quit()` 不执行 → 进程静默挂住 |
| 断言写反 | 期望值凭印象写（如 FNV-1a 测试向量、跳过房间是否消耗预算） | 断言与实现同错时对拍成功 |

**规矩**：新增用例必须先让它**故意失败一次**，确认失败真的会被看见，再改成正确断言；
测试向量只能来自规范或独立实现，不能凭印象写。

**退出码要分三档,不是简单改成"有 FAIL 就非零"**:`_report()` 目前无条件 `quit(0)`,
而且代码注释写明这是**刻意**的("测试台本身跑通了,不代表被测项全过")。直接改成
"有 FAIL 即非零"会破坏第 0 批"预期多数 FAIL、拿基线"的用法。正确做法:
`0` = 全过 / `3` = 测试台正常跑完但有断言失败 / `2` = 测试台自身故障或服务器被冻住。
CI 只有 `0` 通过，`2` 与 `3` 都失败；基线采集可以显式容忍 `3` 但仍须保存输出。外部 watchdog、
子进程崩溃或超时产生的原始 OS 退出码（如 1/124/137）由 wrapper 统一映射为 `2`。

### 测试分级（L1–L4）—— 回归结果只能按级别解释

现有全部回归都是 **L1**。把 L1 结果当成"网络项已修好"是本文档此前最容易犯的错。

| 级别 | 定义 | 当前状态 |
|---|---|---|
| **L1** | 同进程函数探针：直接调用服务端内部函数，手工改字典模拟状态 | ✅ 现有 `adversarial_client` 15/15、`reconnect_check` A–F、`economy`、`determinism` 全在这一级 |
| **L2** | 服务端与客户端**独立进程**，真实 ENet/RPC 收发 | ⬜ 完全没有 |
| **L3** | 六客户端故障注入：丢包、延迟、真实断线、换位、重连 | ⬜ 完全没有 |
| **L4** | 最终候选包 24 小时 soak | ⬜ 完全没有 |

**规则：网络相关问题项只有通过 L2 及以上，才允许从 ⚠️ 改成 ✅。**
目前 C19、A12、A8、B7/B12 的"已完成"部分全部只有 L1 证据。

L1 的具体能力边界（不要高估）：

- watchdog 函数存在但**没有真正参与退出判断**；退出码 `2` 目前只覆盖"服务器创建失败"，
  **不能可靠识别主线程卡死**
- `economy` 与 `determinism` 各有价值，但**基本不覆盖** C19 / A12 / A8 / B7/B12

`--headless --editor --quit` 重建 `.godot/global_script_class_cache.cfg`，否则该类在

### ⚠️ 本轮改动的已知边界（不要当成已解决）

1. **A8 只完成了回包止血。** `count_strike=false` 意味着恶意客户端可以无限高频 ping，
   服务器只是不回 pong —— **RPC 反序列化和 handler 调用的开销仍在，连接也一直占着**。
   它挡的是"回包放大"，不是"入包泛洪"，也不解决连接槽占用。
   入包侧要靠 A13 的连接准入 + R4 的包级预算，两者都未做。
2. **`_atomic_write` 有一个极短的无目标文件窗口**（旧文件转 `.bak` 之后、`.tmp` 转正之前）。
   进程正好在这两步之间被杀时，`_read_with_fallback` 会读到 `.bak`，**不丢档但会回退一步**。
   这是当前 API 下可接受的取舍，不是 bug；真正的原子 rename 需要平台级支持。
3. **`join_seq` 的退化路径仍有残余 A 队偏置。** 缺序号的座位按 `1000000 + slot` 排序，
   也就是仍按 slot 比。正常路径都会分配序号，但旧房间/异常路径会落到这条。
6. **C17 只是单入口止血，不是"系统已经只升不降"。** 只有 `_rpc_team_lobby` 的 round
   加了门；**`_rpc_round_resync` 与 `_rpc_resume_state` 仍无条件覆盖** `server_round_index`、
   `server_phase`、`slot_states`、`ready`。也就是说旧包依然能把 phase 和席位状态写回去，
   客户端仍可能把"新 round"和"旧 phase/旧席位状态"拼在一起。
   完整方案只能是状态信封（`match_epoch + state_revision + round_id + phase + battle_id + payload`），
   客户端**原子接收整份状态**、拒收 revision 不前进的包 —— 归最终同步协议批。
7. **B7 的 60 秒是三处各自的上限，不是总上限。** `_wait_for_team_replay` 与
   `_wait_for_team_match_state` 是**连续两段**等待，最坏累计可达 120 秒。而且它完全
   不解决迟到 replay 进入下一回合、串回合、无 ACK 这三件事 —— 那些要靠
   `battle_id` + 棋盘提交 ACK + 服务端公开 `collecting → simulating → replay_ready` 进度。
   **60 秒只作最后保险超时，不是正常同步机制。**
4. **`_log_safe` 目前只接在宝物路径上。** `public_id`、`token`、各种 `reason` 字符串
   进日志的地方还没统一过一遍 —— R4 要求的是全量矩阵，不是单点。
5. **`_room_try_finalize_boards` 的内部守卫只挡状态，不挡重复。** 同一 `ROOM_BATTLE`
   内被调两次仍会算两次战斗。幂等键（`battle_id/round_id`）仍归 R6/B6。

### 2026-07-28 战斗模拟耗时与 replay 体积实测（`tools/battle_perf_check.tscn`）

此前文档里 replay 大小是估算、模拟耗时**连估算都没有**。现在有实测了。
本机 5 次取中位数，直接驱动服务端会跑的 `compute_team_replay()`。

| 场景 | 单场模拟 | 一房一回合 | 帧数 | 单位数 | 原始 | zstd |
|---|---:|---:|---:|---:|---:|---:|
| PVE 每人 4 兵 | 53.8 ms | 107.6 ms | 82 | 24 | 314 KB | 6.2 KB |
| PVP 每人 7 兵 | 35.8 ms | 71.6 ms | 34 | 33 | 237 KB | 8.5 KB |
| 满棋盘 PVP（7 兵 + 8 佣兵） | 180.4 ms | 360.8 ms | 86 | 60 | 1069 KB | 25.5 KB |

**四条由实测得出的结论**

1. **replay 现在根本没压缩。** `_rpc_team_replay` 直接把 Dictionary 塞进 RPC，
   ENet 也没设 compression。最终战那轮每人实收 2 × 3.6 MB = **7.3 MB**，
   六人 = 服务器一轮发 **43 MB**。这是弱网掉线可量化的直接原因。
   zstd 压缩率 **0.017**、耗时 1.7 ms —— 加压缩后 43 MB → 740 KB。
2. **压缩后不需要分块。** 最坏 61.8 KB，只是勉强够到常见分块阈值（16–64 KB）下沿。
   **B2 应改为"先压缩，大概率不用做分块协议"**；信封仍预留 chunk 字段，实现可缓。
3. **真正贵的是序列化（25.7 ms），不是压缩（1.7 ms）**，差 15 倍。而且现在是
   `rpc_id` 逐个 peer 发 = 同一份 replay 序列化 6 次 = **154 ms 纯浪费**。
   改成"序列化一次 + 压缩一次 → 同一个 `PackedByteArray` 发给所有人"比压缩本身省得还多。
4. **每帧并发闸解决不了单场阻塞。** 它能把"多房扎堆"摊到多帧，但摊不开
   "这一场就要 581 ms"（= 阻塞 17 帧）。要解决后者只能分帧或线程化 ——
   而 **`compute_team_replay_async` 已经存在**（客户端在用），服务端不用它的唯一
   原因是注释写的"分帧 await 期间 GameState 全局会被别的房间改掉"。
   **所以 B4 的解法是去全局化后直接换 async 版，不需要线程化。**

**容量估算**：一局 ≈ 20 × 361 ms + 1162 ms ≈ 8.4 秒/房；一局 30 分钟 = 1800 秒
→ 单进程平均可带 **约 200 房**。平均吞吐不是瓶颈，**突发阻塞才是**
（20 房同时结算最终战 = 23 秒）。

**理论最坏未测到**：四个场景都是 wipeout 结束、最多 181 帧，而硬上限是
`HARD_TIMEOUT 180s ÷ TICK 0.1s` = **1800 帧**。按 33 µs/单位·帧 外推，
打满时长的一场约 **5.8 秒**。`DECAY`（10 秒后开始、每 6 秒全场 ×0.8）让战斗收敛，
但 `hp` 被 clamp 在 1、`atk` 被 clamp 在 1，**不是硬保证**。
结论：概率很低，按**只观测不专门处理**记录（超过 N ms 记一行日志）。

### 2026-07-28 多进程分片落地

Godot 的单线程瓶颈是**每个进程**的，所以扩容方式是开 N 个服务器进程各管一批房间。

### 2026-07-28 状态信封 E3 已实现（结算确认 + 明确退出回执，协议 12）

E3 解决的是同一句话的两面：**"离场"必须是玩家的意思表示，不能是网络的意思表示；
"这一轮过了"必须是所有在场的人都说过了，不能是最快那个人替所有人说。**
对应 `B8` 剩余、`B15`、`C7` 剩余。

**一、结算确认（`battle_id` + `result_ack`）**

| 改动 | 说明 |
|---|---|
| `room.battle_id` | 掷战斗种子时生成 `"房间:回合:seq"`，随 match_state 下发 |
| `room.result_acks` | `slot -> battle_id`。推进下一轮时连同 `battle_id` 一起清空 |
| `send_result_ack()` | 客户端**把结算应用到本地状态之后**才回执（不是收到就回） |
| `_room_result_acks_complete()` | 推进前的闸门；`_room_begin_next_prep` 与 `_rpc_result_ack` 两处都过它 |
| `RESULT_ACK_TIMEOUT_SEC = 60` | 兜底，不是正常机制 —— 正常路径几秒内全部 ACK |

等谁、不等谁（**按已确认的产品规则**）：

| 座位 | 等不等 | 为什么 |
|---|---|---|
| 在线真人 | **等** | 这正是 C7 要修的：此前任意一人按准备就能把还在看回放的人拽走 |
| 掉线真人 | 不等 | 他回来时靠 `room_state` 全量快照直接追上，不需要全房陪等 |
| AI / 空席 | 不等 | 服务器代过 |
| 迟到的旧 `battle_id` | 丢弃 | 否则上一场的确认会把这一场算成"已确认" |
| 同一 `battle_id` 重复 ACK | 幂等，无副作用 | 重发是正常网络行为，不该有第二次效果 |

全部在线真人确认完会**自动推进**，不必再等谁按准备。

**二、明确退出（`leave_intent` / `leave_receipt`）**

分清两件此前混在一起的事：

| 情形 | 入口 | 凭证 | 服务端座位 |
|---|---|---|---|
| 玩家点"退出" | `request_user_leave()` | **收到回执才清** | 释放 |
| 技术失败（replay 没等到、match_state 超时…） | `enter_recoverable_failure()` | **绝不清** | 保留，等重连 |

- `request_id` + `_leave_tombstones`（TTL 600s）：回执丢了就重发同一个 id，服务端重放同一份结果。
- tombstone **存在房间之外** —— 最后一个人退出会立刻关房，他仍要能重取回执。
- `SaveManager.mark_pending_leave()` 落盘：进程在发出意图后被杀，下次启动知道**不要提示重连**。
- `disconnect_session()` 保留为兼容入口，语义等同"玩家明确退出"；**技术失败不要调它**。
- `Main.gd` 两处技术失败改道（这是 B8 的实际修复点）：`replay` 出错、`match_state` 超时。
  此前它们调 `disconnect_session()`，等于自己清掉重连凭证 —— 而服务器那边座位还好好留着。

**三、顺带修掉的两处噪声**（不属于 E3，但会淹掉真错误）

`_assign_peer_to_room` 的遗留 `_rpc_team_lobby` 与 `_tick_idle_peers` 的 `disconnect_peer`
都没判连接状态，对已断开的 peer 操作会刷 `unknown peer ID` / `ERR_CONDITION` 错误栈。

**回归**（全绿）：

| 台 | 级别 | 结果 |
|---|---|---|
| `adversarial_client` | L1 | **25/25**（新增 `result_ack_and_leave` 9 项） |
| `handshake_check` | L2 | ok / bad / silent **三例全 PASS** |
| `persist_check` | L2 | save→load **跨进程 PASS** |
| `reconnect_check` | L1 | PROBE A–F ALL PASS |
| `economy_settle_check` | L1 | failures=0 |
| `determinism_check` | L1 | 两项 true |

**⚠️ 这一轮暴露的验证盲点（比 E3 本身更值得记）**

`handshake_check` 和 `persist_check` 都用 `OS.get_cmdline_args()` 读 `--` 之后的参数，
而 Godot 把那些参数**只**放进 `OS.get_cmdline_user_args()`。后果：

- `handshake_check` 三个用例**全部退化成默认的 `ok`** —— 三连 PASS，但 `bad` / `silent`
  从来没跑过，"协议不符会被拒"这个结论此前**没有证据**。
- `persist_check` 每次都跑 `save`，`load` 那一半从来没执行过 —— 而 `load` 才是
  "文件真的活过进程死亡"这个唯一论点所在。B5 此前的"通过"只覆盖了一半。

修好之后重跑，两台的所有用例都是真跑出来的 PASS（含 `bad` 被拒于连接建立之前、
`silent` 被 `auth_timeout` 拒掉、新进程读回 2 个房间且 HP/阶段/token/保留期全对）。

**教训**：**一个只会输出 PASS 的测试台不是测试台。** 参数没生效、脚本解析失败、
断言写反 —— 这三类都会表现为"全绿"。新增用例时必须先让它**故意失败一次**，
确认失败真的会被看见，再改成正确断言。

### 2026-07-28 状态信封 E4 已实现（交易幂等回执，协议 13）

宝物选择、宝物刷新、黄金祭坛这三笔都是**一次性、有副作用、不可重放**的操作，
此前是「发出去就不管」。请求丢了玩家白点一次；**回复丢了后果更糟**：

| 交易 | 回复丢失后重试会发生什么（修复前） |
|---|---|
| 宝物选择 | offer 用后即弃 → 重试落到 `no_offer`。服务端已经记了归属，客户端永远收不到，两边宝物列表从此不一致 |
| 宝物刷新 | **再摇一次并再进一次 `refresh_index`** —— 玩家为一次刷新付两次钱，第一次看到的候选再也拿不回来 |
| 黄金祭坛 | 再扣 1 点全队 HP、再消耗一次机会，而金币只按收到的回复加 —— **付两份代价拿一份收益** |

**注意这里的对称性**：直接把重试拒掉和执行两次一样糟。前者让玩家白丢一件宝物，
后者让他被扣两次代价。正确答案只有一个 —— **重试必须拿回同一份成功结果，且副作用只发生一次**。

**解法**（和 E3 的 leave receipt 同一套）：`request_id` + 服务端存结果 + 重试重放。

| 层 | 改动 |
|---|---|
| 服务端 | `room.tx_log`：`slot -> Array[{rid, kind, result, at}]`，FIFO **定长 16/座位** |
| | `_tx_context()` 统一入口：限流 → rid 合法性 → 房间/座位 → **幂等命中即重放并返回** |
| | `_tx_replay()` **只念上次的答案，不重做任何副作用** —— 这就是幂等的全部含义 |
| | 裁决拆成 `_room_apply_altar` / `_room_apply_treasure_refresh`（choice 本来就是分开的），返回值直接就是要存的那份结果 |
| 协议 | 四条回复 RPC 签名前置 `request_id`：`_rpc_treasure_offer` / `_rpc_treasure_granted` / `_rpc_treasure_denied` / `_rpc_altar_result` |
| 客户端 | `_tx_pending`（重发用**同一个** rid）+ `_tx_done`（重复回复直接丢，否则金币加两次）；3 秒重试、最多 3 次 |

**为什么 `tx_log` 要进两张表**：

- 进 `SEAT_SLOT_MAPS` —— 座位释放时一起清，否则新玩家继承前任的交易记录。
- 进 `PERSISTED_ROOM_FIELDS` —— 重启后客户端会重发还没拿到回执的交易，丢了回执日志
  就等于同一笔宝物/祭坛被执行两次。定长 16/座位，代价可忽略。

**放弃重发时按「未知」而不是「失败」处理**：3 次都没回执就停手，只发一个 `timeout`
把 UI 解锁（否则宝物弹窗永远转圈），**不伪造失败结果** —— 服务端可能已经成功了，
本地擅自判失败会让两边账目分叉。权威值由下一份 `room_state` 快照纠正（`owned_treasures`
和 `altar_uses` 都在里面），这正是 E2 全量快照买到的东西。

**边界（不要高估）**：这解决的是**同一笔交易不被重复执行**，不是**金币账目本身可信**。
金币仍是客户端自报（A5/P1）。慷慨命运赌博现在完全在客户端、没有 RPC 可幂等化 ——
它归 P1 账本，届时**出生就带 request_id**，走的是同一套信封。

**状态计数不变**：E4 推进的是发布门 `R3`，**不关闭 54 个问题 ID 里的任何一项** ——
`A5`/`A10`/`C18` 要等 P1 完整账本。别把"交易不会重复执行"读成"经济数据可信"。

**回归**：`adversarial_client` **26/26**（新增 `tx_idempotency` 24 项），其余六台全绿。
新用例按新立的规矩**先故意失败过一次**：把定长裁剪改坏 → `tx_log_bounded` FAIL、
退出码 3 —— 确认失败真的会被看见，再改回正确实现。

### 2026-07-28 B9 通道映射（协议 14）

**根因**：ENet 的可靠通道是**按通道各自排序**的 —— 同一条通道上前一个包没送达，
后面的包就算已经到了也得压着不交付。此前 44 个 RPC **全部**是 `reliable` + 默认通道，
于是一份 replay 在弱网重传时会把排在它后面的 pong 一起压住：客户端量到"心跳超时"→
重连 → 再收一份 replay，正反馈。

| 流量 | 改成 | 理由 |
|---|---|---|
| `_rpc_ping` / `_rpc_pong` | **unreliable** | 心跳是周期性的，丢一发几秒后就补上；"被大包压住"才是实际故障 |
| `_rpc_team_replay` | `reliable` + `CH_BULK` | 大包内部仍有序仍可靠，但压不到控制流 |
| `_rpc_client_log` / `_rpc_team_boards` | `reliable` + `CH_BULK` | 同样"大且不急" |
| 其余 40 条 | 不动（`CH_CONTROL`） | 房间状态、结算、交易、握手 |

**踩到并纠正的一个反向错误**：我最初给 `create_server` / `create_client` 显式传了
`max_channels`，注释还写着"不传的话默认只开系统通道，往 CH_BULK 发包会被丢掉"。
**这是错的**。实测（`tools/channel_check.tscn`）：不传时 ENet host 的
`max_channels = 255`；传一个具体数字只会把上限**调低**。已改回不传，并把这条结论
写进 `NetworkConfig`（以后加第三条用户通道时，一个写死的小数字就是静默丢包的陷阱）。

**新增 L2 用例 `tools/channel_check.tscn`**（两个真实进程，server / client 双角色）：

| 断言 | 结果 |
|---|---|
| pong 收到 → unreliable 路通 | PASS |
| 200 KB replay 收到 → `CH_BULK` 路通 | PASS（raw 200100 B → 压缩 1543 B） |
| 拿到座位号 → `CH_CONTROL` 上的 `room_state` 仍通 | PASS |
| 服务端收到 `clientlog` → 客户端→服务端方向的 `CH_BULK` 也通 | PASS（服务端日志可见） |
| `enet host max_channels` | **255** |

**⚠️ 这个用例证明的是"通道配置没写错、包都能到"，不是"队头阻塞真的消失了"。**
回环上没有丢包也没有排队，测不出分离带来的收益。要量化那个收益需要 L3 丢包/延迟注入
（`tc netem` 或等价工具）+ 真实 wire 指标，那仍然没有做。所以 B9 记 **⚠️ 部分完成**：
改动方向确定、配置已核实，**收益未测量**。

### 2026-07-28 状态信封 RFC 已出（待审）

设计稿在 **[`docs/状态信封RFC.md`](状态信封RFC.md)**，只出方案未写码。

它一个人卡着 8 个问题：`B6` `B8` `B15` `C10` `C11`，以及 `C5` / `C7` / `C17` 的剩余部分 ——
这些现在全是"止血已做、完整版等信封"。不先定下来，后面每加一个功能就会各造一套
同步格式，最后重连、恢复、持久化互相打架。

**核心判断**：这八个问题**是同一个根因** —— 房间的权威状态被拆成七八个各自为政的 RPC，
每个都能独立迟到、乱序、互相覆盖。解法是把 `_rpc_team_lobby` / `_rpc_team_leader` /
`_rpc_resume_state` / `_rpc_round_resync` **四合一**成一条带序号的全量快照。

**已在 RFC 里锁定的决定**（都是之前讨论确认过的）：
- 不做 delta（全量快照 + 序号 ⇒ **漏包自愈**，服务器不需要保留任何状态历史）
- 不做 replay 分块（压缩后 61.8 KB，实测低于阈值上沿），但信封预留字段
- 不做 replay 留存（即时素材，阶段推进即丢，无需 TTL/LRU/磁盘 spill）
- `payload_hash` 保留字段但 v1 不填 —— **裸 hash 在明文链路上防不了篡改**，
  只防实现 bug，而 ENet reliable 已有 CRC。真要防篡改得 HMAC，那是 C14 之后的事

**分四阶段实施**：E1 握手 + 错误分级 → E2 `room_state` 全量 + epoch/seq →
E3 ACK（leave receipt / result ack）→ E4 `request_id` 幂等回执。

**未决问题进展**（RFC 第十二节）：4 条已确认 3 条 ——
`match_epoch` 保留（同房可再开一局，重置规则=全部刷新）、
result ACK 按"只等在线真人"、E1 只校验协议号。
**仅剩 `state_seq` 跨重启**，而它依赖 `B5` 持久化，**不阻塞 E1–E4**。

### 2026-07-28 P1 经济账本 RFC 已出（待审）

设计稿在 **[`docs/P1经济账本RFC.md`](P1经济账本RFC.md)**，只出方案未写码。

它解开 `A5` `A10` `C1` `C2` `C6` `C18` —— 也就是"金币/单位/星级/宝物全是客户端自报"
这一整摊。

**核心判断**：不能只给宝物刷新/祭坛/赌博各补一个扣款 RPC。
`grep GameState.gold` 查出**八条**客户端直接改金币的路径，只修三条之后，
改客户端的人仍然可以改存档、白嫖买单位、重复出售刷钱、提交无来源的高星阵容。

**从代码里查实的三件事**（都写进了 RFC 第四节，需要产品拍板）：

1. **出售退款是个可利用的套利**：`floor(def.cost × star × 0.5)` 按**当前定价表**算，
   而不是按实际支付。配合 `money_discount` 宝物 → **折扣买入、原价一半退款**，可反复刷。
2. **黄金祭坛 UI 显示 `+5` 而实际给 `+50`**（`PrepUI.gd:1722` 硬编码传了 `5`，
   而 `ALTAR_GOLD = 50`）。是 UI 写错还是数值该改？
3. **金币在代码里没有任何上限**。审计文档提过 `99,999`，但那是提案不是现状。

RFC 第四节共 **8 条待拍板**，其中 4.1（退款口径）和 4.7（分阶段切分）影响最大。

**排序结论**：账本应排在状态信封**之后** —— 经济 intent 需要一个 canonical 的
`PREP` 阶段门，而现在服务端的 `round_index` 是惰性推进的（战后客户端已进备战、
服务端还停在 `RESULT`），裸加 `phase == PREP` 会误拒合法的第一笔请求。

### 2026-07-28 第三次复核：新增阻断链路与整改方向

本轮不新增平行 A/B/C 编号，而是把分散在现有问题中的组合风险形成可验收工作项。
R1–R7 是发布的**必要但不充分**条件。R1/R3/R5/R6 涉及的新 RPC、ACK、revision 和状态信封
统一纳入最终同步协议批；不指定先发布哪个协议号，也不发布中间版本。原 1A 中
A10/A12/A13/A14、B4 等 P0 阻断项仍须同时通过。

| 补充项 | 关联问题 | 当前风险 | 整改方向 / 验收条件 |
|---|---|---|---|
| **R1：leave 无 ACK，且和技术失败共用出口** | A11、B8、B13 | `disconnect_session()` 发 leave 后立即关 peer；包可能未送达，也可能送达后立即撤 token、转 AI。replay/match-state 超时可能因此永久失去恢复资格 | 拆成 `request_user_leave()` 与 `enter_recoverable_failure()`。只有玩家明确退出才写入 `pending_leave(request_id)` 并发 intent；服务端幂等回 receipt，客户端确认后才清 token。技术失败不发 leave、不清 token |
| **R2：主动 leave 可制造全 AI 空房 churn** | A7、A11、B4、B11、C20 | 玩家转 AI 后可能立即触发同步战斗，再创建新房；旧房跨 RESULT/PREP 存活并占配额 | 每次 leave/断线/宽限到期统一计算在线真人和有效 token。产品规则是零 token 立即关房、有 token 保留 300 秒；工程上使用 monotonic deadline、转 suspended、不启动下一阶段/新模拟、不进公开列表并设数量/内存硬上限 |
| **R3：宝物、金币账本、resume 与幂等未闭环** | A5、B6、C1、C2、C5、C18 | 战斗仍信客户端宝物集；宝物刷新不权威扣款；祭坛缺 entitlement/权威奖励；慷慨命运由客户端开奖；空 offer resume 不清旧 UI；重复操作无 request_id | 保留全部功能并完成 P1 权威账本：canonical owned、`offer_id + round_id + request_id + expected_revision`、receipt、`99,999` 上限、cost_basis 退款；刷新/4 Money/祭坛/慷慨命运按本文已确认规则实现。客户端不预改金币，resume 下发完整账本快照 |

**R1–R7 不可省略的验收边界**

- **R1**：客户端原子保存 `pending_leave(request_id)`，该状态禁止自动 resume；ACK 必须绑定
  room/match/seat/token_revision。服务端撤销 token 后短期保留 leave tombstone/receipt，重复请求
  返回同一结果；即使最后一人退出并立即关房，也能重取 receipt，避免 ACK 丢失后下次启动误恢复
- **R2**：有效 token 只指仍映射到该 room/slot、未撤销且未过期的私有 session token，公开短码
  不计数。进入 suspended 保存原 phase/deadline；恢复时用 monotonic ticks 重基准 timeout，不能把
  保留席位批量变成永久 AI。已开始且不能中断的同步模拟可完成并缓存，但不得启动下一场
- **R3**：choice/refresh/祭坛/慷慨命运在限流、掉包或 ACK 丢失后可用同一 request_id 重试；
  resume receipt 与 canonical owned 必须解除 UI pending。联机刷新始终保留；未完成完整账本前
  只能标记为“待权威化”，不能把关闭功能写成整改手段。
  **⚠️ 部分达成**（2026-07-28，协议 13，E4）：choice / refresh / 祭坛三笔已走 `request_id`
  + 服务端回执重放，重试拿回同一份结果且副作用只发生一次；重试用尽时按“未知”处理并靠
  `room_state` 快照纠正，不伪造失败。**慷慨命运仍完全在客户端**，没有 RPC 可幂等化 ——
  归 P1 账本 —— **已实现**：`gamble` 走 `_rpc_economy_intent`，`roll` 由 Crypto 预先摇好，
  重放回执绝不重摇。**但客户端仍在本地 `randf()` 那条路上**（L4 未做），所以本项
  仍不能勾选：服务端已经准备好，切换要和整个客户端改造一起上
- **R4**：新增、删除或改签名 RPC 后 CI 必须重生成并比对矩阵。长度按原始字节计，不能仅用
  `String.length()`；超限输入不计算完整 hash，避免把日志防护本身变成 O(n) 放大器
- **R6**：先量 P99/Pmax 并预留恢复容量；有效 token 仍处 replay-required 边界时禁止 LRU 静默
  淘汰。收到 match-state 可以先缓存，但双队 stream 验证完成前不得导航到 PREP 或发送
  `result_applied_ack`
- **R7**：生产 logger 的队列满或输出端变慢时丢弃/采样并累计 `dropped_count`，不得反压主循环；
  smoke test 注入换行、控制字符和洪水，确认不能伪造日志级别/事件或泄漏 token/payload

**R1–R7 建议实施顺序（仅为本地开发顺序，不形成可上线的中间包）**：

1. P0-0：R1 leave/技术失败分流 + ACK/幂等。

4. P0-3：R4 按实际 schema 自动生成全部 `any_peer` 输入/RPC 矩阵。
5. P0-4：R7 Release 可观测性、日志注入和背压。
6. P1：R5 leader 公平与 C25 UI；完成 R3 全账本、`+50/+100`、慷慨命运、cost_basis 和金币上限。

   R6 状态信封、阶段恢复、A/B 双 replay 缓存与 ACK。

这只是补充链路的建议顺序，不是完整发布清单；第 1A 与 A/B/C 表中的其他 P0 阻断项仍需

### 9.7 三个延期项的处理结论

**① 宝物刷新：不单独取消客户端预扣 —— 这个判断成立。**
服务端目前只刷新候选、不维护权威余额，单独删掉客户端扣钱会直接变成**免费刷新**。
必须在一次完整切换里做完：

1. 每席位服务端权威金币账本
2. 客户端发送带 `request_id / round_id / offer_revision` 的刷新意图
3. 服务端验证拥有者、阶段、余额与 4 Money
4. 服务端原子完成扣款或免费判定 → 生成候选 → 递增 revision → 写幂等回执
5. **同一次双端更新中**取消联机客户端预扣
6. 水晶生命换钱、赌博、已确认的 `+100`、以及统一上限全部走同一账本
7. 单机 / 教学保持现有本地路径

**② C20 monotonic：可以做成独立的技术前置提交。**
此前写的"单独改一定留下半套时基"不准确 —— 持续时间目前**集中经过 `_now()`**，
可以先单独落地。约束是：

- **不能对已有房间热重载**，必须重启服务器
- 日志时间继续用墙钟；TTL、心跳、限流、300 秒离线宽限统一 monotonic
- 测试 NTP 前跳、后跳与 299/300 秒边界
- 未来做持久化时**不能直接保存裸 monotonic deadline**（重启后基准就变了）
- 仍与 R2 的 300 秒规则一起验收

**③ C16 TeamOutcome：不是普通重构，是现有玩法冲突。**
三处实现的分歧不只是代码重复，而是规则本身不一致：

- 专服在最终回合按**最终战胜负**决定整局
- 本地 fallback 按**剩余水晶生命**决定
- **双杀目前固定判 A 队胜** —— 直接违反已确认的"两队玩家平等待遇"

**在下面两条产品规则确认前，不能安全抽取 `TeamOutcome`。**

### 9.8 ✅ 已确认的胜负规则（2026-07-28 修订，C16 据此实现）

> **⚠️ 本节被记错过两次**，这是定稿版。错法留档以免再犯：
> ① 初版写成"第 21 回合（不分 kind）按最终战结果"；
> ② 二版收窄成"只有第 21 回合的 PVP"，并保留了一条"第 21 回合 PVE/Boss 按血量"的分支
> —— 而**第 21 回合根本不存在 pve/boss 形态**，那条分支是不可达的死规则。

1. **第 21 回合恒为最终战，只有这一种形态**：两队棋子同场对打，
   加上按水晶血量召唤的友军，双方还各自召唤佣兵。
   打完有一方赢 → **那一方直接赢下整局**，水晶血量完全不参与判定。
   只有双方同时全灭（极小概率）→ **平局**。
2. **第 21 回合之前**（pve / boss / pvp 都可能）：对局只在某队水晶归零时结束，
   归零方判负、另一方胜。**唯一依据是水晶血量**，那一轮的战斗胜负本身不决定整局
   （打赢一场 ≠ 赢下整局）。
3. **两队水晶同时归零 = 平局**。PVE/Boss 各打各的怪、各自掉血时可能发生；
   中途 PVP 同场对打只有输方掉血，走不到这里。
4. 任何情况下都不得用"相等就判 A 队"这类回退。

已落地为 `scripts/multiplayer/TeamOutcome.gd`，三处调用点统一。
判定表（唯一真相，改规则只改这一处）：

| 场景 | 结果 |
|---|---|
| 第 21 回合 · 分出胜负 | 本场胜方（血量不参与） |

| 两队水晶都还在却判对局结束 | DRAW（防御性：调用方 run_over 判定有误，不猜胜者） |

**实现刻意不检查 `kind`。** 第 21 回合按定义就是最终战，而 `kind` 的字面值取决于
从哪里读：`RoundService.schedule_kind_for_round(21)` 返回 `"final"`，但
`prepare_team_state` 内部会立刻把它改写成 `"pvp"` 再存进 state/replay。
依赖任何一个字面值，都会在下次有人改写法时**静默走错分支**。对抗台对
`"pvp"` / `"final"` 两个值都做了断言。

**战斗层新增 `is_draw`**：模拟器此前对真平局有两处偏 A 回退 ——
双方全灭时 `player_wins = true`（reason 字面就叫 `double_ko_player_fallback`），
以及超时战力完全相等时用 `player_formation_hp >= enemy_formation_hp` 破平
（服务端进程这两个全局从没被写过，恒相等 → 恒判 A 胜）。
现在这两种情况额外置 `is_draw = true`；`player_wins` **保持原值不动**
（经济结算、伤害盖戳、UI 字幕都在读它，改它会牵动整条链），
只有 `TeamOutcome` 在判第 21 回合 PVP 整局时读 `is_draw`。

**⛔ 还有一格规则没确认：水晶血量完全相等时怎么判？**
包括第 21 回合 PVE/Boss 双方血量相同，以及同回合双双归零（0 : 0）。
你说的"直接分出胜负"在这一格没有依据可用。
当前**暂记平局**（绝不恢复旧的"相等判 A 胜"），需要你定：
判平局？还是有其他破平依据（例如累计伤害、存活单位数）？

### 上传与重启

**下列是目标流程，仓库当前没有对应的 manifest 生成器、维护排空、health probe、systemd unit
或自动 deploy/rollback 脚本。实现并演练前不得宣称“部署流程已完成”。**

```
1. 上传 ZIP 与独立 SHA-256/manifest
2. 校验哈希后解压到全新的版本化目录 releases/<build_id>
3. 在新目录做 JSON/hash 校验与 headless 冷启动 smoke test
4. B5 持久化完成前:进入维护模式、停止新接入并等待房间排空;测试环境若选择强制停机,
   必须明确记录“所有在场对局会丢失”
5. 停止旧进程 -> 原子切换 current -> 用解析后的版本目录启动新进程
6. 检查监听端口、protocol/build/data hash、Release 结构化日志与健康探针
7. 失败立即切回上一 release 并保留完整日志
```

禁止继续用 `unzip -o` 覆盖在线目录:它不会删除新版本已经移除的旧文件,中途失败会留下混合版本。
`journalctl -n 3` 也不足以证明健康;必须看到启动完成、正确 build/manifest、端口监听和最小连通测试。
旧进程不得长期以会变化的 `/current` 为 `--path`，否则切换 symlink 后的延迟资源加载可能混读新旧版本；
systemd 应使用解析后的固定 `releases/<build_id>` 目录。
旧的 `upload ssh code.txt` 仍使用旧 ZIP 名、`pkill -f godot` 与 `nohup`,与 systemd 流程冲突,
应标记为废弃,避免杀掉无关 Godot 进程或形成双重进程管理。

- 挑低峰窗口

### 特性开关

文件位置:`user://server_flags.json`(可用 `--flags=<绝对路径>` 覆盖)。
不存在时启动使用默认值;改完存盘后轮询热重载。

```json
{
  "metrics_payload_sizes": true,
  "metrics_sample_every_n_battles": 1
}
```

| 开关 | 默认 | 说明 |
|---|---|---|
| `metrics_payload_sizes` | `false` | 载荷埋点。`var_to_bytes` 一份大 replay 本身有 CPU 开销,而服务器是同步主循环——**只在测量周开** |
| `metrics_sample_every_n_battles` | `1` | 每 N 场采样一次。测量周先用 1,量到 P99 后调大或关掉 |

当前源码仍存在 `send_rival_replay`，但它违反“每名真人自动获得 A/B 双队完整 replay”的
已确认规则：生产环境不得设为 false，后续应移除或失效化。隔离压测若需要比较单/双 stream，
使用测试参数，不进入玩家环境。

当前只有以上少数 metrics flags,不能代表“首批每项都有独立开关”。热重载还需修两个边界:
- 成功 parse/校验后再更新已处理 mtime;坏 JSON 不应吞掉本次变更,修复后必须能重试
- 文件删除或配置 key 缺失时明确恢复默认值,并对类型、范围和未知 key 做校验

### 部署后要盯的日志

四个影子模式前缀,它们决定后续批次怎么做:

| 前缀 | 含义 | 该怎么读 |
|---|---|---|
| `shadow syn_mismatch` | 客户端派生的 syn 与服务端重建的不一致 | **应恒为零**。非零说明两边对羁绊的理解有分歧,玩家界面会和实际战斗对不上 |
| `shadow treasure_overflow` | 宝物数量超过该回合应有上限 | 大量出现多半是**数据表不同步**而非作弊(依赖 `round_schedule.json` 两端一致,见 C11) |
| `shadow treasure_unowned` | 客户端上报了服务端未发放的宝物 | 当前只记录；R3 上线后应由服务器规范化覆盖，并保留审计计数 |
| `shadow gold_delta` | 上报金币与上一战结算值的差 | **这是 P1 备战账本的重要观测之一,不是唯一依据**。聚合差值不能区分买卖、刷新、赌博、祭坛,仍需代码路径清单和事件级埋点 |

另有 `rate limit` / `zombie peer reaped` / `board watchdog` / `metrics` 前缀可用于观察限流误伤、
僵尸连接、看门狗介入频率和 replay 序列化/压缩 payload 估算;真实 wire bytes、重传和 P99
仍需新增埋点。**R7 完成前这些日志在 Release 专服中可能完全不可见，不能把“没有日志”解释为
“没有异常”。**
