### 落地记录（2026-09-16 第 2 步）

代码：`scenes/menu/ShopScreen.gd` / `BagScreen.gd`、`scripts/pets/PetPreview.gd`、
`scenes/menu/MainMenu.gd`（钱包位与两个入口）、`scenes/main/Main.gd`（路由）、
`backend/app/routes/profile.py`（装备时的归属校验）。

几处落地时定的：

- **宠物在商城/背包里显示的是 3D 小预览，不是图。** `data/pets/pets.json` 的 `icon`
  字段是空的 —— 宠物根本没有 2D 图。原本这段 SubViewport 代码只在 `PetScreen` 里，
  抽成了 `scripts/pets/PetPreview.gd` 给三个界面共用（否则要抄三遍，
  以后调一次相机角度改三处）。
- **钱包拉到之前显示 `—`，不是 `0`。** 0 是一个**看起来正常的错值**，
  玩家会以为自己的钱没了。主菜单与商城两处同一个规则、同一个千分位格式。
- **购买的幂等键存在界面里，整笔重试期间复用。** 失败时只有「明确的失败」
  （4xx，服务端一定没扣钱）才丢掉它；`code == 0`（没发出去 / 没收到响应）和 5xx
  **必须留着** —— 那笔可能已经成交，换新 id 重试就变成第二笔订单。
  这时提示语会明说「再点一次不会重复扣费」。
- **回执里的 `replayed` 要给玩家看。** 服务端重放旧回执时另说一句
  「刚才已经买到了，没有重复扣费」，否则玩家以为又扣了一笔。
- **背包只展示，换装只做宠物。** 头像与头像框的选择器已经在资料页
  （`ProfileScreen` + `AvatarPickerPanel`），在背包再做一份就是两处要同步的逻辑。
  背包里点头像那块跳资料页。
- **装备付费内容前校验归属**（`routes/profile.py` 的 `_require_entitlement`）。
  判据是 `shop.requires_entitlement()` 而不是「归属表里有没有」——
  后者会把现有 20 张免费头像全判成「你没有」。`showcase_pet` 原本完全没有校验，
  一并补上了。

## 三、货币

### 命名纪律（现在就要立，以后改是迁移）

| 概念 | 代码里叫什么 | 归谁 |
|---|---|---|
| 局内金币 | `GameState.gold` / `room.slot_gold` | 战斗服务器，一局一清 |
| 账号黄金 | `coin` | 账号服务器，永久 |
| 账号钻石 | `diamond_paid` / `diamond_free` | 账号服务器，永久 |

UI 上两个都叫「金币」没关系（玩家不看代码），**但代码和数据库里必须用不同的词**。
混了不会报错，表现是「钱对不上」，那是最难查的一类。

### 钻石分付费 / 赠送两列

**游戏里从头到尾只显示一个总数** —— `WalletResponse` 就是 `{diamond, coin}`，
分账任何时候都不下发给客户端。它纯粹是后台账目。

分列是为了退款与对账时能**直接读**「他还剩多少是花钱买的」，
而不是每次都把整条流水重放一遍；而且这样分账对不对不依赖流水有没有被人动过。

扣款顺序固定：**先扣赠送，后扣付费**。反过来扣的话，玩家充值后会先花掉付费那部分、
剩一堆赠送余额，那个数就算不出来了。

> 2026-09-16 这条反复过一轮：中途改成过单列（理由是构成能从流水重放推出来，
> 两列只是缓存），随后拍回分列。留这一句是因为那轮里有个纠正值得记住：
> 我先前写的「这个维度不从第一天记以后永远补不回来」**说过头了** ——
> 真正补不回来的是**流水**，不是钱包那两列。

⚠️ 分列的代价是多一条不变量：**两列的和必须始终等于流水重放的结果**。
所有改钱的路径都只走 `shop._apply()`，就是为了守住它。

### 两条跟钱有关的纪律

1. 🔴 **`wallet_ledger` 永远不许裁剪，一行都不许删。** 这条在这个仓库尤其要防 ——
   `app/maintenance.py` 会清过期私聊会话与好友请求日志，`chat_messages` 更是
   「每对好友只留最近 200 条」。谁照着那个模式给钱包流水也加一条清理，
   当天什么都不会发生，坏的是以后：「这个号的钻石哪来的」再也答不出来
   （客服最常被问的一件事），钱包那两列对不上时也没有东西可以拿来核对。
   要控体积就归档到冷表，不是删。`test_shop.py` 有一条断言钉着
   `maintenance.py` 不许出现 `wallet_ledger`。
2. 🔴 **`source` 不许填错。** 手工发放记 `grant`、充值记 `iap`。
   填错当时没有任何症状，坏的是以后对账。

### 落地记录（2026-09-16 第 3 步：宠物归属上云）

`PlayerProfile` 那个**同步门面留着**（二十来处调用点一个没改），只换数据来源：
`owned_pets` / `active_pet` / `needs_starter_pick` 成了服务端答复的**内存缓存**，
不从 `profile.json` 读、也不写回（`SaveSchema` v6 把这三个键 `erase` 掉并回写）。

几条关键纪律，每一条都对应一个不报错的失败模式：

1. 🔴 **刷新失败时一个字段都不动。** 清空的话，网络抖一下玩家的宠物就没了 ——
   表现是这一局没有加成，而且不报错。首次拉取挂在 Bootstrap 的进门流程里
   （登录成功那一刻发起，与连 WebSocket 并行）。
2. 🔴 **刻意不把它做成放行条件。** 它要读服务器上的 `data/pets/pets.json`，
   而那正是 `update.sh` 第一趟不会复制的文件之一 —— 拿它当进门门槛等于
   「一个数据文件没传上去，全员进不了游戏」。为 1% 的加成换这个爆炸半径不划算。
3. 🔴 **`needs_starter_pick` 只在 `pets_loaded` 之后才当真。** 否则弱网下
   老玩家会被要求重选一遍三选一。拉到之后若确实要选，由 `Main._on_pets_changed` 补一次
   （这也覆盖了注销账号后的情形）。
4. **改出战宠物只有 `PlayerProfile.set_active()` 一条路。** 背包原本直连
   `AccountManager`，已经收回来 —— 两条路各自维护缓存，必然出「背包里换了、
   备战页还是旧的」。
5. **不本地缓存服务端答复。** 缓存就是又一个可改的文件，那「不认本机」整件事就白做了。

删掉的：`PlayerProfile.grant()`、`SaveSchema.PET_ID_RENAMES` / `_rename_id` / `_rename_ids`、
`migrate_profile` 里 `from < 2` 的那两行改名（**`codex_seen` 那行留着**）。

门禁跟着改了两处：`player_identity_check` 原本断言 `active_pet == "pet_rabbit"`
（改名迁移），现在反过来钉「升级后这三个键必须被删掉」；`onboarding_persistence_check`
的「旧档字段没被改坏」不再含宠物，另加一条钉新行为。

## 四、商品目录

目录放 `data/shop.json`，照 `data/avatars.json` 的形状（配置，不是表）。
服务端校验放 `backend/app/shop.py`，照 `backend/app/avatar_catalog.py` 的形状
（「这个 id 存不存在、有没有资格买」，与数据库那层格式校验分开）。

```json
{
  "schema_version": 1,
  "items": [
    {"id": "shop_avatar_005", "kind": "avatar", "grants": "preset:avatar_005",
     "currency": "diamond", "price": 100, "name": "…", "name_en": "…"},
    {"id": "shop_pet_cat", "kind": "pet", "grants": "pet_cat",
     "currency": "diamond", "price": 300, "name": "…", "name_en": "…"}
  ]
}
```

### 🔴 不在目录里的内容一律免费（落地时定的）

判定不是「有没有归属记录」，而是 `shop.requires_entitlement()`：
**只有出现在 `data/shop.json` 里的内容才需要归属。**

反过来写（不在归属表里就是没有）的后果很具体：现有 20 张头像和 `frame_default`
上线时就是免费的，玩家已经在用了 —— 一做商城它们会**一夜之间全部失效**，
而且不报错。那是对已经在用它的玩家的回收。

好处还有一条：存量玩家一行归属数据都不用发。要卖新头像就出新图、给新 id。

**因此第一版能卖的只有宠物**（三选一没选的那两只）。头像和头像框要等美术出新的，
老的不能挪进来。`tools` 门禁里有一条专门钉住这件事
（`test_content_not_in_catalog_is_free`）。

### 🔴 商品 id 与内容 id 是两个东西

```
shop_pet_cat   ← 商品 id，只出现在订单里
pet_cat        ← 内容 id，归属表存的是它
```

**归属表存内容 id，不存商品 id。** 游戏问的是「他有没有这只猫」，不是「他买过哪个礼包」。
分开之后，同一只宠物可以在不同活动里以不同价格、不同包装上架，都指向同一个 `grants`。

### 改什么安全，改什么不安全

| 改什么 | 能不能 |
|---|---|
| 改名、改图、改模型 | ✅ 随便改，`id` 不动就行。这正是 `avatars.json` 里 `_why` 那条 |
| 改价格 | ✅ 随便改，历史订单存的是**下单时的价格快照**，不 join 目录 |
| **改数值 / 效果** | ⚠️ **不一样**。玩家买的是「利息 +1% 的猫」，改成 +0.5% 就是他买的东西缩水了。走 Google Play，玩家可以投诉 |

带战斗数值的商品改数值前**先发公告**。这条是运营纪律，不是代码能挡的。

## 五、出战名片（原「座位票」，协议 30）✅ 09-17 已做

### 问题

战斗服务器不认识玩家，对局里用到的账号级东西，以前是**三样东西三种做法**：

| 东西 | 以前怎么到战斗服务器 | 洞 |
|---|---|---|
| 出战宠物 | 跟着棋盘每回合自报一次（v29 起营地展示再单独报一次） | 只查「宠物表里有没有」，不查归属 —— 卖钱之后就是白嫖 |
| 出战种族 | 准备 / 开始时自报（协议 28） | 以后种族要解锁，同一个洞 |
| 名字头像 | 手机把**登录令牌**交给战斗服务器，战斗服务器回头去问账号服务器 | 登录令牌离开了账号服务器那条链路 |

以及反过来的一面：**手机重开、本机宠物缓存还没拉到**，交上来的棋盘里宠物是空的 ——
玩家买了的宠物，重连回来效果就没了。

以后加皮肤、加要解锁的种族、再加 4 个种族让玩家 8 选 4，都会碰上同一个问题。
所以不是修宠物，是定一条规则。

### 规则（一条）

**对局里用到的账号级东西，一律以入座时账号服务器盖过章的「出战名片」为准；名片存在座位上。**

1. 玩家点建房 / 加入 → 客户端现领一张名片（`POST /v1/battle/card`，60 秒有效）→ 随请求一起交
2. 战斗服务器验章 → 查这张用没用过 → **写进座位**（名字头像、宠物、种族）→ 之后才动任何状态
3. 交棋盘时，棋盘里的 `pet` 一律换成座位上的。战斗开局加成、战后利息、跨回合缓存
   （掉线代打、重连补交）都从这份棋盘取，所以卡这一处就够
4. **断线重连回到同一个座位，名片还在** —— 宠物、种族、头像都一样，效果都在。
   重连**不需要**新名片，账号服务器一时连不上也照样回得来
5. 领不到名片（账号服务器挂了、没配私钥）→ 请求不发，提示「暂时进不了对局，请稍后再试」。
   这和「连不上账号服务器就进不了游戏」是同一条规则

以后加皮肤、可解锁种族：**往名片里加一个字段**，不再发明新做法。

### 分工

- **账号服务器管「有没有资格」**（`backend/app/loadout.py` 的 `build_loadout`）：
  没买的头像 / 头像框换成默认，没买的宠物写空，没解锁的种族去掉。没资格的根本不会写进名片
- **战斗服务器管「合不合规则」**（`scripts/multiplayer/BattleCard.gd`）：
  种族必须正好 4 个、都认识（`RacePick`），不合就用默认；宠物表里没有的（版本不一致）当没带

「5～8 个种族选 4 个、有的要解锁」落在这个分工里不用改结构：解锁归账号服务器
（`player_entitlements` 里有没有），「选 4 个」归战斗服务器。

### 名片长什么样

```json
{"v":1,"pid":"…","code":"好友码","name":"昵称","avatar":"…","frame":"…",
 "pet":"pet_cat","races":["god","dark","undead","human"],"iat":…,"exp":…,"jti":"…"}
```

线格式：`base64(JSON 原始字节).base64(签名)`。**先验签、再解析，绝不重新序列化** ——
签的是那串字节，验的也是那串字节。实测普通名片 705 字节，按数据库上限造的最大名片 1673 字节；
战斗服务器在解码之前就挡掉超过 2048 字符的（`test_loadout.py` 每次都量一遍最大名片）。

### 为什么不放在握手包里（原设计改掉的地方）

原设计是「握手时带票，在 `NetworkTransport.server_verdict()` 验」。落地时改成跟着入座请求交，三个原因：

1. **装不下。** 握手包上限 512 字节（未经验证的对端，不能放宽），名片 700～1700 字节
2. **时机不对。** 连接时领的名片，玩家在房间列表里待一会儿、中途换了宠物，就过时了。
   入座才是「用什么出战」的那一刻
3. **没处放。** 握手时还没有座位，验完的名片只能挂在连接上；入座时直接写进座位，
   换座一起搬、离座一起清、重连原样留着（`RoomService.SEAT_SLOT_MAPS`）

### 签名

非对称：账号服务器持私钥签，战斗服务器只持公钥验。**不用共享密钥的 HMAC** ——
战斗服务器是暴露在公网 ENet 上的进程，被拿下时公钥伪造不了名片，共享密钥可以。

**RSA-2048 / PKCS#1 v1.5 / SHA-256**，09-16 实测 Godot 4.7.1 的 `Crypto.verify()` 能验
Python `cryptography` 签出来的（对的回 true，改一个 bit 回 false，换钥匙回 false）。踩过的点：

1. **`Crypto.verify()` 收的是摘要，不是原文。** 传原文进去会**一直返回 false 且不报错** ——
   很容易被误判成算法不兼容。要先 `HashingContext` 走一遍 `HASH_SHA256`
2. 公钥用 `CryptoKey.load_from_string(pem, true)` 读（`public_only = true`）。
   公钥位置放成了私钥也读不进去 —— 战斗服务器永远不该持有能签名片的钥匙（门禁钉着）
3. Python 那边 padding 必须是 `PKCS1v15()`，不能是 PSS

## 六、表结构

```sql
-- 009_wallet.sql
create table player_wallets (
  player_id    uuid primary key references players(player_id) on delete cascade,
  diamond_paid bigint not null default 0,   -- 充值来的
  diamond_free bigint not null default 0,   -- 活动 / 补偿 / 手工发的
  coin         bigint not null default 0,   -- 黄金。第一版没有产出口，恒为 0
  updated_at   timestamptz not null default now(),
  constraint wallet_non_negative
    check (diamond_paid >= 0 and diamond_free >= 0 and coin >= 0)
);

-- 只追加，永不 update / delete。对账、客服、退款全靠它。
create table wallet_ledger (
  id            bigint generated always as identity primary key,
  player_id     uuid not null references players(player_id) on delete cascade,
  currency      text not null,        -- diamond_paid / diamond_free / coin（**列名**，不是货币名）
  delta         bigint not null,      -- 正入账、负出账
  balance_after bigint not null,
  source        text not null,        -- shop / iap / grant / refund / starter_pick / match_reward
  order_id      uuid,                 -- 关联订单；手工发放可空
  actor         text,                 -- 手工发放时是谁操作的。🔴 不许留空
  note          text,
  created_at    timestamptz not null default now()
);
create index wallet_ledger_by_player on wallet_ledger (player_id, id desc);

-- 010_shop.sql
-- 存的是**内容 id**（pet_cat / preset:avatar_005），不是商品 id。
create table player_entitlements (
  player_id  uuid not null references players(player_id) on delete cascade,
  item_id    text not null,
  granted_at timestamptz not null default now(),
  source     text not null,
  order_id   uuid,
  revoked_at timestamptz,             -- 退款收回。重新购买时置回 null
  primary key (player_id, item_id)
);

create table shop_orders (
  order_id        uuid primary key,
  player_id       uuid not null references players(player_id) on delete cascade,
  client_order_id uuid not null,      -- 幂等键，照 chat_messages.client_msg_id
  item_id         text not null,      -- 商品 id
  currency        text not null,
  price_snapshot  bigint not null,    -- 🔴 下单时的价格，绝不 join 目录
  status          text not null,      -- ok / refunded。**没有 rejected**，见下
  source          text not null,      -- shop / iap / grant / starter_pick
  external_id     text,               -- 渠道订单号 / purchase token（充值用）
  created_at      timestamptz not null default now(),
  settled_at      timestamptz,
  constraint shop_order_client_unique unique (player_id, client_order_id)
);
-- 充值去重靠它：RTDN 会重复推同一笔。
create unique index shop_orders_external
  on shop_orders (source, external_id) where external_id is not null;
```

四张表都 `enable row level security` 且**不建任何 policy**，同 `001_players.sql` 的理由：
FastAPI 用 secret key 绕过 RLS，Godot 永远不直连 Supabase。

### 拒绝不落库（落地时改的）

原方案 `status` 里有 `rejected`。实现时改成**只有 `ok` / `refunded`**，拒绝一律不写库：

1. 拒绝是幂等的 —— 同样的输入永远得到同样的拒绝，不需要记下来重放；
2. 落了库就会被重放。「余额不足 → 去充值 → 用同一个 `client_order_id` 重试」
   会被重放成失败，而玩家看到的是「我明明有钱了」。

代价是订单表里看不到失败尝试，那些在日志里。`error` 列也因此删掉了。

### 手工发放：`grant_diamonds()`（落地时加的）

拍板是「管理员直接改 Supabase 后台」，但**手改两条语句迟早会漏掉流水那条** ——
改完余额忘了 insert，于是「这个号的钻石哪来的」永远查不出来，而且当时毫无症状。

所以手工路径也只给一个入口，一次调用、原子、忘不掉流水、强制填操作人：

```sql
select grant_diamonds('52c7027a-…'::uuid, 500, '补偿 9/20 掉单', 'arvin');
```

只发 `diamond_free`。手工发的钱不是玩家付的，混进 `diamond_paid` 就把退款口径弄脏了 ——
而那一列的全部意义就是「他到底花过多少钱」。流水的 `source` 同理记 `grant`。

### 扣款与发货必须同一个事务

跨事务就一定会出现「钱扣了东西没到」，而且是在付过钱的玩家身上出现。

handler 顺序照 `docs/P1经济账本RFC.md` 第六节，**这个顺序不能变**：

```
1. 认证 player_id
2. 查目录：商品存不存在、价格、货币
3. ★ 先查订单（client_order_id 命中就直接重放原回执，不再执行）
4. 只有新请求才继续：查归属（已拥有就拒）→ 查余额 → 事务内扣款 + 发货 + 写流水 + 写订单
```

**第 3 步必须在第 4 步之前。** 反过来的话，「执行成功但回执丢了」的重试会被
「你已经拥有了」拒掉，玩家钱扣了东西看不见。这是整个幂等设计里最容易写反的一处。

| 预留 | 在哪 | 为什么现在就要 |

### 马来西亚两条实务

1. **本地支付不要自己接。** TnG eWallet / Boost / FPX 这些，是 Google 和 Apple 在它们
   自己的收款页里提供的。游戏内数字商品必须走 IAP，绕过会被下架。
2. **价格是档位不是数字。** 只能从 Google / Apple 的地区定价档里选。
   所以钱包里存的必须是**钻石数量**，不能是钱；价格档 → 钻石数量的映射表另存，且要能按地区不同。

## 十三、已知局限

- **归属表只管非消耗品。** `primary key (player_id, item_id)` 意味着同一样东西只能有一份。
  以后要卖消耗品（体力、道具），得另开一张带数量的表，**不要往这张塞 quantity**。
- **退款后重新购买**要把 `revoked_at` 置回 null，不是插新行（主键挡着）。
- **黄金第一版恒为 0**，因为没有产出口。这是刻意的，不是漏做。
- **排队、抢座位仍然能被绕过** —— 出战名片不绑房间和座位，那是第二版的事，见第五节「仍然没堵的」。
- ~~**断线还不会回登录页。**~~ 09-16 已做（第 2b 步）。规则只有一条：**连不上账号服务器就进不了游戏。**
  启动页在放行前查一次，`Main._watch_account_link` 管进去以后：不在对局 / 教学里、
  实时连接断开超过 `AccountConfig.CONNECT_PATIENCE_SEC`（与启动页共用同一个数）就送回启动页。
  对局中、教学中、被顶号三种不送。门禁 `tools/account_link_check`（变异测过：拿掉任一
  对局界面的标记、或 `_clear()` 不复位标记，都会红）。
  同批把主菜单的「离线自测」收进了 `OS.is_debug_build()` —— 发布包里留着它，
  等于给玩家一个不经账号服务器就能打一整局的入口。
- 手工发放靠 Supabase 后台，**没有正式后台**。延续公告那条决定，但商城改的是钱，
  所以 `wallet_ledger.actor` 不许留空。有不碰代码的运营 / 客服时再做正式后台。
