## 修复内容

- 战斗模拟以房间为单位分片，每帧处理有限计算；网络维护优先，纯数据打包转到后台任务。入队时冻结输入，按片隔离 RNG 和伤害上下文，取消任务不等待运行中的线程。
- 使用有总量、时间及逐客户端预算的回放发送队列；大回放与心跳／控制消息公平调度。重试期限从首次完整发送结束计时，客户端在解码、结构及身份校验成功后才确认。
- 保留协议 32 的 RPC 签名，并对旧接收器做新服务端到旧客户端方向的实际兼容门禁。名义 4 MiB 接收上限与旧分块估算上限不能混为一谈。
- 结算屏障等待本场权威产物及在线真人确认；期限按双侧实际播放时长与有界准备余量计算，准备总上限 120 秒、回放接收上限 60 秒、演出／确认余量 18 秒，绝对等待上限 480 秒；全部在线真人确认后立即推进，不需等待这些上限。每秒检查到期，重复重连不能无限续期，避免固定 60 秒截断正常战斗。离线席位仍遵守原有不阻塞在线玩家的规则。
- 重连恢复同一场战斗时保留已解码回放及游标；冷恢复等待正确战斗身份、完整回放与权威结算匹配，传输失败明确进入可恢复状态。
- 发射后即释放下一次攻击占用，已发出的投射物保留自己的命中时刻。角色死亡不剪掉死亡前已经生成的合法攻击尾部；结算等待必要命中数字完成。
- 模型／本回合特效先异步加载，再执行真实绘制预热。准备阶段不推进战斗模拟，不触发真实声音或数值结算；缓存复用必须按渲染质量条件匹配。

未重写为 Pinus。采用有界调度、网络与重计算分离的思路，保持已有 Godot/ENet 架构和权威战斗协议。Godot SceneTree 不交给工作线程操作。

## 验证和已知限制

本地调度原始验证 255 项、召唤身份 53 项及确定性 111 项通过；后续发送兼容和结算期限修复需以最终重跑记录为准。客户端最后一次门禁：播放恢复与攻击尾部 145 项、Director 96 项、死亡释放 35 项通过；真实绘制准备／取消 7 项通过，无引擎错误。动态 RESULT 期限与主动超时推进 21 项、回放发送 122 项、接收 111 项通过。真实 8 客户端、大回放、旧版接收、本地房主自动泵共 137 项功能断言通过；DTLS 关闭仍有下述引擎错误。QA3 冷缓存真机第 1/20/21 回合最长帧为 75.274/330.311/156.113 ms，source_dead 和 missing_actor 全为 0，未提前结算；仍有 330 ms 长帧，继续修复。实际云服务器已通过候选包默认入口启动，8.06 秒观察窗口内零引擎错误。Linux 首轮默认 60 FPS／12 ms 预算下，1／4／16 个最坏规模 2V2 房间分别在 1.36／5.43／21.86 秒内完成，16 房间帧耗时最大 28.54 ms。Linux 隔离 ENet 回环的并行心跳场景（不含生产 DTLS／账号握手）最终重跑 16 房间用时 27.88 秒，470 条可靠控制消息全部收到，不可靠心跳回复收到 469/470，心跳延迟 p95 26.25 ms、最大心跳间隔 102.29 ms，无心跳误踢；24 项严格通过、无引擎错误。冷连接无负载阶段也会出现 ENet 自适应节流，不据此虚报全链路零丢包。DTLS 与新旧客户端分块兼容由独立 8 客户端大回放门禁验证，公网生产证书握手另行核实。这是该 2 核机器的实测批量吞吐，不能据此宣称无限并发或所有房间都能立即就绪。

Linux 首轮严格门禁没有通过：测试场景的 UI 自动加载项缺少字体；另一个刻意降低到 30 FPS／8 ms 的 16 房间场景触及测试固定 60 秒期限，只完成 13 房间。同步基准实测 CPU 合计 16.13 秒，24% 名义计算时间配额对应至少约 67.21 秒，原测试等待不足。测试等待现按实测基准和预算计算，仍有 180 秒绝对上限，完整结果哈希和 100 ms 单帧门禁未降低，超时仍失败；本地更新后 259 项严格通过。补齐字体及其实际导入资源后，初始基线在云端 259+24 项严格通过、无引擎错误；字体不加入无需 UI 的生产专服包。合入新主线后须对新模拟器重新验证。

旧算法对照中，三组 UID 修复样例有两组结算完全一致；另一组胜负一致但时长、余血和金币有小幅变化。UID 本来参与目标锁定及死亡去重，修复不能宣称所有旧错误数值完全不变。

独立门禁 `treasure_bug0910` 的教学推进断言在恢复 Git HEAD 原技能实现后仍失败；作为已有问题保留。Godot 4.7 的 DTLS 退出清理 mutex 错误可在没有项目代码的最小场景重现；同版本源码显示 CookieContextMbedTLS.clear() 未清除 inited 标志，stop 与析构重复清理，功能断言通过不等于严格零错误门禁通过；没有加入错误豁免。对应引擎源码：[CookieContext 清理](https://github.com/godotengine/godot/blob/5b4e0cb0f/modules/mbedtls/tls_context_mbedtls.cpp#L70)、[DTLS stop](https://github.com/godotengine/godot/blob/5b4e0cb0f/modules/mbedtls/dtls_server_mbedtls.cpp#L41)。

本地诊断 runner 初版误用 `config/custom_user_dir`，Godot 实际使用的字段为 `config/custom_user_dir_name`。旧门禁使用了自定义目录模式，但目录落在 `Application Support/Glory Beta 0.04`，并非报告声称的专用名称；该目录与默认生产的 `Godot/app_userdata/Glory Beta 0.04` 不同。保留旧原始结果，不倒改证据，关键门禁已在修正后以实际 OS 路径断言重跑：调度 255、RESULT 21、投递 122、编解码 111、播放恢复 145 项全部严格通过，零引擎错误；每次测试均为新目录，冻结业务源码未变。安卓独立包名隔离不受此问题影响。

## 生产与客户端交付要求

现场为 `e2-standard-2` 单实例、Godot `4.7.stable.official.5b4e0cb0f`，服务名 `glory-server.service`；实际运行项目目录为 `/home/nins17121/Glory/Beta 0.04`。构建信息指向 `f980e8559eb8cffe27f245fdfcb942f6f5e8da1c`，虽然标记 dirty=true，抽取的 127 个脚本／数据文件均与该 Git 提交完全一致。它与本地最新主分支有上游改动，旧手机 APK 不能作为严格同源码性能基线。

已有服务不支持可靠的在线排空接口。公开房间列表排除了进行中及匹配房间，列表为 0 不能证明无人。部署前需联合完整当前进程连接日志、房间快照及新鲜增量检查，候选包必须在独立 user 目录和隔离端口完成 Linux 启动验证。停服后整体替换项目目录，保留旧代码用于回滚，不能在线解压覆盖。快照不保存完整回放和计算任务，不能承诺任意时刻重启无损。

安卓测试包为 `com.glory.stabilityqa`，与用户原来的 `glory.beta001` 分开安装，原存档未覆盖。客户端特效和恢复修复需要安装包含补丁的新客户端，单更新服务器不会替换手机中的旧脚本。
