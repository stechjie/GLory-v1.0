那份清单的口径定义写得对，这里照用；但它的范围（通用事件格式、去重登记表、分区、战斗服务器落盘补发、报告版本管理……）
是按有数据团队的公司写的。这里是**缩成三批、先做了第一批**的记录。

配套：`database/025_analytics.sql`；`backend/app/analytics.py`（记）、`analytics_report.py`（算）；
后台 `backend/admin_web/` 的「数据」页；测试 `backend/tests/test_analytics.py`。

## 一、为什么先做这一批

「每天谁来过」「每时每刻多少人在线」**过去了就补不回来**：以前只有 `players.last_seen_at`（最后一次）和进程内存里的连接表。
这一批只改账号服务器 —— 不用出新包、不碰战斗服务器，跑一个 SQL + `update.sh` 就开始记。**越早上线，测试第一天的数据越完整。**

## 二、后台「数据」页上每个数怎么来的

全部按**马来西亚时间的自然日**。员工 / 测试 / 压测号（玩家页「运营数据」那一栏标）**全部不算**，排除了几个另外写明。

| 数 | 怎么算 | 已知误差 |
|---|---|---|
| 日活 | 那天游戏开着、连上过账号服务器的人，一人一天一次 | 只续期令牌、收到邮件不算（那些不走这条连接） |
| 近 7 天来过 | 到那天为止 7 天里来过的人，按人去重（不是日活相加） | 7 天里有没开始记的日子时标 *，偏小 |
| 新注册 | `players.created_at` 在那天的号（第一次打开游戏自动建号） | 卸载重装、换手机会再建一个号 → 新注册 ≥ 新来的人。**这一列 025 之前的日子也有**（注册时间一直在存） |
| 在线 / 最高在线 / 平均在线 | 每 15 秒数一次此刻连着账号服务器的真人（一个人几台设备算一个） | 手机切后台后最多 95 秒才算离开；「最高」是 15 秒采样里的最大值，不是毫秒级的瞬时峰值 |
| 人均在线时长 | 连着的时长，只结到最后一次心跳后 45 秒；精度约 1 分钟 | **电脑版最小化会算进去**（心跳不停），手机切后台不算 |
| 采集覆盖 | 那天真正采到了多少时间 | 不到 100% 的那段是重启或数据库写不进 —— **那段没有数，不是 0 人** |
| 打完的对局 | 那天结束、并且有人交了战报的局（013 的表，早就有） | 中途散掉、全员掉线没人交的局**不在里面**（第三批才有） |
| 留存 D1–D7、D14、D30 | 按注册日分组；D*n* = 注册后第 *n* 天**那一整天**来过（10-01 注册，D1 看 10-02，D7 看 10-08） | 只算 025 开始记之后注册的号；注销了的号不算（他的活跃记录已删） |
| 留存合计 | 各天回来的人**相加** / 各天人数**相加**，只算已经过完的格子 | 不是把百分比平均（清单 12.1 第 3 条的例子：合计 50%，不是 70%） |

**三种「没有数」都不是 0**：开始记录之前的日子写「没记」；缺采样的时段看覆盖率；还没到的留存格子写「未到」、今天的格子带「…」。

对局那张表还有：平均在第几回合结束、打满 21 回合的比例、6 个座位都是真人的比例、真人 / AI 座位数、
中途离开（真人座位到最后不在线）、每一回合（标了 Boss / PVP）结束了多少局。

两张表能导出 CSV（Excel 直接打开，中文不乱码）。

## 三、部署顺序

1. 🔴 **Supabase SQL Editor 跑 `database/025_analytics.sql`。** `update.sh` 不跑 SQL（排位那次踩过）。
   - 没跑时：游戏照常；后台「数据」页报「还没跑 025」；账号服务器日志每 10 分钟提醒一次「运营数据没在记」。
   - 它还重定义了 `erase_player()`（注销时多删这两张表）。
2. GitHub Desktop 推送 → 服务器 `update.sh`。**更新那一刻开始记。**
   - 更新 = 账号服务器重启：排队和匹配队列会清空（老规矩，高峰期别部署）。
3. 后台「玩家」页把**员工、QA、压测用的号**逐个标成内部账号。越早标越好（标了之后，他以前的日活、留存也一起排除；只有在线人数的旧采样按采样那一刻的标签算）。
4. **不用出新包，战斗服务器不动。**

验证：更新后等 1 分钟，自己开着游戏打开后台「数据」页 —— 「现在在线」≥ 1、「今天来过」≥ 1、在线曲线有点。
或者 SQL Editor：`select * from analytics_online_samples order by sampled_at desc limit 5;` 每 15 秒多一行。

## 四、存多少、删什么

- 在线采样每天 5,760 行（几百 KB），每人每天一行活跃记录。1,000 人测一个月也就几万行，**不设清理**。
- 注销：删这个人的每日活跃记录和内部账号标签（算个人数据）。代价是他以前的日活从统计里消失 —— 几个人的量，接受。

## 六、第二批：游戏上报的事件（2026-09-30）

配套：`database/026_client_events.sql`；`backend/app/client_events.py`（收，`POST /v1/events`）、
`analytics_report.client_report`（算）；客户端 `scripts/autoload/AnalyticsService.gd`；
门禁 `tools/analytics_check`、`backend/tests/test_client_events.py`。

### 记什么

| 事件 | 什么时候 | 后台用在哪 |
|---|---|---|
| `app_open` | 每次打开游戏（第一次安装后打开标 first） | 新包覆盖、机型 |
| `app_launch` | 第一个能点的界面出来时（StartupTrace 的 t3） | 启动到能点多久 |
| `tutorial_start` / `tutorial_resume` / `tutorial_step` / `tutorial_skip` | 教学开始、从断点接着来、走完一步（带停了多久，只算前台）、确认跳过 | 新手教学漏斗 |
| `match_start` | 对局开始（带模式：自定义 / 休闲 / 排位，真人和 AI 座位数） | 第一次体验、中途离开的分母 |
| `round_result` | 每回合服务器发下来的结算（每人报自己那份） | 回合难度 |
| `match_leave` | 对局打到一半自己退出 | 中途离开 |
| `replay_done` / `replay_failed` | 这一回合的战斗播完了 / 播放失败 | 「服务器算完了、玩家没看到」 |
| `reconnect` / `room_action_failed` | 重连成没成、进房建房失败的原因 | 技术问题 |
| `client_error` | 脚本报错（同一种一次启动只报第一次） | 报错排行 |
| `perf` | 每 5 分钟：帧率、卡顿次数、内存 | 帧率 |

**不记**：聊天内容、令牌、服务器地址、设备序列号。报错文字里的 IP、电脑路径、长串、邮箱在手机上就抹掉了。
记了机型和显卡名（看低端机表现用）。

### 可信度

全是**客户端说的**。回合结果的数是战斗服务器算的、经客户端转来，改过的客户端能乱报 ——
所以只做统计，**不拿它发奖励、判排位、处罚**。服务器按事件编号去重，同一条重发只记一次；
发生时刻按「发送那一刻」对齐到服务器的钟，改手机时间改不了日期。

### 后台「数据」页新加的几块

新包覆盖（每天报过事件的人 / 日活、按版本号）、新手教学漏斗（每一步到达 / 完成 / 跳过 / 停在这步 / 耗时）、
新玩家第一次体验（注册 → 教学 → 第一局 → 打完一局 → 第二天回来）、回合难度（每回合到达的队伍、输了、法阵归零，可按模式看）、
技术问题（播放失败、重连、中途离开、启动耗时、帧率、报错排行）。

⚠️ **只有装了新包的人才会报。** 新包刚发的几天覆盖率低，那时的比例只代表已经更新的玩家 —— 先看「新包覆盖」再看别的。

### 部署顺序

1. 🔴 Supabase SQL Editor 跑 `database/026_client_events.sql`（025 之后）。没跑时 `/v1/events` 回 503，手机把事件留着以后再发，游戏不受影响。
2. 推送 → 服务器 `update.sh`（账号服务器有了 `/v1/events` 和后台新的几块）。
3. **出新包**。先后顺序出错也不丢数：新包先到、服务器还没更新时，手机收到 404 会攒着（最多 500 条、7 天），等服务器更新了再发。
4. 战斗服务器**不用动**，协议号不变。
5. 隐私说明里加一句：游戏会上报玩法进度、报错和帧率用于改进游戏（不含聊天内容）。这条需要你或负责合规的人定措辞。

验证：新包开一次游戏，15 秒后 SQL Editor
`select name, occurred_at, props from analytics_client_events order by received_at desc limit 20;` 能看到 `app_open`、`app_launch`。

### 已知限制

- 手机被系统杀掉前最后不到 30 秒的记录可能丢（切后台那一刻会先存盘）。
- 本机在 `--quit-after` 的空转里帧数很快跑满，门禁里别拿它等 15 秒的发送；端到端要按墙钟等（2026-09-30 本机真游戏 + 假登录验过：上一次没发出去的记录下次打开会补发）。
- 教学「停在这步」包括还没玩完的人，测试刚开始那几天会偏高。

### 「设置等级」为什么出现在清单里

清单第 9.1 节：写清单的人收到的需求里有一条 GM 指令叫「设置等级」，但**游戏里没有账号等级这个东西**，
所以它列了五种可能的意思（排位分、信誉分、局内采集等级、农田等级、棋子星级），默认先做「排位分 / 信誉分纠错」和「只在测试服用的局内指令」。
这两样都不是十月测试采数据的前提，这一批没做；谁提的「设置等级」、想改的是哪一种，问清楚再做。
