## 零、先纠正一条判断，并说明它是怎么被推翻的

### 「不做聊天」—— 作废

`docs/交友系统设计.md` 第七节把聊天列为非目标，理由是
「私聊要消息存储 + 内容审核 + 举报证据链，比交友系统大一个量级」。

**那句话只对私聊成立，对局内/房间聊天不成立。** 局内聊天可以做到不落库、
不审核（只发预设短语 ID）、不碰任何账号字段 —— 它跟交友系统不是一个量级，
是小一个量级。当初把两者捆在一起是想岔了，跟当初把「在线状态」记成
「被 `C14` 卡住」是同一类错误。

### 「第一版不上 WebSocket」—— 提出后当场作废，记录在此

设计过程中先得出过「第一版用轮询、不上 WS」的结论，理由是：② 今天是无状态的、
客户端一条 WS 都没有、移动端长连接不可靠、今天 0 个已发布客户端。
**那个结论的前提是「只做好友私聊」。**

产品范围随后确定为**四条频道**（世界 / 私聊 / 房间 / 局内），前提变了，结论跟着变：

> **世界频道的全部价值是「热闹」。** 轮询间隔即延迟，3 秒一来一回会让对话
> 节奏断掉，然后没人愿意在里面说话，频道就死了。这是**体验问题，不是性能问题**，
> 与在线人数无关 —— 不能用「今天没玩家」来推迟它。

四条频道各自轮询还会让客户端出现四个独立定时器。一条 WS 承载所有频道
是标准做法，**在这个范围下 WS 反而是更简单的那个**。

保留这段记录是因为：下一个人看到「聊天用了 WebSocket」时，
很容易以为它是默认选择。它不是 —— 它是被世界频道**逼**出来的，
如果哪天世界频道被砍掉，这个决定应该重新评估。

## 一、四条频道，分别走哪条线

这是本文最关键的一张表。**它们不是一个系统，是四个**，一致性要求、
存储成本、审核义务完全不同：

| 频道 | 传输 | 落库 | 审核强度 | 说明 |
|---|---|---|---|---|
| **世界频道** | ② WebSocket | 7 天（仅为举报） | 🔴 最严 | 主界面那个「聊天」按钮 |
| **好友私聊** | ② WebSocket（同一条连接） | 30 天 / 每会话 100 条 | 🟡 中 | 点对点 |
| **房间聊天**（大厅等人） | 🔴 **③ ENet** | **不落库** | 🟡 中 | `Team3v3Lobby` 左下已预留位置 |
| **局内聊天**（对战中） | 🔴 **③ ENet** | **不落库** | 🟡 中 | 右下角按钮，待做 |

### 🔴 房间/局内聊天为什么必须走 ENet，不能走 ②

看起来 ② 已经知道谁在哪个房间了 —— `player_presence.room_id`，心跳自报的。
拿它做房间频道路由只要一行代码。

**这会直接踩爆 `docs/交友系统设计.md` 第二节那条最硬的红线**：

> 自报只能用于「说谎没有收益」的数据。

谎报房间号进别人的房间频道 = **有收益**。那是一个开箱即用的定向骚扰入口：
随便填一个房间号，就能对着六个陌生人说话，且不需要真的进房间。
这与「谎报房间号让好友进错房间」有本质区别 —— 后者没收益，前者有。

**③ 不存在这个问题**：座位是它分配的（`RoomService` 的 `seat_tokens`），
谁在房间里它自己知道，不需要任何人自报。

所以房间/局内聊天走 ENet 是**唯一既不需要新基础设施、又不破红线**的路。
顺带的好处：**不需要 ②↔③ 通道，座位票仍然不是本系统的前置**
（`docs/账号系统RFC.md` 9.2 仍然未拍板，本系统不推动它，也不被它挡住）。

### 「谁在说话」这件事已经免费有了

`RoomService.public_seat_identity()`（`scripts/multiplayer/RoomService.gd:64`）
已经在房间里同步 `friend_code` / `player_name` / `avatar`。
气泡挂在座位上即可，**不用新增任何字段**。

⚠️ 顺带澄清一条容易误读的红线：RFC 🔴 第 3 条「`NetProtocol` 不加账号身份字段」
指的是 **JWT 那类凭证**，不是公开资料。昵称头像今天已经在 ENet 上传了，
两者不冲突。**判据是「泄漏了会不会丢号」** —— 昵称不会，JWT 会。

## 二、传输层：② 的 WebSocket

### 与现状的差别

今天 `AccountManager._request` 是「问一句、答一句、挂断」，每个请求独立，
**② 完全无状态**。WS 打破这一点：服务器必须记住「哪条连接属于哪个玩家」。

| | 现状（HTTP） | 加了 WS 之后 |
|---|---|---|
| 新消息怎么到 | 客户端定时问 | 服务器主动推 |
| 延迟 | = 轮询间隔 | 几十毫秒 |
| ② 有没有状态 | 无 | **有：连接表在进程内存里** |
| 加一个 worker | 直接加 | 🔴 **消息会丢** |

### 🔴 第一版必须钉死单进程单实例

连接表在进程内存里。开两个 uvicorn worker，A 进程上的玩家发消息，
B 进程上的玩家**收不到** —— 不报错，就是收不到。

这与 `backend/app/rate_limit.py` 注释里那个坑是同一个根因（进程内状态），
但后果完全不在一个量级：

| | 多进程后的表现 |
|---|---|
| `rate_limit` | 额度翻倍。软失败，能忍 |
| WS 连接表 | **消息投递不到**。硬失败，且只在扩容那天才暴露 |

**要写进部署文档，并且在代码里加断言**：启动时检测到 workers > 1 直接拒绝启动。
「靠人记得别加 worker」不是方案 —— 这类错误的代价是静默的。

扩容前的正确做法是 Redis pub/sub 或粘性会话。**那是逃生口，不是第一版内容**
（同交友文档第四节第 4 条对 presence 缓存的处理）。

### 客户端：一个新的连接状态机

要写重连退避、心跳、token 过期后重连、Android 切后台被杀后恢复。

`scripts/multiplayer/ReconnectService.gd` 与 `ReconnectBackoff.gd` 已经为 ENet
写过一遍这类逻辑，**思路可以抄，代码不能共用**（一个 ENet 一个 WebSocketPeer）。
抄的时候要连同它们踩过的坑一起抄，别只抄结构。

### 部署

Caddy 反代 WebSocket 是原生支持的，`deploy/Caddyfile` 需要确认没有会掐长连接的
超时配置。这是上线前必须实测的一条 —— 本机跑通不代表过了反代还通。

## 三、数据库

按 `database/README.md` 的规矩，**编号只增不改**。本系统占 `007_chat.sql`。

### 私聊会话：canonical 对，理由同 `player_friendships`

```sql
create table chat_conversations (
  low_id          uuid not null references players(player_id) on delete cascade,
  high_id         uuid not null references players(player_id) on delete cascade,
  last_message_id bigint,
  updated_at      timestamptz not null default now(),
  primary key (low_id, high_id),
  constraint ordered check (low_id < high_id)
);
```

**为什么不用「每人一行」**：那样能表示出「A 的会话里有 5 条、B 的会话里有 3 条」
这个坏状态。写漏不报错，表现是「他看到的和我看到的不一样」。
canonical 对让这个坏状态**不可表示** —— 与交友文档第三节同一条理由。

### 消息

```sql
create table chat_messages (
  message_id  bigserial primary key,
  low_id      uuid not null,
  high_id     uuid not null,
  sender_id   uuid not null references players(player_id) on delete cascade,
  body        text not null,
  created_at  timestamptz not null default now(),
  deleted_at  timestamptz,
  constraint sender_is_party check (sender_id in (low_id, high_id))
);
create index chat_messages_by_conv on chat_messages (low_id, high_id, message_id desc);
```

#### 🔴 游标必须是 `bigserial`，不能用时间戳

增量拉取（「给我 message_id > X 的」）的正确性**全押在游标单调上**。
时间戳会撞（同毫秒两条）、会因为时钟回拨倒退。

这一条事后改是 🔴：所有客户端的本地游标全部作废，
而症状是「偶尔丢一条消息」或「偶尔重复一条」，极难复现、极难定位。
**一次做对，没有第二次机会。**

#### 🔴 `deleted_at` 软删，不是真删

举报单条消息没有用，必须带前后上下文。玩家点「删除聊天记录」时服务端
**不能真删** —— 否则当事人可以自己销毁证据。

代价是一条必须写下来的隐私义务：消息保留 30 天，举报后延长保留。
这句话要出现在玩家可见的地方。

### 已读状态：存游标，不存计数器

```sql
create table chat_read_state (
  player_id    uuid not null references players(player_id) on delete cascade,
  low_id       uuid not null,
  high_id      uuid not null,
  last_read_id bigint not null default 0,
  primary key (player_id, low_id, high_id)
);
```

#### 🔴 未读 = `max(message_id) > last_read_id`，绝不存 `unread_count`

可变计数器在任何一次并发、重发、乱序下都会漂，**而且不报错** ——
只表现为「红点消不掉」或「有新消息不亮」。

这与 `player_presence` **没有「离线」字段**是同一条教训：
**不存会说谎的状态，存能推出真相的事实。**

#### 更新必须是单调的

```sql
update chat_read_state set last_read_id = greatest(last_read_id, $1) ...
```

`greatest()` 不能省。同一账号两台设备同时在线时，设备 B 的一次滞后写会把
游标从 100 退回 50，表现为「已经看过的消息又变成未读」。
写成单调之后，**两台设备读同一个服务端游标，天然一致** ——
「在 A 设备看过了，换到 B 设备也是看过的状态」自动成立，不需要额外机制。

### 世界频道：**不进上面这套表**

世界频道是广播，塞进 `chat_messages` 会让那张表变成一张只增的巨表，
而且 99% 的行永远不会被任何人查第二次。

```sql
create table world_messages (
  message_id bigserial primary key,
  sender_id  uuid not null references players(player_id) on delete cascade,
  body       text not null,
  created_at timestamptz not null default now()
);
create index world_messages_recent on world_messages (message_id desc);
```

- **显示**走 ② 进程内的环形缓冲（最近 50 条），不查库
- **落库只为举报**，保留 7 天，定期清理
- 新玩家进频道时下发那 50 条打底 —— **人少时频道是空的，玩家会以为坏了**

## 四、内容审核

这是整个系统真正的关键路径，**不是 WebSocket**。

### `text_guard` 的三层，能复用哪些

`backend/app/text_guard.py` 第一句话写着「这不是敏感词系统，不要这么叫它」。
那句话是对的，逐层拆：

| 层 | 用在聊天上 | 理由 |
|---|---|---|
| ① 结构管控（零宽 / Zalgo / bidi / 空白 / 长度） | ✅ **直接复用，且必须用** | 与内容无关，纯防显示破坏。聊天里同样有人会用 Zalgo 糊屏幕 |
| ② 引流检测（微信 / QQ / 长数字） | ⚠️ **只对世界频道用** | 见下 |
| ③ 词表 | ❌ **不能当唯一防线** | 昵称是低频、一人一个、可人工审；聊天是高频海量。同一份词表会同时漏（谐音拆字随便过）和误杀（正常对话被拦，玩家不知道为什么） |

### ✅ 已定：私聊**不拦**引流，世界频道**拦**

这与签名栏的策略**相反**，是刻意的 —— 场景不同：

| | 性质 | 引流的危害 |
|---|---|---|
| 签名 / 世界频道 | **广播**，一个人发给所有看到的人 | 代练与外挂广告的主战场，必须拦 |
| 私聊 | **点对点**，对方已经同意加好友 | 交换联系方式是正常社交行为，硬拦很烦人 |

私聊的引流内容**记录但不拦，靠举报后处理**。这是已确认的产品决定。

### 外部审核：选型与封装

**选阿里云内容安全（文本审核）**，理由：

1. ② 是 Python，阿里云有官方 Python SDK，也提供纯 HTTP API —— **不依赖任何
   Godot 侧支持**，审核全在 ② 完成
2. 按调用量计费、有免费额度，起步成本接近 0；今天 0 玩家时基本不花钱
3. 中文游戏黑话（谐音、拆字、变体、插符号）是它的主场，这正是词表做不到的部分
4. 文档与案例最多，出问题时能搜到东西

⚠️ **价格与具体产品名会变，接入前必须自己去核实一次**，本文不承诺这些。

#### 🔴 但比选哪家更重要的是：封装成 provider 接口

```
app/moderation/__init__.py     # check(text, scene) -> Verdict
app/moderation/local.py        # text_guard 结构层 + 词表（永远在线，第一道）
app/moderation/aliyun.py       # 外部服务（可插拔，第二道）
```

三个理由，每个都会真的发生：

- **换厂商**：效果或价格不满意时，只改一个模块，不改调用点
- **降级**：外部服务超时/欠费/故障时，聊天不能整个瘫掉
- **测试**：门禁不能真打外部 API，必须能注入假 provider

#### 🔴 外部服务挂了怎么办 —— 按频道分级，不能一刀切

| 频道 | 策略 | 理由 |
|---|---|---|
| 世界频道 | **fail-closed**（拒发，提示稍后重试） | 一条违规全服可见 + 会被截图传出去。宁可发不出去 |
| 私聊 / 房间 / 局内 | **fail-open**（放行，标记待审） | 影响面小到一个人或六个人，且聊天完全不能用比漏一条严重得多 |

**这个分级必须显式写在代码里**，不能是「默认行为恰好如此」——
默认行为会在重构时悄悄翻转。

#### 同步调用，第一版不做异步

发消息时等审核结果返回（约 100–300ms）。代价是发消息的 P99 取决于外部服务，
收益是不存在「违规内容先送达再撤回」这个状态。

聊天不是每秒几百条的东西，这点延迟玩家感知不到。
**量真上来了再改异步，那时候再说。**

### 频率控制

| 频道 | 限制 | 理由 |
|---|---|---|
| 世界频道 | ✅ **CD 8 秒**（已定） | 广告刷屏是必然，不是可能 |
| 世界频道 | ✅ **等级门槛**（已定，见下） | 挡批量小号 |
| 私聊 | 不设 CD，每分钟上限 30 条 | CD 会让正常对话很难受 |
| 房间 / 局内 | 每座位轻 CD（2 秒） | 由 ③ 判，防刷屏 |

#### 🔴 世界频道的门槛判在数据库上，不能用 `rate_limit.py`

`rate_limit.py` 是进程内滑动窗口，**重启即清零**，它自己的注释写着这一点。
用它做 8 秒 CD 是可以的（重启清零无所谓），但用它做**每日发言配额**不行。
这与「改名冷却判在数据库」「好友请求配额判在数据库」是同一条教训。

更硬的一条：🔴 **按 `player_id` 限流，不能按 IP**。理由同交友文档第四节第 2 条 ——
手机运营商 NAT 下同一出口 IP 是成片的正常玩家。

#### 等级门槛：现在还没有等级制度，怎么预留

✅ 已定：用等级门槛，但等级制度尚不存在。

**预留不等于什么都不做。** 直接留一个永远为真的开关等于没留 ——
它会在等级上线那天被发现根本没接过线。做法：

1. 代码里就有一个 `can_speak_in_world(player) -> bool` 的判据函数，
   **今天就调用它**，走通整条路径
2. ✅ 已定：**今天的实现直接返回 `True`，不挡任何人。**
   曾考虑用「账号创建满 24 小时」当临时判据，**否决了** —— 今天 0 玩家、
   没有广告号，那条限制唯一的实际效果是挡住自己人的测试账号。
   真正需要时再换实现（现成的判据是 `players.created_at`，广告号的共同特征
   正是「刚建的」）。
3. 等级制度上线、或真的出现广告号后，只改这个函数体，调用点一处不动

**函数与调用点今天就存在**，所以这条路径是活的、被测过的，
不是一个等着被想起来的 TODO —— 需要它的那天只是换一个函数体，
而不是在一堆调用点里找该往哪插。

## 五、单点登录（顶号）

✅ 已定：要做。

### 它是被聊天逼出来的，但它属于账号层

聊天是第一个让「同一账号两台设备」显形的功能，但顶号本身是账号系统的能力，
实现应该落在 `AccountManager` / `routes/auth.py`，**不要写进聊天模块**。

### 🔴 JWT 是无状态的 —— 顶号有一个不可消除的时间窗

`backend/app/jwt_verify.py` 的文件头写着：令牌 `exp = iat + 3600`，
**ES256 非对称验签，后端不需要任何密钥**。这个设计很好，但它的直接后果是：

> **签发出去的 access_token，在过期前无法被撤销。**

撤销 Supabase 的 refresh_token 只能阻止旧设备**续期**，
它手上那个 access_token 在剩余寿命内（最长 1 小时）**仍然验得过**。

要做到即时撤销，只有两条路，都有代价：

| 路 | 代价 |
|---|---|
| 每个请求查一次「当前活跃会话」 | 每个接口多一次 DB 往返。为了顶号给所有接口加成本，不划算 |
| **只对长连接即时生效** | 顶号在聊天上立刻可见，HTTP 接口有 ≤1 小时残留 |

**选第二条。** 具体形状：

1. 登录时 ② 生成 `device_session_id`，记为该账号的**当前活跃设备**
2. 客户端建 WS 时带上它，② 校验
3. 新设备登录 → 旧设备的 WS 被**服务端主动断开**，下发 `kicked` 事件
4. 客户端收到 `kicked` → 🔴 **弹一个需要手动确认的对话框**，
   玩家点「确定」之后才回登录界面

#### 🔴 绝不能自动跳回登录界面

✅ 已定。玩家正在玩，画面突然自己跳回登录页，**在他眼里就是崩溃或掉线**，
不是「我被顶号了」—— 他会去截图报 bug，而不是去想「谁登了我的号」。

必须满足三条：

- **必须手动点确认才走**，不做倒计时自动跳转
- 提示语要说清楚是**什么事**：「你的账号在另一台设备上登录了」，
  而不是「连接已断开」「登录已失效」这类什么都没说的话
- **对局中被顶号不要立刻弹**（弹窗会直接打断操作），先在聊天入口挂一个提示，
  回到主界面时再弹。战斗连接本来就不受这套机制影响，见下

因为客户端最终会被送回登录界面，那个 ≤1 小时的 HTTP 残留窗口在正常路径上
**不会被用到**（只有手动构造请求的人能用）。**这个边界要写下来**，
不能让下一个人以为顶号是即时且彻底的。

⚠️ **顶号只作用于 ①↔② 这条链路，不碰 ③ 的座位。** `session_token` 仍然是
「这条连接拥有哪个座位」，与账号是两回事（RFC 第八节的两层模型不变）。
被顶号的设备如果正在对局中，它的战斗连接**不会**被这套机制断掉 ——
那属于座位票的范畴，仍然未拍板。

### 🟡 今天它没有触发条件，但架子现在就要留

匿名账号的凭证是本机 `user://glory_account.json` 里那个 refresh_token，
**只有一份、只在这台设备**（交友文档第一节第 ② 条讲得很清楚）。
所以今天事实上很难出现「两台设备同一账号」。

**真正的触发条件是绑定登录（Google / Apple OAuth）。**
顶号的完整实现可以排在 OAuth 之后，但 `device_session_id` 这个字段
**现在就要加进 WS 握手**：事后往一个已经上线的握手协议里插字段，
要处理新旧客户端并存，比现在多写三行贵得多。

#### 🔴 右下角的真正约束：两套锚打架，而它只在矮窗口下暴露

第一版把聊天贴着屏幕右缘、按钮锚在 `offset_top = -340`（想着避开占 -200 ~ -70
的商店刷新按钮）。**在参考画布 941 高下毫无问题，出图也看不出任何毛病。**

1280×720 下它盖住了萝卜计数器，消息条压在萝卜按钮旁边。原因是两边用的锚不同：

| | 锚 | 占位 |
|---|---|---|
| `side_col`（佣兵 / 队伍佣兵 / 萝卜 / 萝卜计数） | **屏幕顶部**往下 | 固定排到 y=518 |
| 聊天入口 | **屏幕底部**往上 | 随窗口高度浮动 |

**窗口越矮，两者越近。** 941 高时相隔 80 多像素，720 高时直接叠上。

⚠️ 这类 bug 有一个共同特征：**在开发者的窗口尺寸下永远不出现**。
所以调这几个数时必须用矮窗口出图，不能用参考画布的高度 ——
`tools/chat_ui_capture.tscn` 的备战那一段因此写死 1280×720。

最终位置（`PrepUI` 的 `CHAT_RIGHT` / `CHAT_BTN_TOP`）：

- **横向**右边界收到 -148，让开那一列（`STATS_BTN_SIZE.x` 140 + 贴边 8）
- **纵向**按钮压到 -200 ~ -68，与商店刷新按钮同一水平带 —— 那是右下角唯一
  本来就安全的高度（518 之下）。横向已经错开（刷新在 -105 ~ 25），所以并不会
  真的叠上刷新
- 短语面板**往上弹**，与消息条同列同宽。不往左弹：那会横穿到棋盘中央，
  往上只压掉自己那几条消息，代价最小

#### z_index：商店开着时聊天就该点不到

聊天按钮 z=20，商店弹窗 40、卖出区 50。**这是有意的** ——
那时玩家在买卖，一个压在商店上面的聊天按钮只会造成误触。

#### 三条交互约束（都已实现）

- 🔴 **备战阶段不能挡棋盘。** 这是玩家操作最密集的阶段（拖棋子、买卖）。
  入口是折叠的：平时只有一颗按钮，短语面板点开才有，发完自动收起。
  **不上遮罩** —— 萝卜营地那种全屏 dimmer 在这里是错的，
  玩家要能一边看着棋盘一边发短语。
- 🔴 **消息条 `mouse_filter` 必须是 `IGNORE`。** 它压在棋盘右下方的空域上，
  而且是**自动出现**的。少了这一行，一条飘过的消息会把它盖住的那格棋盘
  变成点不动的 —— 玩家只会觉得"卡了"，且只在有人正好说话时发生，极难复现。
  有门禁钉着（`tools/chat_check.tscn`）。
- 🟡 **不用弹窗、不用音效。** 备战期被打断是玩家最容易生气的事。

#### 一处与原设计不同：**没有未读红点**

原设计写的是"按钮 + 未读小红点，点开才看得到消息"。实现时改成
**收到的消息常驻显示在按钮上方并自动淡出**（3 条，停 6 秒后淡出 1 秒）。

理由：局内的聊天是"瞥一眼"，不是"读列表"。要玩家在摆棋的时候先看见红点、
再点开面板、再读一句"稳住"，那句话早就没有意义了。消息直接飘出来之后，
未读红点这个概念本身就不需要了。

⚠️ 每条消息**各自管自己的寿命**（tween 挂在那条 Label 上），不能共用一个 Timer ——
共用的话后到的消息会重置前一条的计时，表现为"一直有人说话时最早那条永远不消失"。

### 批次 A 为什么便宜到不成比例

发的不是文本，是**短语 ID**：`{seat: int, phrase_id: int}`。

- 内容审核归零 —— 短语表自己写，审一次管终身
- 不碰 RFC 🔴 第 3 条 —— 载荷里只有座位号和一个 int
- 不需要 ②↔③ 通道 —— 转发全在 ③ 内存里
- 载荷上界天然存在 —— 符合 `NetProtocol.gd:12` 那条「任何容器必须常数级步数被拒」
- 「谁说的」免费 —— `public_seat_identity` 已经在同步昵称

**预设表情与快捷短语是同一件事**（发 ID，不发内容），一起做。

⚠️ **快捷短语不是自由文本的替代品，是补充。** 做了 D 之后 A 也不作废 ——
对战中打字太慢，手机上尤其。LoL 有信号轮盘也有聊天框，两个都要。

## 八、容易写错的地方

### 🔴 0. 加 `@rpc` 方法必须顶协议号，并重新部署战斗服务器

**2026-09-10 实测踩过，放在第一条。**

批次 A 加了两个 `@rpc` 方法（`_rpc_team_chat_submit`、`_rpc_team_chat`）却没顶
`NETWORK_PROTOCOL_VERSION`。客户端连线上服务器时直接刷：

```
process_simplify_path: The rpc node checksum failed.
Make sure to have the same methods on both nodes. Node path: NetworkService
```

Godot 会比对两端 `NetworkService` 的方法表，对不上就拒绝为这个节点建立路径缓存。

**但这条错误本身还不是最要命的。** 它背后的事实是：两端方法表已经不一致，
于是 `v17` 注释里那件事同时成立 —— **方法编号错位，RPC 可能被派发到别的方法上**。

⚠️ 方法表不一致时，联机行为是**未定义的**。
不要试图靠观察症状去判断「是不是还能用」—— 那是在拿静默错算结果赌运气。

`NetworkConfig.gd` 的 `v17` 注释早就写过同一条（「加 `@rpc` 方法会平移整套 RPC 的
wire ID」），`v18` 那一格更是**补顶的**。这是第三次踩，所以这次加了断言
（`tools/chat_check.gd` 的 `PINNED_RPC_COUNT`）——踩过三次的东西该由断言挡着，
不该靠记性。

**两步都要做，缺一不可：**

1. 顶 `NETWORK_PROTOCOL_VERSION`（21 → 22 ✅），并同步
   `carrot_online_check.gd` 的 `PINNED_PROTOCOL`、
   `chat_check.gd` 的 `PINNED_RPC_COUNT` / `PINNED_RPC_PROTOCOL`
2. **重新打包部署战斗服务器**：`make_server_zip.ps1`（会从源码实读协议号，
   产出 `glory_server_p22.zip`，并做冷启动冒烟测试），然后上传部署

⚠️ **顶号本身不会消除那个 checksum 错误。** 它只让版本语义正确、让旧客户端在握手时
拿到一个可读的 `protocol_mismatch`。**真正的修复只有重新部署服务器。**

⚠️ 第 2 步机器验不了。唯一的证据是服务器启动日志里的 `server started protocol=22`
（`journalctl -u glory-server`）—— 注意是 **started**（过去式），不是 starting。

### 🔴 1. 房间频道用 ② 的自报 `room_id` 路由

见第一节。**这条被突破时不会报错**，只会凭空造出一个定向骚扰入口。
房间成员关系只有 ③ 知道，这是它必须走 ENet 的全部理由。

### 🔴 2. 未读用计数器

见第三节。症状是「红点消不掉」，而代码看起来是写了的。

### 🔴 3. 游标用时间戳

见第三节。症状是「偶尔丢一条 / 重复一条」，几乎不可能复现。

### 🔴 4. WS 上了之后有人加 worker

见第二节。要有启动断言，不能靠人记得。

### 🔴 5. 房间/局内自由文本不落库 → **无法举报**

这是批次 D 一个必须正面回答的问题，**很容易漏掉**。

不落库是对的（那是它便宜的全部原因），所以举报材料只能由**举报者的客户端**
上传本地保留的最近 N 条上下文 —— LoL 的做法也是这个。

**代价必须写下来：举报材料由举报方提供，原理上可伪造。** 只能靠人工判断，
以及「伪造聊天记录去举报」本身可罚。想避开这一点只有让 ③ 落库，
那需要 ②↔③ 通道 —— 不值得为举报去开那条通道。

### 🔴 6. 「在线可见性」与「消息可达性」被混为一谈

✅ 已定：**隐身的人照样收私聊。**

presence 的隐身开关管的是「别人能不能看到我在线」，
与「消息能不能送到我这里」是两个概念。混在一起会造出
「我隐身了所以朋友的消息我收不到」这种没有人能理解的行为。

写代码时的具体表现：投递逻辑**绝对不能查 `presence_visibility`**。

### 🟡 7. 被拉黑者发消息：✅ 已定**静默丢弃**

对发送方显示为「已发送」，实际不投递。理由同交友文档第六节第 6 条
「删好友不通知对方」—— 告诉对方「你被拉黑了」等于制造对抗，而对方也做不了什么。

⚠️ 静默丢弃的消息**仍然落库**（举报证据），只是不投递、不进对方的未读。

### 🟡 8. 客户端本地缓存

第一版**只做内存缓存，不落 `user://`**。落盘就要处理「本地缓存与服务端游标
不一致」，而那个不一致只在换设备、清数据、消息被删这些边角场景出现 ——
最难测、最容易错。

代价是每次开面板都要拉一次最近 N 条。可以接受。

### 🟡 9. 世界频道人少时是空的

0 人在线 = 空频道 = 玩家以为坏了。用那 50 条环形缓冲打底。
**这不是可选的润色，是必须的** —— 空白界面在玩家眼里就是 bug。

### 🟢 10. 举报与拉黑在 UI 上要分开

同交友文档第六节第 7 条。举报是给我们看的、异步的；拉黑是即时生效的。

### 🟢 11. 消息长度上限

世界频道 100 字，私聊 / 房间 200 字。响应体和 UI 布局都需要一个上界，
理由同「好友数上限 100」。

## 九、语音：单独说，因为它比整个文字聊天加起来还贵

✅ 产品上要做，但**不进本轮排期**，理由如下。

### 自己做：在 Godot 里没有便宜的路

需要麦克风权限、实时 Opus 编解码、抖动缓冲、**回声消除（AEC）**、噪声抑制。
后两项是关键 —— 移动端外放不做 AEC 会直接啸叫。这些在 Unity / UE 有成熟轮子，
Godot 基本要自己啃或写 GDExtension。是几个月的工程，且大概率做不好。

### 接第三方：正常选择，但有一个真实的未知

腾讯云 GME、声网 Agora、ZEGO 都是成熟方案，**但它们官方支持 Unity / UE / 原生，
Godot 通常不在列表里**。安卓上要通过 Godot Android Plugin 走 JNI 自己封一层。
**能不能通、要多久，今天没有人知道。**

外加：按分钟计费的流量成本，以及语音内容审核（实时转文字）是另一项收费服务。

### 🔴 建议：先做一天的 timebox 技术验证

照 `docs/交友系统设计.md` 第八节对 OAuth 的处理 —— 只验一件事：

> **能不能在 Godot 安卓包里跑通一次第三方语音 SDK 的进出房间。**

把未知变成已知，比把它排进计划表有用，也比做到一半发现卡住便宜得多。
验证通过之前，语音在计划表上只能是一个问号，不能是一个日期。

- **不做已读回执。** ✅ 已定。它需要的实时性正好是这套架子最贵的那一档，
  而产品价值很低。
- **不做玩家上传图片。** 预设表情 🟢 很便宜（发 ID），玩家上传 🔴 很贵：
  对象存储 + CDN + 流量费 + **图片审核必须接第三方**（比文字更难更贵）
  + 举报要留原图。**两者差 100 倍，别因为都叫「图片」就当成一件事。**
  这是内容风险最高的功能，没有之一。
- **不做自定义多人群组。** 房间聊天已经覆盖「一起玩的人一起说话」这个需求，
  而自定义群组会把关系模型从 pair 变成 N 方，数据模型完全不同。
- **不做聊天记录搜索、不做消息撤回、不做消息转发。**
- **不缓存、不上 Redis。** 同交友文档第四节第 4 条 —— 那是真上量后的逃生口。
- **不碰 ②↔③ 通道。** 本系统四条频道全部避开了它。
