## 一、Bug：四星合成音被错误替换

### 现象
用户反馈：**「黑龙四星合成音效被错误替换，战斗、特效里的音效只用于战斗场景中的技能释放」**，
并要求检查其他四星是否有同类问题。

### 根因
`SfxService.star4_cue_for()` 被**两个不同场景**共用：

| 场景 | 调用点 | 应当播的音 |
|---|---|---|
| 备战页**合成 / 升星** | `PrepUI.gd:1633`、`PrepBoardController.gd:314` | **合成音**（9.18 之前的原素材） |
| 战斗里**自身棋子释放技能** | `BattleVfx.gd:387`、`:879`（母灵处决） | **技能音**（9.18 用户新给的素材） |

9.18 把新素材直接登记进 `STAR4_CUES`（唯一的表），于是**合成时刻也播了技能音**。

### 影响范围（逐个核对）

| 单位 | 合成音是否被顶掉 | 说明 |
|---|---|---|
| `god_king` 神王 | **是** | 原合成音 217476B → 被 17180B 技能素材覆盖 |
| `undead_mother` 母灵 | **是** | 原 33062B → 被 17180B 覆盖 |
| `dark_dragon` 黑龙 | **是** | 原 81128B → 被 33062B 覆盖 |
| `god_archangel` 大天使 | **是（9.19 补判）** | 9.17 时**复用 `god` 文件**做合成音；9.18 拆出后合成改指向新的 `star4_archangel.mp3`（实为技能音） |
| `dark_doom` 末日守卫 | **是（9.19 补判）** | 9.17 时**复用 `dark` 文件**做合成音；9.18 拆出后合成改指向新的 `star4_doom.mp3`（实为技能音） |
| `human_king` 人王 | 否 | 文件从未被动过（48945B），且 9.18 源目录**没有**「人王技能释放」素材 |

> **关键更正（用户二次反馈）**：最初判断「大天使 / 末日守卫不受影响」是错的。
> 核对源目录 `音乐\0918\` 可见，9.18 那批素材**全部是技能音**，一个合成音都没有：
> ```
> 战斗、特效\四星大天使技能释放.mp3    17180
> 战斗、特效\四星末日守卫技能释放.mp3  17180
> 战斗、特效\四星母灵技能释放.mp3      17180
> 战斗、特效\四星神王技能释放.mp3      17180
> 战斗、特效\四星黑龙技能释放.mp3      33062
> ```
> 因此「9.18 之后才拆出、本就只有一份素材」不成立——那一份素材是**技能音**，
> 合成音应回到 9.17 时的共享口径（大天使用 god、末日用 dark）。

### 修法：两条路径分离

1. **音频文件**
   - 9.18 新素材另存为 `star4_god_skill.mp3` / `star4_undead_mother_skill.mp3` / `star4_dark_skill.mp3`；
   - 从 `C:\Users\WINDOWS\Desktop\9.18_替换前原件\assets\audio\sfx\prep\` 把 3 个**原合成音**还原回工程。
2. **`ui/services/SfxService.gd`**
   - 新增 `CUE_STAR4_GOD_SKILL` / `CUE_STAR4_UNDEAD_MOTHER_SKILL` / `CUE_STAR4_DARK_SKILL` 三条并登记进 `CUES`；
   - 新增 `STAR4_SKILL_CUES`：神王 / 母灵 / 黑龙指向 `*_skill` 副本，大天使 / 末日守卫指向各自
     `star4_archangel.mp3` / `star4_doom.mp3`（那两个文件本身就是 9.18 的技能音），
     人王 9.18 没给技能音故沿用 `star4_human_king.mp3`；
   - **`STAR4_CUES`（合成表）回滚**：`god_archangel` → `CUE_STAR4_GOD`、`dark_doom` → `CUE_STAR4_DARK`
     （即 9.17 时「神王·大天使共用 god」「黑龙·末日守卫共用 dark」的原合成音口径）；
   - `star4_cue_for(unit_id, is_skill := false)`：`is_skill` 为真取 `STAR4_SKILL_CUES`，否则（默认）取 `STAR4_CUES`。
3. **`scenes/battle/BattleVfx.gd`**：两处改为 `star4_cue_for(uid, true)` / `star4_cue_for("undead_mother", true)`；
   `PrepUI` / `PrepBoardController` 保持默认参数（合成）。
4. **门控不变**：仍是「自身不包括队友」——`_is_local_owned_unit()`（`owner_slot == local_slot`）。
5. **`tools/audio_sfx_check.gd`**：`EXPECTED_CUE_COUNT` 34 → 37；三条 `_SKILL` 加入 `INDIRECT_CUES`（它们同样只经 `star4_cue_for` 间接派发）。

### 验证
- `--import` 重导 6 个 star4 文件（3 个还原 + 3 个新增）→ 成功。
- `audio_sfx_check` → **CHECK_RESULT name=audio_sfx status=PASS checked=143 failures=0**。
- `project.godot` sha256 未变（`ec06205…`）。

## 二、离线自测：加「升星」功能

用户要求：**「点击场上一个棋子，就可以选择无条件升星直到 4 星，方便我测试音效问题」**

改动全部在 `officetest/OfficeTestScreen.gd`：

- 新增成员 `_editing_existing_piece` / `_upgrade_row` / `_upgrade_btn` / `_to4_btn`；
- 选择器面板加一行 **「升星：升星 +1★ / 直接到 4★」**，仅在**编辑一个已摆放棋子**时显示
  （`_on_grid_pressed` 置位、`_refresh_picker` 切换可见性）；
- 新增 `_on_upgrade_star(delta)`：`+1★` 可连点直到 4★，`99` 一步到位，封顶 `GameConstants.MAX_STAR`（4）；
- **升到 4★ 的瞬间播合成音** `SfxService.play(SfxService.star4_cue_for(unit_id))`；
  `_on_picker_star`（直接选 4★）与 `_on_picker_unit`（直接摆 4★）同样触发，覆盖所有验证路径；
- `_ready` 加 `SfxService.install()`（幂等），保证自测页也有播放器池。

用法：进离线自测 → 点格摆放棋子 → 点该格打开选择器 → 「升星 +1★」连点或「直接到 4★」→ 听到合成音。

## 三、离线自测：阵营与「自身」，音效按正式对战

用户要求：**「下面三方为我方，上面三方为敌方，并且红方为自身，音效也要按正式对战的来」**

- **布局**本就满足：`OfficeTestSim.build_test_state` 中 slots 0-2（红A/蓝B/绿C）= player = 屏幕下方，
  slots 3-5（黄1/紫2/橙3）= enemy = 上方（由 `grid_sim_pos` 的 y 决定）。
- **「红方为自身」**：新增 `_is_local_owned_unit()` 覆写，强制 `owner_slot == 0`（红 A）为自身。
  原因：`BattleVfx` 原实现取 `NetworkService.team_local_slot if NetworkService.team_active else 0`，
  而**从组队大厅进入自测时 `team_active` 可能为真、槽位可能是蓝方**，导致红方不算自身、四星技能音不响。
  覆写后不依赖 NetworkService，且只在本自测场景生效（不动 `BattleVfx` 的线上逻辑）。
- 因此演示运行时，红方四星单位的技能音会按正式对战口径响起。

## 四、顺手修掉的既存编译错误（9.17 遗留）

`OfficeTestScreen.gd` 里 `_start_test_demo()` 仍写着：

```gdscript
if _battle_music_player != null:
    _battle_music_player.play()
```

而 `_battle_music_player` 这个 `AudioStreamPlayer` 在 **9.17「BGM 统一走 MusicService、五处页面自带播放器全删」**
时已被移除，**全工程再无任何声明** → 该脚本**整个编译不过**，离线自测场景根本打不开。

改为调用父类现成的 `_start_battle_music()`（内部 `MusicService.play(_battle_music_path())`），
与正式对战起 BGM 的口径一致。

## 五、末日守卫（四星）技能音：只在开始释放时播一次

用户要求：**「四星末日守卫技能释放音效优化为 只在开始释放时播放一次，后续链接效果不播放」**

### 根因

末日守卫的技能是 `shared_hp_link`（血契连线）。它是**一次性**技能：命中后
`_skill_shared_hp_link()` 置 `shared_link_spent`，之后再调用直接 return。但是模拟器
`scripts/battle/BattleSimulator.gd:896-898` 的收尾**不看这个标记**：

```gdscript
"shared_hp_link":
    _skill_shared_hp_link(caster, opponents, d, state)
    ...
caster.skill_ready = float(state.elapsed) + 1.0   # 即使 spent 也照推
```

于是 `skill_ready` 每秒都被推到未来 1 秒 → `BattleVfx._play_skill_cast_vfx()` 的
「`skill_ready` 上升沿」判定**每秒都重新满足一次** → 连线持续期间音效被反复重播
（即用户听到的「后续链接效果也在播」）。

> 注：改模拟器（spent 后不再推 `skill_ready`）会影响技能节拍，属玩法改动；
> 本次只在**表现层**加播放记录，模拟器逻辑一字未动。

### 修法

1. `scenes/battle/BattleVfx.gd`
   - 新增成员 `_doom_skill_sfx_played: Dictionary`（按 `sim_uid` 记「这一只已经响过」）；
   - `_play_skill_cast_vfx()` 的播音处：

     ```gdscript
     var once_only := uid == "dark_doom" or sid == "shared_hp_link"
     if not once_only or not _doom_skill_sfx_played.has(_sim_uid):
         if once_only:
             _doom_skill_sfx_played[_sim_uid] = true
         SfxService.play(SfxService.star4_cue_for(uid, true))
     ```

     判据同时认 `uid` 与 `skill_id`：`uid` 保证「末日守卫」本体，`skill_id` 保证将来若有别的单位
     复用该连线机制也不会重复响（数据里 `shared_hp_link` 目前只有 `dark_doom` 一家，见
     `data/units/race_units.json:461`）。其余四星走原分支，行为不变。
2. `scenes/battle/BattleScreen.gd`：`_start_replay()` 里 `_doom_skill_sfx_played.clear()`
   —— 否则同一实例跑第二局（离线自测回编辑态后再演示）时那一次也不会响。

### 验证（行为级 + 变异测试）

临时探针 `tools/_qa_doom_once_check.tscn`：**只 `new()` 出 `BattleVfx.gd` 脚本**（不
`.instantiate()` 重型 `.tscn`），手工喂 `_state` 后直接调 `_play_skill_cast_vfx`，用
`SfxService.play_count(cue)` 数真实播放次数。5 项全绿：

| 检查 | 期望 | 实测 |
|---|---|---|
| doom_plays_once（第 1 次施放） | 1 | 1 |
| doom_no_repeat（间隔 90ms 共 3 次） | 1 | 1 |
| doom_replays_next_battle（清空后重放） | 1 | 1 |
| other_star4_still_repeats（负对照：神王 2 次） | 2 | 2 |
| other_star4_not_marked（负对照：神王不被记标记） | 不记录 | 只含 `doom1` |

> ⚠️ **两次施放之间必须等过 40 ms**：`SfxService` 有 `RETRIGGER_GUARD_MSEC = 40`
> （同一 cue 40 ms 内只发一次）。第一版探针连续调用，「只播一次」其实是重触发保护造成的
> **假阳性**，负对照神王也假红；加 `await create_timer(0.09)` 隔开后才是有效证明。

**变异测试**（首跑绿不算数）：把 `once_only` 改成 `false` → `doom_no_repeat` 变红
（3 次施放播了 3 声），证明断言真的在测这个改动；随后还原，
`BattleVfx.gd` sha256 复验 `B915FCE4…` 与改前**逐字节相同**。

回归门禁：`audio_sfx_check` PASS（143/0）、`battle_cue_profile` PASS（169/0）、
`battle_presentation_event` PASS（8314/0）、`battle_hit_victory` PASS（39/0）。
探针用后已删除（留在 `res://tools` 会给 `asset_manifest` 门禁留下增量）。

## 六、踩坑记录（重要）

1. **别在战斗继承链里重复声明 `const SfxService`**
   链为 `OfficeTestScreen → BattleScreen → BattleResult → BattleVfx → BattleRenderer → BattleArena → BattleUI`，
   而 **`BattleUI.gd:69` 已声明 `SfxService`**；子类再 `preload` 会报
   `Parse Error: The member "SfxService" already exists in parent class BattleUI.gd`。
   （`BattleVfx` 能裸用 `SfxService` 正是因为继承自 `BattleUI`——它不是 autoload，也没有 `class_name`。）
2. **headless 下不要 instantiate 重型 3D 战斗场景**：`OfficeTestSmoke.tscn` 跑了 7 分钟无输出。
   改用「一个 trivial 场景只 `preload` 目标 `.gd`（不 `.instantiate()` `.tscn`）」即可完整编译继承链，
   几秒出结果。
3. **`--script` 模式不注册 autoload**：会假报 `Identifier not found: GameState / DataRegistry`，
   并级联出 `_battle_music_player not declared` 之类的误报。判定编译是否通过，**必须以真场景运行为准**。
4. **Godot 路径**：可执行文件在 `Desktop/Godot_v4.7.2-stable_win64.exe/Godot_v4.7.2-stable_win64_console.exe`
   （同名目录套 exe）；`--path` 必须用 Windows 风格 `C:/...`，写 `/c/...` 会报 `Invalid project path`。
5. **本机 bash 的 `rm`/`grep`/`sha256sum` 会走坏掉的 safe-delete shim**（`dirname: command not found`），
   删文件请用 PowerShell `Remove-Item -LiteralPath`。
