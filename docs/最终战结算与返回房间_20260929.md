# 最终战结算与返回房间（2026-09-29）

## 已确认的行为

来源为桌面 `bug提交及修复.docx` 与 `最终战结算面板_设计交付/设计说明.md`，并包含本次对话确认：

1. 原房主仍看结算时保留其房主身份，返回主菜单或离线后才转交。
2. 本次仅原自定义房间可返回；排位、休闲匹配不直接再开同阵容房间。
3. 金币标题与数值统一右对齐，类似表格列错位一并检查。

## 结算详情

胜负页的按钮为「查看详情」。详情页为一个纵向滚动区域：红队、蓝队各三席，随后是按伤害降序排列的最终一战统计，底部提供返回操作。阵容、佣兵与宝藏图标来自现有资源；宝藏包含已激活联动/套装。棋子有星标，佣兵不显示星标。点击图标显示名称，棋子追加星级及该单位战斗结束时的技能层数。

数字列的表头和数据使用相同列宽、内边距及右对齐。图标过多时换行并增高当前行，不增加横向滚动，也不覆盖下一位玩家。玩家颜色按绝对座位取 `GameConstants.team_slot_color`。

- 总金币 = 开局 100 + 战后所有实收 + 备战正向收入，不扣任何消耗。
- `EconomyService.settle_post_battle_breakdown` 在原本每个入账分支记录 `income_by_reason`，保持原计算顺序及随机抽取次数；原 `settle_post_battle_gold` 整数接口保留。
- 服务端累计每轮战后实收；权威经济模式使用账本累计备战收入。现有影子模式仍使用客户端累计备战实收（卖出/祭坛/赌博），经棋盘快照上传并限幅，可信度与现有影子金币相同，不能作为新增反作弊依据。
- 升级石按玩家成功抽取记录天/地/人数量；消费或队友使用不会扣减本列。
- 统计来自服务端最终一战的单位统计，按双方 owner_slot 分别取一次，排除 Boss/法阵友军；不是整局所有回合的累计伤害。
- 不硬编码示例玩家、金币或单位行数。数据缺失的旧对局仅提示无完整详情。

## 返回房间

首位返回者触发服务端创建一次新房间。仍看旧战斗/结算的玩家继续留在旧房间，新房间仅保留其结算中座位；因此不会收到新房间状态而中断旧回放。真正返回者迁移到其原座位，签发新凭证，先重置旧同步序号再发送新房间快照。重复返回请求不会创建第二个房间。

新房间保留开局 AI 席位、玩家座位、身份、宠物和出战种族，金币、准备状态、战斗与回合状态从新局开始。原房主在结算中仍保留管理权，离开后按原加入顺序顺延。房主可以请离结算中的其他座位；请离只撤销保留位置，不强制关闭对方结算页。被请离者再点击返回时服务端拒绝，客户端回主菜单。

仍有结算中座位时不能开始下一局。已返回者可准备、聊天。只要还有有效的在线结算中玩家，新房间不会因实际入房人数暂时为零而回收。旧房间沿用现有超时回收规则；服务端进程重启使旧连接离线，恢复新房间时清除失效的结算中占位。

## 同步与人工验收

**客户端和 Godot 战斗服务端都要同步，协议升级为 35。需重启战斗服务端并重新导出/运行更新后的客户端。账号服务与数据库无需修改。本次未操作线上部署，也没有替换已导出的游戏包。**

请结束旧对局后更新，以新开自定义对局验证完整累计：

1. 一局结束后选择查看详情，核对六席、阵容、星标、宝藏和收入。出售、祭坛、赌博后总金币应增加，购买不应扣总金币；使用升级石不应扣获取数。
2. 在 1600 和较窄窗口查看表头与数值同一右边线；点击头像/宝藏后上下滚动，气泡应消失而行高不变。
3. 原房主留在结算，队友先返回：新房间显示原房主结算中。原房主随后返回仍为房主。
4. 原房主返回主菜单或断线，房主转交；队友返回仍为同一房间，座位不变。
5. 新房主请离一个结算中的玩家：该玩家详情页保留，再按返回房间回主菜单。
6. 所有结算中座位均已返回/释放后，可准备开局；匹配对局的详情页不显示返回房间。
