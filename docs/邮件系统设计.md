## 一、拍板记录

| 事项 | 结论 |
|---|---|
| 范围 | **只有系统邮件**：服务端发，玩家读、领附件、删。不做玩家之间的邮件（聊天已经有了） |
| 管理员从哪发 | 延续公告那条：**Supabase 后台**，没有正式后台。但邮件会发钱，所以**只给三个函数入口**，不手写 insert |
| 全服邮件发出之后才注册的新玩家 | **每封发的时候选**。默认只给发送那一刻已有的玩家（补偿用）；打开开关后，过期前注册的新玩家也能收到（活动礼包用） |
| 过期 | **默认 30 天**，发信时可以改（1～365 天）。过期后玩家看不到，没领的附件也就没了 |
| 附件里的东西玩家已经有了 | **跳过，明说「已经拥有」**，不折算成钻石。其余附件照常到账 |
| 玩家删邮件 | **只能删已读、并且附件已领完的**。删了只是他自己看不到，邮件和领取记录都还在 |
| 附件能发什么 | 钻石（进**赠送**那一列）、金币、头像、头像框、宠物。东西**只能是商品目录里卖的**（见第四节） |
| 读 / 领 / 删存在哪 | 账号服务器。换手机不会重新提醒，两台手机也不会各领一份 |
| 战斗服务器 | 不动，不顶协议号 |

## 二、玩家看到什么

| 形态 | 在哪 |
|---|---|
| 入口与红点 | 主菜单右上角「邮件」。有没读的邮件、或者有没领的附件时亮红点 |
| 列表 | 左边，新的在前，最多 100 封。没读 / 没领的那一行有红点，有没领附件的标「附件」 |
| 详情 | 右边：标题、「3 天前 · 还剩 27 天」、正文、附件清单（领过的变灰、标「已领取」） |
| 领取 | 详情里「领取」，顶上「一键领取」。到账后提示领到了什么；已经拥有的写明「已经拥有，跳过：……」 |
| 删除 | 详情里「删除」（已读、附件已领完才出现），顶上「删除已读」（要确认） |
| 新邮件 | 在线时半分钟内红点亮起；不在线的，下次登录 / 回主菜单时看到 |

点开一封就算读过，红点马上灭，不等网络。

## 三、管理员操作手册

所有操作都在 **Supabase 后台 → SQL Editor**。函数用**具名参数**调，不用记顺序。

### 发给一个人

```sql
select send_mail(
  p_friend_code => 'ABCD2345',
  p_title_zh    => '9/20 掉单补偿',
  p_body_zh     => '抱歉，这是补给你的钻石。',
  p_actor       => 'arvin',
  p_diamond     => 500);
```

返回邮件编号。好友码在玩家的资料页能看到（大小写、前后空格都没关系）。

### 发给全服

```sql
select send_mail_all(
  p_title_zh            => '开服礼包',
  p_body_zh             => '感谢参加测试！',
  p_actor               => 'arvin',
  p_diamond             => 100,
  p_include_new_players => true,
  p_days                => 14);
```

- `p_include_new_players`：**补偿不要开**（事故之后才注册的人没受影响）；活动礼包才开。
- 一封全服邮件在表里只有一行，几万人也一样。

### 所有参数

| 参数 | 必填 | 说明 |
|---|---|---|
| `p_title_zh` | ✅ | 标题，1～60 字 |
| `p_body_zh` | ✅ | 正文，最多 2000 字，可以是空串。纯文本，不支持格式 |
| `p_actor` | ✅ | **你是谁**。空着会报错 —— 以后要查「谁给这个号发了钱」 |
| `p_diamond` | | 钻石，0～100000。进玩家的**赠送**钻石 |
| `p_coin` | | 金币，0～1000000 |
| `p_items` | | 物品，最多 10 件，写**内容 id**：`array['pet_cat']`。只能是 `data/shop.json` 里卖的 |
| `p_days` | | 有效天数，默认 30，1～365 |
| `p_note` | | 内部备注（为什么发、哪次事故），**玩家看不到** |
| `p_title_en` / `p_body_en` | | 英文。空着时英文玩家看中文 |
| `p_friend_code` | 单人 ✅ | 收件人好友码 |
| `p_include_new_players` | 全服 | 见上 |

单封钻石上限 100000、金币上限 1000000 是**防手滑**（500 多打两个 0）。真要发更多就分几封。

### 发之前先自测

先用 `send_mail` 发给**自己的好友码**，进游戏看一眼标题、正文、附件对不对，再发全服。

### 看有没有发出去：`problem` 列

发完半分钟后看一眼：

```sql
select mail_id, title_zh, problem from mails order by mail_id desc limit 10;
```

`problem` 不是空的 = 这封**没给玩家看**，原因写在里面。最常见的是附件写错：

- 拼错了（`pet_catt`）
- 发了免费的东西（`preset:avatar_001`）—— 不在商品目录里的东西人人都有，发了等于没发
- 同一样东西写了两次

改好附件就行，服务器半分钟内自动放出来，在线玩家会收到提醒：

```sql
update mails set items = array['pet_cat'] where mail_id = 12;
```

**只改附件，不要改钻石金币的数** —— 已经领了的人按旧数领的，改了账就对不上了。数发错了就撤回、重发一封。

### 撤回

```sql
select withdraw_mail(12);
```

没领的人就看不到了。**已经领走的收不回来** —— 真要回收走退款流程，不要直接改余额。
**不要删行**（`delete from mails`）：钱包流水里记着「这笔钱是哪封邮件发的」，删了就查不到了。

### 查「这个号的钻石哪来的」

```sql
select l.created_at, l.currency, l.delta, l.source, l.mail_id, m.title_zh, m.actor, m.note
from wallet_ledger l
left join mails m on m.mail_id = l.mail_id
where l.player_id = (select player_id from players where friend_code = 'ABCD2345')
order by l.id desc
limit 50;
```

### 查一封邮件有多少人读了 / 领了

```sql
select count(*) filter (where read_at is not null)    as 读了,
       count(*) filter (where claimed_at is not null) as 领了
from mail_states where mail_id = 12;
```

没打开过的人在 `mail_states` 里没有行，所以这里只数得出「读了多少、领了多少」。

## 四、实现要点（为什么这么做）

### 🔴 领取只算一次

领取的事务**先锁住 `mail_states` 那一行，再发钱发东西，最后记「已领」**，都在同一个事务里。
两台手机同时点、弱网重试，第二个请求会在锁上等第一个提交，然后看到「已经领过」——
只回报当前余额，什么都不再发。顺序反过来（先发再记）的话，两个请求都会在记之前把东西发出去。

一键领取是**每封一个事务**：一封出错不连累别的，已经领到的不回滚。老的先领 ——
两封里有同一样东西时，结果和一封封点一样（先发的那封给，后发的算「已拥有」）。

### 附件只能是商品目录里卖的东西

判据是 `shop.requires_entitlement()`：不在 `data/shop.json` 里的内容本来就人人免费。
有不能发的附件时**整封不给玩家看**，原因写进 `problem` 列 —— 宁可晚到，
不能让玩家点了「领取」却什么都没拿到。改好之后下一轮自动放出来并推送。

### 一封群发只存一行

玩家打开邮箱时按「发给我的 + 我有资格收的群发」现算；读过 / 领过 / 删过才在 `mail_states` 落一行。
群发的资格：开关打开 = 谁都能收（过期那条已经挡住过期后注册的）；没打开 = `players.created_at <= mails.created_at`。

### 钱怎么记

钻石进 `diamond_free`（邮件发的钱不是玩家付的，同 `grant_diamonds`）。
流水 `source = mail`，并在新加的 `wallet_ledger.mail_id` 里记是哪封 —— 一键领取会在同一刻写好几笔，只靠时间对不上。
物品走和购买同一个发货函数（`shop._grant`，`source = mail`）。

### 推送只是提醒

账号服务器每 30 秒看一次新邮件（`mail.Postman`），推一条不带内容的 `{"t": "mail"}` 给收件人（全服邮件就广播），
客户端收到就拉一次列表。不带内容是因为群发的资格、已读已领都要按人算。
**刚重启的第一轮不推**：那时表里的都是旧邮件，玩家登录本来就会拉。

旧 APK 收到这条推送会直接忽略（实时连接对不认识的类型只转给各服务，各服务按类型过滤）。

### 时间只发相对值

接口发「发出多久了」「还有多久过期」（秒），不发绝对时间 —— 手机的钟可能是错的。

### 本机什么都不存

`MailService` 只有一份快照，拉到新列表就整份换掉。领取、删除**等服务端说成功了才改快照**；
只有「已读」是先改本机（点开那一刻红点就该灭），服务端没记上的话下次拉列表会重新变回未读。

## 五、部署

🔴 **先跑 SQL，再更新账号服务器。**

账号服务器先上的话，邮件的接口全部报错（表还不存在），日志里每 30 秒一条「检查新邮件出错」。
商城不受影响 —— 流水新加的 `mail_id` 一列只有邮件附件那一路才写，这是刻意的
（`shop._apply`，`test_mail.py` 钉着），为的就是顺序弄反时坏的只是邮件。

1. **Supabase**：SQL Editor 跑 `database/012_mail.sql`
2. **账号服务器**：`sudo bash /opt/glory/src/deploy/update.sh`（这次没有新数据文件，跑一次就够；多跑一次也没关系）
3. **新 APK**：邮件界面在客户端里，旧 APK 看不到邮件（主菜单的邮件仍是「敬请期待」）
4. **战斗服务器不动**，协议号不变

验证：发一封给自己（第三节），半分钟内主菜单邮件亮红点，领取后钻石数变了。

## 七、已知局限

- **没有正式后台**，发信靠 SQL。有不碰代码的运营 / 客服时再做，写的还是这两张表。
- **重装游戏 = 新账号**（匿名游客），收不到重装之前发的「只给已有玩家」的补偿。这是账号体系的现状，不是邮件的问题。
- **推送最多晚 30 秒**；推送丢了靠回主菜单时的刷新（60 秒节流）补上。
- **列表最多 100 封**。正常不会同时有这么多没过期的；真到了，老的先看不到。
- **撤回收不回已领的**，回收走退款流程。
- **附件没有数量**：头像、宠物这些本来就只能有一份（同归属表）。以后要发消耗品，得先有带数量的表。
