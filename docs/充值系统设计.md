## 一、拍板记录

| 事项 | 结论 |
|---|---|
| 渠道 | **只接三家官方**：安卓 Google Play 结算、iOS App Store、电脑 Steam 钱包。不自己接 TnG / FPX，不做官网充值、Codashop（第二期再说） |
| 顺序 | 账号服务器统一流程（**含 Apple 的服务器端**）→ 安卓 → Steam → iOS 客户端（要 Mac，等同事） |
| 卖什么 | **只卖钻石包**（消耗型）。宠物、皮肤照旧用钻石在商城买 |
| 汇率 | **RM 1 = 10 钻**（基础量） |
| 首充 | **每档第一次买双倍**，按账号算，全平台共用 |
| 钱包 | 一份，全平台共用 |
| 退款时钻石已经花掉 | **记欠账**（第七节） |
| 游客 | **能充**，付款确认页提醒「游客号会丢」 |
| 测试单 | 按方案 C（第八节）。10-23 推荐时他没明确回，按推荐写，看文档时可以改 |
| 安卓现状 | 现在是**直发 APK**，还没上 Play。开发和测试用 Play 的**内部测试**，正式收钱前要把玩家迁到 Play 版（第十节） |

### 为什么只接官方

1. **规则强制。** Google Play 和 App Store 里，游戏内的数字商品必须走它们的结算；没查到马来西亚在 Google 的第三方结算名单里。
   Steam 的文档写明：Steam 版里的游戏内购买只能用 Steam 钱包（`ISteamMicroTxn`）。
2. **平台是卖方。** 马来西亚的数字服务税、信用卡 / TnG / 运营商代扣、风控、退款都由平台处理。
   自己接的话，报税、拒付、退款纠纷全要自己扛，还要公司主体和收单资质。
3. 抽成：Google、Apple 都有「年收入 100 万美元以内 15%」的档，**都要在后台主动登记**，不登记按 30%；Steam 30%。

### 为什么不用 RevenueCat 这类第三方

它不管 Steam；入账去重、首充、欠账这些还是得我们自己做。它能省的只有「向 Google / Apple 核实单据」，这部分本身不大。
多一家依赖、多一份钱，换不来什么。

## 二、档位

| 商品编号 | 价格 | 基础钻石（付费列） | 平时加送（赠送列） | 首次购买（双倍） | 上线时 |
|---|---|---|---|---|---|
| `diamond_pack_1` | RM 5 | 50 | — | 100 | 开 |
| `diamond_pack_2` | RM 20 | 200 | +20 | 400 | 开 |
| `diamond_pack_3` | RM 50 | 500 | +60 | 1,000 | 开 |
| `diamond_pack_4` | RM 100 | 1,000 | +150 | 2,000 | 关 |
| `diamond_pack_5` | RM 200 | 2,000 | +400 | 4,000 | 关 |
| `diamond_pack_6` | RM 400 | 4,000 | +1,000 | 8,000 | 关 |

规则：

- **基础量严格 RM 1 = 10 钻。** 平时加送 10%–25% 照原神的做法：买得越多送得越多。
- **首次购买 = 基础 × 2，代替平时加送，不叠加。** 多出来的那份基础量记**赠送列**（它不是玩家付的钱）。
  例：第一次买第 3 档，付费列 +500、赠送列 +500；以后再买，付费列 +500、赠送列 +60。
- **首充按账号算、全平台共用。** 在 Steam 买过第 1 档，手机上第 1 档就没有双倍了。
- **退款不恢复首充资格。** 资格在入账那一刻占掉，退款只扣钻石（第七节）。
- **商品编号按档位起名，不写钻石数。** Google 和 Apple 的商品编号建了就永远占着，删掉也不能再用；
  写成 `diamond_500` 的话，以后调量就名不副实。
- **价格最后要对到 Apple 的令吉价位**，可能变成 RM 4.90 这类，钻石数不变。Google、Steam 填和 Apple 一样的价。
- **Steam 填 MYR 和 USD 两列**，其它币种 Steam 按汇率自动换算。Steam 是全球卖的，只在马来西亚发行也会有别国玩家。

### 为什么上线只开前 3 档

钻石现在**只能花在抽宠物上**：`data/shop.json` 里用钻石标价的只有抽宠物（75 钻一抽），冰雪棋盘和七日头像框是 0 价、没上架。
池子里两只宠物，最坏不超过 1,500 钻全抽到；新玩家光七日登录（5 × 100）和升到 7 级、15 级（2 × 100）就白拿 700 钻。

所以一个玩家现在**最多只需要再花约 RM 80**。第 3 档首充拿 1,000 钻，加上白送的 700 已经超过 1,500 ——
更大的档买了没东西花，反而容易招来「买错了」的退款。**有新的钻石内容时，改一个开关就能开 4–6 档。**

🔴 **收入上限在内容，不在档位。** 钻石还能买什么，是策划要定的事，本文不定。

### 目录放在哪

`data/iap_products.json`，**只在账号服务器读**。客户端不打包档位数字，打开钻石商店时问服务器要（第四节的 `GET /v1/iap/catalog`），
当地价格由平台 SDK 给。

lenoliew 09-30 做过一版：`data/diamond_products.json`（100 / 300 / 500 / 750 / 1000）和 `scenes/menu/DiamondStoreDialog.gd`
（现在显示「平台购买尚未开放」）。接充值时界面沿用，**那个 json 删掉**（档位以服务器为准，客户端再留一份就是两份真相）。动之前跟他说一声。

## 三、数据库：`040_iap.sql`

编号写代码时按当时最新的定。039 现在被图鉴同步占着（worktree `gifted-kalam-bef849`，未提交），所以暂定 040。

### `iap_orders`：真钱订单

**不复用 `shop_orders`。** 商城订单是「花钻石买东西」，状态只有 ok / refunded、明文规定拒绝不落库、价格是钻石数。
真钱订单要先建一张「待付款」的单（Steam 要服务器先下单；Google / Apple 要把订单号塞进付款请求），
还要记平台、环境、真钱币种。硬塞进 `shop_orders` 就要改一张有真实数据的表的约束。

| 列 | 说明 |
|---|---|
| `order_id uuid` 主键 | 服务器生成。Google 的 `obfuscatedProfileId`、Apple 的 `appAccountToken` 都填它 |
| `order_no bigint` 自增、唯一 | **Steam 的 orderid 必须是 64 位整数**，用它 |
| `player_id` | 外键 players |
| `client_order_id uuid` | 幂等键，`unique (player_id, client_order_id)`，同商城那套 |
| `platform` | `google` / `apple` / `steam` |
| `product_id` | `diamond_pack_N` |
| `environment` | `production` / `sandbox`。sandbox 就是测试单（第八节） |
| `status` | `pending` → `credited` / `cancelled`；`credited` → `refunded` |
| `external_id` | 去重键：Google = 付款凭证的 sha256（凭证本身太长且长度不定）、Apple = transactionId、Steam = transid。**`unique (platform, external_id)`** |
| `purchase_token` | Google 的原始凭证（退款通知只带它） |
| `steam_id` | Steam 单子付款的那个 Steam 账号 |
| `diamond_paid` / `diamond_free` | 入账时实际给了多少（快照，退款按它扣） |
| `first_bonus` | 这一单是不是首充双倍 |
| `price_amount` / `price_currency` | 最小货币单位。Steam 是我们下单时报的价；Apple 是交易里带的价（只记两位小数的币种）；Google 查单接口不给价格，留空。**只作参考，结算以平台报表为准** |
| `created_at` / `credited_at` / `refunded_at` | |
| `note` | 取消、退款的原因 |

### `iap_first_bonus`：首充资格

`(player_id, product_id)` 主键，外加 `order_id` 和时间。入账时 `insert … on conflict do nothing`，
**插进去了 = 这一单双倍**。和钱包行锁在同一个事务里，两笔同档的单同时到也只有一笔拿得到双倍。测试单不插（第八节）。

### 欠账：`player_wallets.diamond_debt`

钱包有 `>= 0` 的约束，扣不成负数，所以加一列 `diamond_debt bigint not null default 0`（也 `>= 0`），
`wallet_ledger.currency` 的取值加上 `diamond_debt`。

**不变量：有欠账时付费、赠送两列一定是 0。** 只在两列都扣光之后才记欠账，而任何入账都先还欠账（第七节），所以这条一直成立。

### 删掉 `shop_orders` 上的充值预留

010 给充值预留了 `shop_orders.external_id` 和唯一索引 `shop_orders_external`，现在决定另开 `iap_orders`，这两样永远用不上，
**040 一起删掉**（照「只要没用就删除」）。这一列线上全是空值，删它不影响任何数据。`shop.SOURCES` 里预留的 `iap`、`refund` 两个名目保留，充值正好用上。

### 流水名目

| 名目 | 什么时候 |
|---|---|
| `iap` | 正式单入账：付费列 + 基础量；赠送列 + 加送或首充那份（同一 `order_id` 两行） |
| `iap_test` | 测试单入账（只进赠送列） |
| `refund` | 退款扣回：付费 / 赠送列负数，不够的记欠账列正数 |

还欠账时进来的钱，写成「欠账列负数 + 余下的进对应列」，名目照原来的（`iap` / `mail` / `seven_day_login` …）。

### 注销

`iap_orders`、`iap_first_bonus` 都归「留账目」那边（017 的规矩）：Google / Apple 可能在玩家注销后才发来退款通知。
`backend/tests/test_profile.py` 要求每张引用 players 的表都归到删 / 留之一，两张新表要加进去。

🔴 `iap_orders` 和 `wallet_ledger` 一样**永不裁剪**，`maintenance.py` 不许出现它，加一条断言钉住。

## 四、统一流程

```
客户端                         账号服务器                         平台
  │  选第 N 档                      │                                │
  ├── POST /v1/iap/orders ────────▶ 建 pending 单，回 order_id         │
  │                                 │（Steam：这里直接调 InitTxn）─────▶│
  ├── 调平台付款（带 order_id）─────────────────────────────────────────▶│
  │◀─ 付款结果 / 凭证 ──────────────────────────────────────────────────┤
  ├── POST /v1/iap/<平台>/confirm ─▶ 向平台核实（不握数据库连接）────────▶│
  │                                 │ 一个事务：锁单 → 锁钱包 → 首充 → 入账 → 改单
  │                                 │ 然后：Google 消耗 / Steam 已在核实时扣款
  │◀─ credited + 新余额 ─────────────┤                                │
  └── Apple：finish 交易             │                                │
```

### 接口

| 接口 | 用途 |
|---|---|
| `GET /v1/iap/catalog?platform=` | 档位、钻石数、每档还有没有首充、当前欠账 |
| `POST /v1/iap/orders` | 建单。带 `client_order_id`、`platform`、`product_id`；Steam 还要带一张新的 Steam 票（第五节） |
| `POST /v1/iap/google/confirm` | 交 `order_id` + 付款凭证 |
| `POST /v1/iap/apple/confirm` | 交 `order_id` + StoreKit 2 的签名交易 |
| `POST /v1/iap/steam/confirm` | 交 `order_id` + overlay 回调里的 authorized |
| `GET /v1/iap/orders/{order_id}` | 查单（「处理中」时客户端轮询） |
| `POST /iap/google/rtdn` | Google 实时通知（Pub/Sub 推送）。不在 `/v1` 下，同 `/oidc/steam`，避开客户端版本检查 |
| `POST /iap/apple/notifications` | Apple 服务器通知 V2 |

### 入账只有一个函数

`iap.credit()`，所有路径（客户端 confirm、平台通知、定时对账、运营后台「重新核实」）都走它：

1. 先在**事务外**向平台核实，拿到一份「已付款」的证明。
2. 开事务：`select … for update` 锁订单。已经 `credited` → 原样回执（重放）。
3. 查 `external_id` 有没有被别的单用过 → 有就拒（同一张凭证不能入两张单）。
4. 锁钱包（`shop._lock_wallet`）→ 插 `iap_first_bonus` 定首充 → `shop._apply` 入账 → 订单置 `credited`。
5. 提交，然后推送余额。

### 🔴 外部请求不许握数据库连接

核实要连 Google / Apple / Steam，慢的时候好几秒。账号服务器出过「握着数据库连接等发送」把整台服务器拖卡的事
（好友在线推送那次）。这里同理：**核实在事务外做、每个外部请求都设超时**，拿到结果再借连接，事务里只做数据库的事。
沿用 `app/steam.py` 的写法（`httpx.Timeout(10.0, connect=5.0)`，httpx 日志压到 WARNING，防密钥进日志）。

### 客户端看到的三种结果

| 服务器回 | 客户端显示 |
|---|---|
| `credited` | 「已到账」+ 新余额 |
| `cancelled` | 「已取消」（只有平台明确说没付款才这么回） |
| `pending`、超时、断网 | 「处理中，钻石会自动到账」，然后轮询查单 |

**超时不等于失败**（商店刷新超时那次的教训）：钱多半已经扣了，只是回程丢了。

### 账号对得上才入账

- 订单的 `player_id` 必须是当前登录的人。
- Google：平台返回的 `obfuscatedProfileId` 必须等于这张单的 `order_id`，`obfuscatedAccountId` 必须等于玩家编号的散列。
- Apple：`appAccountToken` 必须等于 `order_id`。
- Steam：付款的 Steam 账号必须是这个号绑定的那个（第五节）。

这样一张凭证拿到别的号上交，或者交到别的单上，都不认。

### 开关

`.env` 里每个平台一个开关（`GLORY_IAP_GOOGLE_ENABLED` 等），默认关。**关掉只挡「建新单」**，
confirm、平台通知、定时对账一律照常 —— 不然已经付了钱的单就卡死在半路。出了问题先关开关，不用出包。

## 五、各平台

### Google Play（安卓）

客户端：Play 结算库 **8 以上**（v7 的截止日 2026-08-31 已过，延期到 11-01；v8 的截止日是 2027-08-31）。
付款时 `obfuscatedAccountId` 填玩家编号的 sha256、`obfuscatedProfileId` 填 `order_id`。

服务器：

1. 用服务账号调 Android Publisher API `purchases.products.get`，核对：包名 `com.glory.game.google`、商品编号、
   `purchaseState = 0`（已付款）、两个混淆编号对得上。
2. `purchaseState = 2`（待付款，比如便利店付现金）→ 回 `pending`，**不入账**，等实时通知。
3. 入账后服务器调 `purchases.products.consume` 消耗掉。消耗失败不影响入账，定时任务重试；
   客户端下次启动查到这张没消耗的单会再交一次，服务器看到已入账就只补消耗。
4. 🔴 **3 天内不确认 Google 会自动退款**，所以「入账了但没消耗」不能放着不管。
5. `purchaseType = 0` 是许可测试员的测试单。

实时通知（RTDN）：Play Console 把通知发到一个 Pub/Sub 主题，主题推送到 `https://glorytd-api.duckdns.org/iap/google/rtdn`。
- 收到「已购买」→ 用凭证查单 → 按 `obfuscatedProfileId` 找到我们的订单 → `iap.credit()`。玩家付完就关游戏也能到账。
- 收到「已作废」→ 走退款（第七节）。
- 推送要验 Google 签的身份令牌，不认不带令牌的请求。

兜底：每天调一次「已作废购买」接口（Voided Purchases API），防实时通知丢。

### Steam（电脑）

1. 客户端建单时带一张新的 Steam 票（`SteamBridge.ticket()`，登录用的同一种）。服务器验票得到 Steam 编号，
   再查这个号在 Supabase 上绑的 `custom:steam` 身份 —— **对不上就不让下单**（防止用 A 的 Steam 钱包给 B 充）。
   比对的是那个身份的占位邮箱 `steam-<Steam 编号>@steam.invalid`（`steam.placeholder_email`），里面就是 Steam 编号。
2. 服务器调 `GetUserInfo` 拿玩家钱包的币种，从目录里取 MYR 或 USD 价，调 `InitTxn`（`orderid` = `order_no`，`usersession=client`）。
   成功后 Steam 在游戏里弹 overlay 让玩家确认。
3. 客户端收到 `MicroTxnAuthorizationResponse` 回调，把 authorized 交给 `/v1/iap/steam/confirm`。
   authorized = true → 服务器调 `FinalizeTxn`，**这一步才真正扣钱**，成功了再 `iap.credit()`；false → 置 `cancelled`。
4. 兜底：定时任务每分钟扫一小时内还在 `pending` 的 Steam 单，调 `QueryTxn`：
   `Approved` 就替玩家 `FinalizeTxn` 并入账（玩家点了确认但游戏崩了）；其它状态放着，超过一小时置 `cancelled`。
5. 退款、拒付：定时调 `GetReport`（文档要求至少每天一次，我们每 10 分钟一次），看到 Refunded / Chargedback 等状态走第七节。

overlay 弹不出来是真实风险（Godot 4.7 加你们的渲染器没实测过，MSI 也还没装 Steam 客户端）。
**Steam 客户端第一件事就是实测 overlay**；不行就改用 `usersession=web`，服务器拿回一个网址，客户端用浏览器打开付款。

测试：Steam 有 `ISteamMicroTxnSandbox`，同样的请求、不扣钱。`.env` 里列一组测试员 Steam 编号，
这些人下单时服务器走沙盒、订单记 `sandbox`。

发行商密钥就是登录用的那把（`steam_web_api_key`），已经在服务器上。

### Apple（服务器端先做，客户端等 Mac 同事）

客户端（同事）：StoreKit 2，`purchase(options: [.appAccountToken(order_id)])`，把签名交易（JWS）交给 `/v1/iap/apple/confirm`；
服务器回 `credited` 后才 `finish()`；每次启动查一遍没 finish 的交易再交。

服务器：

1. 用 Apple 官方的 Python 库（`app-store-server-library`）验签名链，核对 bundle id、商品编号、`appAccountToken`、
   交易类型是消耗型、没被撤销；环境（Production / Sandbox）从交易里读。
2. Apple 服务器通知 V2：`REFUND` 走退款；`REFUND_REVERSED` 第一期只记录，交运营后台手工处理。
   `CONSUMPTION_REQUEST`（玩家申请退款时 Apple 来问用掉多少）第一期不回。
3. 要的配置：App Store Server API 密钥（.p8，放服务器文件，不进仓库）、Key ID、Issuer ID、bundle id、App Apple ID。

## 六、补单（掉单兜底）

掉单一定会发生：断网、杀进程、回程丢包。三层兜底：

| | 客户端重交 | 平台通知 | 定时对账 |
|---|---|---|---|
| Google | 每次启动 / 回前台查没消耗的单 | RTDN「已购买」 | 补消耗、每天查作废 |
| Apple | 每次启动查没 finish 的交易 | 服务器通知 | — |
| Steam | — | — | 每分钟 `QueryTxn` 扫 pending |

🔴 **补单不走邮件附件。** 邮件发的钻石进赠送列（`backend/app/mail.py` 的领取逻辑），用它补单会把付费口径弄乱。
补单直接 `iap.credit()` 进付费列。

如果是后台补进去的（玩家当时不在线），另发一封**不带附件**的系统邮件「你有一笔 RM xx 的充值已到账」，
让玩家知道钻石是哪来的。服务器直接写 `mails` 表，不走 `send_mail()`（那个按好友码、是给运营手工用的）。

## 七、退款与欠账

### 从哪知道退款了

Google 实时通知「已作废」+ 每天查作废接口；Apple 服务器通知 `REFUND`；Steam `GetReport`。都走同一个函数 `iap.refund()`。

### 扣多少、怎么扣

扣回这一单当初给的**全部**钻石（`iap_orders.diamond_paid + diamond_free`，含首充那份）：

1. 先从付费列扣，不够再从赠送列扣。
2. 还不够的部分记进欠账列。
3. 订单置 `refunded`，流水名目 `refund`。

退款用掉的东西（抽到的宠物等）**不收回**：钻石是通用的，欠账已经把差额记下了。收回宠物还会牵扯出战名片、对局记录，不值得。

### 有欠账时

- **不能花钻石**（商城钻石商品、抽宠物），其它照常玩。
- **任何钻石入账都先还欠账**：充值、邮件、七日登录、升级奖励，一律先抵欠账，剩下的才进余额。
- 游戏里余额显示成负数（比如 -300），红色。

实现上只改两处：

- `shop.Wallet.diamond` 改成「付费 + 赠送 - 欠账」。商城（`shop.purchase`）和抽宠物（`pet_draw.draw`）本来就用它判余额，
  欠账时自然是「钻石不足」，不用另加判断。旧客户端照样显示这个数。
- `shop._apply` 遇到钻石入账、且有欠账时，先抵欠账。所有入账路径都经过它，一处改全部生效。

### 反复退款的人

运营后台列出「有欠账 / 退款超过 N 次」的号，要不要封由人决定，不自动封。

## 八、测试单（方案 C）

### 什么是测试单

有些人点「购买」会看到正常的付款页，但**不扣钱**：

| 平台 | 谁 | 服务器怎么认出来 |
|---|---|---|
| Google | Play Console 里登记的许可测试员 | `purchaseType = 0` |
| Apple | **所有从 TestFlight 装的人**，以及 Apple 审核员 | 交易里 `environment = Sandbox` |
| Steam | `.env` 里列的测试员 Steam 编号 | 服务器自己决定走沙盒 |

### 为什么不能一律拒收，也不能当真单

- 一律拒收：Apple 审核员会真的点购买，看到失败就拒审；而服务器分不清审核员和 TestFlight 玩家（都是 Sandbox）。
- 当真单发：现在的测试包连的是正式服，TestFlight 上的玩家就能无限白拿钻石。

### 规则

1. **照真单的规则算钻石**（含首充双倍），这样审核员看到的和真玩家一样。
2. **全部进赠送列**，流水名目 `iap_test`，订单 `environment = sandbox`。收入统计只算 `production`。
3. **不占首充资格**（不插 `iap_first_bonus`）：TestFlight 玩家以后在 App Store 版真买时，双倍还在。
4. **每个号 24 小时内最多 1 张测试单入账**（按入账时间往回数 24 小时，不按日历日，免得卡在时区上）。
   超了的单置 `cancelled`（原因记 `test_daily_limit`），但照样消耗 / finish，免得客户端一直重交。

## 九、客户端

### `scripts/account/BillingBridge.gd`

照 `SignInBridge.gd` / `SteamBridge.gd` 的样子，一层门面盖住三个平台：取当地价格、发起付款、查没完成的单、收付款结果。
AccountManager 加充值那一节（catalog / 建单 / confirm / 查单），和商城那节同一个写法。

### 安卓插件：自己写 `glory_billing`

照 `android_plugins/glory_signin` 自己写一个薄插件，用现成的 `build_aar.ps1` 编。理由：

1. **结算库版本自己定**。Google 要求 8 以上；Godot 官方插件（godot-sdk-integrations/godot-google-play-billing）的结算库版本页面上没写，要读源码才知道。
2. 要用的就五个功能：连接、查商品价格、带混淆编号付款、查没完成的单、付款回调。量不大。
3. **错误自己分类**。Google 登录那次就是插件把失败报成「取消」，一声不吭；付款这里分错代价更大。
4. 顺带能读「这个包是不是从 Play 装的」（安装来源），直发包据此不显示购买按钮（第十节）。

### 钻石商店（`DiamondStoreDialog.gd`，lenoliew 的界面）

- 档位从服务器拿，价格从平台拿，没拿到价格的档不显示购买按钮。
- 每档标「首充双倍」，用过就不标。
- 付款确认前，游客号多一行：「游客号卸载或换机后会丢失，建议先绑定 Google」。
- 状态只有四种：付款中 / 已到账 / 已取消 / 处理中（会自动到账）。
- 直发包：不显示购买，显示「请从 Google Play 下载正式版后充值」。

### 启动和回到前台时

查一遍没完成的单，逐张交给服务器。和登录流程并行，**不做进门条件**（同宠物归属那条：一个外部服务慢不能让全员进不去）。

### 🔴 抽宠物公示概率

钻石能用钱买之后，Google 和 Apple 都要求**付款前**显示抽取概率。`scenes/menu/PetDrawDialog.gd` 抽之前要写明：
「每抽 10% 获得宠物；每抽都累积 1 点能量，满 10 抽必得（提前抽到不清零）；没抽中返还 100 游戏币」
（数字和规则从 `backend/app/pet_draw.py` 来：`PRICE` / `MISS_COIN` / `PITY_LIMIT`，以及「只有保底那一抽才清零能量」。改了要一起改）。
**这条不做，充值开关不能开。**

## 十、直发 APK 迁到 Play

直发包签的是我们自己的密钥（CN=Leno，9A:BE…），Play 版签的是 Play 的应用签名（9B:1F…）。
**签名不同，安卓不让原地升级**，玩家只能卸载再从 Play 装；卸载会清掉本机数据，**游客号就丢了**（游客凭证只存在本机）。

步骤：

1. 开发期：用 Play **内部测试**（不用审核、最多 100 人、不受「12 人连测 14 天」限制）。测试的人从内部测试链接装。
2. 正式收钱前：用直发渠道再出一版，发公告「先绑 Google，再去 Play 下载新版」。迁移是一次性的事，用公告，不改「游客提醒只用红点」那条规矩。
3. Play 正式版上线后**不再出直发包**。直发包的购买按钮一直是「请去 Play 下载」；
   下一次顶账号服务器的最低版本时，直发包自然被挡（新版本只在 Play 上有），不用另做「认渠道」的判断。

前提：Play 能不能直接上正式版。2023 年 11 月以后建的**个人**开发者账号，要先在封闭测试里有 12 人连续测 14 天，在 Play Console 信息中心能看到。

## 十七、不做 / 已知局限

- 不做月卡、订阅、礼包、官网充值、Codashop。要做的时候另开。

- 没有 Google 服务的手机（比如华为）用不了 Play 结算，第一期不管。
