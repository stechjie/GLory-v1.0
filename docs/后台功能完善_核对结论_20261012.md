## 四 任务书不知道、但能省大量工作的两处现成机制

这是本次核对最有价值的部分 —— 任务书因为读的是 10-06 的代码，两套都没看到。

### 4.1 补丁服务已经有账号服务器 ↔ 战斗服务器的状态桥

**已核实：** `backend/app/patch_service.py:121 configure_battle()` 构造 `BattleBridge(desired_path, status_path, instance_id)`；战斗服务器端是 `scripts/multiplayer/BattleHotfixAgent.gd`；已有测试 `backend/tests/test_patch_battle_bridge.py`。

配置项在 `backend/.env.example:91-93`：

```
GLORY_PATCH_BATTLE_DESIRED=/var/lib/glory-patches/battle-desired.json
GLORY_PATCH_BATTLE_STATUS=/var/lib/glory-battle-hotfix/status.json
GLORY_PATCH_BATTLE_INSTANCE=main
```

**账号服务器写 desired、战斗服务器写 status、账号服务器读回**，这正是任务书第九节「同步任务」实体要的形状：

> 操作编号、目标服务、状态版本、重试次数、最后错误及完成时间；通知失败可恢复，不重复执行业务扣款

**建议：OPS-05 的跨服务状态同步照这个扩，不要重新设计。** 任务书第七节第 3 条要求「后台展示…关键服务实际同步情况」，这个桥已经提供了 status 回读。

### 4.2 单端登录（034）的拒绝模式正好是任务书要的

**已核实：** `backend/app/login_sessions.py:19` 用 HTTP **409 `session_replaced`**，注释写：`Distinct from an expired Supabase token: never silently retry/register.`

这正是任务书第二节第 8 条要的纪律：

> 维护、被封和禁赛不得伪装成会导致客户端清凭证的认证失效

**但有个真实差距要补：** `login_sessions` 是**拉取模型** —— 下一次请求被拒才知道。而 OPS-05 第七节第 5 条要的是**主动推送**（「建议健康在线时 5 秒内通知，推送断开时 30 秒内轮询兜底」）。推送通道本身已经有（WebSocket Hub），但要注意：

🔴 **往多人发东西必须用 `broadcast`/`publish`，或者自己包超时。** `Hub.send`/`send_to_player` 没有超时；在握着数据库连接时串行 await 它，一个卡死的 socket 就能拖垮整个账号服务器 —— 这个已经真实发生过一次。维护开关要给全服推状态，正是最容易踩的场景。

## 五 禁语音「禁说不禁听」的真实工作量（已拍板）

**已拍板（2026-10-12）：** 禁语音必须是「禁止说话、仍可收听」，不接受「直接踢出语音房」。

任务书第四节把这条写成「建议规则，须由运营确认」，但它**没有说清这是两端新代码**。本次核对的结论：

### 5.1 便宜的部分（已核实）

LiveKit 管理调用通道**两端都已经有**，加 `UpdateParticipant` 是小改：

| 端 | 现状 | 要加什么 |
|---|---|---|
| 战斗服务器 | `scripts/voice/LiveKitAdmin.gd:37 _post()` 是通用的（方法名 + 请求体字典），已有 `RemoveParticipant`、`DeleteRoom` | 一个 `UpdateParticipant` 包装，约 4 行 |
| 账号服务器 | `backend/app/party_voice.py:78 delete_room()` 已在签管理令牌 + POST twirp | 同形状的 `UpdateParticipant`，权限位从 `roomCreate` 换成 `roomAdmin` |

**关键确认：权限够用。** `scripts/voice/LiveKitAuth.gd:97 admin_token()` 在 `can_delete=false` 时签的是 `{"roomAdmin": true, "room": room}` —— 这正是 `UpdateParticipant` 需要的授权，**鉴权侧不用动**。

### 5.2 贵的部分

**（1）两个签令牌的地方都把 `canPublish` 写死了**（已核实）

- 组队大厅语音：`backend/app/party_voice.py:71` `"canPublish": True`
- 局内语音：`scripts/voice/LiveKitAuth.gd:87` `"canPublish": true`

两处都要改成读处罚状态。账号服务器那边有数据库，直接查；战斗服务器那边**没有数据库连接**，这就引出下一条。

**（2）🔴 战斗服务器怎么知道玩家被禁语音了**

这是整条需求里最硬的一块，要两条路**都做**：

- **新入场的人** —— **建议**让处罚状态随**出战名片**进对局。名片由账号服务器用 RSA 私钥签、战斗服务器用公钥验（`scripts/multiplayer/BattleCard.gd`，账号服务器签在 `backend/app/loadout.py:251 card_payload()`）。
  🔴 **但名片是 `BattleCard.gd:62 VERSION := 1` 的签名结构，加字段要升版本号** —— 这意味着**客户端和战斗服务器必须一起部署**，和升协议号同级的约束。
- **对局中途被禁的人** —— 名片已经签发了，塞不进去。必须账号服务器实时通知战斗服务器 + 调 `UpdateParticipant`。**建议**走 4.1 那个 desired/status 桥。

**（3）🔴 旧令牌重连会恢复发言 —— 验收 S02 直接考这条**

**已核实：** `scripts/voice/LiveKitAuth.gd:18 JOIN_TTL_SEC := 600`。入房令牌有效期 **10 分钟**。

LiveKit 只在首次进房时检查令牌（`LiveKitAdmin.gd` 文件头注释写明了这一点）。`UpdateParticipant` 改的是**当前会话**的权限；玩家用那张还没过期的旧令牌重连，LiveKit 会按**令牌里的 grants** 重新授权 → `canPublish: true` 回来了。

任务书验收 S02 要求：「局内禁语音、旧令牌重连、解除 —— 重连不能绕过」。所以必须在这三条里选（**建议**第一条）：

1. 重连进房后**立即重新调一次** `UpdateParticipant`（最稳，不依赖令牌内容）
2. 把 `JOIN_TTL_SEC` 砍短（牵动正常重连体验，**待验证**）
3. 发令牌前查处罚（只挡新签，挡不住已签发的 600 秒窗口）

**（4）解除后要能恢复、失败要可重试**

任务书第四节第 3 条要求的，这部分`LiveKitAdmin.gd` 已有「失败重试两次 + 只写日志、绝不阻塞对局」的现成态度可以沿用，但「保留执行状态并提示管理员」需要新的同步任务记录（见 4.1）。

### 5.3 小结

| 子项 | 工作量 |
|---|---|
| 两端 `UpdateParticipant` 调用 | 小（通道和权限都现成） |
| 处罚表 + 两处签令牌读状态 | 中（新迁移 035 + 账号服务器改动） |
| 名片带处罚状态 | 中，**但要升名片版本 → 客户端 + 战斗服务器同时部署** |
| 中途禁语音的实时通知 | 中（建议复用 desired/status 桥） |
| 旧令牌重连不绕过 | **这是最容易做漏、而验收 S02 专门考的一条** |

## 八 这份核对没做的事

说清楚边界，避免被当成比实际更强的保证：

- **没有登录后台、没有碰生产数据。** 任务书自己也是 `/admin/api/me` 返回 401 就停了。
- **没有核实线上部署版本与已跑迁移。** 本文所有结论基于**本地仓库代码**。线上实际跑到第几个迁移，要同事在 Supabase 核 —— 这个项目没有迁移台账，漏跑迁移已经发生过三次（030、032，031 可能）。
  启动自检 `backend/app/schema_check.py` 已经写好（**未提交**），它会在启动时把结构与代码的不一致以 `SCHEMA` 前缀、**error 级别**打到日志（`schema_check.py:127`），`journalctl -u glory-backend | grep SCHEMA` 一眼能看到，且只报警不拒绝启动。
- **没有验证 LiveKit 服务端版本是否支持 `UpdateParticipant` 的权限更新语义。** 第五节的方案是基于 LiveKit 的通用接口形状，**待验证**：要在部署的那个 LiveKit 版本上实测「改权限后当前会话立即停止发布」。任务书第四节也提醒了「本地相关注释存在不同假设，不能直接照注释保证生效」。
- **没有估工期。** 六个工作包跨账号服务器、战斗服务器、Godot 客户端，35 条验收，远超一轮工作量。
