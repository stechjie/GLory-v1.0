## 1. 证据先行：先证明偏移是真的、再证明它从哪来

上一轮（9.30）我给这条 bug 只做了**结构断言**，并明确声明「未做观感验收」。
这一轮不再靠推理，直接建门禁把像素级现象量出来。

### 1.1 判据为什么成立（不是自证）

备战界面里，上阵格子的屏幕位置由这一条链路决定：

```
screen = grid.global_position + cell.position
cell.position = _plane_circle_screen_pts(u, v, r) - grid.global_position
```

而 `_plane_circle_screen_pts` → `_world_to_main_screen` 的**三个输入**全部与面板布局无关：

| 输入 | 值 | 会不会被面板布局影响 |
|---|---|---|
| `_prep_river_camera` | `PREP_RIVER_CAMERA_POSITION/FOV` 常量 | 否 |
| `_prep_river_viewport.size` | `PREP_RIVER_VIEWPORT_SIZE` 常量 | 否 |
| `get_viewport().get_visible_rect().size` | 主窗口尺寸 | 否（窗口没动） |

3D 石台在备战期间也固定不动。**所以 `screen` 必须恒定** —— 它一旦变化就是 bug，
不需要拿「看起来对不对」当判据。

### 1.2 新门禁 `tools/prep_ring_layout_check`

三个用例，**各用一个独立 PrepScreen 实例**（共用一个实例时，前一个用例留下的
偏差会被后一个用例的基准吸收，会出现「A 红 B 也红」但说不出各自责任的情况 ——
第一版就是这么写的，已改）。

| 用例 | 挤动方式 | 验的是哪条防线 |
|---|---|---|
| A | 宝物入袋，走**生产收尾函数** `_finish_treasure_change` | 显式重排那一刀 |
| B | 往 board_frame 所在 HBox 前插 120px 占位 | 确定性挤动，与「谁引起」无关 |
| C | 同上，但 96px，**不调用任何重排** | `item_rect_changed` 信号兜底能不能独立成立 |

每个用例都带**前置体检**：必须实测到 `grid.global_position` 真的变了，否则判 FAIL
（本环境挤不动面板 = 什么都没测到，不许假绿）。

判据取**终态**（最后 10 帧的最大漂移 ≤ 1.5px），不取全程峰值 —— 布局刚变的那一两帧
本来就没补偿，属过渡；用户报的是「偏了之后一直被留着」。

## 2. 定位：根因是 `item_rect_changed` 压根没响

### 2.1 复现

```
用例A: grid (280,84) -> (358,84)  moved=true  peak=78.00  tail=0.00  settled_at=4
用例B: grid (358,84) -> (486,84)  moved=true  peak=128.00 tail=0.00  settled_at=4
用例C: grid (358,84) -> (462,84)  moved=true  peak=104.00 tail=0.00  settled_at=4
CHECK_RESULT status=PASS checked=17 failures=0
```

基线（含上一轮那一刀显式重排）三例全绿。漂移量**恰好等于 grid 的位移量**，
说明格子完全没有跟随补偿 —— 但 4 帧内就自愈了。

### 2.2 变异 M1：把 `_finish_treasure_change` 里的显式重排删掉

```
用例A: tail=78.00  settled_at=-1  over_threshold_frames=45 | versions: f0:v1
用例B: tail=0.00   settled_at=4                         | versions: f0:v2
用例C: tail=0.00   settled_at=4                         | versions: f0:v2
FAIL [case_a_ring_drift]
```

**A 偏 78px 且 45 帧从不自愈 —— 与用户描述「偏移、点赌博才恢复」逐字吻合。**
还原 sha256 `c48305fca433d595...` MATCH。

### 2.3 三条诊断把责任钉死

| 诊断 | 结果 | 排除了什么 |
|---|---|---|
| 偏了之后手动补一次 `_realign_prep_board_cells()` | drift 78.00 → **0.00** | 重排函数本身**完全有效**，问题是它没被调到 |
| 跟踪 `_prep_model_root.visible`（协程跑到最后才会设回 true） | 用例A **轨迹为空** | `_apply_prep_model_layout_after_frames` **从没跑过** |
| 跟踪 `board_frame.global_position` + 信号连接状态 | frame 280→358 位移了、`is_connected=true` | 信号**连着、但没响** |

**根因**：`Control.item_rect_changed` 只在**自己的局部 rect**（position/size）变化时
发出。而「拿到宝物 ⇒ 左侧羁绊面板多一个赌博按钮 ⇒ 面板变尺寸」走的是另一条路：
面板变尺寸 ⇒ `body`/`center` 重新排布 ⇒ **board_frame 被祖先带着整体平移**，
它自己的局部 position 没变 ⇒ **信号根本不发**。

B/C 用例之所以能触发，是因为往 HBox 里插占位会让 HBox **重新排布 board_frame**
（局部 position 变了）——同样是「棋盘被挪了」，两条路径的信号行为完全不同。

## 3. 修复：加一道与「谁引起的平移」无关的持续守卫

`scenes/prep/PrepBoardModels.gd`：

```gdscript
var _prep_aligned_grid_pos := Vector2.INF

func _connect_prep_layout_guard() -> void:
	var tree := get_tree()
	if tree == null:
		return
	if not tree.process_frame.is_connected(_tick_prep_board_layout_guard):
		tree.process_frame.connect(_tick_prep_board_layout_guard)

func _tick_prep_board_layout_guard() -> void:
	... 前置条件检查 ...
	var now := _board_hud.grid.global_position
	if _prep_aligned_grid_pos.is_finite() and now.is_equal_approx(_prep_aligned_grid_pos):
		return
	_realign_prep_board_cells()
	_realign_prep_standby_cells()
	_update_prep_board_glow()
```

锚点 `_prep_aligned_grid_pos` 由 `_realign_prep_board_cells()` 自己在末尾写入 ——
**谁调的、什么时候调的，都算对过账**，不需要第二处维护。

**边界（都用实测定的，不许顺手扩）**：

* **接 `SceneTree.process_frame`**，不写 `_process` —— 后者会被继承链上的子类覆盖
  （`PrepScreen ← PrepBoardController ← PrepFlowController ← PrepUI ← PrepBoardModels`）。
* **只补 2D 那一层，不碰 `_reposition_existing_prep_models()`**：3D 棋子是固定投影到
  石台上的，被祖先带着平移的是 2D 层；实测 M1 下偏的也只有 2D 光圈（3D 模型没偏）。
  把棋子也拽走只会错得更远。
* **不走 `_queue_prep_model_layout_refresh()`**：那条路会先把 3D 模型藏两帧再放出来
  （防闪烁设计），每帧这么做会闪成一片。
* 常态成本 = 一次 `Vector2` 比较，只在真的挪了的时候才重算。

## 5. 第一条「神3吸血其他种族依然有效」：代码层复查结论

**没有发现第二条吸血路径，当前工作树的实现是对的。** 逐条排除：

| 候选 | 结论 | 依据 |
|---|---|---|
| 吸血纹章 `def_lifesteal_emblem`（也是 20%、也是造成伤害后） | 需要**持有该宝物**才生效 | `BattleSimTreasures.gd:232` 以 `_f_has_treasure` 为前提；用户明确「左下角都没选宝」 |
| 佣兵被算成神族 | 不可能 | `data/mercenary/mercenaries.json` 里 `"race"` 出现 **0 次** ⇒ `d.get("race","")` 恒为 `""` |
| 佣兵吃宝物 | 不可能 | 同表 `rules.affected_by_treasure = false`，且 `_ignores_treasure` 排除佣兵 |
| 第二条读 `god_lifesteal` 的地方 | 不存在 | 全工程只有 `SynergyService.gd:36`（定义）与 `BattleSimulator.gd:1009`（读） |
| 第二条回血出口 | 不存在 | `unit.hp = mini(...)` 只在 `BattleSimShared.gd:1447`（`_heal_unit` 实体） |
| 离线自测跑的是旧录像 | 不成立 | `OfficeTestSim.compute_test_replay_async:300` 内部 `build_test_state` **重新模拟** |
| 判定写错（`race` 字段名） | 不成立 | `data/units/race_units.json` 字段名就是 `"race"` |
| **神族技能的「治疗」被看成「吸血」** | **不能排除 —— 高置信候选** | `_skill_lowest_ally_heal`（神侍 `god_priest`）治疗最低血量友军 6% 最大生命；`_skill_nearby_ally_heal_buff`（天使 `god_angel`）范围内友军治疗 8% + 加攻。**两者都会给非神族友军回血**，是合法技能效果。大祭司 `_skill_nearest_ally_bless` 只给 atk/aspd 加成、**不治疗**。用户图 1「攻击榜」里有大祭司 ⇒ 阵容是神族 ⇒ 队里很可能带神侍/天使 |

**区分方法（给用户的可操作判据）**：吸血只在**该单位自己造成伤害时**回血，回血量 ≈ 自己这一下的**实际伤害 × 20%**；队友治疗则**与它是否在攻击无关**，回血量 ≈ **它自己的最大生命 × 6~8%**，且施法者身上会有 `_mark_vfx_target` 的目标标记。看两三个回合就能分开。

现有实现（`BattleSimulator.gd:1009-1011`）：

```gdscript
var lifesteal := SynergyService.safe_factor(syn, "god_lifesteal")
if lifesteal > 0.0 and str(d.get("race", "")) == "god":
	_heal_unit(attacker, maxi(1, int(dealt * lifesteal)))
```

与羁绊文案真源一致（`SynergyPanel.gd:154`「**神族单位**造成伤害时回复实际伤害 20% 生命」）。

**⇒ 待用户确认**：这一条复现时跑的是哪个可执行/安装包。已在代码层确认
`GLory-v1.0`、`GLory-codex` 两个仓与两处导出产物路径（`Desktop/GloryBeta0908.apk`、
`Glory steam version/glory_test.exe`）**都不存在或都不含本轮修复**。
若用户跑的是不含 9.30 那一刀的构建，这一条与第 3 条会**同时**复现 —— 而用户报告
的正是这两条同时存在（第三条并未随第三条一起修好前的截图时间 9-29 22:55）。

## 6. 口径声明

* 本门禁只覆盖**备战界面**的上阵/待命格子对齐；战斗界面内不适用。
* `SETTLE_FRAMES=45`（约 0.75s @60fps）是观察窗口，不是「要求 N 帧内必须好」的 SLA。
* 批跑清单只覆盖「备战界面 + 本轮直接相邻」的门禁，**批跑 ≠ 全集**，
  且本轮**未做真机观感验收**。
* 3D 棋子模型是否也该跟着面板平移，本轮**未动**（见 3 节边界说明）；实测偏的是
  2D 光圈，若真机上棋子也偏，需另开一条。
