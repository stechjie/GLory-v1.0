## ★★★ 订正（同日第四轮）：③ 神王落雷**劈到了非技能目标**

### 14.1 这一轮不是"接错模块"，而是"目标集合是猜的"

第三轮已经修好了「神王到底是谁」和「用哪个落雷模块」，但**落点集合**仍由表现层自己推断。
`BattleVfx` 的 `global_divine_blast` 分支原来有**两个**推断来源，**两个都不对**：

| 来源 | 为什么错 |
|------|---------|
| ① 本帧的**伤害事件** (`_enemy_damage_events`) | 那是**帧级**的 —— 里面混着**其它单位**在同一帧打出的伤害。别条路上的敌人被别人打掉血，也会在它头上落一道雷 |
| ② 取不到就退回**全部存活敌人** (`_living_enemy_world_positions`) | 完全无视 `_can_target` 的**路数限制**（`team_mode` 下只打自己这一路），多目标技直接变成**全屏技** |

用户截图里被劈的正是**不在神王那一路**的敌人。

★ 值得单记的是：**这个 bug 编译绿、门禁全绿、连上一轮的行为探针（38 条）也全绿。**
因为探针验的是「3 个目标 → 3 道雷」，而**那 3 个目标是探针自己喂进去的** ——
判据落在了一个我猜出来的输入上，恰好绕开了真正出错的环节。
**探针喂的输入必须来自生产实现，不能来自我自己的假设。**

### 14.2 修法：在**判定发生的地方**把结果记下来

不在表现层补猜，而是让模拟器把**它真正选中的目标**交给表现层：

```gdscript
# BattleSimSkills._skill_god_king
var struck := []
for o in opponents:
    if not bool(o.get("alive", false)) or not _can_target(caster, o, opponents): continue
    ...
    struck.append(o)
_mark_vfx_targets(caster, struck)          # ← 新增：记录真实目标
```

`_mark_vfx_targets` 是 `_mark_vfx_target` 的多目标版，**复用既有的纯表现列**
`vfx_skill_target_uid`（逗号连接），所以**不需要新增回放列** ——
`ReplayDigest.SIMULATION_TOP_FIELDS` 含 `frames`，加列必然改哈希，那条路走不通。
uid 形如 `player_ember_3` / `enemy_boss_x`，**不含逗号**，逗号可安全作分隔符。

表现层改为**只认记录**，并把退回旧口径的开关用 `recorded.is_empty()` 锁死：

```gdscript
var recorded:=str(unit.get("skill_target_uid",""))
var enemy_targets:Array=resolve_skill_target_positions(current,recorded)
if recorded.is_empty():          # ★ 只有「根本没有记录」才退（老回放）
    ...旧口径...
```

★ 关键取舍：**有记录却解析为空时不许退**。一退就等于把别处的敌人当成技能目标劈了 ——
那正是本条 bug 本身。宁可少放一道雷。

### 14.3 两个容易做反的细节

1. **不许按 `alive` 过滤落点。** 记录是在选目标时写下的，那时它必然活着；
   能出现在记录里的必然是本技能认下的目标。同一帧里它可能已经被**本技能的雷**劈死 ——
   那道雷恰恰是最该看见的一道。按 `alive` 过滤等于把「劈死目标的那道雷」删掉：
   目标无声倒下、头顶没雷。而且 `alive=false` 的单位**不会**被移出 `state.player/enemy`
   （模拟器只标记不删），所以它在 `current` 里始终找得到、`world_foot` 仍然有效。
2. **不许为了修这个 bug 就把目标锁死在本路。** `_can_target` 有一条**既有回退**：
   本路没有存活敌人时允许跨路。收窄成 `lane == caster.lane` 会破坏它。
   探针 Part 5 专门留了一条反面断言守这个。

### 14.4 判据：探针从 38 → 57 条，变异 6 → 10 个

新增两层，**都必须能红**（§14.5 有变异证明）：

* **Part 5（sim 侧，跑生产实现 `_skill_god_king`）**：神王放 0 路，敌方三路各一只。
  **期望值由 lane 独立算出**（只用 `lane` 与 `alive` 数，**不借 `_can_target`**，避免自证）。

  本路清空后仍会跨路选目标（既有回退未被破坏）。

### 13.1 神王：上一轮把 `human_king`（人王）当成了神王

| 单位 | id | `skill_id` |
|------|----|-----------|
| **神王** | `god_king` | **`global_divine_blast`** |
| 裁决者 | `god_arbiter` | `judgement_strike` |
| 人王 | `human_king` | `unique_king_growth` |

上一轮我把 `unique_king_growth` 接上了落雷 —— 那是**人王**的技能 id。后果是**一错两伤**：

1. **神王**（用户真正要改的那只）技能没动，仍走 `_oga_pack_multi_melee`，屏幕上没有可见落雷；
2. **人王**的普攻表现被**悄悄换成了落雷** —— 这是我引入的新回归。
   人王没有 `skill_cd`，`unique_king_growth` 是它的**被动成长技**，
   这个分支实际只服务它的**普通攻击**（`BattleVfx._play_unit_procedural` 里人王直连到这里），
   于是一刀一剑的金色天剑全变成了雷。

**订正后的实现** —— 两条都接到**字面上同一个函数**：

```gdscript
"judgement_strike":_aoe_thunder(origin,target,{})                 # 裁决者：单体
"global_divine_blast":_aoe_thunder(origin,target,context)          # 神王：全体
...
"unique_king_growth":_king_attack(origin,target,context)           # 人王：还原天剑
```

```gdscript
func _aoe_thunder(_origin:Vector3, target:Vector3, context:Dictionary) -> void:
	var targets:Array = _capped_targets(context.get("targets", []))
	if targets.is_empty():
		targets = [target]
	for value:Variant in targets:
		if not value is Vector3:
			continue
		var at:Vector3 = value
		var arc:VFXLightningArc = VFX_LIGHTNING_ARC.new()
		arc.name = "DivineThunder"
		add_child(arc)
		arc.play_arc(at + Vector3(0.0, 2.85, 0.0), at, HOLY_THUNDER_PALETTE)
```

★ 用户要的是「**和裁决者用同一落雷特效，区别只在于目标是多个敌人**」。
这句话**不靠"两处参数抄得一样"来满足** —— 那样两个人各改一处就会漂移。
做到字面同一段代码之后，「区别只在于目标个数」是**结构上成立**的：
裁决者传空 context → 退回 `[target]` 一道；神王传 `context["targets"]`（当场所有敌人）→ N 道。

神王的落点集合在 `BattleVfx` 侧填（先取本 tick 的敌方伤害事件落点，
拿不到再退回"当场所有存活且不同队的单位"），并关掉旧贴图层：

```gdscript
elif sid=="global_divine_blast":
	var enemy_targets:Array=[]
	for event in _enemy_damage_events(unit,damage_events):enemy_targets.append(event.get("world_foot",Vector3.ZERO))
	if enemy_targets.is_empty():
		enemy_targets = _living_enemy_world_positions(unit,current)
	context["targets"]=enemy_targets
```

配色仍用 §4.2 的白芯暖金 `HOLY_THUNDER_PALETTE`；两道弧共用同一配色表，不新增第二份色值。

### 13.2 末日守卫：策反在模拟层是**永久**的，但回放帧里**根本没有这一列**

先把模拟层的真实语义读清楚 —— 它和"连线"是两件事：

```gdscript
# BattleSimulator._convert_link_target_to_caster_team（由 shared_hp_link 触发）
target.team = caster.team        # 永久改写，**没有任何回退分支**
```

也就是说：**策反不是"被绑住"，而是"变成我方棋子"**，守卫死了也不还。
（`shared_hp_link` 这个名字容易让人以为它只是个绑定，这也是我上一轮理解偏掉的地方。）

问题在于表现层根本**看不到**这件事：

| 通道 | 是否携带策反信息 |
|------|-----------------|
| 回放 `frames` 行 | ❌ **13 列，没有 `team` 列**（`uid, x, y, hp, alive, attack_count, skill_ready, shield, skill_stacks, statuses, damage_dealt, vfx_attack_target_uid, vfx_skill_target_uid`） |
| 回放 `roster` | ❌ **首帧快照**，对被策反单位永远说原队伍 |
| 第 12 列 `vfx_skill_target_uid` | ✅ 守卫这一行**带着"我锁了谁"** —— 唯一可用的线索 |

**上一轮的做法（`SHARED_LINK_BAR_COLOR` 契约色）错在两处**：

1. 它把配对双方染成**暗红色**，而用户要的是"被策反者变成**我方绿色**"；
2. 它的存活判据跟着**连线**走，连线断（任一方死亡）就恢复原色 ——
   正好和用户强调的「**这种变化不会随末日守卫死亡而停止**」相反。

**订正后的实现**（三步，全部可被探针直接驱动）：

1. `BattleScreen.latched_conversions_in_frame(frame, by_uid)` —— 纯 static 函数，
   从某一帧里扫出 `shared_hp_link` 施法者行的第 12 列，得到 `uid → 策反后队伍`；
2. `BattleScreen.apply_latched_team(f, uid, conversions)` —— 纯 static 函数，把队伍写回该 fighter；
   `_apply_replay_frame` 里**先整帧扫、后逐条解码**（守卫会把目标搬到己方数组**尾部**，
   同一帧里目标可能排在守卫前面，边扫边应用会漏帧），锁存表 `_converted_ally_ids` 每局清空；
3. `BattleRenderer` 每帧按**当前队伍**重算血条颜色：
   ```gdscript
   var want_color: Color = _hp_color_for_team(_display_team(f))
   if hp_bar.color != want_color:
       hp_bar.color = want_color
   ```
   同一帧直切，不做渐变（用户要"同步改变"）。旧的契约色整套删除 ——
   留着只会和队伍色打架。

**为什么不干脆给回放帧加一列 `team`**：`ReplayDigest` 把 `frames` 算进被冻结的模拟摘要里
（`SIMULATION_TOP_FIELDS` 含 `frames`），加列会改掉已冻结的回放哈希 ——
那是比这轮修复大得多的破坏面。而锁存方案已被证明**足够**（见 §13.3 的探针读数）。

`BOLT_KIND_BY_UNIT` + `PROJECTILE_TEX_BY_UNIT` 上（当时还自以为踩过「换一半 = 白换」的坑，

真正的路由在 `_basic_attack` 开头 —— 它**先查 OGA 目录、命中即 `return`**：

```gdscript
func _basic_attack(origin, target, race, mode, context) -> void:
    var uid := str(context.get("source_unit_id", ""))
    if mode == "ranged":
        var projectile_spec: Dictionary = OGA_CHESS_CATALOG.projectile_for(uid)
        if not projectile_spec.is_empty():
            ...play_spec(...)
            return                     # ← 玩家棋子到这里就结束了
    ...
    var bolt_tex := str(PROJECTILE_TEX_BY_UNIT.get(uid, "")) if mode == "ranged" else ""
    _spawn(VFX_RACE_BASIC_ATTACK, profile, {...})   # ← 玩家棋子永远走不到
```

链路上的每一环都核对过（不是推测）：

| 环 | 位置 | 结论 |
|----|------|------|
| 快照带真实 unit_id | `BattleVfx.gd:348` `u["unit_id"] = str(f.get("id",""))` | ✓ |
| cue 把它放进 attack 字典 | `BattleVfx.gd:1335` `"unit_id": str(source.get("unit_id",""))` | ✓ |
| 再放进 context | `BattleVfx.gd:426` `context["source_unit_id"] = attack_unit_id` | ✓ |
| composer 拿它查 OGA 目录 | `UnitSkillVFXComposer3D.gd:241/246` | ✓ 命中即 return |
| 两只都在目录里 | `OgaChessVFXCatalog.PROJECTILES` | ✓ |

**所以「神侍 ↔ 极光射手」的普攻弹体由 `OgaChessVFXCatalog.PROJECTILES` 决定，
`BOLT_KIND_BY_UNIT` / `PROJECTILE_TEX_BY_UNIT` 对它们是死代码。**

### 为什么当时「全绿」却没人发现

因为**没有任何既有门禁覆盖这条链路**：编译通过、当时 20 条批跑全绿、用户肉眼毫无变化。
这正是本项目中反复出现的同一类失败，只是这次发生在表现层。

## 二、① 通用：把「命中结算」的表演时机推到弹体落地

### 2.1 根因 —— 弹体是对的，cue 的节拍是错的

先排除一个误判方向：**3D 弹体本身早就正确落地了**。
`effects/vfx3d/modules/VFXRaceBasicAttack3D.gd` 的 `_play_ranged` 按
`travel_duration = clampf(距离 / 弹速, 0.28, 0.80)` 飞，落地那一帧才播命中冲击。

真正错的是**上层 cue 的节拍**。派发链是：

```
BattleSimulator 派发 cue 序列：attack_start → projectile_spawn → impact → hit_number (→ death)
   ↓
BattlePresentationDirector（数据 / cue 驱动）
   ↓
LegacyBattleVfxAdapter.play_cue() 按 cue 名分发
   ↓
BattleVfx 的 cue_* 方法
```

`LegacyBattleVfxAdapter` 里 `projectile_spawn` 的完成时间是**写死的短节拍**
`PROJECTILE_SEC = 0.10`，`impact` 再 `IMPACT_SEC = 0.08` ——
于是「屏震 + 伤害飘字（`hit_number`）」在弹体**还在飞的时候**就打出去了。
这就是用户看到的「命中前就已结算状态和伤害」。

### 2.2 修法 —— 让 cue 等真实飞行时长（纯表现层）

1. `scenes/battle/BattleVfx.gd` 新增纯表现查表：

```gdscript
const _RANGED_BOLT_SPEED := { "arrow": 10.0, "dart": 8.8, ... "lance": 7.6, ... }
const _RANGED_BOLT_KIND_BY_UNIT := { "human_archer": "arrow", "human_mage": "orb", ... }
const _RANGED_MIN_TRAVEL := 0.28
const _RANGED_MAX_TRAVEL := 0.80
```

（镜像 `UnitSkillVFXComposer3D.BOLT_KIND_BY_UNIT` 的映射，**仅供前端算飞行时长用**，与弹形选择解耦。）

2. 新增 `cue_ranged_flight_time(source_uid, target_uid)`，用**与 `_play_ranged` 完全相同的公式**
   算飞行时长（取世界坐标 x/z 平面投影距离 ÷ 弹速，限幅 [0.28, 0.80]）。
   位置取自 `_cue_unit_snapshot()`（`world_cast` / `world_hit` / `world_foot` / `unit_id`）。

3. `effects/runtime/presentation/adapters/LegacyBattleVfxAdapter.gd` 的 `_play_projectile`：
   cue 完成时间由固定 `PROJECTILE_SEC` 改为**查询到的真实飞行时长**：

```gdscript
var flight := _beat_seconds(event, PROJECTILE_SEC)
if _host.has_method("cue_ranged_flight_time"):
    var computed := float(_host.call("cue_ranged_flight_time", source_uid, _first_target(event)))
    if computed > 0.0:
        flight = computed
return _finish_after(flight / speed, completion, "projectile_spawn")
```

**★ 边界**：改动只在**表现层**（cue 的完成时刻）。模拟器的伤害 / 状态结算顺序一个字没动 ——
所以伤害数值、暴击判定、战斗胜负与 9.23 完全一致，回放兼容。`_host.has_method` 兜底 +
`computed > 0.0` 兜底，任何一侧查表缺失都退回原节拍，不会把流程卡死。

### 2.3 逐单位 SFX 时序（用户逐条指定）

| 单位 | skill_id | 音效时机 | 依据 |
|------|----------|----------|------|
| 神侍 | `lowest_ally_heal` 等 | **触发技能即播**（治疗音） | 用户原话：「神侍音效是治疗音效，并不是投射物造成的，触发技能就播放」 |
| 暗影法师 | `silence_bolt` | **命中时** | 用户原话：「沉默箭是命中音效要在命中时播放」→ 见 §5.3 |
| 法师 | `random_attribute_bolt` | **释放时**（魔法释放音） | 用户原话：「法师属性弹是魔法释放音效，释放时就播放」→ 本身已是此行为，见 §10 |
| 弓箭手 | 普攻 | **发射时**（拉弓） | 用户原话：「弓箭手=发射时（拉弓）」 |

### 8.2 ★ 双向死亡判据（用户报的 bug 本体）

`BattleVfx._sync_persistent_unit_vfx` 原判据只看**守卫自身**是否还活着 / 目标是否变了：

```gdscript
var active := ... and bool(unit.get("alive", false)) and ... 
```

补上**目标存活**检查：

```gdscript
var target_alive := bool((current.get(bound_target, {}) as Dictionary).get("alive", false))
var active := ... and not bound_target.is_empty() and target_alive
```

## 九、⑨ 法师首技能：无声无弹道的真根因

### 9.1 定位过程

先排除了「SFX 表缺项」这一层：`SfxService` 里法师的 cue 是有的，`_oga_element_projectile`
也会被调用。于是写了一个**行为级探针**（`work/_qa_922/probe_mage_cast_924.gd`），
分别走**离散 tick 路径**与**回放路径**，实测两条路各自「期望施法 N 次 / 实际补演几次」。

结论：

* **离散 tick 路径正常** —— 说明派发代码本身没写错；
* **回放路径第一次施法整段丢失** —— 与用户「首次发动技能」的措辞精确吻合。

### 9.2 根因：播种帧把第 0 tick 的上升沿吃掉了

真实 3v3 打的**不是本地模拟**，而是 `BattleScreen._start_replay` → `_apply_replay_frame` 播**回放**。

* `_replay_capture_frame` 是在 `step_state` **之后**才写帧 → 所以 `frames[0]` 已经是
  **step 过一次之后**的状态；
* 而播种帧拿它当基线：`_vfx_prev_units = current`；
* 法师 `range = 4`（288px）**已覆盖开战站位距离**，第 0 tick 就会施法；
* 于是它的 `skill_ready` 上升沿**整段落在基线之前** →
  逐单位循环里那句 `now.skill_ready > prev.skill_ready + 0.1` **永远看不到它**。

**用户看到的「只造成伤害」是对的**：伤害在模拟里照常算（所以血是掉的），
而弹道与技能音走的是表现层的上升沿检测，一次都没触发。

### 9.3 修法：播种帧补演「基线之前已经施过法」的技能

`BattleVfx` 新增：

```gdscript
const SEED_ALREADY_CAST_TRACE := {
    "random_attribute_bolt": "attack_count",
}

func _seed_cast_already_fired(unit: Dictionary) -> bool:
    var trace := str(SEED_ALREADY_CAST_TRACE.get(str(unit.get("skill_id", "")), ""))
    if trace.is_empty(): return false
    return int(unit.get(trace, 0)) > 0
```

播种帧里：`if _seed_cast_already_fired(unit): _play_skill_cast_vfx(unit, unit, [], current)`。

**★ 判据必须是「施法才会写的痕迹」，不能用 `skill_ready`。** 三条理由：

1. 带 `opening_cd` 的单位（`race_units.json` / `formation_allies.json`）开场就把
   `skill_ready` 抬起来，但**根本没有施法**；
2. 镜像魔君的分身固定 `skill_ready = 9999.0`（`BattleSimTreasures.gd`），
   那是「**永不施法**」的哨兵值；
3. 法师的 `random_attribute_bolt` 满足条件：模拟器施法时同步 `attack_count += 1`
   （`BattleSimulator.gd` `_tick_skills` 分支），所以 `attack_count` 就是它的施法计数。

`previous` 传 `unit` **自身**（播种帧没有上一帧可比）。这对目标解析无影响 ——
`_exact_skill_target` 读的是快照里的 `skill_target_uid`，施法时由 `_mark_vfx_target` 写好并一直留着。
`shared_hp_link` 那一支正因为「`now_uid == previous.skill_target_uid` 直接 return」，
**天然不会与既有血契分支重复播放**。

**★ 表为空 / 字段为 0 一律返回 false —— 宁可不补，也不凭空播一次不该有的施法演出。**
这也是为什么把它做成**表**而不是无条件补：`SEED_ALREADY_CAST_TRACE` 目前**只有法师一条**，
探针实测整个阵容里只有它一个会在 `frames[0]` 之前施法。将来发现别的单位有同样症状，
往表里加一行即可，不必再动判据逻辑。

`composer = 1 / sfx = 1`，回放 **3/3 PASS**。
